# Аналитика сессий

Инструмент — `scripts/orch/stats.py`, источник — журналы в `~/.claude/projects`.
Никакой разметки работы не требуется: фазы определяются по составу инструментов в ходе.

## Коротко

Смотреть **расход на задачу**, не общий: общий растёт вместе с объёмом работы.
Порядок: снять замер → внести **одно** изменение → через неделю сравнить.
Два изменения сразу не разделить.

```bash
scripts/orch/stats.py --snapshot docs/metrics/$(date +%F).json
scripts/orch/stats.py --baseline docs/metrics/baseline-YYYY-MM-DD.json
```

## Команды

```bash
scripts/orch/stats.py                       # свод
scripts/orch/stats.py --days 14             # за период
scripts/orch/stats.py --phases              # структура расхода по фазам
scripts/orch/stats.py --sinks               # куда уходит объём: инструменты и вызовы
scripts/orch/stats.py --waste               # отказы, повторные чтения, ходы без инструментов
scripts/orch/stats.py --skills              # загрузки скиллов, делегирования, цена ревью
scripts/orch/stats.py --compare 14          # 14 дней против предыдущих 14
scripts/orch/stats.py --snapshot docs/metrics/YYYY-MM-DD.json   # зафиксировать замер
scripts/orch/stats.py --baseline docs/metrics/YYYY-MM-DD.json    # сравнить с опорным
```

## Две ловушки измерения — обе стоили неверных выводов

**1. Один ответ — несколько записей с общим usage.** Ответ модели пишется в журнал
отдельными записями на `thinking`, `text` и каждый `tool_use`, и у всех них **один и тот же**
блок usage. Сырой подсчёт по записям завышает расход примерно вдвое: первый замер дал
примерно вдвое больше токенов и ходов на задачу, чем на деле. Склейка — по `requestId`
(он же `message.id`); в `stats.py` она уже есть.

**2. Подагенты не логируются вовсе.** Ходов с `isSidechain` в журналах ноль, отдельных
файлов подагентов на диске нет. Всё, что считает этот инструмент, — **только родительские
сессии**. Отсюда следствие, которое надо проговаривать при каждом выводе: экономию от
делегирования эти данные **не доказывают**. Видно лишь то, что делегирование убрало из
родителя; собственная цена подагента есть только в биллинге.

## Какой показатель смотреть

**Расход на задачу**, не общий. Общий растёт вместе с объёмом работы и ничего не говорит
о качестве процесса. На задачу — падает, только если процесс действительно улучшился.

Рядом полезны два: **ходов на задачу** (меньше ходов при том же результате — лучше) и
**медиана контекста** (она показывает, режутся ли сессии).

## Опорный замер

Первый замер сохранить как опорный: `docs/metrics/baseline-YYYY-MM-DD.json`, дальнейшие
сравнивать с ним. Записать в нём: общий расход, вывод модели, число ходов и задач,
расход и ходы на задачу, медиану контекста.

Что смотреть в структуре по фазам: ходы **только с `Bash`** обычно дают основную долю расхода,
потому что каждый ход перечитывает весь контекст, а сам ответ инструмента мал. Вывод не
«оболочка дорогая», а **«дорог каждый ход»**: складывать команды в один ход выгоднее, чем
экономить на выводе. Полосы контекста: ходы распределены почти ровно, расход — нет;
небольшая доля ходов с самым большим контекстом даёт непропорциональную долю расхода.

## Как строить улучшения на этих числах

1. Снять замер до изменения: `--snapshot before.json`.
2. Внести одно изменение процесса. Не несколько сразу — иначе не разделить эффекты.
3. Через одну-две недели: `--baseline before.json`.
4. Смотреть на расход **на задачу**. Рост общего расхода при падении удельного — это успех,
   а не провал.

Что нельзя доказать этими данными: выгоду делегирования (см. ловушку 2), качество результата,
время работы (часы в журналах календарные, включая простой).
