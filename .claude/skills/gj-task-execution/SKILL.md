# Выполнение задач в GJ-Ecommerce

Собрано по разбору реальных ошибок в OPSOMN002-274 (корзина, смена региона). Каждое правило —
не лозунг, а следствие конкретной поломки, которая доехала до ревью или до релизной ветки.

Здесь — **корректность**: что проверить, чтобы правка была верной. Как задача нарезается на
сессии, что уходит подагентам и чем закрывается фаза — в `gj-task-orchestration`.

## 1. Постановка: читать первоисточники, а не цитаты

- Тикет Jira — через `mcp__buddy-mcp__jira_get_issue`, комментарии отдельно.
- Все ссылки из тикета (Confluence: спеки ручек, ADR, ТЗ) читать **самому**, а не доверять цитатам в
  описании. В OPSOMN002-274 цитата из спеки была верной, а вот вывод «спека противоречит ADR»
  подтвердился только после чтения обеих страниц: спека действительно врала.
- Большие страницы — `documents_read_manifest` + `documents_read_chunk`, не `confluence_get_page`.
- Зафиксировать в `docs/tasks/<дата>-<тикет>-<тема>.md`: что требуется, чем подтверждено, что открыто.
- Утверждение ТЗ о форме входящих данных («по SKU одна строка», «ключ уникален») сверить
  с данными до того, как строить на нём логику: у загрузчика — промежуточная таблица
  (`imported_items.body`), у сервиса — прод через `data_pg_query`. ФТ 289 обещала один документ
  на SKU, в данных у 4 292 SKU их несколько. [02.10.2026, webapi-connector !30; `docs/tasks/2026-10-02-opsomn002-268-skills-rules.md` п. 6]

## 2. Перед правкой: понять, чем является поле, которое меняешь

Прежде чем менять семантику существующей колонки или поля запроса — найти **всех** читателей:

```bash
grep -rn "<имя_поля>" app --include="*.php" | grep -v Tests
```

Ловушка из задачи: `basket_items.init_qty` несёт три роли одновременно — намерение покупателя,
признак недоступности позиции (`init_qty == 0` в двух `splitItemsByValid`, по нему же
`ListenOrderAction` переносит позиции после заказа) и потолок для `qty`. Правка «пусть init_qty
будет только намерением» ломала разметку недоступных позиций и суммы. Решение — новая колонка,
а не переопределение смысла.

## 3. Правило про форму запроса: пройти цепочку целиком

**Никогда не опираться на «клиент присылает / не присылает поле X», проверив только клиент и
конечный сервис.** Между ними стоит витрина (`customers-api-web`), и её работа — нормализовать
payload и подставлять дефолты.

Что проверять по порядку:

1. клиент: `platform/mobile-app/gj-app`, `platform/site/gj-ng-front` — все места, формирующие запрос;
2. **витрина**: `app/Http/Api*/Modules/*/Requests/*.php` (методы-геттеры!) и `app/Domain/*/Actions/*`
   — маппер в межсервисный запрос;
3. целевой сервис: правила валидации и конвертация в доменные данные.

Ловушка: в baskets нулевое количество означает «удалить», и той же ручкой приходит переключение
выбора. Различие «удаление приходит без `is_selected`» верно на клиентах, но витрина во всех трёх
версиях дописывала признак всегда (`(int) ($item['isSelected'] ?? true)`, а в mobile V1 — жёстко `1`).
Правка, построенная на этом различии, сделала удаление недоступных позиций невозможным.

**Вывод-правило:** различать операции по наличию необязательного поля нельзя. Если контракт не даёт
явного признака — менять контракт либо отдавать решение владельцу контракта.

## 4. Тесты: три обязательных типа

**Тест на границе систем.** Для любой правки, меняющей смысл поля в межсервисном запросе, — тест,
который ассертит **исходящий** payload, а не ответ ручки:

```php
$this->mockBasketsCustomerBasketsApi()
    ->shouldReceive('setBasketCustomerItem')
    ->with(Mockery::capture($outgoing))
    ->andReturn(new EmptyDataResponse());
// ...
expect(array_key_exists('is_selected', (array) $outgoing->getItems()[0]))->toBeFalse();
```

204 зелёных теста в baskets не показывали дефект: все они постят в сервис напрямую, минуя витрину,
то есть проверяют payload, которого в проде не существует.

**Сценарный тест с действиями посередине.** Не «переключил регион дважды», а «переключил, потрогал
корзину, вернулся». Дефект «намерение схлопывается при любом касании корзины» не был виден именно
потому, что круги смены региона шли без промежуточных действий покупателя.

**Guard-проверка каждого нового теста.** Снять свою правку и убедиться, что тест падает. Тест,
который проходит и до правки, ничего не доказывает.

Как всё это запускать локально, включая ловушки окружения — `.claude/skills/gj-local-test-runs/SKILL.md`.

## 5. Слепые зоны

- **`skip()` у тестов задетых ручек** — проверять `grep -n "skip()" <файл теста>`. Отключённый тест
  часто означает «ручка сломана давно» (так было с `customer:patch-seller`): CI на регресс промолчит.
- **phpstan и cs-fixer в CI не запускаются** — в пайплайне ENSI только `test:php-test-ci`. Зелёный
  пайплайн не доказывает статическую чистоту. Гонять локально:
  `php -d memory_limit=2G vendor/bin/phpstan analyse` и `php-cs-fixer fix --dry-run --diff`.
- **Типизированные свойства без дефолта.** Добавляя чтение `$data->someProp` в общий код, проверить
  всех, кто строит этот объект: непроинициализированное свойство даёт `Error`, а не исключение
  домена, и `catch (ValidateException)` его не поймает.
- **Сравнение строковых ключей.** Стоп-проверку роста ключа при постраничном отборе писать
  через `strcmp($next, $after) <= 0`, а не `<=`: строки, похожие на числа, PHP сравнивает как
  числа (`"2" <= "100"` → true), а порядок в базе задаёт collation. [02.10.2026, webapi-connector !44; `docs/tasks/2026-10-02-opsomn002-268-skills-rules.md` п. 9]
- **Тесты с заглушкой сгенерированного клиента** не ловят ошибку разбора его ответа — проверка
  в `gj-local-test-runs`, «Сгенерированный клиент под заглушкой».

## 6. Утверждения об ущербе: измерять, а не выводить из кода

Перед тем как назвать severity или написать «портится X» — проверить данными через Buddy:

- прод-БД: `mcp__buddy-mcp__data_pg_query` (`ensi-gs-*`, `oms-awg-*`);
- логи: `mcp__buddy-mcp__data_logs_raw_search` (обёртки `search_message`/`recent` на части таргетов
  не работают — сразу raw);
- рантайм: `data_k8s_*`, каталог таргетов — `data_list_targets`.

Ловушка: я написал в MR «нулевые строки портят состав заказа — сборка, отчётность, ХД», опираясь на
чтение DTO. Замер показал: в OMS 5 385 242 строки заказов и **ни одной** с нулевым количеством —
приём раскладывает строку на N единичных, при N=0 не создаёт ни одной. Правка оказалась гигиеной,
а не закрытием дефекта, и вопрос перестал требовать эскалации к владельцу заказов.

**Правило:** завышенная оценка ущерба меняет решения не меньше, чем заниженная.

## 7. Миграции и прод-объёмы

- Перед `UPDATE` по таблице — узнать размер (`count(*)` через `data_pg_query`). В `basket_items`
  12,36 млн строк: вместо backfill сделана nullable-колонка с рантайм-фолбэком.
- `nullable` без `default` и `boolean default false` на PostgreSQL — метаданные, без перезаписи.
- Миграции в ENSI идут **до** раскатки подов: в `ms-helm-chart` job помечен
  `helm.sh/hook: pre-install,pre-upgrade,pre-rollback`. Обратный порядок невозможен.
- `down()`, который дропает колонку, — это потеря данных. Продумать шаг откатa по данным.
- Новое поле, которое потребитель узнаёт только из событий, у существующих записей не появится:
  в план входит первичная загрузка и её место в порядке выкатки (`ensi-kafka`, Payload Design п. 7).
- Новая команда по расписанию в ENSI запускается блоком `cronjobs:` в `ms-helm-values`, а не
  `Kernel::schedule()`: без записи в values в проде она не выполнится (`gj-ci-deploy-map`, ловушка 4).

## 8. Парные MR и релиз

- Если правка задевает несколько репозиториев — сразу планировать порядок выкатки и писать его
  в описания обоих MR. В OPSOMN002-274: витрина не позже корзины, иначе позиция, которую корзина
  перестала удалять, теряется в ответе `basket/current`.
- Ветку резать от актуальной релизной (`git fetch origin +refs/heads/<release>:refs/remotes/origin/<release>`
  — в shallow-клонах обычный fetch может не сдвинуть remote-ref).
- Образ на `release-*` собирается только web-триггером: пайплайн стоит в `manual`, деплоя нет.
  Это окно, в котором можно править вперёд без ревёрта релиза.
- Не переопределять поведение, зафиксированное существующими тестами других версий API, «за компанию».
  Либо виза владельца, либо сузить правку до версии, где ожидания нет.
- Подъём замка на коммит клиента `dev-master` проверять по `git log старый..новый` в репозитории
  клиента и по `require` его `composer.json`: одна строка `reference` может тянуть мажорную линию
  guzzle/psr7. [02.10.2026, webapi-connector !44; `docs/tasks/2026-10-02-opsomn002-268-skills-rules.md` п. 5]

## 9. Git в мультирепозиторном воркспейсе

Корень воркспейса — **тоже git-репозиторий** (`e-commerce/development-platform`), и рабочий каталог
между командами сохраняется. Отсюда две реальные аварии:

- коммит с сообщением про сервис уехал в корень воркспейса, потому что предыдущая команда сделала
  `cd` туда; `git add -A` собрал ~200 несвязанных файлов из чужих сессий;
- `cd platform/...` относительным путём молча не срабатывает, если каталог уже сменился, и вся
  цепочка `&&` выполняется не там, где ожидалось.

Правила:

- каждая команда с `git` начинается с **абсолютного** `cd` в нужный репозиторий;
- перед `git add -A` — `pwd` и `git branch --show-current`;
- `git status --porcelain | wc -l` до коммита: если файлов больше, чем правил, — стоп;
- в корне воркспейса git-операций не делать вообще (правило из `CLAUDE.md`);
- если ошибка уже случилась: `git reset --mixed HEAD~1` возвращает дерево без потерь, но проверить,
  не ушёл ли push.

## 10. Нейминг

Имя должно совпадать с тем, что делает код. `DeleteItemsAction` не может решать, удалять ли —
он удаляет; условие живёт в отдельной стадии `CancelUnavailableItemsDeleteAction`. Метод данных —
`cancelDeletion($offerIds)`, а не `removeDeleteItems()`. Если название приходится объяснять
абзацем — оно неверное.

## 10.1. Комментарии

По `.claude/rules/code-comments.md`: в коде — только «почему так» и реальная опасность,
одной-тремя строками. Ход работы, замеры и историю правки — в коммит, описание запроса
или `docs/tasks/`, не в код. Старые комментарии-истории в изменяемом участке — удалять
попутно, чужие участки ради этого не трогать.

## 11. Ревью

Кросс-репозиторную правку отдавать ревью-агенту, который видит все репозитории
(`.claude/skills/gj-gitlab-mr-review` + платформенный addendum). Обе серьёзные ошибки в
OPSOMN002-274 нашлись именно так — ни один прогон тестов их не показывал.

Результат ревью проверять самому: находки бывают верными по сути и неверными по механизму
(например, «OMS сохраняет нулевые строки» — по коду да, по данным нет).

## Чек-лист перед сдачей

- [ ] первоисточники требований прочитаны, расхождения с кодом выписаны;
- [ ] найдены все читатели полей, чью семантику меняю;
- [ ] цепочка клиент → витрина → сервис пройдена для каждого поля, на которое опирается логика;
- [ ] есть тест на границе систем, если менялся межсервисный payload;
- [ ] есть сценарный тест с действиями покупателя посередине;
- [ ] каждый новый тест проверен снятием правки;
- [ ] проверено, нет ли `skip()` у тестов задетых ручек;
- [ ] phpstan и cs-fixer прогнаны локально;
- [ ] в диффе нет комментариев-истории («исправлено», «замер показал», «сначала пробовал»)
      и абзацев длиннее трёх строк — ни новых, ни старых в изменённых участках;
- [ ] утверждения об ущербе подтверждены замером, а не чтением кода;
- [ ] порядок выкатки парных MR описан в обоих;
- [ ] разбор задачи лежит в `docs/tasks/`;
- [ ] коммиты ушли в те репозитории, в которые правил (проверено `pwd` перед каждым `git`).
