# Деньги, время и номера без тихих искажений

Go-контракт по деньгам — в `gj-money-discount-contracts`. Здесь — то же для PHP (ИС, ENSI)
и для дат и номеров, на которых держится сопоставление.

## 1. Деньги

- **Не во float.** Скидки, `totalCost`, итоги по акциям копятся во float, округление только
  в презентере — итог в OMS расходится с кассой на копейки. Считать в копейках (`int`) или
  через `bcmath`, округлять **в одном месте**.
- **Одно округление на оба поля.** `loyaltyPointsBurn = (int) $amount`, а цена уменьшена на
  дробный `$amount` (333 против 333.33) — «бонусы + оплата» не равно итогу. Округлить один раз
  (правило уточнить, для целых бонусов `floor`) и это же значение вычесть из цены.
- **Состав суммы.** Формулу (`refund = sumPaid − totalCost`) сверить с тем, что реально лежит
  в `sumPaid` / `paidCost`: доставка, услуги. Подтвердить у аналитика и записать в разбор задачи.
- **Один свод — один метод.** Свод скидок по `promoId` дважды, разными реализациями (ключ
  `string` здесь, `int` там) — расхождение между кассой и OMS вопрос времени. Свод один,
  разные представления — в презентерах.
- **Сочетаемость скидок.** Если правило гласит «бонусы — единственная скидка на единице»,
  то **каждая** ветка, накладывающая скидку, его проверяет (специальная акция из
  `additionalSales` накладывалась поверх). Приоритет акций — явным правилом, а не «первая
  в ответе сервера».
- **Источник раскладки — один для отката и для повторного списания.** В !918 откат брал
  раскладку из `marketing.promoApplied`, а восстановление — из `items[].loyaltyPointsBurn`,
  который в проде пуст у всех позиций.

## 2. Время

- **Дата действия — `date`, а не `timestamp`.** Срок документа — календарная дата. В
  `timestamp(6)` она уходит наружу ISO-строкой с `Z` и сдвигается.
- **Пояс входа.** `Date::parse('…+03:00')` сохраняет смещение, а Eloquent пишет время без
  перевода в UTC: 00:00 по Москве ложится как 00:00 UTC, на 3 часа позже. Значение без
  смещения молча считается UTC. Разбирать явно в поясе источника (уточнить у владельца
  выгрузки) и переводить в UTC.
- **Дата сравнения порядка** (`external_updated_at`) — особенно: на ней держится «новее ли
  строка» (`gj-retry-safe-writes` §7).
- **Заглушки** вроде `1900-01-01 00:00:00.000` превращать в `null` везде, а не в одной ветке.
- **Формат на входе и в событии зафиксировать примером** в OpenAPI и в описании контракта
  события: `Y-m-d H:i:s.v` от источника — это не `date-time` RFC 3339.
- **Пояс согласовать по всей цепочке.** Аксапта отдаёт московское время без смещения, загрузчик
  читает его как UTC, PIM пишет как есть — сейчас календарный день доезжает верно, потому что ошибки
  компенсируют друг друга. Исправлять пояс только в одном звене нельзя: дата окончания уедет на сутки.
  Правка — сразу во всех звеньях, одним планом и тестом сквозного формата.
- **Тест на дату** сравнивает момент с поясом, а не `format('Y-m-d')`: сдвиг на 3 часа
  такой тест не видит.

## 3. Номера и идентификаторы

Если уникальность или сопоставление держатся на строке, которую набрал человек (номер
сертификата, декларации, купона):

- нормализовать: схлопнуть пробелы, неразрывный пробел (U+00A0) → обычный, `trim`;
- латиница на месте кириллицы (`C`/`С`, `Д` против похожих) в номерах ЕАЭС визуально
  неотличима и даёт второй документ с тем же номером. Как минимум логировать такие номера,
  замену согласовать с аналитиком;
- производное поле (`registry_url` из `type` + `registry_id`) расходится с исходными при
  любой их смене. При смене `type` сбрасывать производное. По возможности собирать на лету.
- раздел внешнего реестра (`rss` / `rds`) принимать от того, кто нашёл запись, и сверять
  с видом документа, а не выводить из нашего поля.

## 4. Имена

Одно имя — один смысл. `promoApplied` был и булевым «купон применился», и массивом
применённых акций в том же теле запроса к OMS. Внутреннее поле переименовать
(`couponApplied`), а имя, навязанное контрактом, переводить только в презентере.

## Самопроверка

1. Ни одной денежной суммы во float между входом и презентером, округление в одном месте.
2. Каждая сумма, уходящая в два поля, округлена один раз.
3. Каждая дата: тип хранения, пояс входа, формат наружу записаны.
4. Каждое сопоставление по номеру — с нормализацией.
5. Нет имени, которое в соседнем контракте значит другое.
