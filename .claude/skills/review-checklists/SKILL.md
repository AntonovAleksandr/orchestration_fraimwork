# Чек-листы ревью и ответ на ревью

Дополняет скилл порядка ревью (проходы, вердикт P0–P3) — тот скилл не правим,
всё своё лежит здесь. Справочные страницы:

- `references/correctness-checklist.md` — домен, деньги, данные и транзакции, интеграции и
  идемпотентность, безопасность, контракты, миграции, время; по убыванию цены ошибки.
- `references/quality-checklist.md` — архитектура, качество кода, комментарии, производительность,
  наблюдаемость, тесты, документы задачи, выпуск.
- `references/defect-patterns.md` — каталог типовых дефектов: признак в коде,
  контрпример, исправление.
- `references/comments.md` — метки `[блокер]/[важно]/[замечание]/[мелочь]/[вопрос аналитику]` и их
  связь с P0–P3, структура комментария (заголовок → механизм → контрпример → исправление → тест),
  итоговая заметка, публикация, актуализация тредов после влития и **ответ автора на ревью**.

Комментарии в GitLab — по-русски, с этими метками и в этой структуре.

## Где сейчас код

Влитый запрос — не закрытый вопрос. До оценки серьёзности выяснить, куда код дошёл и не
исправлен ли позже:

```sh
git -C <клон> fetch origin --prune
git -C <клон> branch -r --contains <merge_commit_sha>
git -C <клон> log --oneline <head_sha>..origin/<ветка> -- <файлы запроса>
git -C <клон> diff <head_sha> origin/<ветка> -- <файл>
```

Поток веток — из `docs/deploy/branch-registry.md`, не по названиям. «Влито в ветку» ≠ «выложено»:
подтверждать джобами деплоя. Код может быть влит, откатан и перенесён на другую
линию. Для влитого запроса вердикт формулировать для
следующего шага: «нельзя выкатывать / переключать потребителя», «нужен отдельный запрос».

## Ответ на ревью нашего запроса

Порядок — `references/comments.md`, раздел «Ответ автора на ревью». Набор запросов — работником:
`scripts/orch/orchestrate.sh respond <адреса>`. Из скиллов классов дефектов
(`scripts/orch/defect-skills.txt`) загружать только те, к классам которых относятся треды.
