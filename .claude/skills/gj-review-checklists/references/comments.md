# Комментарии в GitLab: запись, публикация, актуализация, ответ автора

Источник: руководство ревью Олейникова (gj-ai-workspace, `code-review-comments.md`), нормализовано
под этот воркспейс 2026-10-02. Раздел «Ответ автора на ревью» — свой, по разбору !918/!927/!237.

Комментарий читают автор, которому исправлять, и тимлид, которому решать, можно ли выпускать.
Он должен быть понятен без разговора, из которого родился.

## Шкала меток и связь с P0–P3

| Метка | Значит | P в `gj-gitlab-mr-review` |
| --- | --- | --- |
| **[блокер]** | нельзя вливать или выкатывать: неверные деньги, потеря событий, порча данных, простой, уязвимость, исключение в штатной ветке | P0 / P1 |
| **[важно]** | исправить до слияния; отложить — только с принятием риска владельцем (P2 в `gj-gitlab-mr-review`): гонка, нет версии событий, тихий отказ на редком пути, нарушение контракта | P2 |
| **[замечание]** | исправить, не блокирует: валидация, дублирование, тест не ловит регресс, неточный OpenAPI | P3 |
| **[мелочь]** | попутно: мёртвый код, устаревший docblock, лишний индекс, имя | P3 |
| **[вопрос аналитику]** | бизнес-развилка не описана в постановке | — |

Метки сочетаются: `[важно, архитектура]`, `[блокер выкатки]`, `[важно, нужно решение аналитика]`.
Гипотеза помечается словом «гипотеза» и способом проверки.

## Комментарий к строке

1. **Заголовок жирным с меткой** — одна фраза: что не так и чем кончится.
2. **Механизм** — почему так, со ссылками `файл:строка`, метод.
3. **Контрпример** — конкретные данные или порядок событий. Для денег — суммы, для гонок — порядок запросов.
4. **Исправление** — наименьшее достаточное, при нужде варианты от предпочтительного.
5. **Тест**, который упал бы до исправления.

Правила: тред под строкой, где дефект проявляется; общий — в итоговой заметке. Один дефект — один
тред. Обычный язык, без оценок людей («нет проверки», а не «вы забыли»). Утверждение о фреймворке,
БД, чужом сервисе — с источником (файл:строка, лог CI, версия библиотеки), иначе «гипотеза». Без
похвалы и пересказа изменений. Не повторять одно в нескольких тредах — ссылаться. Постановка — с ID
и версией: «ФТ 190974834 v15 §2.4». Секреты не цитировать: место и «перевыпустить».

## Итоговая заметка

Вердикт → блокеры → важно → замечания → расхождения с постановкой и описанием MR → процесс →
чем проверено и что не проверялось. Каждый пункт — строка со ссылкой на тред. «Чем проверено»
обязательно: SHA, тесты, phpstan, источники с версиями. Связанные MR — заметка в каждом со ссылкой.

Для влитого MR вердикт формулируется для следующего шага: «нельзя выкатывать в прод /
переключать потребителя», «нужен отдельный MR с исправлениями».

## Публикация

Только по прямому поручению пользователя — это внешнее действие.

- Тред к строке — `mcp__buddy-mcp__gitlab_create_merge_request_thread` с `position` по `diff_refs`
  текущей вершины; строка должна быть в показанном фрагменте диффа, иначе GitLab отвечает
  `line_code can't be blank`.
- Общая заметка — `gitlab_add_merge_request_note`; черновики — `gitlab_create_merge_request_draft_note`
  и `gitlab_publish_merge_request_draft_notes`.
- Перед записью перечитать обсуждения (`gitlab_list_merge_request_notes`), чтобы не дублировать.
- Buddy в обслуживании — REST API GitLab с токеном из `~/.config/gj/gitlab_pat` (`gj-gitlab-git`).

## Актуализация после публикации

1. Где сейчас код — раздел «Где сейчас код» в `gj-review-checklists`.
2. По каждому треду: жив ли дефект на текущей `origin/<ветка>` — сверять кодом, не сообщением коммита.
3. Исправлено — ответ «исправлено в `<sha>` (`<ветка>`)», тред резолвится.
4. Не исправлено, но код дошёл до прода — ответ «на <дата> в `<ветка>`/<среда>», метка повышается,
   если ущерб стал реальным.
5. Итоговую заметку не переписывать: добавить ответ «Состояние на <дата>».
6. Чужие треды не резолвить; свои — только после проверки кода.

## Ответ автора на ревью

Когда ревью получила наша правка, ответы готовятся так же строго, как находки.

1. **Сверить каждое замечание с текущим кодом** той ветки, где код живёт сейчас: запрос мог быть
   влит, откатан и перенесён. Итог — «исправлено / не исправлено / частично» по каждому треду.
2. **Искать доводы против** — только с доказательством: сценарий недостижим (замер на данных стенда),
   уже защищён (файл:строка), противоречит контракту или ФТ (ID, версия, раздел), опровергнут кодом
   соседней системы. Довод без доказательства не пишется.
3. **Вердикт по треду:** снимается · смягчается · принято · принято, серьёзнее, чем написано.
   Довод, ослабляющий посылку, не снимает дефект: «касса не повторяет запрос» сделало блокер про
   порядок шагов хуже, а не мягче.
4. **Вопросы владельцам** — только то, что не закрылось ни кодом, ни данными, ни документом.
   Готовым сообщением, с цифрами и вариантами.
5. **Доработки** — каждая с номерами тредов, которые закрывает, и с меткой «сначала / после ответов /
   следом». Отдельный MR поверх влитого.
6. Если в треде уже есть наш ответ — проверить, верен ли он, и не дублировать.

Ревьюер из нашей команды (например, Олейников — Surf) — коллега: ответы без «мы и вы».

## Чего не делать

- Не публиковать находки подагента без проверки.
- Не смягчать серьёзность, потому что «уже влито» или «срочно».
- Не предлагать терпимость к ошибке, повтор или `try/catch`, чтобы скрыть необъяснённый сбой.
- Не требовать рефакторинга вне задачи без связи с найденным дефектом; связь — показать.
