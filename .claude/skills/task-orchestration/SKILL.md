# Организация работы над задачей

Правила корректности — в `task-execution`. Здесь — как задача устроена во времени:
чем нарезается на сессии, что уходит подагентам, чем закрывается.

## Коротко: порядок работы

```bash
scripts/orch/orchestrate.sh lead   <КЛЮЧ> "заголовок"   # отдельный агент-координатор во вкладке
scripts/orch/orchestrate.sh task   <КЛЮЧ> "заголовок"   # завести и запустить
scripts/orch/orchestrate.sh list | say | read | wait     # следить и вмешиваться
scripts/orch/orchestrate.sh review <адрес запроса>       # ревью
scripts/orch/orchestrate.sh done   <КЛЮЧ>                # сдача, по явной команде
```

`lead` — когда задачу ведёт не эта сессия: новая вкладка «<КЛЮЧ> · координатор» сама
запускает работника, держит `wait`, отвечает на его вопросы, по готовности зовёт ревью и
докладывает. Сдача — по-прежнему только по явной команде. Реплика — `.tasks/<ключ>/lead.md`;
для вёрстки третьим аргументом `front`.

Пачкой, когда задач несколько:

```bash
scripts/orch/fleet.sh run TASK-1 TASK-2:front TASK-3@feature-tree
scripts/orch/fleet.sh status | watch | stop все
```

Вид после `:` — `task` (по умолчанию), `front`, `review`. Имя дерева после `@` — задача
уйдёт в отдельное дерево Orca со своей вкладкой; нет такого — создастся от `main`.
Без `@` работник садится в текущее дерево, вкладку Orca даёт сама.

Пачка останавливается на первом отказе заслона, а не запускает половину молча.

1. **Постановка** — первым действием перевести задачу в трекере в статус «В работе»
   (раздел 1 ниже). Затем прочитать первоисточники, вписать во вводную цель одной фразой
   и критерий готовности. Не формулируется критерий — вернуть постановщику.
2. **Разведка** — вопросы выписать до поиска; закрывать сначала по ТЗ, потом по коду;
   поиск вести подагентами (codegraph — где есть индекс). Человеку выносить только то,
   что нельзя закрыть самому.
3. **Правка** — по `task-execution`. Фрагмент файла читать `sed`, не целиком.
4. **Контроль** — бэк: прогон плюс форматтер и статанализатор. Вёрстка: `orca emulator ax`
   для состава, `scripts/orch/golden.sh check` для внешнего вида.
5. **Ревью** — `review-delegation`, свежим работником, не в своей сессии.

**Деплой, анализ веток и статуса задачи, исследование, ревью — подагентам по
`subagent-delegation`**: какой подагент, какой контекст ему передать, как он спрашивает
родителя и как родитель ему отвечает. Координатор сам эти работы не ведёт: измерения показывают, что именно они
съедают основную долю его расхода при раздутом контексте.
6. **Сдача** — только по явной команде, раздел ниже.

**После деплоя артефакта с номером сборки — прислать номер.** Если тестировщик находит сборку
по номеру (мобильное приложение, пакет, образ), то как только прошла джоба деплоя — вывести
версию и номер сборки из её лога. Без номера проверять нечего, и работа не считается сданной.
Где и как печатается номер — в проектном скилле про CI и выкатку, если он есть.

**Резать сессию** — при переходе контекста за 250 тыс., при смене задачи, перед ревью.
Проверять себя так: **каждый десятый ход смотреть `/context`**; перешёл порог — доделать
текущий шаг, дописать во вводную что сделано и что осталось, начать новую сессию.
Правило с действием выполняется, правило с числом — нет: без проверки большинство ходов
работника проходит выше потолка.

**Складывать независимые команды в один ход.** Это самый крупный рычаг из измеренных:
обычно на ход приходится около одной команды, а ходы только с оболочкой дают основную долю
расхода: ответ инструмента дёшев, дорог сам ход — он перечитывает весь контекст.

Складывание по три сократило бы число ходов втрое и сэкономило около половины расхода —
больше, чем дали разделение сессий, выжимка запросов и сверка вёрстки вместе.

Как это выглядит: проверки, поиски, чтения разных файлов почти всегда независимы —
их в один ход через `;` или `&&`. Зависимые (второе нужно считать по результату первого)
остаются раздельными. То же для инструментов доступа к трекеру и хостингу кода: несколько
запросов идут одним блоком, а не по одному.

**Ответы человеку — плотные.** Ходы без инструментов тоже стоят дорого:
каждый перечитывает весь контекст ради нескольких сотен слов. Промежуточные
«сейчас проверю» не писать — писать результат.

**Чего не тянуть в контекст никогда:** полные кадры экрана (сотни КБ, десятки тысяч токенов —
снимать `scripts/orch/shot.sh`, сверять `golden.sh`), полные диффы сгенерированного кода,
выдачу поиска, целые файлы вместо фрагментов.


## Фазы задачи и потолки контекста

Фазы 1–2 и 3–4 идут в одной сессии, фаза 5 — всегда в новой.

| Фаза | Где идёт | Потолок | Чем закрывается |
|---|---|---|---|
| 0. Заведение | скрипт, без модели | 0 | `task.sh` положил вводную |
| 1. Постановка | сессия задачи | 100 тыс. | цель и критерий готовности вписаны во вводную |
| 2. Разведка | codegraph + подагенты | 150 тыс. | вопросы закрыты, человеку вынесен только остаток |
| 3. Правка | та же сессия | 250 тыс. | правка внесена |
| 4. Контроль | скрипты | +0 | форма контроля прошла |
| 5. Ревью | **работник Orca** (`orchestrate.sh review`) | ~0 в родителе | отчёт с вердиктом |

**Граница сессии** — одно из двух: контекст перевалил 250 тыс. либо задача перешла
к ревью. Не «когда надоело».

### 0. Заведение — оркестратором

```bash
scripts/orch/orchestrate.sh task   TASK-1 "короткий заголовок"
scripts/orch/orchestrate.sh front  TASK-2 "короткий заголовок"
scripts/orch/orchestrate.sh review <адрес запроса>
scripts/orch/orchestrate.sh done   TASK-1
```

Открывает отдельную вкладку и запускает в ней сессию. Модель на этом шаге не работает.

Управление уже запущенным:

```bash
scripts/orch/orchestrate.sh list                # что сейчас идёт и в каком состоянии
scripts/orch/orchestrate.sh say  <вкладка> "…"  # вмешаться: дослать указание
scripts/orch/orchestrate.sh read <вкладка> 60   # посмотреть, что там
scripts/orch/orchestrate.sh wait <вкладка>      # дождаться, пока освободится
scripts/orch/orchestrate.sh go   <вкладка>      # переключиться и вести руками
```

Заслон по ресурсам перед запуском проверяет память, а не число сессий: новый работник не
стартует, если свободно меньше `ORCH_RESERVE_MB` (по умолчанию 2 ГБ) или своп больше `ORCH_MAX_SWAP_MB`
(по умолчанию 4 ГБ). Ограничения по числу сессий нет. Одна сессия занимает 200–700 МБ и растёт
вместе с контекстом. Обойти — `ORCH_FORCE=1`, но сначала освободить память: закрыть ненужные терминалы
и тяжёлые приложения.

Жёсткого лимита ОЗУ на процесс тут нет и быть не может: `claude` — нативный бинарь,
`ulimit` на него не действует, cgroups в macOS отсутствуют. Ограничивается то, что
поддаётся: свободная память и своп на входе.

**Почему через оркестратор, а не просто `claude`.** Он вписывает вызовы нужных скиллов
первой строкой стартовой реплики. Подбор скиллов по описанию почти не срабатывает — триггерные
фразы в живых репликах встречаются редко. Текст, пришедший в самом сообщении, срабатывает всегда.

### 0.1. Две ловушки запуска — обе уже сорвали задачи

**Рабочее дерево git не содержит вложенных клонов.** Если воркспейс — набор отдельных
репозиториев, лежащих внутри корневого, то в новое рабочее дерево корня они не попадают: остаются
одни `README`. Работник получает вводную и не находит файлов, которые надо править.
Оркестратор отказывается стартовать в дереве без клонов; обойти — `ORCH_SKIP_TREE_CHECK=1`,
если задача их правда не трогает.

**`--worktree current` берёт активное дерево интерфейса Orca, а не каталог запуска.**
Запуск из одного дерева может посадить работника в основное. Поэтому оркестратор задаёт дерево
явно — `path:<дерево вызвавшего агента>` (корень git по каталогу запуска).

**Работник садится в дерево агента, который его запустил.** Не в главное: умолчание «главное
дерево» может увести работника в чужой каталог без предупреждения. Если в дереве агента нет
клонов, заслон остановит запуск и подскажет путь в главное дерево. Направлять туда нужно только
явно: `ORCH_WORKTREE=path:<путь>` или `fleet.sh run КЛЮЧ@main`, и сказать об этом пользователю
до запуска.

**Вводная, оставшаяся шаблоном, — признак, что работа не начиналась.** `done` на такой
задаче отказывает: сдавать нечего.

### 1. Постановка

**Первым действием — статус «В работе» в трекере.** Только для задач (`task`, `front`),
не для ревью и не для сдачи:

1. получить задачу — посмотреть текущий статус. Уже «В работе» или дальше по процессу
   (ревью, тестирование, закрыта) — ничего не делать: назад задачу не двигать.
2. получить список переходов — найти переход, **целевой статус** которого называется
   «В работе» (без учёта регистра). Номер перехода не запоминать и не переносить
   между задачами: он зависит от схемы процесса и текущего статуса.
3. выполнить найденный переход.
4. Перехода нет или трекер не отвечает (например, упал VPN) — не останавливать задачу:
   одной строкой записать во вводную «статус не переведён: <причина>» и доложить
   в итоге, чтобы человек перевёл руками.

Читать первоисточники по `task-execution` §1. Большие страницы вики читать по частям
(манифест и фрагменты), полную страницу не тянуть.

Вписать во вводную две строки: **цель одной фразой** и **критерий готовности**. Если
критерий не формулируется — задача не готова к работе, возвращать постановщику.

### 2. Разведка — закрыть вопросы самому, человеку нести только остаток

Цель фазы не «изучить код», а **закрыть открытые вопросы**. Человеку уходит только то,
на что не нашлось однозначного ответа ни в требованиях, ни в коде.

#### 2.1. Обновить индекс — до начала, не по ходу

```bash
codegraph status <путь к репозиторию>   # ПЕРВЫМ ДЕЛОМ — есть ли индекс вообще
codegraph init   <путь к репозиторию>   # если «Not initialized» — завести, в фоне
codegraph sync   <путь к репозиторию>   # подхватить правки, быстро
codegraph index  <путь к репозиторию>   # после смены ветки или крупных правок, в фоне
```

**Начинать со `status`.** Индекс может отсутствовать, даже если скилл `codegraph-usage`
утверждает обратное. Пока индекс не заведён, вызовы `codegraph_*` бесполезны, и разведка
идёт подагентом.

Индекс отстаёт от правок примерно на секунду через watcher, но после переключения ветки
и после чужих пушей ему верить нельзя. Прогон на устаревшем индексе даёт ответы про
несуществующий код — это хуже, чем отсутствие ответа.

На больших репозиториях `init` и `index` запускать в фоне и дождаться. Репозитории без
индекса разведываются подагентом.

#### 2.2. Выписать вопросы до поиска

Открытые вопросы выписать списком **до** того, как лезть в код: иначе разведка
превращается в чтение всего подряд, а вопросы всплывают на ревью. Формулировка вопроса —
такая, чтобы ответ был проверяемым: не «как работает корзина», а «чем различаются
удаление позиции и снятие выбора в payload шлюза».

#### 2.3. Закрыть каждый вопрос по двум источникам

Порядок обязателен: **сначала требования, потом код.** Код показывает, как есть; требования
говорят, как должно быть. Ответ «в коде так» не закрывает вопрос, если ТЗ требует иного —
это находка, а не ответ.

| Источник | Чем берётся |
|---|---|
| Требования | задача в трекере + комментарии отдельно; вики — по частям (манифест и фрагменты), полную страницу не тянуть |
| Код в проиндексированном репозитории | `codegraph_explore` — один вызов, отдаёт исходник нужных символов |
| Код в остальных репозиториях | подагент (навигатор по системе, `researcher`, `Explore`) |
| Поведение в боевой среде | запрос к базе на чтение, поиск по логам — когда вопрос про «а как оно на самом деле» |

#### 2.4. Кто ищет — codegraph или подагент

Задание подагенту, наборы контекста и канал связи — `subagent-delegation`.

Это разные инструменты под разные области, и путать их дорого:

- **Проиндексированный репозиторий — codegraph.** `codegraph_explore` отвечает одним вызовом
  и отдаёт исходник нужных символов. Делегировать сюда подагента — значит оплатить его контекст
  ради того, что и так лежит готовым. Открывать `Read`-ом файлы, которые `codegraph_explore`
  уже показал, тоже не нужно.
- **Репозитории без индекса — только подагент.** Поиск там идёт обходом файлов, и вся выдача
  осела бы в основном контексте до конца работы.

Полезные вызовы помимо `explore`: `codegraph_impact` перед правкой символа (что заденет),
`codegraph_callers` (кто вызывает). Каждый вызов — с `projectPath`, иначе падает
с `No project loaded`.

На разведку по задачам подагенты без явного правила используются почти никогда.

**Договор с подагентом.** В задании всегда: «верни выводы со ссылками `файл:строка`,
содержимое файлов не приводи». Хороший ответ — 20–40 строк: что нашлось, где именно, что из
этого следует. Подагент, вернувший выдачу `grep`, работу не сделал — его ответ занимает
столько же, сколько самостоятельный поиск.

#### 2.5. «Не проверено» — это незакрытый шаг, а не ответ

Прежде чем написать человеку «не проверял», «в коде не нашёл», «на живом контуре не
смотрел», «тесты не гонял» — **пойти и проверить**. Это самая частая претензия к работе
агентов: вопрос отдают человеку вместо того, чтобы потратить пять минут на замер.

Таблица: что делать вместо каждой формулировки.

| Собрался написать | Сначала сделать |
|---|---|
| «на живом контуре не проверено» | дёрнуть тестовую среду напрямую: хосты и доступы взять из конфигурации проекта; гостевой сценарий часто работает без авторизации |
| «как ведёт себя в проде — неизвестно» | запрос к боевой базе на чтение, поиск по логам; если обёртки поиска на части таргетов молчат — сразу сырой поиск |
| «в коде не нашёл» / «не смотрел» | `codegraph_explore` там, где есть индекс, подагент — где нет; `grep -rn` по конкретному репозиторию |
| «тесты не прогонял» | `local-test-runs`: прогон по затронутому пути, не весь набор |
| «не знаю, доехало ли до прода» | слияние в боевую ветку **и** успешная джоба боевого деплоя на её вершине; ветки — из реестра веток проекта |
| «не знаю, собирается ли» | список джоб пайплайна по ветке, лог упавшей |
| «сколько таких случаев — не считал» | посчитать: `grep -c`, запрос с `count(*)` |
| «какая версия у сборки» | лог джобы сборки |

**Правило:** если средство проверки существует и доступно — проверка обязательна.
Человеку уходит результат замера, а не просьба замерить за тебя.

**Сверка отчёта с самим собой — перед отправкой.** Типичный случай: в одном пункте
отчёта сказано «доступ к тестовой среде в задаче есть», в соседнем — «по живой среде
не проверено». Средство было названо тем же отчётом и не применено; вместо замера код
сделали «устойчивым к обоим вариантам имён», то есть угадали два ответа там, где можно
было увидеть один настоящий.

Перед отправкой пройти по каждому «не проверено» и спросить: **не упоминается ли средство
проверки где-то ещё в этом же отчёте, в задаче или в конфигурации?** Если упоминается — идти
проверять, а не отправлять.

**Догадка вместо замера — тоже отписка.** Код, написанный «на оба варианта», потому что
настоящий формат не смотрели, — не запас прочности, а непроверенная гипотеза в двух
экземплярах. Замерить и оставить один путь.

**«Что осталось» — только незакрытые вопросы.** Осознанные решения о порядке выкатки,
зависимости между запросами и отложенные по плану шаги идут в раздел «Выкатка». Попав
в «осталось», они читаются как недоделка и заставляют человека разбираться, чего от него
ждут. Признак: если рядом написано «делается после X» — это порядок, а не открытый вопрос.

**У законно открытого вопроса обязательны две вещи:** что уже сделано для его закрытия
(у кого и когда запрошен доступ, что пробовали) и является ли обходной путь временным
или окончательным. Иначе человек додумывает за агента.

#### 2.6. Что действительно уходит человеку

Только то, что **нельзя** закрыть самому. Законных причин четыре:

1. **Решение за владельцем** — контракта, продукта, архитектуры. Не факт, а выбор.
2. **Требования противоречат друг другу** либо коду, и чья правда — вопрос к постановщику.
3. **Оба источника молчат** — ни в ТЗ, ни в коде ответа нет.
4. **Нужен доступ, которого нет** — запись в боевую среду, выкатка, физическое устройство,
   публикация в магазине приложений. Либо средство сейчас недоступно (упал контур) — и тогда так
   и писать: «проверю, когда поднимется», а не «не проверено».

Формат выноса — три строки на вопрос:

```
Вопрос: <формулировка>
Проверено: ТЗ <ссылка/пункт> — <что там>; код <файл:строка> — <что там>;
           замер <команда> — <результат>
Почему открыт: <одна из четырёх причин выше>
Мой вариант: <что предлагаю, чтобы человеку было проще подтвердить, чем решать с нуля>
```

Строка «Проверено» без конкретики — признак того, что шаг 2.5 пропущен. «Посмотрел код»
не считается: нужны файл и строка. «Проверил на тестовой среде» не считается: нужен запрос и ответ.

Если открытых вопросов не осталось — не спрашивать ничего и идти к правке.

### 3. Правка

Правки по `task-execution`. Что не тянуть в контекст:

- **целые файлы**, когда нужен фрагмент — `sed -n 'A,Bp'` вместо `Read`;
- **выдачу поиска** — считать `grep -c`, читать точечно;
- **полные диффы сгенерированного кода** — см. фазу 5;
- **снимки экрана** — см. фазу 4.

Ответ `Bash` дешёвый, но **ход дорог сам по себе**: ходы только с `Bash` дают основную долю
расхода, потому что каждый перечитывает весь контекст. Отсюда два правила, а не одно: брать
`Bash` вместо `Read` — и складывать несколько команд в один ход вместо цепочки ходов.

### 4. Контроль — по виду задачи

**Бэк.** Локальный прогон по затронутому пути (`local-test-runs`), затем форматтер и
статанализатор по **всем** файлам диффа — если в CI их нет, зелёный пайплайн статическую
чистоту не доказывает.

**Самопроверка — для любого вида.** Раздел «Самопроверка» вводной заполняется по чек-листам
`retry-safe-writes`, `fail-loud-boundaries`, `value-precision`, `change-hygiene` (для вёрстки —
`change-hygiene`; перечень — `scripts/orch/defect-skills.txt`). `orchestrate.sh done` с
незаполненным разделом останавливается, хук `mr-gate` не даёт открыть запрос на слияние: эти
классы дефектов ревьюеры находили после зелёных прогонов.

**Вёрстка.** Эталонные экраны:

```bash
scripts/orch/shot.sh ios .golden/shots/screen.png   # снять с симулятора
scripts/orch/golden.sh check                        # сверить весь набор
scripts/orch/golden.sh accept screen                # принять снимок как эталон
```

Сравнение идёт числами вне модели. Ответ — одна строка итога. Картинка попадает в сессию
только при расхождении выше допуска и только вырезкой по области расхождения.

**Полный кадр в контекст не тянуть никогда.** Полный кадр — сотни КБ, десятки тысяч токенов, и он
перечитывается на каждом следующем ходе. Это самая дорогая привычка при работе с вёрсткой.

Если эталона ещё нет, макет кладётся в `.golden/ref/<экран>.png` руками. Снимать нужно на
фиксированных данных: на живых ценах и счётчиках проверка перестаёт ловить настоящие сдвиги.

### 5. Ревью — делегированием, не в своей сессии

Порядок целиком — в `review-delegation`. Коротко:

```bash
scripts/orch/orchestrate.sh review <адрес запроса>
```

Собирает выжимку и запускает **работника Orca** со свежим контекстом — в родительскую сессию
возвращается только отчёт. Подагент `architect` — запасной путь, когда Orca недоступна.

Зачем: ревью большого набора съедает сотни тысяч токенов и остаётся в сессии до конца
её жизни. Выжимка сокращает вход подагента, делегирование не даёт разбору осесть в родителе.

Находки проверять самому — по `task-execution` §11.

## Сдача задачи

Запускается **только по явной команде** «задача выполнена» / `orchestrate.sh done <ключ>`.
Сама по себе, по факту зелёных тестов, не запускается никогда.

Ветки брать из **реестра веток проекта** (`docs/deploy/branch-registry.md`, если он есть) — не
выяснять заново. Если нужной системы там нет или запись помечена непроверенной, сначала сверить
(`scripts/orch/branch-registry.sh check <проект>`) и обновить файл.

### Порядок — жёсткий

1. **Убедиться, что всё влито в ветки задачи.** По каждому затронутому репозиторию:
   незакоммиченного нет, локальная ветка запушена, ветка задачи содержит все правки.
   Расхождение — остановиться и доложить, а не «долить по ходу».

2. **Запросы в промежуточную (тестовую) ветку.** По одному на репозиторий, из ветки задачи в
   промежуточную ветку из реестра. Коммиты схлопнуть, описание — по `commit-and-mr-writing`.
   Какая ветка считается промежуточной, у каждой системы своё — по реестру.

3. **Одобрить и влить** запросы в промежуточную ветку.

4. **Запустить деплой в тестовую среду.** Джобы — из реестра. Особенности пайплайна
   (ручные триггеры, порядок) — по проектному скиллу про CI и выкатку, если он есть.

5. **Подготовить запросы в ближайший релиз — и оставить открытыми.** Из ветки задачи
   в релизную ветку, которая поедет следующей. Нужны, чтобы к моменту боевой выкатки
   всё было готово и отревьюено.

6. **Номер сборки — если тестировщик ищет сборку по номеру.** После успешной джобы деплоя
   вывести в доклад версию и номер сборки из лога джобы. Без него сдача такой задачи не закрыта.

7. **Доложить**: что влито, что задеплоено, какие запросы ждут, в каком порядке выкатывать.
   Для сборок — с номером.

### Чего не делать при сдаче

- **Не вливать в боевые ветки.** Запросы туда не открывать вовсе.
- **Не вливать подготовленные релизные запросы** — они остаются открытыми до решения
  о выкате.
- Не запускать боевые джобы: ручной запуск — это защита, а не неудобство.
- Не считать слияние в основную ветку признаком боевой выкатки: у части сервисов джоба
  месяцами висит незапущенной.

## Когда резать сессию

- контекст перешёл 250 тыс. — доделать текущий шаг и начать новую;
- задача сменилась — **всегда** новая сессия, даже если прошлая короткая;
- переход к ревью — всегда новая;
- разбор затянулся и уехал в сторону — новая с вводной, а не продолжение.

Передача между сессиями идёт через файл вводной, а не через пересказ: дописать в
`.tasks/<ключ>/brief.md` что сделано и что осталось, новую сессию начать с него.

## Почему именно так

Почти весь расход — перечитывание контекста. Вывод модели занимает ничтожную долю от общего
расхода: каждый ход перечитывает весь накопленный контекст целиком, поэтому
**цена хода = размер контекста**, а не сложность работы.

Расход распределён неравномерно: небольшая доля ходов с самым большим контекстом даёт
непропорционально большую долю расхода. Свежая сессия стартует с небольшого контекста, и один
и тот же ход в конце долгой сессии стоит на порядок дороже, чем в начале свежей.

Причина накопления: много задач на одну сессию. Контекст закрытой задачи перечитывается во
всех следующих.

## Как проверять, что стало лучше

```bash
scripts/orch/stats.py                       # свод: расход, на ход, на задачу
scripts/orch/stats.py --phases              # структура по фазам работы
scripts/orch/stats.py --skills              # загрузки скиллов и делегирования
scripts/orch/stats.py --compare 14          # две недели против предыдущих двух
scripts/orch/stats.py --snapshot base.json  # зафиксировать замер
scripts/orch/stats.py --baseline base.json  # сравнить с ним позже
```

Показатель, по которому судить об алгоритме, — **расход на задачу**, а не общий расход.
Общий растёт вместе с объёмом работы; на задачу — падает, только если алгоритм работает.

Две поправки к любому выводу из этих чисел: ходы подагентов в журналы могут не попадать,
и один ответ пишется несколькими записями с общим usage — инструмент их склеивает по
`requestId`, сырой подсчёт завышает примерно вдвое. Подробности — `session-analytics`.

## Смежные скиллы

- `commit-and-mr-writing` — как оформлять коммиты и описания запросов.
- `orca-workflow` — раскладка скиллов Orca на эти фазы; делегирование работникам Orca
  вместо внутренних подагентов, потому что их расход виден аналитике.
- `task-execution` — корректность правки: семантика полей, цепочка клиент → промежуточный слой →
  сервис, тесты на границе систем, парные запросы и порядок выкатки.
- `codegraph-usage` — полный набор вызовов индекса, обслуживание, ловушка `projectPath`.
- `local-test-runs` — фаза 4.
- `review-delegation` — фаза 5: запуск ревью через оркестрацию.
- `retry-safe-writes`, `fail-loud-boundaries`, `value-precision`, `change-hygiene` — классы дефектов и самопроверка фазы 4. Хуки, которые их подсказывают и
  требуют, — `scripts/orch/install-hooks.sh`.

## Приёмка по следу — критерий готовности через expect.sh

**`worker_done` не является сдачей.** Работник шлёт `worker_done` сам и сам же решает,
что закончил. Проверка того, что работа действительно готова, идёт через **критерий готовности**
— команду оболочки, которая возвращает 0, если всё хорошо, и 1 если нет.

```bash
# Запуск задачи с критерием готовности:
scripts/orch/orchestrate.sh task TASK-1 --expect 'тест_что_готово'

# Проверка вручную:
scripts/orch/orchestrate.sh verify TASK-1

# При wait: если expect.sh есть и вернула не-0, работник ожидает исправления
scripts/orch/orchestrate.sh wait
```

**Где хранится expect.sh:** `.tasks/<ключ>/expect.sh` (для обычных задач) или
`.tasks/review-<ключ>/expect.sh` (для ревью). Файл создаётся при флаге `--expect`,
содержит одну bash-команду, исполняется `bash -c` из рабочего дерева работника.

**Три примера критериев:**

1. **Число файлов в диффе через API хостинга кода:**
   в `.tasks/<ключ>/expect.sh` — запрос к сравнению веток, ожидание заданного числа файлов.
   Файлов не столько → exit 1, НЕ ПРИНЯТО.

2. **Ноль открытых веток обсуждения через API хостинга кода:**
   в `.tasks/review-<проект>-<iid>/expect.sh` — запрос к обсуждениям запроса.
   Найдены открытые ветки → exit 1, НЕ ПРИНЯТО.

3. **Нет незапушенных коммитов:**
   в `expect.sh` — проверка, что в основной ветке нужного репозитория нет коммитов, которых
   нет на сервере. Найдены → exit 1, НЕ ПРИНЯТО.

### Приёмка смотрит туда, куда смотрит ревьюер

**Правило:** проверка измеряет то, что видит принимающая сторона (хостинг кода, ревьюер, пайплайн, слияние),
а не состояние рабочего дерева исполнителя. Локальный дифф доказывает только намерение. Типичный
случай: `verify` вернула ПРИНЯТО по локальному диффу в 4 файла, а на сервере было 8 (работник не запушил).

| Что проверяем | Где смотрим | Не трогаем |
|---|---|---|
| Правка в репозитории | сравнение веток или запрос на слияние в API хостинга кода | локальный `git diff` |
| Ответы ревьюера | обсуждения запроса в API хостинга кода | файл `ready.md` у работника |
| Прогон | джоба в пайплайне CI | вывод в терминале работника |
| Выкатка | статус окружения, джоба деплоя | слова работника «я запустил» |

**Три исхода проверки:**
- **ПРИНЯТО** (код 0): `expect.sh` вернула 0 и exit code 0.
- **НЕ ПРИНЯТО** (код 1): `expect.sh` вернула exit code 1 (ожидаемость не выполнена).
- **ПРОВЕРКА НЕ ВЫПОЛНЕНА** (код 2): `expect.sh` не найдена, не может быть выполнена, синтаксическая ошибка, 
  сеть, нет доступа (exit code ≠ 0, 1).

**Счётчик провалов:** Каждая проверка логируется в `.tasks/<ключ>/verify.log` с кодом и исходом.
На второй подряд провал (НЕ ПРИНЯТО или ПРОВЕРКА НЕ ВЫПОЛНЕНА) — печатается **ВЫНЕСТИ ЧЕЛОВЕКУ**, не предлагается третий заход.

**При `wait` и `release`:** После `worker_done`, если есть `expect.sh`:
- **ПРИНЯТО** (код 0): работник отпущен обычным порядком.
- **НЕ ПРИНЯТО** (код 1): `expect_checked`, работник retained, координатору
  предлагается `say <dispatch> "…"` для доработки.
- **ПРОВЕРКА НЕ ВЫПОЛНЕНА** (код 2): `expect.sh` не выполнена (сеть, доступ, синтаксис). 
  Работник retained; координатор выясняет причину и либо переводит в НЕ ПРИНЯТО, либо вносит поправку в expect.sh.

**Доклад и шпаргалки:** В `worker_done` координатор требует полного **следа** —
commits SHA, номера MR, ID отправленных note'ов, вывод expect.sh. Доклад без следа
не считается сдачей (см. `spec_for` в orchestrate.sh).

## Чего этот скилл не делает

Не заменяет `task-execution`: там ловушки корректности (семантика полей, цепочка
клиент → промежуточный слой → сервис, тесты на границе систем, парные запросы и порядок выкатки).
Здесь только организация работы и расход.

## Модель под вид работы

| Вид работы | Команда | Модель |
|---|---|---|
| Разведка: факт, число, цитата требований, «кто вызывает» | `orchestrate.sh research <КЛЮЧ> "<вопрос>"` | Haiku (`ORCH_RESEARCH_MODEL`) |
| Правки кода, ревью, координация, разбор противоречий | `task` / `front` / `review` / `lead` | модель по умолчанию, при нужде `ORCH_MODEL` |

Разведчик решений не принимает: увидел развилку — описал и вернул. Проверка, что делегирование
удалось: в родительской сессии не появилось ни одного `Read` по файлам, о которых спрашивали.
