# Устройство правки: что ревьюер увидит первым

Замечания этого класса не роняют прод сразу, но из-за них ревьюер перестаёт доверять
остальному. В !918 они же **прятали** блокеры: неопределённая переменная в V1 прошла, потому что
phpstan гоняли только по V3, а копия метода из V2 унесла с собой старый неверный порядок шагов.

## 1. Куда класть код

- **Не дописывать большой сценарий в перегруженный класс.** В `V3\OrderService` к ~1200 строкам
  добавили ~1230: HTTP-сценарий, хранилище состояния, машина состояний списаний, два клиента
  сервера скидок и сборка тел для OMS. Отдельный модуль: репозиторий состояния (чтение и запись
  через типизированный DTO), сервис операций, сборщик тел. Старый класс — оркестратор.
  Порог: если правка добавляет в класс больше трети его объёма, остановиться и разложить.
- **Не копировать метод из соседней версии с правками** (`updateStatusByArmV3` как копия V2,
  `collectArmOrderItemUpdateDataV3` с 11 параметрами, из них 3 по ссылке). Копия уносит дефекты
  оригинала и расходится при первой правке. Вынести общее в трейт, базовый класс или сервис.
- **У сохранённого формата один владелец.** Если формат состояния (`rolledBack`,
  `spendingsConfirmed`) знают V1 и V3 по отдельности, со своим `json_decode` и строковым
  литералом вместо константы, — нужен один класс с DTO, которым пользуются оба.
- Константы класса — в начале класса. Новый метод не вставлять между чужим docblock и методом.

## 2. Механизмы проекта не обходить

- События — механизмом проекта, после коммита (`gj-retry-safe-writes` §6); обход ревьюер спросит.
- Запись через query builder мимо модели с `AuditWithTransform` обходит аудит. Если обход нужен
  (не будить наблюдатель), делать явно: `saveQuietly` + запись аудита, с объяснением.
- `load()` в конструкторе нагрузки события, вызываемом для **каждого** события сущности, — это
  +1 запрос на сообщение по всей системе. `loadMissing`, а в массовых местах
  (`PushModelChangesCommand`, наблюдатель товара) — пакетная предзагрузка.
- N+1: запрос на каждый элемент пакета свести в один (`GROUP BY`, `whereIn`, один `UPDATE`).
- Простое писать просто: `whereNull()` вместо `where(x, null)` с комментарием; enum сравнивать
  напрямую; `whereNotIn(…, [])` без магического `?: [0]`; не оборачивать в `transaction()` один
  `save`; `bin2hex(random_bytes(6))` вместо `substr(bin2hex(random_bytes(8)), 0, 12)`.

## 3. Комментарии

Правило воркспейса (см. память `code-comments-no-process` и `AGENTS.md`): в коде только
«почему» и опасность, 1–3 строки.

- Не пересказывать ТЗ, историю ревью («в первой версии», «раньше»), номера задач. Это место
  для описания запроса и коммита.
- **Комментарий, обещающий защиту, проверить кодом.** «От повтора защищает статус на следующем
  шаге» и «блокировка не даст дубля» оказались неверны. Формулировка из ФТ дословно — не
  доказательство.
- Docblock после правки обновить: устаревшие `@throws`, описание прежнего правила, неописанные
  параметры. `@throws` — коротким именем, если пространство импортировано.
- Мёртвые присваивания, ненужные значения по умолчанию у параметра, который все передают
  явно, — убрать.

## 4. Тесты, которым можно верить

- **Фикстуры по форме прод-данных.** Перед тем как построить фикстуру, снять реальную форму
  (`data_pg_query`, `data_logs_raw_search`, живой ответ стенда). В !918 фикстура заполняла
  `items[].loyaltyPointsBurn`, а в проде оно пусто у всех позиций; в !237 фикстура несла ISO
  `+03:00`, а источник шлёт `Y-m-d H:i:s.v` без пояса. Тест зелёный на данных, которых не бывает.
- **Сценарий через публичный метод**, а не 30 кейсов на protected-методы через наследников-обёрток.
  Фрагментные тесты не видят порядка шагов и неопределённых переменных между ними.
- **Подмена должна проверять.** `allows('execute')` глушит Kafka и ничего не доказывает.
- **Новая ветка — свой тест.** Тест, который проходит и без новой ветки, её не держит.
- Общий `setUp` / `tearDown` — в базовый TestCase, а не копией в каждый файл.
- Сценарии сбоя — по `gj-retry-safe-writes`, отказы — по `gj-fail-loud-boundaries`.

## 5. Статический анализ — по всему диффу

phpstan и cs-fixer гонять по **каждому** затронутому файлу, а не по «основному» каталогу правки.
В Lumen notice превращается в `ErrorException` (`error_reporting(-1)`): неопределённая
переменная — это 500 в проде, а не предупреждение.

```bash
# клоны неглубокие: двухточечный diff, удалённые файлы отбросить
git diff --name-only --diff-filter=d origin/<основа> HEAD -- '*.php' | xargs php -d memory_limit=2G vendor/bin/phpstan analyse
```

Унаследованные ошибки в задетом классе не повод не смотреть на новые: сравнить число до и после.

## 6. Описание запроса = код

- Каждое утверждение описания («снимает старый риск», «идемпотентно», «защищено от повтора»)
  проверить по коду и тесту. В !927 «снимает риск выкупа не той единицы» было верно для
  пересчёта и неверно для подтверждения.
- Открытый вопрос к аналитику в описании означает, что запрос не готов. Закрыть до слияния
  (коды ошибок, семантика ответов внешней системы, поведение на краевом случае).
- **Отступление от ФТ** (признак на `sku_products`, а ФТ знает только `base_products`) внести
  в ФТ и в разбор задачи. Иначе следующий исполнитель «исправит» его обратно.
- **Описание обновлять после каждого коммита.** В !831 описание писалось до последнего коммита
  и не говорило, что код отошёл от постановки. Перед сдачей перечитать описание против итогового диффа.
- Docblock не может обосновывать поведение, которое этот же запрос изменил.
- «Задача без владельца» в комментарии («пока источник не свели к одному») — либо задача в Jira
  со ссылкой, либо убрать.
- Мёртвые колонки и поля, которые источник не отдаёт (`manufacturer_name`), не добавлять «на будущее».

## Самопроверка перед сдачей

Записать в вводную задачи ответ по каждому пункту:

1. Ни один класс не вырос больше чем на треть; копий методов из соседних версий нет.
2. У каждого сохранённого формата один владелец.
3. Механизм событий, аудит и предзагрузка — как принято в проекте; N+1 нет.
4. Комментарии — только «почему»; каждое обещание защиты подтверждено тестом.
5. Фикстуры сняты с прод-формы; есть сценарный тест через публичный метод.
6. phpstan и cs-fixer прогнаны по всем файлам диффа, новых ошибок 0.
7. Каждое утверждение описания подтверждено; открытых вопросов к аналитику нет;
   отступления от ФТ внесены в ФТ.

## Смежные скиллы

- `gj-task-execution` — корректность: семантика полей, цепочка клиент → витрина → сервис.
- `gj-commit-and-mr-writing` — формат описания запроса.
- `gj-local-test-runs` — как прогнать тесты и phpstan локально.
