# Организация работы над задачей

Правила корректности — в `gj-task-execution`. Здесь — как задача устроена во времени:
чем нарезается на сессии, что уходит подагентам, чем закрывается.

## Коротко: порядок работы

```bash
scripts/gj/orchestrate.sh lead   <КЛЮЧ> "заголовок"   # отдельный агент-координатор во вкладке
scripts/gj/orchestrate.sh task   <КЛЮЧ> "заголовок"   # завести и запустить
scripts/gj/orchestrate.sh list | say | read | wait     # следить и вмешиваться
scripts/gj/orchestrate.sh review <адрес запроса>       # ревью
scripts/gj/orchestrate.sh done   <КЛЮЧ>                # сдача, по явной команде
```

`lead` — когда задачу ведёт не эта сессия: новая вкладка «<КЛЮЧ> · координатор» сама
запускает работника, держит `wait`, отвечает на его вопросы, по готовности зовёт ревью и
докладывает. Сдача — по-прежнему только по явной команде. Реплика — `.tasks/<ключ>/lead.md`;
для вёрстки третьим аргументом `front`.

Пачкой, когда задач несколько:

```bash
scripts/gj/fleet.sh run OPSOMN002-294 OPSOMN002-416:front OPSOMN002-422@beauty-422
scripts/gj/fleet.sh status | watch | stop все
```

Вид после `:` — `task` (по умолчанию), `front`, `review`. Имя дерева после `@` — задача
уйдёт в отдельное дерево Orca со своей вкладкой; нет такого — создастся от `main`.
Без `@` работник садится в текущее дерево, вкладку Orca даёт сама.

Пачка останавливается на первом отказе заслона, а не запускает половину молча.

1. **Постановка** — первым действием перевести задачу в Jira в статус «В работе»
   (раздел 1 ниже). Затем прочитать первоисточники, вписать во вводную цель одной фразой
   и критерий готовности. Не формулируется критерий — вернуть постановщику.
2. **Разведка** — вопросы выписать до поиска; закрывать сначала по ТЗ, потом по коду;
   поиск вести подагентами (codegraph — где есть индекс). Человеку выносить только то,
   что нельзя закрыть самому.
3. **Правка** — по `gj-task-execution`. Фрагмент файла читать `sed`, не целиком.
4. **Контроль** — бэк: прогон плюс phpstan и cs-fixer. Вёрстка: `orca emulator ax`
   для состава, `scripts/gj/golden.sh check` для внешнего вида.
5. **Ревью** — `gj-review-delegation`, свежим работником, не в своей сессии.

**Деплой, анализ веток и статуса задачи, исследование, ревью — подагентам по
`gj-subagent-delegation`**: какой подагент, какой контекст ему передать, как он спрашивает
родителя и как родитель ему отвечает. Координатор сам эти работы не ведёт — замер 16–30.09:
63% его расхода ушло именно на них при контексте 420–490 тыс., делегирований было 5 ходов.
6. **Сдача** — только по явной команде, раздел ниже.

**После деплоя мобильного — прислать номер сборки.** Всегда, а не только в рамках сдачи:
как только прошла джоба `android-staging`, `ios-staging`, `android-production`,
`ios-production` или `android-production-rustore` — вывести **versionName и versionCode**
из её лога (строки `Version name` / `Version code`). Без номера тестировщику нечего искать
в сторе и в Nexus, и мобильная работа не считается сданной. Подробности — `gj-ci-deploy-map`.

**Резать сессию** — при переходе контекста за 250 тыс., при смене задачи, перед ревью.
Проверять себя так: **каждый десятый ход смотреть `/context`**; перешёл порог — доделать
текущий шаг, дописать во вводную что сделано и что осталось, начать новую сессию.
Правило с действием выполняется, правило с числом — нет: замер на задаче 289 показал,
что 72% ходов работника прошли выше потолка, потому что его никто не проверял.

**Складывать независимые команды в один ход.** Это самый крупный рычаг из измеренных:
за три дня 3 268 команд прошли в 3 130 ходов — **1,04 команды на ход**, больше одной
лишь в 4% случаев. При этом ходы только с оболочкой дают **74,6% всего расхода**: ответ
`Bash` весит 1,1 КБ и дёшев, дорог сам ход — он перечитывает 353 тыс. контекста.

Складывание по три сократило бы 3 130 ходов до 1 090 и сэкономило около **720 млн
токенов за три дня** — половину всего расхода за период. Больше, чем дали разделение
сессий, выжимка запросов и сверка вёрстки вместе.

Как это выглядит: проверки, поиски, чтения разных файлов почти всегда независимы —
их в один ход через `;` или `&&`. Зависимые (второе нужно считать по результату первого)
остаются раздельными. То же для инструментов Buddy: несколько запросов к Jira и GitLab
идут одним блоком, а не по одному.

**Ответы человеку — плотные.** 10% ходов не содержат инструментов вовсе и стоят 182 млн
за три дня: каждый перечитывает весь контекст ради нескольких сотен слов. Промежуточные
«сейчас проверю» не писать — писать результат.

**Чего не тянуть в контекст никогда:** полные кадры экрана (390 КБ ≈ 97 тыс. токенов —
снимать `scripts/gj/shot.sh`, сверять `golden.sh`), полные диффы сгенерированного кода,
выдачу поиска, целые файлы вместо фрагментов.


## Фазы задачи и потолки контекста

Фазы 1–2 и 3–4 идут в одной сессии, фаза 5 — всегда в новой.

| Фаза | Где идёт | Потолок | Чем закрывается |
|---|---|---|---|
| 0. Заведение | скрипт, без модели | 0 | `task.sh` положил вводную |
| 1. Постановка | сессия задачи | 100 тыс. | цель и критерий готовности вписаны во вводную |
| 2. Разведка | codegraph + подагенты | 150 тыс. | вопросы закрыты, человеку вынесен только остаток |
| 3. Правка | та же сессия | 250 тыс. | правка внесена |
| 4. Контроль | скрипты | +0 | форма контроля прошла |
| 5. Ревью | **работник Orca** (`orchestrate.sh review`) | ~0 в родителе | отчёт с вердиктом |

**Граница сессии** — одно из двух: контекст перевалил 250 тыс. либо задача перешла
к ревью. Не «когда надоело».

### 0. Заведение — оркестратором

```bash
scripts/gj/orchestrate.sh task   OPSOMN002-123 "короткий заголовок"
scripts/gj/orchestrate.sh front  OPSOMN002-124 "короткий заголовок"
scripts/gj/orchestrate.sh review <адрес запроса>
scripts/gj/orchestrate.sh done   OPSOMN002-123
```

Открывает отдельную вкладку и запускает в ней сессию. Модель на этом шаге не работает.

Управление уже запущенным:

```bash
scripts/gj/orchestrate.sh list                # что сейчас идёт и в каком состоянии
scripts/gj/orchestrate.sh say  <вкладка> "…"  # вмешаться: дослать указание
scripts/gj/orchestrate.sh read <вкладка> 60   # посмотреть, что там
scripts/gj/orchestrate.sh wait <вкладка>      # дождаться, пока освободится
scripts/gj/orchestrate.sh go   <вкладка>      # переключиться и вести руками
```

Заслон по ресурсам перед запуском: не больше `GJ_MAX_AGENTS` (по умолчанию 20) сессий
одновременно и не меньше `GJ_MIN_FREE_MB` (2 ГБ) свободной памяти. Одна сессия занимает
200–700 МБ и растёт вместе с контекстом. Обойти — `GJ_FORCE=1` либо поднять потолки
переменными.

Жёсткого лимита ОЗУ на процесс тут нет и быть не может: `claude` — нативный бинарь,
`ulimit` на него не действует, cgroups в macOS отсутствуют. Ограничивается то, что
поддаётся: число одновременных сессий и свободная память на входе.

**Почему через оркестратор, а не просто `claude`.** Он вписывает вызовы нужных скиллов
первой строкой стартовой реплики. Замерено: скиллы загружаются в 0,17% ходов, и из
54 русских триггерных фраз в 1 438 репликах встретились шесть — подбор по описанию
не работает. Текст, пришедший в самом сообщении, срабатывает всегда.

### 0.1. Две ловушки запуска — обе уже сорвали задачи

**Рабочее дерево git не содержит клонов `platform/*`.** В нём остаются одни `README`:
вложенные клоны — отдельные репозитории, в worktree они не попадают. Работник получает
вводную и не находит файлов, которые надо править.

Так сорвалась OPSOMN002-422: четыре работника отработали, следов в `customers-api-web`
ноль. Оркестратор теперь отказывается стартовать в дереве без клонов; обойти —
`GJ_SKIP_TREE_CHECK=1`, если задача их правда не трогает.

**`--worktree current` берёт активное дерево интерфейса Orca, а не каталог запуска.**
Проверено 17.09: запуск из `flyingfish` посадил работника в основное дерево. Поэтому
оркестратор задаёт дерево явно — `path:<дерево вызвавшего агента>` (корень git по
каталогу запуска).

**Работник садится в дерево агента, который его запустил.** Не в главное: 30.09 на
OPSOMN002-534 умолчание «главное дерево» увело работника из `flyingfish` в чужой каталог
без предупреждения. Если в дереве агента нет клонов, заслон остановит запуск и подскажет
путь в главное дерево. Направлять туда нужно только явно: `GJ_WORKTREE=path:<путь>` или
`fleet.sh run КЛЮЧ@main`, и сказать об этом пользователю до запуска.

**Вводная, оставшаяся шаблоном, — признак, что работа не начиналась.** `done` на такой
задаче отказывает: сдавать нечего. Так выяснилось про OPSOMN002-295.

### 1. Постановка

**Первым действием — статус «В работе» в Jira.** Только для задач (`task`, `front`),
не для ревью и не для сдачи:

1. `jira_get_issue` — посмотреть текущий статус. Уже «В работе» или дальше по процессу
   (ревью, тестирование, закрыта) — ничего не делать: назад задачу не двигать.
2. `jira_list_transitions` — найти переход, **целевой статус** которого называется
   «В работе» (без учёта регистра). Номер перехода не запоминать и не переносить
   между задачами: он зависит от схемы процесса и текущего статуса.
3. `jira_transition_issue` с найденным номером.
4. Перехода нет или Jira не отвечает (502 = упал VPN) — не останавливать задачу:
   одной строкой записать во вводную «статус не переведён: <причина>» и доложить
   в итоге, чтобы человек перевёл руками.

Читать первоисточники по `gj-task-execution` §1. Большие страницы Confluence — только
`documents_read_manifest` + `documents_read_chunk`, полную страницу не тянуть.

Вписать во вводную две строки: **цель одной фразой** и **критерий готовности**. Если
критерий не формулируется — задача не готова к работе, возвращать постановщику.

### 2. Разведка — закрыть вопросы самому, человеку нести только остаток

Цель фазы не «изучить код», а **закрыть открытые вопросы**. Человеку уходит только то,
на что не нашлось однозначного ответа ни в требованиях, ни в коде.

#### 2.1. Обновить индекс — до начала, не по ходу

```bash
codegraph status platform/mobile-app/gj-app   # ПЕРВЫМ ДЕЛОМ — есть ли индекс вообще
codegraph init   platform/mobile-app/gj-app   # если «Not initialized» — завести, в фоне
codegraph sync   platform/mobile-app/gj-app   # подхватить правки, быстро
codegraph index  platform/mobile-app/gj-app   # после смены ветки или крупных правок, в фоне
```

**Начинать со `status`.** Проверено 15.09.2026: индекса в воркспейсе нет ни одного —
`.codegraph/` отсутствует везде, включая `gj-app`, хотя скилл `codegraph-usage` утверждает
обратное. Пока индекс не заведён, вызовы `codegraph_*` бесполезны, и разведка по мобайлу
идёт подагентом, как по остальным платформам.

Индекс отстаёт от правок примерно на секунду через watcher, но после переключения ветки
и после чужих пушей ему верить нельзя. Прогон на устаревшем индексе даёт ответы про
несуществующий код — это хуже, чем отсутствие ответа.

`gj-app` — около 1 800 файлов, поэтому `init` и `index` запускать в фоне и дождаться.
Остальные платформы не проиндексированы вовсе.

#### 2.2. Выписать вопросы до поиска

Открытые вопросы выписать списком **до** того, как лезть в код: иначе разведка
превращается в чтение всего подряд, а вопросы всплывают на ревью. Формулировка вопроса —
такая, чтобы ответ был проверяемым: не «как работает корзина», а «чем различаются
удаление позиции и снятие выбора в payload витрины».

#### 2.3. Закрыть каждый вопрос по двум источникам

Порядок обязателен: **сначала требования, потом код.** Код показывает, как есть; требования
говорят, как должно быть. Ответ «в коде так» не закрывает вопрос, если ТЗ требует иного —
это находка, а не ответ.

| Источник | Чем берётся |
|---|---|
| Требования | `jira_get_issue` + комментарии отдельно; Confluence — `documents_read_manifest` + `documents_read_chunk`, полную страницу не тянуть |
| Код в `gj-app` | `codegraph_explore` — один вызов, отдаёт исходник нужных символов |
| Код в остальных платформах | подагент (`ensi-navigator`, `*-researcher`, `Explore`) |
| Поведение в проде | `data_pg_query`, `data_logs_raw_search` — когда вопрос про «а как оно на самом деле» |

#### 2.4. Кто ищет — codegraph или подагент

Задание подагенту, наборы контекста и канал связи — `gj-subagent-delegation`.

Это разные инструменты под разные области, и путать их дорого:

- **`platform/mobile-app/gj-app` — codegraph, если индекс заведён; иначе подагент.** С индексом
  `codegraph_explore` отвечает одним вызовом и отдаёт исходник нужных символов. Делегировать
  сюда подагента — значит оплатить его контекст ради того, что и так лежит готовым.
  Открывать `Read`-ом файлы, которые `codegraph_explore` уже показал, тоже не нужно.
- **Все остальные платформы — только подагент.** ENSI, OMS, сайт, ИС, OTS не проиндексированы,
  поиск там идёт обходом файлов, и вся выдача осела бы в основном контексте до конца работы.

Полезные вызовы помимо `explore`: `codegraph_impact` перед правкой символа (что заденет),
`codegraph_callers` (кто вызывает). Каждый вызов — с `projectPath`, иначе падает
с `No project loaded`.

Замерено 15.09.2026: делегирований всего 74 на 14 833 хода (0,5%), и 58 из них — `architect`
на ревью. На разведку по задачам подагенты не используются практически никогда.

**Договор с подагентом.** В задании всегда: «верни выводы со ссылками `файл:строка`,
содержимое файлов не приводи». Хороший ответ — 20–40 строк: что нашлось, где именно, что из
этого следует. Подагент, вернувший выдачу `grep`, работу не сделал — его ответ занимает
столько же, сколько самостоятельный поиск.

#### 2.5. «Не проверено» — это незакрытый шаг, а не ответ

Прежде чем написать человеку «не проверял», «в коде не нашёл», «на живом контуре не
смотрел», «тесты не гонял» — **пойти и проверить**. Это самая частая претензия к работе
агентов здесь: вопрос отдают человеку вместо того, чтобы потратить пять минут на замер.

Таблица: что делать вместо каждой формулировки.

| Собрался написать | Сначала сделать |
|---|---|
| «на живом контуре не проверено» | дёрнуть test/stage напрямую: хосты и креды в `.env` мобильного и в `gj-live-e2e-checkout-contour`; гостевой сценарий работает без авторизации |
| «как ведёт себя в проде — неизвестно» | `data_pg_query` по прод-БД, `data_logs_raw_search` по логам; обёртки `search_message`/`recent` на части таргетов молчат — сразу raw |
| «в коде не нашёл» / «не смотрел» | `codegraph_explore` там, где есть индекс, подагент — где нет; `grep -rn` по конкретному репозиторию |
| «тесты не прогонял» | `gj-local-test-runs`: прогон по затронутому пути, не весь набор |
| «не знаю, доехало ли до прода» | слияние в прод-ветку **и** успешная джоба прод-деплоя на её вершине; ветки — из `docs/deploy/branch-registry.md` |
| «не знаю, собирается ли» | `gitlab_list_pipeline_jobs` по ветке, `gitlab_get_job_log` по упавшей |
| «сколько таких случаев — не считал» | посчитать: `grep -c`, `data_pg_query` с `count(*)` |
| «какая версия у сборки» | лог джобы: строки `Version name` / `Version code` |

**Правило:** если средство проверки существует и доступно — проверка обязательна.
Человеку уходит результат замера, а не просьба замерить за тебя.

**Сверка отчёта с самим собой — перед отправкой.** Разобранный случай: в одном пункте
отчёта сказано «ключ к тестовому контуру в задаче есть», в соседнем — «по живому контуру
не проверено». Средство было названо тем же отчётом и не применено; вместо замера код
сделали «устойчивым к обоим вариантам имён», то есть угадали два ответа там, где можно
было увидеть один настоящий.

Перед отправкой пройти по каждому «не проверено» и спросить: **не упоминается ли средство
проверки где-то ещё в этом же отчёте, в задаче или в `.env`?** Если упоминается — идти
проверять, а не отправлять.

**Догадка вместо замера — тоже отписка.** Код, написанный «на оба варианта», потому что
настоящий формат не смотрели, — не запас прочности, а непроверенная гипотеза в двух
экземплярах. Замерить и оставить один путь.

**«Что осталось» — только незакрытые вопросы.** Осознанные решения о порядке выкатки,
зависимости между запросами и отложенные по плану шаги идут в раздел «Выкатка». Попав
в «осталось», они читаются как недоделка и заставляют человека разбираться, чего от него
ждут. Признак: если рядом написано «делается после X» — это порядок, а не открытый вопрос.

**У законно открытого вопроса обязательны две вещи:** что уже сделано для его закрытия
(у кого и когда запрошен доступ, что пробовали) и является ли обходной путь временным
или окончательным. Иначе человек додумывает за агента.

#### 2.6. Что действительно уходит человеку

Только то, что **нельзя** закрыть самому. Законных причин четыре:

1. **Решение за владельцем** — контракта, продукта, архитектуры. Не факт, а выбор.
2. **Требования противоречат друг другу** либо коду, и чья правда — вопрос к постановщику.
3. **Оба источника молчат** — ни в ТЗ, ни в коде ответа нет.
4. **Нужен доступ, которого нет** — запись в прод, выкатка, физическое устройство,
   публикация в сторе. Либо средство сейчас недоступно (упал контур) — и тогда так
   и писать: «проверю, когда поднимется», а не «не проверено».

Формат выноса — три строки на вопрос:

```
Вопрос: <формулировка>
Проверено: ТЗ <ссылка/пункт> — <что там>; код <файл:строка> — <что там>;
           замер <команда> — <результат>
Почему открыт: <одна из четырёх причин выше>
Мой вариант: <что предлагаю, чтобы человеку было проще подтвердить, чем решать с нуля>
```

Строка «Проверено» без конкретики — признак того, что шаг 2.5 пропущен. «Посмотрел код»
не считается: нужны файл и строка. «Проверил на стенде» не считается: нужен запрос и ответ.

Если открытых вопросов не осталось — не спрашивать ничего и идти к правке.

### 3. Правка

Правки по `gj-task-execution`. Что не тянуть в контекст:

- **целые файлы**, когда нужен фрагмент — `sed -n 'A,Bp'` вместо `Read`;
- **выдачу поиска** — считать `grep -c`, читать точечно;
- **полные диффы сгенерированного кода** — см. фазу 5;
- **снимки экрана** — см. фазу 4.

Ответ `Bash` дешёвый — 1,1 КБ против 213 КБ у чтения файла. Но **ход дорог сам по себе**:
10 141 хода только с `Bash` дали 67% всего расхода, потому что каждый перечитывает
весь контекст. Отсюда два правила, а не одно: брать `Bash` вместо `Read` — и складывать
несколько команд в один ход вместо цепочки ходов.

### 4. Контроль — по виду задачи

**Бэк.** Локальный прогон по затронутому пути (`gj-local-test-runs`), затем phpstan и
cs-fixer — в CI ENSI их нет, зелёный пайплайн статическую чистоту не доказывает.

**Вёрстка.** Эталонные экраны:

```bash
scripts/gj/shot.sh ios .golden/shots/pdp.png   # снять с симулятора
scripts/gj/golden.sh check                     # сверить весь набор
scripts/gj/golden.sh accept pdp                # принять снимок как эталон
```

Сравнение идёт числами вне модели. Ответ — одна строка итога. Картинка попадает в сессию
только при расхождении выше допуска и только вырезкой по области расхождения.

**Полный кадр в контекст не тянуть никогда.** Кадр iPhone — 390 КБ ≈ 97 тыс. токенов, и он
перечитывается на каждом следующем ходе. По журналам 219 таких чтений дали 99% всего
объёма чтения файлов — это самая дорогая привычка из найденных.

Если эталона ещё нет, макет кладётся в `.golden/ref/<экран>.png` руками. Снимать нужно на
фиксированных данных: на живых ценах и счётчиках проверка перестаёт ловить настоящие сдвиги.

### 5. Ревью — делегированием, не в своей сессии

Порядок целиком — в `gj-review-delegation`. Коротко:

```bash
scripts/gj/orchestrate.sh review <адрес запроса>
```

Собирает выжимку и запускает **работника Orca** со свежим контекстом — в родительскую сессию
возвращается только отчёт. Подагент `architect` — запасной путь, когда Orca недоступна.

Зачем: ревью последних наборов съедало свыше 200 тыс. токенов и оставалось в сессии до конца
её жизни. Выжимка сокращает вход подагента, делегирование не даёт разбору осесть в родителе.

Находки проверять самому — по `gj-task-execution` §11.

## Сдача задачи

Запускается **только по явной команде** «задача выполнена» / `orchestrate.sh done <ключ>`.
Сама по себе, по факту зелёных тестов, не запускается никогда.

Ветки брать из **`docs/deploy/branch-registry.md`** — не выяснять заново. Если нужной
системы там нет или запись помечена непроверенной, сначала сверить
(`scripts/gj/branch-registry.sh check <проект>`) и обновить файл.

### Порядок — жёсткий

1. **Убедиться, что всё влито в ветки задачи.** По каждому затронутому репозиторию:
   незакоммиченного нет, локальная ветка запушена, ветка задачи содержит все правки.
   Расхождение — остановиться и доложить, а не «долить по ходу».

2. **Запросы в стейдж.** По одному на репозиторий, из ветки задачи в стейдж-ветку из
   реестра. Коммиты схлопнуть, описание — по `gj-commit-and-mr-writing`. Для ENSI это `release-<ГГ.ММ>` текущего релиза, для ИС — `stage`,
   для витрины — **`deploy/stage`** (единственная система, где стейдж не релизная ветка).

3. **Одобрить и влить** запросы в стейдж.

4. **Запустить деплой стейджа.** Джобы — из реестра (`stage:deploy-*`,
   `deploy:is-api-stage` и `deploy:is-cron-stage`, `deploy:front-stage-ru`).
   В ENSI помнить: на `release-*` образ собирается только веб-триггером, иначе деплой
   упадёт на pre-upgrade hooks.

5. **Подготовить запросы в ближайший релиз — и оставить открытыми.** Из ветки задачи
   в релизную ветку, которая поедет следующей. Нужны, чтобы к моменту выката прода
   всё было готово и отревьюено.

6. **Номер сборки мобильного — обязательно.** После успешной джобы деплоя мобильного
   приложения (`android-staging`, `ios-staging`, `android-production`, `ios-production`,
   `android-production-rustore`) вывести в доклад **versionName и versionCode**.

   Где брать: они печатаются в лог джобы строками `Version name (IMPORTANT!!!)` и
   `Version code (IMPORTANT!!!)`. Читать через `gitlab_get_job_log` по id успешной джобы.

   Как считается: `versionCode = CI_PIPELINE_IID + OFFSET_PARAM`, где `OFFSET_PARAM = 85000`
   (переменная в `.gitlab-ci.yml` мобильного). То есть номер сборки привязан к номеру
   пайплайна, а не к версии в `package.json` — по `package.json` его определить нельзя.

   Без номера сборки сдача мобильной задачи не закрыта: по нему тестировщик находит
   сборку в сторе или в Nexus, и без него проверять нечего.

7. **Доложить**: что влито, что задеплоено, какие запросы ждут, в каком порядке выкатывать.
   Для мобильного — с номером сборки.

### Чего не делать при сдаче

- **Не вливать в прод.** Ни в `master` ENSI, ни в `production` ИС, ни в
  `release/production` витрины. Запросы туда не открывать вовсе.
- **Не вливать подготовленные релизные запросы** — они остаются открытыми до решения
  о выкате.
- Не запускать прод-джобы. В ENSI `prod:deploy` ручная — это защита, а не неудобство.
- Не считать слияние в `master` признаком прода: у части сервисов джоба месяцами висит
  незапущенной.

## Когда резать сессию

- контекст перешёл 250 тыс. — доделать текущий шаг и начать новую;
- задача сменилась — **всегда** новая сессия, даже если прошлая короткая;
- переход к ревью — всегда новая;
- разбор затянулся и уехал в сторону — новая с вводной, а не продолжение.

Передача между сессиями идёт через файл вводной, а не через пересказ: дописать в
`.tasks/<ключ>/brief.md` что сделано и что осталось, новую сессию начать с него.

## Почему именно так

99,8% расхода — перечитывание контекста. Вывод модели за два месяца занял 12 млн токенов
из 6,72 млрд. Каждый ход перечитывает весь накопленный контекст целиком, поэтому
**цена хода = размер контекста**, а не сложность работы.

| Полоса контекста | Доля ходов | Доля расхода |
|---|---|---|
| до 150 тыс. | 12,4% | 2,9% |
| 150–300 тыс. | 23,0% | 11,3% |
| 300–500 тыс. | 24,4% | 21,3% |
| 500–700 тыс. | 17,3% | 22,9% |
| свыше 700 тыс. | 22,9% | **41,7%** |

Свежая сессия стартует с 62 тыс. токенов. Медианный ход идёт при 414 тыс., девятый
дециль — 829 тыс. Один и тот же ход в конце долгой сессии стоит вдесятеро дороже, чем
в начале свежей.

Причина накопления: на 66 сессий пришлось 1 437 задач — **по 22 задачи на сессию**.
Контекст закрытой задачи перечитывается во всех следующих.

## Как проверять, что стало лучше

```bash
scripts/gj/stats.py                       # свод: расход, на ход, на задачу
scripts/gj/stats.py --phases              # структура по фазам работы
scripts/gj/stats.py --skills              # загрузки скиллов и делегирования
scripts/gj/stats.py --compare 14          # две недели против предыдущих двух
scripts/gj/stats.py --snapshot base.json  # зафиксировать замер
scripts/gj/stats.py --baseline base.json  # сравнить с ним позже
```

Показатель, по которому судить об алгоритме, — **расход на задачу**, а не общий расход.
Общий растёт вместе с объёмом работы; на задачу — падает, только если алгоритм работает.

Две поправки к любому выводу из этих чисел: ходы подагентов в журналы не попадают вовсе,
и один ответ пишется несколькими записями с общим usage — инструмент их склеивает по
`requestId`, сырой подсчёт завышает примерно вдвое.

## Приёмка по следу — критерий готовности через expect.sh

**`worker_done` не является сдачей.** Работник шлёт `worker_done` сам и сам же решает,
что закончил. Проверка того, что работа действительно готова, идёт через **критерий готовности**
— команду оболочки, которая возвращает 0, если всё хорошо, и 1 если нет.

```bash
# Запуск задачи с критерием готовности:
scripts/gj/orchestrate.sh task OPSOMN002-123 --expect 'тест_что_готово'

# Проверка вручную:
scripts/gj/orchestrate.sh verify OPSOMN002-123

# При wait: если expect.sh есть и вернула не-0, работник ожидает исправления
scripts/gj/orchestrate.sh wait
```

**Где хранится expect.sh:** `.tasks/<ключ>/expect.sh` (для обычных задач) или
`.tasks/review-<ключ>/expect.sh` (для ревью). Файл создаётся при флаге `--expect`,
содержит одну bash-команду, исполняется `bash -c` из рабочего дерева работника.

**Три примера критериев:**

1. **Число файлов в диффе (OPSOMN002-289):**
   ```bash
   [ $(git diff task-OPSOMN002-289-attempts-limit main -- \
       app/Domain/Certificate/Actions | grep -c '^+' ) -eq 4 ]
   ```
   Вердикт: файлов в диффе не 4, ещё работаем.

2. **Ноль открытых тредов в запросе (customers-api-web !831):**
   ```bash
   gh api repos/gloria-jeans/customers-api-web/pulls/831/comments \
     --jq '.[] | select(.in_reply_to_id == null) | .id' | wc -l | grep -q '^0$'
   ```
   Вердикт: 9 открытых тредов, ответы не написаны.

3. **Только класс сертификатов в диффе (OPSOMN002-12):**
   ```bash
   git diff task-OPSOMN002-12 main -- app/Domain | \
     grep -E '^[\+-]\+\+\+' | grep -qv 'Certificate' && exit 1 || true
   ```
   Вердикт: правка ушла в чужие классы.

**Счётчик провалов:** Каждая проверка логируется в `.tasks/<ключ>/verify.log` с кодом выхода.
На второй подряд провал — печатается **ВЫНЕСТИ ЧЕЛОВЕКУ**, не предлагается третий заход.

**При `wait` и `release`:** После `worker_done`, если есть `expect.sh`:
- **ПРИНЯТО** (код 0): работник отпущен обычным порядком.
- **НЕ ПРИНЯТО** (код 1): `expect_checked`, работник retained, координатору
  предлагается `say <dispatch> "…"` для доработки.

**Доклад и шпаргалки:** В `worker_done` координатор требует полного **следа** —
commits SHA, номера MR, ID отправленных note'ов, вывод expect.sh. Доклад без следа
не считается сдачей (см. `spec_for` в orchestrate.sh).

## Чего этот скилл не делает

Не заменяет `gj-task-execution`: там ловушки корректности (семантика полей, цепочка
клиент → витрина → сервис, тесты на границе систем, парные запросы и порядок выкатки).
Здесь только организация работы и расход.
