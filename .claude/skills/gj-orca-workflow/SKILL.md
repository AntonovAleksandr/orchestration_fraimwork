# Orca в работе над проектом

Раскладка, а не пересказ. Фазы, потолки контекста и порядок сдачи — в
`gj-task-orchestration`; здесь только то, чего там нет.

## Что из Orca на какой фазе

| Фаза | Скилл Orca | Обязательный скилл GJ |
|---|---|---|
| Заведение, рабочее дерево | `orca-cli` | — |
| Постановка | — (Buddy MCP) | `gj-task-orchestration` |
| Разведка | `orchestration` для веера | то же, §2 |
| Правка | `orca-cli` | `gj-task-execution` + классы дефектов: `gj-retry-safe-writes`, `gj-fail-loud-boundaries`, `gj-value-precision`, `gj-change-hygiene`, `gj-rollout-safety` |
| Самопроверка | — | разделы «Самопроверка» тех же пяти; `orchestrate.sh done` и хук `mr-gate` без них не пускают |
| Ответ на ревью | `orchestration` (работник) | `orchestrate.sh respond`, `gj-review-checklists` |
| Контроль вёрстки | `orca-emulator`, `orca-emulator-android` | `gj-task-orchestration` §4 |
| Ревью | `orchestration` (работник) | `gj-review-delegation` |
| Сдача | `orca-cli` | `gj-task-orchestration`, раздел «Сдача» |
| Падение джобы, деплой | — | `gj-ci-deploy-map` |
| Измерение | — | `gj-session-analytics` |

**`linear-tickets` и `orca-linear` не загружать** — у нас Jira, скилл уведёт на чужой трекер.

## Почему работникам Orca, а не подагентам

Работники Orca — обычные сессии: их видно целиком, с Run, диспетчем и ключом задачи.
Подагенты тоже пишутся в журнал (`<сессия>/subagents/*.jsonl`), но без привязки к задаче,
и `stats.py` их пока не читает. Замер 16–30.09: ревью работником Orca — 8,3 млн, ревью
подагентом внутри координатора — 12,7 млн плюс запуск в раздутом контексте.

Подагент или работник: подагент — когда нужен вывод или короткое действие в пределах
текущей работы (деплой, ветки, исследование, ревью — `gj-subagent-delegation`); работник —
правка в ветке задачи, долгое ожидание, работа, которую продолжат другие сессии.

## Вопросы работников — только через `reply`

`orchestration ask` у работника ждёт ответа **на своё сообщение**. Закрывает его только
`orchestration reply --id <id вопроса>`; `send` и прежний `say` доходят до работника, но его
ask продолжает висеть. Замер 16–30.09: 0 вызовов `reply` против 25 `say`/`send`, ни один
вопрос не получил ответа, работники ждали до 15 часов и повторяли ask по 9 раз.

```bash
scripts/gj/orchestrate.sh questions [dispatch]      # открытые вопросы живых работников
scripts/gj/orchestrate.sh answer <dispatch> "…"     # reply на самый старый открытый
scripts/gj/orchestrate.sh say    <dispatch> "…"     # висит вопрос — отвечает на него, иначе send
scripts/gj/orchestrate.sh wait                      # сначала открытые вопросы, потом новые события
```

- Координатор после `worker-start` держит `wait` в фоне и на каждый вопрос отвечает сразу.
- Вопрос висит 15 минут (`wait` помечает «ВЫНЕСТИ ЧЕЛОВЕКУ», порог `GJ_ASK_ESCALATE_MIN`) —
  выносить человеку, а не ждать второй круг.
- Работник спрашивает с `--timeout-ms 110000` (Bash рвёт команду на 120 с) и продолжает
  через `ask --resume <message_id>`, а не новым вопросом. Это вписано в стартовую реплику.
- Нужно действие человека (веб-пайплайн в GitLab, доступ, решение владельца) — работник
  шлёт `escalation` сразу: координатор кнопку не нажмёт, а ожидание ask ничего не даст.

## Терминалы завершённых работников

Orca по `worker_done` терминал **не закрывает**: решение за координатором — отдать под
новый диспетч, оставить или отпустить. Когда решения нет, терминалы висят неделями
и забивают заслон `GJ_MAX_AGENTS` (30.09: 22 сессии при потолке 4).

- `orchestrate.sh wait` и `fleet.sh watch` отпускают работника сразу по `worker_done`.
  Вывод при этом архивируется (`worker-read` работает), журнал сессии остаётся.
- Оставить живым, чтобы дать ещё работу в пределах часа: `orchestrate.sh retain <dispatch>`
  или `GJ_RETAIN=1`. Позже часа продолжение дороже нового работника: кеш остыл.
- `orchestrate.sh sweep` (он же `release все`) — по всем Run; его же вызывает ежедневный
  `daily-log.sh`. Что Orca закрыть не может, печатается списком:
  - `retained: user_takeover` — в терминал писал человек, закрыть только руками.
    Не писать в терминал работника: отвечать через `answer`.
  - `release_unknown` — после перезапуска Orca запись ссылается на старый терминал.
    Вкладку закрыть руками; сама запись останется, ресурсов она не держит.
- Успех `worker-release` — по полю `state` в ответе, не по `ok`: `release_unknown`
  приходит с `ok: true`.

## Спецификация работнику

Скилл `orchestration` требует пяти вещей: цель, изменение, ограничения, границы владения,
наблюдаемый признак готовности. Шестым добавлять **строку с именами скиллов**: «Загрузи
скиллы X, Y до любых действий» — иначе работник начнёт без них. Замер: скиллы грузятся
в 0,17% ходов, подбор по описанию не работает.

## Контроль вёрстки: дерево против снимка

- **Состав и расположение** — `orca emulator ax --json`: дерево доступности, до 500 узлов,
  координаты 0..1. Несколько тысяч токенов, утверждения точные.
- **Внешний вид** — `scripts/gj/golden.sh check`: сверка с эталоном числами, картинка только
  при расхождении и только вырезкой.

Команды снимка экрана у Orca нет — скрипты её не дублируют. Начинать с дерева: дешевле
и даёт проверяемые утверждения.

## Ресурсы хоста

`orca diagnostics memory --json` — память по каждой сессии с привязкой к дереву. Жёсткого
лимита ОЗУ на процесс в macOS нет (`claude` — нативный бинарь, cgroups отсутствуют).

Память сессии почти не зависит от контекста (170–529 МБ при 60–900 тыс. токенов) — контекст
живёт на сервере. Поэтому **потолок по числу сессий важнее потолка по памяти**:
`GJ_MAX_AGENTS`, `GJ_MIN_FREE_MB`, обход `GJ_FORCE=1`.

Дороже всех сессий вместе — симулятор iOS (4,4 ГБ) и браузер (4,7 ГБ). Гасить симулятор
между замерами.
