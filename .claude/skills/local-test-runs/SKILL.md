# Локальный прогон тестов сервиса

Общий порядок локального прогона и ловушки, на которых теряется время. Конкретные команды
(интерпретатор, менеджер зависимостей, раннер) в примерах условные: подставлять свои.
Проектные особенности окружения (версии, адреса баз, пути) держать в проектном скилле или README сервиса.

## Интерпретатор и зависимости

- Версию рантайма задавать явно (полный путь к бинарю или менеджер версий): системная может
  быть новее поддерживаемой, и часть инструментов на ней падает.
- Лимиты памяти и платформенные проверки при установке зависимостей — явно, если без них
  набор не доходит до конца. Расширения, которых нет локально и которые тестам не нужны,
  обходить флагом установки, а не ставить.
- Приватные пакеты тянутся с корпоративного реестра: нужны доступ к сети и токен в пользовательском конфиге.
- Каталог зависимостей может быть огромным (десятки ГБ, если пакеты ставятся из исходников).
  Учитывать при копировании и работе в рабочем дереве.

## База и окружение

Если тесты используют откат транзакций, а не пересоздание схемы, **база должна существовать
и быть промигрирована заранее**.

```bash
cp .env.example .env
# создать тестовую базу, прогнать миграции
DB_DATABASE=service_test <runner> migrate
```

- Пример окружения часто смотрит на контейнерные хосты: править хост, пользователя и пароль под локальную базу.
- Переменные окружения перебивают файл окружения — базу удобно выбирать на ходу.
- После смены ветки миграции прогонять заново: в ветке могут быть чужие.

## Как сужать прогон

- один файл; один тест по части названия (`--filter`); группа (`--group`).
- **Один путь на прогон.** Некоторые раннеры молча отрабатывают только первый аргумент:
  несколько путей вызывать по очереди и складывать вывод в лог.
- **Полный набор может идти десятки минут последовательно** (в CI быстрее за счёт параллельности).
  Гонять в фоне (`run_in_background`) с выводом в файл, иначе упрётся в таймаут Bash.
  Параллельный режим локально может требовать прав на создание дополнительных баз.

**Полный набор может ходить во внешние сервисы и вставать в сетевом таймауте.** Моки в части
тестов покрывают не все вызовы, запросы уходят наружу по-настоящему, а таймаут в примере
окружения может быть огромным. При нестабильной сети прогон встаёт намертво и выглядит как
«просто долго». Подставлять заведомо мёртвый адрес и короткий таймаут:

```bash
EXTERNAL_API_URL=http://127.0.0.1:9 EXTERNAL_API_TIMEOUT=2 <runner> test --without-tty < /dev/null
```

**Как отличить зависание от «долго» — по приросту тестов, а не по CPU.** Процесс в сетевом
ожидании даёт ненулевые доли процента и выглядит живым. Надёжный признак — счётчик пройденных
тестов в логе за минуту:

```bash
sed 's/\x1b\[[0-9;]*m//g' run.log | grep -acE "✓|⨯"   # замерить, подождать 60 с, замерить снова
```

Не сдвинулся — встал. Последний тест в логе назовёт внешний сервис.

**В фоне запускать без интерактивного вывода и с закрытым stdin** (`--without-tty`, `< /dev/null`
или аналог раннера). Иначе принтер пытается работать интерактивно, дочерний процесс блокируется
на чтении stdin, и прогон висит навсегда при 0% CPU без сокетов. Признаки:

```bash
ps -o pid,etime,%cpu,stat -p <pid>          # 0.0% CPU + STAT S = висит
lsof -a -p <pid> -i -n -P                   # пусто = сети не ждёт
pgrep -P <pid>                              # дочерний процесс раннера; у него fd 0 — пайп без писателя
```

Перед запуском проверить, что база существует и что нет висящих соединений к ней.

## Ловушки рабочих деревьев и клонов

- **Каталог с сегментом пути, начинающимся с точки**, может сломать сборку тестового класса
  (раннер не находит корень). Рабочее дерево делать в пути без точек.
- **Symlink на каталог зависимостей** из основного клона ломает раннеры, которые определяют
  корень проекта через него. Нужен настоящий каталог: копия или отдельная установка.
- **Клон занят соседней сессией.** Перед работой смотреть текущую ветку и `git status --porcelain`:
  в общем дереве ветку не переключать и чужие изменения не сташить — делать `git worktree add`.
- **Shallow-клоны.** `git fetch origin <branch>` может не сдвинуть remote-ref. Явно:
  `git fetch origin +refs/heads/<branch>:refs/remotes/origin/<branch>`.

## Ловушки самих тестов

**Серверная ошибка вместо внятной в компонентном тесте.** Если тесты проверяют ответ против
контракта API, любое пустое значение в обязательном поле превращается в 500. Причина обычно —
забытый или неполный мок. Чтобы увидеть текст, отключить обработчик исключений в тесте.

**Флейки из фабрик.** Фабрики со случайными данными делают неполный мок плавающим: тест падает
не всегда. Правило: в новом тесте задавать явно все поля, от которых зависит проверка, и
прогонять кейс 5–8 раз, если он трогает фабрики.

**Чужие флейки.** Перед тем как считать падение своим, прогнать тот же файл на базовой ревизии.

**Отключённые тесты.** Искать `skip` по задетым ручкам: пропуск часто означает «сломано давно»,
и CI на новый регресс промолчит.

**Сгенерированный клиент под заглушкой.** Тест, где мокается клиент, не видит ошибок разбора
ответа. Правку клиента или подъём его версии проверять на версиях из замка зависимостей, с
HTTP-моком, возвращающим реальное тело ответа, и настоящим вызовом метода чтения.

**Нестабильный в CI тест.** Если тест падает в CI, но проходит локально и при перезапуске джобы,
зафиксировать это (какая ветка, какая джоба, что прошло до падения), не маскировать и не считать
своей правкой. Типичная гипотеза — зависимость от порядка при параллельном прогоне: проверять
запуском с теми же параметрами параллельности.

## Статика

- Форматтер и статанализатор прогонять локально на изменённых файлах: **часто в CI их нет**,
  и зелёный пайплайн статику не доказывает. Узнать по конфигу пайплайна.
- Базовый файл исключений статанализатора устаревает: сравнивать число ошибок с базовой
  ревизией, а не с нулём.

## Порядок проверки правки

1. точечный прогон затронутых файлов;
2. **guard**: вернуть файл к базовой ревизии `git checkout <base> -- <файл>`, прогнать новый тест —
   он обязан упасть, затем вернуть правку. Восстановление вешать на `trap`, иначе
   прерывание прогона (Ctrl+C, kill) оставит репозиторий с откаченной правкой:

   ```bash
   trap 'cp "$F.bak" "$F"' EXIT INT TERM
   cp "$F" "$F.bak"
   git show <base>:"$F" > "$F" && <runner> test --without-tty --filter "…" < /dev/null
   ```

   После любого прерванного прогона — `git status` и проверка, что своя правка на месте.

   **`git checkout <base> -- <файл>` переписывает и индекс.** Восстановление `git checkout -- <файл>`
   после него берёт файл из индекса, то есть возвращает **базовую** версию, а не правку — правка
   молча пропадает, а следующий прогон становится зелёным «на пустом месте». В свежем рабочем
   дереве, где `HEAD` и есть база, `git checkout HEAD -- <файл>` даёт тот же эффект. Надёжно:
   `cp <файл> <файл>.bak` до подмены, `git show <base>:<файл> > <файл>` для подмены и `cp` обратно;
   после guard'а — `grep` по своей правке, а не только `git status`.

   **Не `git stash push`**: если правка уже закоммичена, сташить нечего, команда молча ничего не
   делает, тест проходит — и создаётся ложное чувство доказанности. После guard'а обязательно
   `git status`: откат файла смывает другие незакоммиченные правки в нём;
3. вернуть правку, прогнать группу или полный набор в фоне;
4. форматтер и статанализатор на изменённых файлах;
5. для межсервисных правок — тест на границе систем, см. `task-execution`.
