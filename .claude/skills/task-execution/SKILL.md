# Выполнение задач

Каждое правило — следствие конкретной поломки, которая доехала до ревью или до релизной ветки.

Здесь — **корректность**: что проверить, чтобы правка была верной. Как задача нарезается на
сессии, что уходит подагентам и чем закрывается фаза — в `task-orchestration`.

## 1. Постановка: читать первоисточники, а не цитаты

- Тикет читать через инструмент трекера целиком, комментарии отдельно.
- Все ссылки из тикета (спеки ручек, ADR, ТЗ) читать **самому**, а не доверять цитатам в
  описании. Цитата из спеки может быть верной, а вывод «спека противоречит ADR» — подтвердиться
  только после чтения обеих страниц.
- Большие страницы читать по частям (манифест и фрагменты), а не одним вызовом.
- Зафиксировать в `docs/tasks/<дата>-<тикет>-<тема>.md`: что требуется, чем подтверждено, что открыто.
- Утверждение ТЗ о форме входящих данных («по SKU одна строка», «ключ уникален») сверить
  с данными до того, как строить на нём логику: у загрузчика — промежуточная таблица,
  у сервиса — боевая база. Требование «один документ на позицию» может не выполняться
  для тысяч позиций.

## 2. Перед правкой: понять, чем является поле, которое меняешь

Прежде чем менять семантику существующей колонки или поля запроса — найти **всех** читателей:

```bash
grep -rn "<имя_поля>" <каталог кода> | grep -v Tests
```

Типичная ловушка: одно поле несёт несколько ролей одновременно — намерение пользователя,
признак недоступности (`field == 0` в нескольких местах) и потолок для соседнего значения.
Правка «пусть поле будет только намерением» ломает разметку и суммы. Решение — новая колонка,
а не переопределение смысла.

## 3. Правило про форму запроса: пройти цепочку целиком

**Никогда не опираться на «клиент присылает / не присылает поле X», проверив только клиент и
конечный сервис.** Между ними часто стоит промежуточный слой (шлюз, BFF), и его работа —
нормализовать payload и подставлять дефолты.

Что проверять по порядку:

1. клиент: все места, формирующие запрос (каждый клиент и каждая версия);
2. **промежуточный слой**: валидаторы запросов (геттеры, а не только правила) и мапперы
   в межсервисный запрос;
3. целевой сервис: правила валидации и конвертация в доменные данные.

Ловушка: нулевое количество означает «удалить», и той же ручкой приходит переключение выбора.
Различие «удаление приходит без `is_selected`» верно на клиентах, но промежуточный слой во всех
версиях дописывал признак всегда. Правка, построенная на этом различии, сделала удаление
невозможным.

**Вывод-правило:** различать операции по наличию необязательного поля нельзя. Если контракт не даёт
явного признака — менять контракт либо отдавать решение владельцу контракта.

## 4. Тесты: три обязательных типа

**Тест на границе систем.** Для любой правки, меняющей смысл поля в межсервисном запросе, — тест,
который ассертит **исходящий** payload, а не ответ ручки:

```text
mock(downstreamClient).expect(call).capture(outgoing)
// ... выполнить сценарий через промежуточный слой ...
assert 'is_selected' not in outgoing.items[0]
```

Сотни зелёных тестов могут не показывать дефект, если все они постят в сервис напрямую, минуя
промежуточный слой: они проверяют payload, которого в проде не существует.

**Сценарный тест с действиями посередине.** Не «переключил настройку дважды», а «переключил,
потрогал состояние, вернулся». Дефект «намерение схлопывается при любом касании» не виден, если
круги идут без промежуточных действий пользователя.

**Guard-проверка каждого нового теста.** Снять свою правку и убедиться, что тест падает. Тест,
который проходит и до правки, ничего не доказывает.

Как запускать локально, включая ловушки окружения — `local-test-runs`.

## 5. Слепые зоны

- **Отключённые тесты у задетых ручек** — искать `skip` в файлах тестов. Отключённый тест
  часто означает «ручка сломана давно»: CI на регресс промолчит.
- **Форматтер и статанализатор могут не запускаться в CI.** Зелёный пайплайн тогда не доказывает
  статическую чистоту. Проверить конфиг пайплайна и гонять локально.
- **Типизированные свойства без значения по умолчанию.** Добавляя чтение свойства в общий код,
  проверить всех, кто строит этот объект: непроинициализированное свойство даёт системную ошибку,
  а не исключение домена, и перехват доменного исключения её не поймает.
- **Сравнение строковых ключей.** Стоп-проверку роста ключа при постраничном отборе писать
  сравнением строк по правилу базы данных (collation), а не обычным `<=`: строки, похожие на числа,
  некоторые языки сравнивают как числа.
- **Тесты с заглушкой сгенерированного клиента** не ловят ошибку разбора его ответа — см.
  `local-test-runs`, «Сгенерированный клиент под заглушкой».

## 6. Утверждения об ущербе: измерять, а не выводить из кода

Перед тем как назвать severity или написать «портится X» — проверить данными (запрос к боевой
базе на чтение, поиск в логах, состояние рантайма):

- логи: если обёртки поиска по сообщению не работают на части таргетов — сразу сырой поиск;
- не выводить масштаб из чтения DTO или кода: код допускает больше, чем бывает в данных.

Ловушка: в описании запроса написано «нулевые строки портят состав заказа», основание —
чтение DTO. Замер показал: в хранилище миллионы строк и **ни одной** с нулевым количеством —
приём раскладывает строку на N единичных, при N=0 не создаёт ни одной. Правка оказалась
гигиеной, а не закрытием дефекта, и вопрос перестал требовать эскалации.

**Правило:** завышенная оценка ущерба меняет решения не меньше, чем заниженная.

## 7. Миграции и боевые объёмы

- Перед `UPDATE` по таблице — узнать размер (`count(*)`). На больших таблицах вместо backfill
  делать nullable-колонку с рантайм-фолбэком.
- `nullable` без `default` и `boolean default false` в PostgreSQL — метаданные, без перезаписи.
- Выяснить, идут ли миграции **до** раскатки новой версии или после, и проектировать совместимость
  в обе стороны.
- `down()`, который дропает колонку, — это потеря данных. Продумать шаг отката по данным.
- Новое поле, которое потребитель узнаёт только из событий, у существующих записей не появится:
  в план входит первичная загрузка и её место в порядке выкатки.
- Новая задача по расписанию должна быть зарегистрирована там, откуда её запускает среда
  (конфиг деплоя), а не только в коде приложения: иначе в боевой среде она не выполнится.

## 8. Парные запросы на слияние и релиз

- Если правка задевает несколько репозиториев — сразу планировать порядок выкатки и писать его
  в описания обоих запросов: какой слой выкатывать раньше, иначе позиция, которую один слой
  перестал удалять, теряется в ответе другого.
- Ветку резать от актуальной релизной (`git fetch origin +refs/heads/<release>:refs/remotes/origin/<release>`
  — в shallow-клонах обычный fetch может не сдвинуть remote-ref).
- Не переопределять поведение, зафиксированное существующими тестами других версий API, «за компанию».
  Либо виза владельца, либо сузить правку до версии, где ожидания нет.
- Подъём замка зависимостей на коммит клиента без тега проверять по `git log старый..новый` в
  репозитории клиента и по списку его зависимостей: одна строка ссылки может тянуть мажорную
  линию транзитивной библиотеки.

## 9. Git в мультирепозиторном воркспейсе

Корень воркспейса может быть **тоже git-репозиторием**, и рабочий каталог между командами
сохраняется. Отсюда типичные аварии:

- коммит с сообщением про сервис уехал в корень воркспейса, потому что предыдущая команда сделала
  `cd` туда; `git add -A` собрал сотни несвязанных файлов из чужих сессий;
- `cd` относительным путём молча не срабатывает, если каталог уже сменился, и вся цепочка `&&`
  выполняется не там, где ожидалось.

Правила:

- каждая команда с `git` начинается с **абсолютного** `cd` в нужный репозиторий;
- перед `git add -A` — `pwd` и `git branch --show-current`;
- `git status --porcelain | wc -l` до коммита: если файлов больше, чем правил, — стоп;
- в корне воркспейса git-операций не делать, если он не предназначен для них;
- если ошибка уже случилась: `git reset --mixed HEAD~1` возвращает дерево без потерь, но проверить,
  не ушёл ли push.

## 10. Нейминг

Имя должно совпадать с тем, что делает код. `DeleteItemsAction` не может решать, удалять ли —
он удаляет; условие живёт в отдельной стадии. Метод данных — `cancelDeletion($ids)`, а не
`removeDeleteItems()`. Если название приходится объяснять абзацем — оно неверное.

## 10.1. Комментарии

По правилу комментариев проекта (`.claude/rules/code-comments.md`, если есть): в коде — только
«почему так» и реальная опасность, одной-тремя строками. Ход работы, замеры и историю правки —
в коммит, описание запроса или `docs/tasks/`, не в код. Старые комментарии-истории в изменяемом
участке — удалять попутно, чужие участки ради этого не трогать.

## 11. Ревью

Кросс-репозиторную правку отдавать ревью-агенту, который видит все репозитории
(`review-delegation`). Серьёзные межсервисные ошибки обычно находятся именно так — ни один
прогон тестов их не показывает.

Результат ревью проверять самому: находки бывают верными по сути и неверными по механизму
(например, «хранилище сохраняет нулевые строки» — по коду да, по данным нет).

## 12. Классы дефектов из ревью

Пять скиллов собраны по повторяющимся замечаниям ревьюера. Ни тесты, ни статанализ этих
дефектов не ловят:

- `retry-safe-writes` — несколько записей подряд: повтор, порядок, параллельность, события;
- `fail-loud-boundaries` — валидация, коды ошибок, никакого правдоподобного 200;
- `value-precision` — деньги, даты и пояса, нормализация номеров;
- `change-hygiene` — устройство правки, комментарии, фикстуры по боевым данным, описание = код.

Порядок выкатки, индексы, задания планировщика, ключи и адреса сред — по проектному скиллу
про выкатку, если он есть.

Раздел «Самопроверка» каждого применимого скилла заполняется во вводной перед сдачей,
`orchestrate.sh done` без него не запускается, а хук `mr-gate` не даёт открыть запрос на слияние.

## Чек-лист перед сдачей

- [ ] первоисточники требований прочитаны, расхождения с кодом выписаны;
- [ ] найдены все читатели полей, чью семантику меняю;
- [ ] цепочка клиент → промежуточный слой → сервис пройдена для каждого поля, на которое опирается логика;
- [ ] есть тест на границе систем, если менялся межсервисный payload;
- [ ] есть сценарный тест с действиями пользователя посередине;
- [ ] каждый новый тест проверен снятием правки;
- [ ] проверено, нет ли отключённых тестов у задетых ручек;
- [ ] форматтер и статанализатор прогнаны по всем файлам диффа;
- [ ] в диффе нет комментариев-истории («исправлено», «замер показал», «сначала пробовал»)
      и абзацев длиннее трёх строк — ни новых, ни старых в изменённых участках;
- [ ] утверждения об ущербе подтверждены замером, а не чтением кода;
- [ ] порядок выкатки парных запросов описан в обоих;
- [ ] разбор задачи лежит в `docs/tasks/`;
- [ ] коммиты ушли в те репозитории, в которые правил (проверено `pwd` перед каждым `git`);
- [ ] раздел «Самопроверка» вводной заполнен по скиллам §12.
