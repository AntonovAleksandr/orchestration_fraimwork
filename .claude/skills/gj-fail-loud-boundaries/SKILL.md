# Отказ громко, а не правдоподобный ответ

Самый частый класс замечаний в трёх запросах (14 из 49): код получает неверные или неполные
данные и **отвечает 200 правдоподобным результатом**. Касса показывает клиенту сумму,
деньги уходят в неверное состояние, в логах пусто.

**Правило:** нарушение контракта — это ошибка с различимым кодом. Не исправлять вход молча,
не подставлять значение, не возвращать пустоту.

## 1. Вход: что проверять в правилах

| Что | Как было | Как надо |
|-----|----------|----------|
| Пустой массив | `present` + `array` пропускают `<items/>` → «выкуп ничего» → 200 | `min:1`; пустой состав — это другая операция (отмена) |
| Повторяющийся id | суммируется или схлопывается в `mapWithKeys` | `distinct` и своя ошибка |
| Количество сверх заказа | `min(запрошено, в заказе)` → 200 | отказ с кодом |
| Перечисление | `need_certification` — любой integer, лишнее → `null` | `in:1,2` |
| Идентификатор, идущий в URL | `sprintf` без проверки → `../`, `?`, `#` | `regex:/^\d+$/` + `max`; кодировать при сборке |
| Поле проверено, но не используется | `barcode`, `style_no` | убрать или написать, зачем |
| Связанные поля | `good_id` обязателен, но с `productId` позиции не сверяется | сверять, иначе перепутанная позиция незаметна |
| Размер пакета | нет предела | `max:` + `maxItems` в OpenAPI |
| `nullable` в правилах | в OpenAPI `type: string` без `nullable` | одинаково в обоих: сгенерированный клиент иначе не отправит `null` |

Тест, который закрепляет молчаливое исправление (`testKeptQuantityIsCappedByOrder`),
переписать на отказ.

## 2. Разрешённое — белым списком

Чёрный список статусов («всё, кроме COMPLETED и CANCELLED») разрешает ON_VALIDATION, сборку,
курьерку и **любой будущий статус модели**. Если этап ограничен (C&R и C&C на выдаче) —
белый список статусов плюс проверка типа доставки, своя ошибка на остальное.

## 3. Обязательное поле без значения по умолчанию

`$item['price'] ?? 0`, `$item['id'] ?? ''`, `?? 1` на обязательных полях дают кассе
правдоподобный ответ с нулевой ценой. Отсутствие обязательного поля — исключение.

Запасной путь для идентификатора (`?? $this->makeRevisionId()`) хуже отсутствия: наружу ушёл
`null`, в заказе лежит другой id, и подтверждение отклонит корректный запрос.

Проверка, которая работает «только если касса прислала поле» (`revisionId`), ни от чего
не защищает. Если поле нужно — внести его в контракт и требовать. Если в контракте его пока
нет, это блокер переключения, а не повод сделать проверку необязательной.

## 4. Выход: невозможный результат — ошибка

- Отрицательная сумма возврата → `null` прячет несошедшийся расчёт. Нужна ошибка.
- Пустая раскладка бонусов при `loyaltyPointsBurn > 0` → `[]` → клиент молча платит больше.
  Нужна ошибка либо предупреждение с метрикой.
- Выключенная схема сервера скидок (`validateAndProcessSchema` = `false`) → расчёт по полной
  цене после уже выполненного отката. Если без внешней системы ответ неверен — отказ,
  а не расчёт без неё.

## 5. Коды ошибок различимы по действию

Кассе и загрузчику важно одно: **повторять или нет**. Один HTTP 400 на «уже зафиксировано»,
«заказ завершён», «позиции нет» и «сбой OMS» не даёт этого понять.

- Сбой внешней системы (повторять) и бизнес-запрет (не повторять) — разные коды.
- «Занято параллельным запросом» — свой код, по которому повторяют позже.
- Коды — из `ErrorCodeEnum`, как в соседних версиях (V2 АРМ: 30001, 30005).
- Таблицу ошибок согласовать с аналитиком **до** запроса на слияние. Открытый вопрос
  «какие коды» в описании запроса означает, что запрос не готов.
- Формат ошибки = формат успешного ответа этой ручки (атрибуты против элементов в XML АРМ).
  Копировать презентер ошибки из другой версии и наследовать от успешного ради одного метода
  не нужно.

## 6. Разбор входа не глушит причину

Трейт `UsesXmlRequest` глотает исключение разбора, и клиент получает «Некорректный запрос»
без следа в логе. Любой `catch`, превращающий исключение в ответ, пишет в лог причину и ключ
сущности. Предобработка входа регулярным выражением (`beforeConvert`) — с тестами на
`<item …></item>` и на `>` внутри значения атрибута.

## 7. Отображение состояний — одна функция и по постановке

По customers-api-web !831 (статус эквайринга):

- Одно и то же сочетание данных не должно давать `paid` по одному пути и `unknown` по другому.
  Сведение «попытки оплаты → состояние» — одна функция, все пути через неё.
- Сверить каждое состояние с постановкой (пункт и версия). Исключение, добавленное «по ревью»,
  которое противоречит постановке, — вопрос аналитику до слияния, а не молчаливая правка.
- `match` / `switch` с `default => null` прячет неполноту раскладки. Либо перечислить все случаи
  и бросать на неизвестном, либо держать тест, который перебирает все значения перечисления.
- Состояние ожидания должно заканчиваться: брошенная запись `new` без срока давности оставляет
  клиента на экране ожидания навсегда.
- Предупреждение на каждый опрос клиента засоряет журнал. Писать один раз на сущность или с
  ограничением частоты.

## Самопроверка

Пройти по диффу и записать в вводную:

1. Каждый массив во входе: `min`, `distinct`, `max`.
2. Каждое перечисление: `in:`. Каждый id, идущий в URL или SQL: формат.
3. Нет `??` и `?:` с правдоподобным значением на обязательных полях.
4. Каждый `min()` / `max()` / `(int)` над входом — это осознанное правило, а не исправление
   чужой ошибки.
5. Разрешённые статусы и типы — белым списком.
6. У каждой ошибки ответа понятно, повторять ли её; коды согласованы.
7. Ни один `catch` не превращает исключение в ответ без записи в лог.
8. Каждое состояние ответа выводится одной функцией и сверено с постановкой; `default` не прячет новые значения.
