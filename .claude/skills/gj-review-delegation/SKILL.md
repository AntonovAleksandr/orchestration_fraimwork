# Запуск ревью запроса на слияние

**Этот скилл — пусковой, а не сам порядок ревью.** Порядок задают
`gj-gitlab-mr-review` плюс ровно один платформенный addendum; их не переписывать
и не подменять своей процедурой.

## Коротко

```bash
scripts/gj/orchestrate.sh review <адрес запроса>   # выжимка + запуск работника
```
Разбор ведёт **свежий** работник, не эта сессия. Право записи в GitLab — НЕТ по умолчанию.
Проверка, что делегирование состоялось: в этой сессии не должно появиться ни одного
`Read` по файлам запроса. Появился — значит разбор уехал в родителя, остановиться.

## Зачем делегировать

Ревью последних наборов съедало свыше 200 тыс. токенов в родительской сессии — и оставалось
там до конца её жизни, дорожая каждый следующий ход. Разбор запроса не нужен родительской
сессии ни для чего, кроме вердикта.

Две меры, вместе дающие порядок экономии:

1. **Выжимка вместо диффа** — `mr-brief.py` схлопывает одинаковые правки. `cms!7`:
   587 файлов → 25 различных правок, 4 тыс. токенов вместо сотен тысяч.
2. **Разбор в отдельном работнике Orca** — его контекст умирает вместе с ним, в родительскую
   сессию возвращается только отчёт.

## Шаг 1. Собрать выжимку — до запуска ревьюера

```bash
scripts/gj/mr-brief.py <адрес запроса> --out .tasks/review-<ключ>/brief.md
```

Дифф берётся локальным git в кеш-клоне. **Не брать дифф из интерфейса GitLab**: при большом
наборе он молча отдаёт пустые диффы — на `cms!7` пустыми пришли 566 файлов из 587, и ревью
по ним было бы слепым.

Выжимка — вход ревьюера, а не замена доказательствам: массовые правки он смотрит по
образцу, единичные — открывает полностью сам.

## Шаг 2. Заполнить вводные

```
MR: <адрес или проект + iid>
Ожидаемый результат: <бизнес-цель правки>
Jira/Confluence: <ссылки или НЕТ>
Парные запросы: <ссылки или НЕТ>
Режим: ПЕРВИЧНОЕ | ПОВТОРНОЕ
Прошлые находки: <список или НЕТ>
Особые опасения: <вопросы или НЕТ>
Право записи в GitLab: НЕТ ПО УМОЛЧАНИЮ | ЧЕРНОВИКИ | КОММЕНТАРИИ | АПРУВ
Язык отчёта: РУССКИЙ ПО УМОЛЧАНИЮ
Выжимка: <путь к brief.md>
```

Незаполненное поле — это «НЕТ», а не «на усмотрение ревьюера». Право записи по умолчанию
отсутствует: апрув и комментарии только по явной команде пользователя.

## Шаг 3. Делегировать — через оркестрацию

**По умолчанию ревью ведёт работник Orca, а не подагент этой сессии:**

```bash
scripts/gj/orchestrate.sh review <адрес запроса>   # выжимка + работник со свежим контекстом
scripts/gj/orchestrate.sh wait                      # вопросы и worker_done; answer <dispatch> "…"
```

Почему работник: его расход виден в журналах с привязкой к задаче, ревью стоит дешевле
(в среднем 8,3 млн против 12,7 млн у подагента внутри координатора), и разбор не оседает
в родителе. Вопросы работника закрывать `orchestrate.sh answer`, итог — из его `worker_done`
и отчёта в `.tasks/review-<проект>-<iid>/`.

**Подагент `architect` — только запасной путь**, когда Orca недоступна (`orca` не найдена,
`worker-start` отказал). Тогда — новый подагент со свежим контекстом, ему все вводные
целиком, и в отчёте отметить, что ревью шло без оркестрации.

Когда правка существенно задевает Gloria OTS, 1С/ARM, WMS, ХД, DevOps, платёжные и
фискальные системы, `platform-new`, `platform-next`, владение корпоративными данными или
несколько границ ответственности — вписать в «Особые опасения», что нужен корпоративный
разбор: работник отдаст кросс-системные трассы подагенту `corporate-architect`.

Если ни работника, ни подагента запустить не удалось — доложить, что **делегирование
заблокировано**, и не разбирать запрос в родительской сессии.

**Если ты сам работник ревью** (стартовая реплика «ЦЕЛЬ: ревью запроса …») — ревью ведёшь
ты, по разделу ниже. `orchestrate.sh review` заново не запускать: это породит работника,
который запустит следующего.

## Задание ревьюеру (работнику или подагенту)

Это read-only ревью кода и архитектуры, а не проектирование.

- Прочитать `$WORKSPACE/AGENTS.md` и `$WORKSPACE/CLAUDE.md`.
- Не создавать архитектурные документы, планы, правки кода, ветки, коммиты и фиксы.
- Не требовать разработки через тесты и коммитов «тест раньше кода».
- Применить `gj-gitlab-mr-review` **ровно один раз** и `gj-review-checklists` — чек-листы,
  каталог дефектов и формат комментариев.
- Затем применить **ровно один** платформенный addendum по основному репозиторию запроса:
  `ensi-gitlab-mr-review`, `integration-gitlab-mr-review`, `oms-gitlab-mr-review`,
  `site-gitlab-mr-review` либо `mobile-gitlab-mr-review`.
- Загрузить обязательные и условные под-скиллы, объявленные базовым скиллом и выбранным
  addendum. Тематические скиллы — только по процессам, которых правка действительно касается.
- Соблюдать правила доказательств, проходов ревью, серьёзности, вердикта, повторного ревью,
  записи в GitLab и формата вывода, заданные этими скиллами. Не подменять их своей процедурой.
- Разбирать **фактический запрос на текущей вершине**, а не пересказ автора. Требования из
  Jira и Confluence и синхронизированный локальный код — там, где этого требуют скиллы.
- Кросс-системное влияние проверять **обязательно**, даже если менялся один репозиторий.
  Проверять действующий бизнес-путь и его контракты по ENSI, Integration, OMS, сайту, мобайлу,
  OTS, 1С/ARM, ХД, DevOps, по легаси- и запасным версиям и по будущим контурам платформы.
- Особое внимание: владение данными и источник истины, совместимость API и событий,
  сгенерированные клиенты, идентификаторы и идемпотентность, деньги, чекаут, оплата, доставка,
  BPMN, контекст покупателя, персональные данные, аналитика, уведомления, порядок выкатки,
  смешанные версии, откат, переигрывание, сверка.
- Топологию интеграций **не выводить из документации**. Доказывать действующих вызывающих,
  потребителей, рантайм-конфигурацию и запасные пути доказательствами.
- Пройти дифф по разделам «Самопроверка» скиллов `gj-retry-safe-writes`,
  `gj-fail-loud-boundaries`, `gj-value-precision`, `gj-change-hygiene`, `gj-rollout-safety`. Это классы, которые
  прежние ревью пропускали, а ревьюер (Олейников) нашёл (ИС !918/!927, PIM !237): повтор после
  сбоя на каждом шаге, параллельные запросы, тихий успех, деньги и даты, устройство правки.
- Выполнить состязательный и повторный проходы, которых требует базовый скилл. Каждую находку
  перед включением в отчёт перепроверять на контрдоводы.
- При повторном ревью: проверить все прошлые находки, осмотреть исправления на новые регрессии,
  разобрать каждый добавленный коммит.
- Ограниченные read-only трассировки по платформам отдавать профильным подагентам. Их
  доказательства проверять самому, ответственность за вердикт оставлять за собой.
- Перед итоговым вердиктом и перед любой разрешённой записью в GitLab — перечитать вершину
  запроса заново.
- GitLab держать read-only, пока вводные явно не разрешили конкретное действие записи.
- Комментарии в диффе — по `.claude/rules/code-comments.md`: история задачи, пересказ кода
  или абзац длиннее трёх строк — P3; нет предупреждения о реальной опасности, которую
  вносит правка (необратимость, деньги, прод-данные, порядок), — P2.

Отчёт вернуть в формате, заданном `gj-gitlab-mr-review`.

## Прогноз о потребителе проверяется у потребителя

Самая частая ошибка ревью здесь: посмотреть на изменённую сторону, вообразить потребителя
и предсказать поломку. Предсказание из диффа — гипотеза, а не находка.

**Перед тем как написать «это сломает X», ответить на четыре вопроса — командами, не рассуждением:**

| Вопрос | Чем закрывается |
|---|---|
| Как X вообще собирается? | `composer install` по локу или `update`? образ или сборка из исходников? Правка манифеста не ломает того, кто ставит по локу |
| Кто на самом деле это вызывает? | `grep -rn` по коду потребителя, не по интерфейсу; подагент по платформе |
| Путь вообще активен? | флаг, версия API, запасная ветка — активна ли она в рантайме |
| Что говорят данные? | `data_pg_query`, `data_logs_raw_search` — прод отвечает точнее, чем чтение кода |

### Три случая из практики, все — ложные тревоги

- **Границы зависимостей.** Вывод «подъём `guzzle` до `^7.15.2` сломает десять сервисов»
  сделан по манифесту. Проверка сборки показала: она идёт `composer install` по локу,
  и не ломается ничего до первого `composer update`. Серьёзность была завышена.
- **Тип в клиентах.** Утверждение «`map[string,object]` испортит значения в cms, pim
  и customers» не пережило одной команды: такой тип есть только у BU.
- **Нулевые строки заказа.** «OMS сохраняет позиции с `quantity=0`» — по коду да,
  по данным прода ни одной из 5 385 242 строк. Замер снял вопрос с эскалации.

**Правило:** находка о поведении потребителя без команды, выполненной **у потребителя**,
не блокирует. Она идёт в отчёт как «требует проверки» с указанием, что именно проверить.

### Исправление ревьюера проверяется у потребителя так же

Обратный случай: поломку вносит не автор, а предложенное ревьюером исправление. Замечание
к загрузчику документов предлагало разбирать даты в `Europe/Moscow`. Даты в источнике —
полночь без пояса, PIM хранит `timestamp` без пояса и отдаёт UTC: `2019-05-30` превратился бы
в `2019-05-29T21:00:00Z`, и витрина показала бы срок на день раньше.

**Правило:** раздел «Что закрывает находку» проходит те же четыре вопроса, что и сама находка.
Исправление, не проверенное у потребителя, помечать «требует проверки», а не предлагать как готовое.
[02.10.2026, webapi-connector !30; `docs/tasks/2026-10-02-opsomn002-268-skills-rules.md` п. 7]

## «Не проверено» в отчёте ревью

Ревьюер обязан закрывать свои сомнения сам. Прежде чем написать «на живом контуре не
проверялось», «поведение в проде неизвестно», «потребителей не искал» — пойти и проверить:
прод-данные через `data_pg_query`, логи через `data_logs_raw_search`, потребителей через
`grep -rn` и подагентов, сборку через джобы GitLab.

**Находка без доказательства не блокирует.** Каждая находка несёт команду, которая её
доказывает, и её фактический вывод. Находка уровня P0/P1, опирающаяся только на чтение
кода, понижается до «требует проверки» — в этом воркспейсе уже был случай, когда «OMS
сохраняет нулевые строки» подтверждалось кодом и опровергалось данными прода.

В разделе «остаётся открытым» оставлять только то, что нельзя закрыть без доступа,
которого нет, или без решения владельца. С указанием, чего именно не хватило.

## Критерий готовности ревью — expect.sh

По умолчанию ревью считается готовым, когда ревьюер шлёт `worker_done`. Для контроля добавьте
**--expect**, и ревью не будет считаться готовым, пока файл отчёта не создан и не содержит
вердикта:

```bash
scripts/gj/orchestrate.sh review <адрес> \
  --expect 'grep -q "^## вердикт:" .tasks/review-<ключ>/report.md'
```

Проверить вручную: `scripts/gj/orchestrate.sh verify <ключ> review`.

Если проверка не пройдена, ревьюер остаётся в контексте (retain) и координатор может дослать
ему указание `say <dispatch>`.

## Ответы ревьюеру — через discussions, а не файлы

**Доказательство ответа ревьюеру это ветка обсуждения в GitLab `discussions`, а не файл `ready.md` 
или `notes.md` на рабочем дереве работника.** Ревьюер смотрит на интерфейс GitLab, а не в её репозиторий.
Готовый ответ, написанный в `ready.md`, но не отправленный в `discussions`, выглядит как невыполненный.

**Правило для ревьюера:** ответы пишутся через GitLab API `discussions` с методом `POST /discussions/<id>/notes`.
Если ревьюер строит ответ по шаблону и шаблон предполагает правку кода (что запрещено), он отправляет
ссылку на проблему: координатор либо разрешит ему дописать в discussions код, либо откроет отдельную задачу.

## Что возвращается в родительскую сессию

Только отчёт: вердикт, вершина, находки по серьёзности, что проверено, что осталось открытым.
Дифф, содержимое файлов и трассировки в родительскую сессию не поднимать.

Находки проверять самому — по `gj-task-execution` §11: они бывают верными по сути и неверными
по механизму. Пример из практики: «OMS сохраняет нулевые строки» — по коду да, по данным прода
ни одной такой строки.

## Смежные скиллы

- `gj-subagent-delegation` — общий договор с подагентом: вершина в вводных, «уже
  установлено», канал вопросов подагент ↔ родитель.

- `gj-gitlab-mr-review` — сам порядок ревью (базовый).
- `ensi-` / `integration-` / `oms-` / `site-` / `mobile-gitlab-mr-review` — addendum'ы.
- `gj-task-orchestration` — фаза 5 общего алгоритма задачи, потолки контекста.
- `gj-gitlab-git` — запись в GitLab, токен, создание запросов.
