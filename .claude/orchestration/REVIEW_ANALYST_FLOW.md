# 🔄 Поток взаимодействия: Ревьювер → Аналитик → Разработчик

**Версия:** 1.0  
**Дата:** 2026-10-06  
**Важно:** этот процесс **циклический** с участием аналитика в ревью-цикле

---

## 📋 Процесс (с участием Аналитика)

### Классическая схема (до уточнения)

```
❌ Неправильно (старая схема):
   Reviewer → замечания → Developer → фиксит → конец

❌ Проблема: разработчик может не понять замечание архитектурного смысла
```

### Правильная схема (НОВАЯ)

```
✅ Правильно (новая схема):
   
   Reviewer-1 & Reviewer-2 (параллельно)
        ↓
        замечания (в том числе архитектурные вопросы)
        ↓
   Аналитик (анализирует замечания)
        ├─ Может разрешить сам?
        │   ├─ ДА → адаптирует постановку
        │   │       → передаёт разработчику
        │   │
        │   └─ НЕТ → спрашивает человека
        │       (параллельно:)
        │       ├─ [зависимые вопросы] → человек
        │       └─ [независимые доработки] → сам выполняет
        │
   Developer (получает уточнённые замечания)
        ↓
   фиксит (основано на анализе аналитика)
```

## 🔍 Роль Аналитика в ревью-цикле

### Что делает Аналитик когда получит замечания от Reviewer

#### Шаг 1: Проанализировать замечания

```
Reviewer-1 (бизнес + архитектура):
  [MUST] Это нарушает контракт между сервисами
  [SHOULD] Можно оптимизировать

Reviewer-2 (security + perf + design):
  [SECURITY] SQL injection risk
  [PERF] N+1 query
  [DESIGN] Не соответствует макету

Аналитик анализирует:
  - Замечание от Rev-1 о контракте
    → Нужно ли уточнение от человека?
    → Можно ли разрешить через текущую постановку?
  
  - Замечание Rev-2 о security
    → Базовая security issue или кейс для V2?
```

#### Шаг 2: Разделить вопросы на категории

**Категория A: Аналитик может разрешить сам**

```
Пример: "Это нарушает контракт с OMS"
↓
Аналитик анализирует:
  - Читает текущую постановку
  - Проверяет исходный контракт (из research-code-oms)
  - Может ли это быть решено в рамках текущего scope?
  
Результат:
  ✅ Понял, это действительно нарушение контракта
  → Уточнить постановку разработчику
  → Developer должен исправить по новому контракту
```

**Категория B: Зависит от ответа человека**

```
Пример: "SQL injection risk в этом запросе"
↓
Аналитик анализирует:
  - Это真の problem или false-positive?
  - Базовая security issue → fix now
  - Или edge-case → может быть в V2?
  
Результат:
  ❓ Не уверен → спрашивает человека
  → "Это критичная security issue? Фиксить сейчас или V2?"
  → Ждёт ответа человека
```

**Категория C: Независимые доработки постановки**

```
Пример: Ревьювер нашел, что:
  - Нарушен контракт (вопрос A)
  - N+1 query (вопрос B)
  - Не соответствует макету (вопрос C)

Аналитик:
  [A] Контракт → аналитик может разрешить → готовит уточнение
  [B] N+1 → спрашивает человека ("это блокер для V1?")
  [C] Макет → аналитик может разрешить → готовит уточнение

Параллелизм:
  ✅ [A] + [C] готовятся одновременно
  ✅ [B] идёт в ожидание ответа от человека
  ✅ Developer получает уточнения по [A] и [C] сразу
  ✅ Уточнение по [B] придёт когда человек ответит
```

#### Шаг 3: Параллельное выполнение

```
Аналитик одновременно:

ПОТОК 1: Независимые доработки
  ├─ Анализирует замечания типа А
  ├─ Уточняет постановку
  └─ Готовит обновлённую постановку для Developer

ПОТОК 2: Блокирующие вопросы
  ├─ Выявляет вопросы типа B (зависят от ответа)
  ├─ Спрашивает человека
  ├─ Ждёт ответа
  └─ Когда ответ пришёл → обновляет постановку

Developer (получает обновления ASAP):
  ├─ Получает поток 1 сразу (не ждёт ответа)
  ├─ Начинает фиксить независимые замечания
  └─ Когда готово поток 2 → добавляет доработки
```

#### Шаг 4: Передать разработчику

```
Аналитик отправляет Development:
  
  "Вот уточнённые замечания ревьюеров с моим анализом:
  
  [MUST] Замечание 1 (контракт)
    → Аналитик: нужно изменить вот так
    → Постановка обновлена
    → Developer: исправить по новой постановке
  
  [SHOULD] Замечание 2 (N+1 query)
    → Статус: ждём ответа человека
    → Если ответ = 'фиксить' → обновлю постановку
    → Если ответ = 'V2' → пока игнорируешь
  
  [DESIGN] Замечание 3 (макет)
    → Аналитик: макет требует вот это
    → Постановка обновлена
    → Developer: исправить"
```

## 🎯 Правила для Аналитика в ревью-цикле

### ✅ ДЕЛАТЬ

- ✅ Анализировать каждое замечание ревьювера
- ✅ Разрешать самому если возможно
- ✅ Спрашивать человека если нужно
- ✅ **ПАРАЛЛЕЛЬНО** выполнять независимые задачи
- ✅ Передавать Developer **уточнённые** замечания (не копировать ревью)
- ✅ Помечать вопросы как [BLOCKER] если ждёт ответа человека
- ✅ **ВЫЯВИТЬ и ПОДСВЕТИТЬ блокирующие вопросы для человека**
  - Если решение блокирует разработку → явно написать BLOCKER
  - Если аналитик не может разрешить самому → попросить человека срочно
  - Developer НЕ должен ждать, но и НЕ должен писать зависимый код
- ✅ **Не позволять Developer начинать доработку которая зависит от [BLOCKER] вопроса**
  - Если вопрос блокирует конкретный кусок кода → Developer его пропускает
  - Developer работает на независимых замечаниях

### ❌ НЕ ДЕЛАТЬ

- ❌ Просто копировать замечания ревьювера Developer'у
- ❌ Ждать ответа на [BLOCKER] перед тем как дать Developer независимые доработки
- ❌ Спрашивать человека по замечаниям которые можно разрешить самому
- ❌ Задерживать Developer с ответами на вопросы которые они могут делать параллельно
- ❌ **Позволять Developer начинать на коде который зависит от [BLOCKER] вопроса**
- ❌ **Тихо держать вопрос который блокирует разработку без внимания человека**
- ❌ Помечать вопрос как [NB] если он на самом деле [BLOCKER]

## 🚨 КРИТИЧНО: Блокирующие решения (BLOCKER)

### Что такое BLOCKER в ревью-цикле?

```
[BLOCKER] = замечание ревьювера которое блокирует часть разработки

Примеры BLOCKER:
  ✅ "Контракт с OMS не совпадает" 
     → Developer не может писать OMS взаимодействие без этого

  ✅ "Security issue: это нельзя исправить в V1"
     → Developer не может использовать этот подход

  ✅ "Архитектурный вопрос: где должна быть эта логика?"
     → Developer не может размещать код без этого уточнения

Примеры НЕ BLOCKER:
  ❌ "Нужно добавить индекс на колонку"
     → Developer может написать код, индекс добавит после

  ❌ "Стиль: лучше назвать переменную X"
     → Developer может сделать рефакторинг параллельно
```

### Как Аналитик должен обрабатывать [BLOCKER]

#### Шаг 1: Выявить блокер

```
Ревьювер пишет: "Контракт с OMS не совпадает с постановкой"

Аналитик анализирует:
  → Это действительно блокер?
  → Developer не может продолжать без этого?
  → Разрешить самому или нужен человек?

Вывод:
  [BLOCKER] ДА, это блокирует OMS интеграцию
  → Нужен анализ и уточнение от человека
```

#### Шаг 2: Попробовать разрешить самому

```
Если это можно разрешить через анализ:
  
  ✅ Аналитик смотрит в research-code-oms
  ✅ Находит текущий контракт
  ✅ Понимает разницу между ревью-замечанием и текущей постановкой
  ✅ Обновляет постановку
  → Developer получает уточнение, продолжает работать

Если аналитик не может разрешить:
  
  ❓ Аналитик не уверен в деталях контракта
  ❓ Нужны уточнения от человека (PM / архитектор)
  → Аналитик ЯВНО помечает как [BLOCKER] и спрашивает
```

#### Шаг 3: Спросить человека срочно

```
/blocker-escalate-critical --question "Контракт с OMS..."
```

**Что это делает:**
- Отправляет срочный запрос человеку (не планировать на потом!)
- Отмечает вопрос как CRITICAL (блокирует разработку)
- Developer видит что код зависит от ответа
- Developer НЕ должен писать зависимый код пока ответа нет

#### Шаг 4: Блокировать зависимый код

```
Developer видит [BLOCKER]:
  
  "Контракт с OMS — ждёт уточнения (BLOCKER)"
  
Developer делает:
  ✅ Пишет код который НЕ зависит от OMS контракта
  ✅ Оставляет OMS часть (помечает как TODO: ждём BLOCKER)
  ✅ Не начинает писать OMS код пока аналитик не разрешит
  
Developer НЕ делает:
  ❌ "Ладно, напишу OMS как я понимаю" (может быть неправильно!)
  ❌ "Напишу, потом переделаю" (пустая трата времени)
```

## 🎛️ Команды для работы с BLOCKER в ревью

```bash
# Аналитик спрашивает человека срочно (блокирует разработку)
/blocker-escalate-critical --question "Контракт с OMS должен быть X или Y?"

# Это выведет разработчику:
# "⏸️ [BLOCKER-CRITICAL] Ревьювер нашёл вопрос который блокирует твой код"
# "⏹️ Developer НЕ должен начинать писать OMS код"
# "⏳ Ждём ответа от человека"

# Показать все BLOCKER'ы в текущем цикле ревью
/review-blockers --show-all

# Показать BLOCKER'ы которые блокируют конкретного Developer
/review-blockers --blocking-developer "dev-001"

# Когда человек ответил на BLOCKER
/blocker-resolve-critical "blocker-001" --answer "..."
# → Developer получит уточнение и может начать писать зависимый код
```

## 🎓 Правило GOLDEN: Не позволять зависимый код

**ВАЖНО:**

Это правило **ВЫШЕ** любых других:

```
НИКОГДА Developer не должен писать код который зависит от неразрешённого [BLOCKER]

Даже если:
  ❌ "Я напишу как я понимаю"
  ❌ "Я напишу, потом переделаю"
  ❌ "Это быстро, потом поправим"

Неправильно.

Правильно:
  ✅ Аналитик разрешает [BLOCKER]
  ✅ Developer получает уточнение
  ✅ Developer пишет код по уточнению
  ✅ Результат: первый раз правильно
```

## 🎓 Пример: реальный цикл ревью

### Сценарий: новый OMS статус

**t=0: Reviewer-1 находит замечания**

```
[MUST] Контракт с Integration не совпадает
  → Это нужно обновить в postановке
  
[SHOULD] Нужна миграция БД для нового поля
  → Это в постановке была?
```

**t=1: Reviewer-2 находит замечания**

```
[SECURITY] Новый статус может быть exploited если юзер быстро переходит
  → Или это edge-case для V2?
  
[PERF] Новое поле нужно индексировать
  → В миграции есть индекс?
```

**t=2: Аналитик получает все замечания**

```
Анализирует:
  [A] Контракт с Integration
      → Читает research-code-integration
      → Находит текущий контракт
      → Понимает как нужно изменить
      → Обновляет постановку (✅ может разрешить)
  
  [B] Миграция БД
      → Это в исходной постановке?
      → Смотрит исходные выводы
      → Понимает что есть пробел
      → Уточняет постановку (✅ может разрешить)
  
  [C] Security edge-case
      → Это базовая issue или edge-case?
      → Не уверен → спрашивает человека (❓ ждёт ответа)
  
  [D] Performance индекс
      → Нужен ли индекс для новой колонки?
      → Не уверен → спрашивает человека (❓ ждёт ответа)
```

**t=3: Параллелизм**

```
ПОТОК 1: Независимые доработки
  ├─ Аналитик готовит уточнения по [A] и [B]
  ├─ Отправляет Developer: "Вот обновленная постановка"
  └─ Developer начинает фиксить по новой постановке

ПОТОК 2: Блокирующие вопросы
  ├─ Аналитик спрашивает человека про [C] и [D]
  └─ Ждёт ответа
```

**t=10: Developer запушил фиксы по [A] и [B]**

```
Исправил:
  ✅ Контракт с Integration (по уточнённой постановке)
  ✅ Добавил миграцию БД (по уточнённой постановке)
  ⏳ Security edge-case (ждёт уточнения от аналитика)
  ⏳ Индекс на колонку (ждёт уточнения от аналитика)
```

**t=15: Человек ответил**

```
"Security: это edge-case, может быть в V2"
"Index: нужен индекс для WHERE clause"

Аналитик обновляет постановку:
  [C] V2 → Developer может пропустить
  [D] индекс нужен → обновляет миграцию
```

**t=16: Developer получил уточнения**
