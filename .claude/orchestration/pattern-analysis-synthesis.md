## 📋 Описание

**Явный паттерн синтеза** - как аналитик превращает 5 выводов исследователей в постановку.

Аналитик **ДОЛЖЕН ВСЕГДА** следовать этим 5 шагам. Нет импровизации.

---

## 🎯 5 обязательных шагов

### 1️⃣ КОНФЛИКТЫ (Detect & Resolve Conflicts)

**Что делать:**
- Для каждого вывода исследователя: есть ли противоречие?
- Conf говорит X, Code говорит Y → это конфликт?
- Пытаться разрешить через анализ (читать источники)
- Если не можешь разрешить → отметить [CONFLICT-BLOCKER]

**Процесс:**
```
Conf-researcher: "Контракт должен быть в OMS"
Code-researcher: "Контракт может быть в Integration"

Аналитик анализирует:
  ✅ Читает оба вывода
  ✅ Проверяет исходные источники
  ✅ Понимает: это не конфликт, просто разные аспекты
  ✅ Разрешил → нет конфликта

vs.

Conf-researcher: "API версия V1"
Code-researcher: "API версия V2"

Аналитик анализирует:
  ✅ Читает оба вывода
  ✅ Проверяет исходные источники
  ❌ Не может понять какая версия в проде
  ❌ Отметить [CONFLICT-BLOCKER] → спросить человека
```

---

### 2️⃣ ПРОБЕЛЫ (Identify Gaps)

**Что проверять:**

1. **По сервисам:**
   - ENSI? → есть research-code-ensi? ✅
   - OMS? → есть research-code-oms? ✅
   - Integration? → есть research-code-integration? ✅
   - Если нет → [BLOCKER] пробел в информации

2. **По аспектам:**
   - ТЗ требование? → есть Conf-researcher ✅
   - Текущий код? → есть Code-researchers ✅
   - Поведение на стенде? → есть Logs-detective ✅
   - API behavior? → есть Black-box-researcher ✅
   - Если нет → [BLOCKER] пробел в информации

3. **По деталям:**
   - Есть ли информация о версионировании?
   - Есть ли информация о backward-compatibility?
   - Есть ли информация о edge-cases?
   - Если нет → [NB] пробел (не критичен, но важен)

**Как отметить:**
```
Пробелы обнаружены:
✅ Покрыто: основное требование, текущая реализация, поведение
❓ Пробелы: версионирование API, edge-cases
[NB] Нужно уточнить: как обрабатываем быстрые переходы?
```

---

### 3️⃣ ВАЛИДАЦИЯ (Validate Against CLAUDE.md)

**Что проверять:**

1. **Соответствие CLAUDE.md:**
   - Правило: "все изменения должны быть в platform/sервис/"
   - ✅ Требование соответствует?
   
2. **Соответствие service-index:**
   - Правило: "каждый сервис имеет владельца"
   - ✅ Знаем кто владелец?

3. **Соответствие типу задачи:**
   - Это ENSI feature? → следовать ensi-* правилам
   - Это OMS feature? → следовать oms-* правилам
   - ✅ Понимаем тип задачи?

**Процесс:**
```
Требование: "добавить новый статус заказа"

Валидация:
✅ CLAUDE.md: изменения в platform/starfish24/ ✅
✅ service-index: OMS owns OrderStatus ✅
✅ Тип: это OMS feature ✅
✅ Все соответствует правилам ✅
```

### 4️⃣ СТРУКТУРИРОВАНИЕ (Structure Requirement)

**Писать постановку в ТОЧНО ТАКОМ формате:**

```markdown
## Постановка: [требование]

### ЧТО (What)
Требование из ТЗ + выводы от Conf-researcher

Пример:
"Добавить новый статус заказа SHIPPED_TO_CUSTOMER
 который должен быть видимый пользователю"

### ГДЕ (Where)
Какие сервисы трогаем?

Пример:
"- OMS: добавить в OrderStatus enum, создать handler
 - Integration: обновить маршрут delivery-update
 - Site: добавить отображение нового статуса
 - Mobile: обновить DTO"

### КАК (How to verify)
Как проверяем что сделали правильно?

Пример:
"- Unit: OrderStatus enum содержит новый статус
 - Integration: маршрут правильно распределяет статус
 - E2E: на стенде заказ переходит в новый статус
 - UI: статус видимый в списке заказов"

### РИСКИ (Risks & Limitations)
Что может пойти не так? Какие ограничения?

Пример:
"- [BLOCKER] Лаг между OMS и Integration 3 сек (known issue)
 - [NB] Site пока не поддерживает новый статус (V2)
 - [NB] Нужно перегенерировать BFF клиенты"
```

```markdown
[ограничения и [BLOCKER] вопросы]

[ссылки на исследования]

📝 **ВАЖНО для Developer'а:**
- Если есть [BLOCKER]: подождать уточнения от Координатора

- Все остальное - обязательно сделать
```

## ✨ Важные правила

### Правило 1: ВСЕГДА 5 шагов
- Нет сокращений
- Даже если кажется что всё ясно - пройти все 5 шагов

### Правило 2: ЯВНЫЕ [BLOCKER] и [NB]
- Если есть сомнение → отметить [BLOCKER]
- Если не критично → отметить [NB]
- Developer должен ЯВНО знать что блокирует, что нет

### Правило 3: ЦИТАТЫ из исследований
- Не писать "я понял что..."
- Писать "исследователь сказал: '...'"
- Со ссылками на источники

### Правило 4: СТРУКТУРА как шаблон
- ЧТО, ГДЕ, КАК, РИСКИ
- Всегда в этом порядке
- Developer должен легко понять структуру

### Правило 5: ПРОВЕРКА перед выводом
- Перед тем как отправить Developer'у: перечитать
- Понятно ли ЧТО делать?
- Ясно ли ГДЕ делать?
- Знаешь ли как КАК проверять?
- Отмечены ли все РИСКИ?

```markdown
# Постановка: новый статус заказа SHIPPED_TO_CUSTOMER

## ЧТО
Добавить новый статус SHIPPED_TO_CUSTOMER для заказов, 
видимый пользователю в списке заказов

Источник: Confluence ТЗ OPSOMN002-XXX

## ГДЕ
- OMS:
  - OrderStatus enum: добавить SHIPPED_TO_CUSTOMER
  - deliveryUpdateHandler: добавить обработку нового статуса
  
- Integration:
  - delivery-update route: маршрутизировать новый статус
  - отправить в Site/Mobile через BFF
  
- Site (gj-ng-front):
  - order-list component: отображать новый статус
  - status-badge component: добавить стиль для нового статуса
  
- Mobile:
  - OrderDTO: обновить enum значения
  - order-list screen: отображать новый статус

## КАК
- Unit test: OrderStatus.SHIPPED_TO_CUSTOMER exists ✅
- Integration test: delivery-update route handles new status ✅
- E2E test: на стенде заказ переходит в новый статус ✅
- Manual: UI отображает статус красиво

## РИСКИ
[BLOCKER] Лаг между OMS и Integration: 3+ сек (known issue, не блокирует)
[NB] Site может не сразу обновить статус (кэш?)
[NB] Нужно перегенерировать clients (pim-client, cms-client)

## Источники
- Conf: https://confluence/.../OPSOMN002-XXX
- Code-OMS: platform/starfish24/core/Order/OrderStatus.java:42
- Code-Integration: platform/integration/www/routes/delivery-update.php
- Logs: последние обновления статусов на стенде показывают лаг 3 сек
```
