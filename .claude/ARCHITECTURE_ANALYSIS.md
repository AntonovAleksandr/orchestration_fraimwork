### Пробелы и возможности улучшения 🔴

```
🔴 Поведение агентов не полностью паттернизировано
   → Каждый раз чуть по-другому выполняют задачи
   → Нет явных "happy path" и "edge cases"

🔴 Frontend-специфика не выделена
   → develop-site.md слишком общий
   → Нет разделения на UI/routing/state/SSR
   → Нет специализации для дизайна/a11y

🔴 Координатор тратит время на повторяющиеся действия
   → Каждая задача = одинаковые вопросы
   → Можно автоматизировать интерпретацию статуса
   → Можно создать "рецепты" по типам задач

🔴 Нет явных паттернов "сценарий работает хорошо → сохранить"
   → Что если задача прошла за 80 мин вместо 100?
   → Можно ли скопировать эту скорость на следующую?

🔴 Аналитик работает в "слепую" (не видит полную картину)
   → Не знает какие типы замечаний дают ревьюеры
   → Не может предугадать вопросы
   → Каждый цикл как первый
```

## 🎯 Анализ: паттерны поведения агентов

### Паттерн 1: Исследователь (Research phase)

**Текущее поведение:**
```
Research-agent получает задачу
  ├─ Читает источник (Confluence/code/logs/API)
  ├─ Находит факты
  ├─ Выводит отчёт
  └─ Готово
```

**Повторяющиеся действия:**
1. **Поиск по ключевым словам** (всегда)
   - Ищет: "OMS", "Integration", "контракт", "API"
   
2. **Валидация источника** (всегда)
   - Проверяет: "актуальна ли информация?"
   
3. **Выявление конфликтов** (часто)
   - Ищет: противоречия в информации

4. **Проверка полноты** (всегда)
   - Спрашивает: "хватает ли информации?"

**Паттерн для скилла:**
```markdown
# research-standard-flow

**Шаги исследователя (ВСЕГДА следовать):**

1. ПОИСК
   - Идентифицировать ключевые слова (сущности, сервисы)
   - Поиск в источнике по ключевым словам
   - Выписать релевантные куски

2. ВАЛИДАЦИЯ
   - Дата источника (актуально ли?)
   - Версия/branch (правильная ли?)
   - Авторство (кто писал, доверяем ли?)

3. КОНФЛИКТЫ
   - Есть ли противоречия?
   - Источник-A говорит X, источник-B говорит Y?

4. ПОЛНОТА
   - Хватает ли информации?
   - Есть ли пробелы?
   - Нужна ли доинформация?

5. ВЫВОД
   - Структурированный отчёт
   - С ссылками на источники
   - С [BLOCKER] и [NB] вопросами
```

### Паттерн 2: Аналитик (Analysis phase)

**Текущее поведение:**
```
Аналитик получает 5 выводов
  ├─ Читает их
  ├─ Выявляет конфликты
  ├─ Спрашивает человека если нужно
  ├─ Пишет постановку
  └─ Готово
```

**Повторяющиеся действия:**
1. **Поиск конфликтов** (ВСЕГДА)
   - Conf говорит X, Black-box говорит Y?
   
2. **Заполнение пробелов** (ВСЕГДА)
   - Есть ли пробелы в информации?
   - Можно ли разрешить самому?

3. **Валидация против CLAUDE.md** (ВСЕГДА)
   - Соответствует ли CLAUDE.md?
   - Соответствует ли service-index?

4. **Структурирование постановки** (ВСЕГДА)
   - ЧТО (требование)
   - ГДЕ (сервисы)
   - КАК (верификация)
   - РИСКИ (ограничения)

**Паттерн для скилла:**
```markdown
# analyze-standard-flow

**Шаги аналитика (ВСЕГДА следовать):**

1. КОНФЛИКТЫ
   - Читать каждый вывод исследователя
   - Для каждого вывода: есть ли противоречие с другими?
   - Отметить [CONFLICT] если есть

2. ПРОБЕЛЫ
   - Есть ли информация по каждому сервису?
   - Каждый сервис → есть ли исследование?
   - Если нет → [BLOCKER] вопрос

3. ВАЛИДАЦИЯ
   - Соответствует ли CLAUDE.md?
   - Соответствует ли service-index?
   - Соответствует ли типу задачи?

4. СТРУКТУРИРОВАНИЕ
   - Раздел ЧТО (из ТЗ + выводы)
   - Раздел ГДЕ (сервисы + компоненты)
   - Раздел КАК (tests + verification)
   - Раздел РИСКИ (limitations + [BLOCKER]'s)

5. ВЫВОД
   - Постановка структурирована
   - Готова для разработчика
```

### Паттерн 3: Разработчик (Development phase)

**Текущее поведение:**
```
Developer получает постановку
  ├─ Читает её
  ├─ Пишет код
  ├─ Пишет тесты
  ├─ Коммитит
  └─ Запушил MR
```

**Повторяющиеся действия:**
1. **Понимание постановки** (ВСЕГДА)
   - Прочитать ЧТО, ГДЕ, КАК
   
2. **Выбор эпика кода** (ВСЕГДА)
   - С какого файла начать?
   - Какие зависимости?

3. **Синтаксис/style** (ВСЕГДА)
   - Применить shared-code-style
   - shared-security-checklist

4. **Тесты** (ВСЕГДА)
   - Unit tests для каждой функции
   - Integration tests если нужно

5. **Коммит/MR** (ВСЕГДА)
   - Правильная ветка
   - Co-Authored-By
   - Описание MR

**Паттерн для скилла:**
```markdown
# develop-standard-flow

**Шаги разработчика (ВСЕГДА следовать):**

1. ПОНИМАНИЕ
   - Прочитать FULL постановку
   - Понять требование (ЧТО)
   - Понять сервисы (ГДЕ)
   - Понять верификацию (КАК)

2. ПЛАН
   - Какие файлы трогаем?
   - Какой порядок имплементации?
   - Какие зависимости?

3. КОД
   - Писать по shared-code-style
   - Комментарии только "почему"
   - Переменные ясные

4. SECURITY
   - Чек shared-security-checklist
   - Нет injection?
   - Нет secrets in code?

5. ТЕСТЫ
   - Unit tests на каждую функцию
   - Integration tests если API
   - Edge-cases покрыты?

6. КОММИТ
   - Правильная ветка (feature/*, fix/*)
   - Сообщение ясное
   - Co-Authored-By добавлен

7. MR
   - Правильный target branch
   - Описание (ссылка на OPSOMN)
   - Все тесты зелёные
```

## 🎨 Специализация Frontend (новое разделение)

### Текущая проблема

```
develop-site.md охватывает всё:
  - Angular компоненты
  - NgRx state
  - NestJS SSR
  - Routing
  - i18n
  - Storybook
  - Jest tests
  - Cypress e2e
  - CSS/styling
  - a11y
  - Performance (lighthouse)
```

**Это слишком широко!**

### Решение: разделить Frontend на специализации

```
[DEVELOPMENT] → добавить специализированные скилы:

develop-site-ui.md
  └─ UI компоненты, styling, a11y, responsive
  
develop-site-state.md
  └─ NgRx state, actions, selectors, effects
  
develop-site-routing.md
  └─ Route guards, lazy loading, navigation
  
develop-site-ssr.md
  └─ NestJS SSR server, hydration, CSR/SSR sync
  
develop-site-i18n.md
  └─ Transloco, локали (ru/en/kz), plurals
  
develop-site-testing.md
  └─ Jest, Cypress, Storybook, lighthouse
```

### Почему это улучшение?

| До | После |
|----|----|
| Один develop-site.md (20K tokens) | Пять специализированных скилов (4K каждый) |
| Developer тратит время на поиск | Developer читает ровно то что нужно |
| Context raздут | Context узкий |
| Сложнее найти pattern | Каждый скилл = явный pattern |

## 🔄 Улучшение 3: Автоматизация координатора

### Паттерн: "Координатор как интерпретатор"

**Текущее поведение координатора:**
```
Coord видит статус:
  "Phase 1 Research: 70% готово"
  
Coord думает:
  "Это нормально? Быстро? Медленно? Нужна помощь?"
  
Действие: спрашивает человека
```

**Улучшенное поведение:**
```
Coord видит статус:
  "Phase 1 Research: 70% готово, Conf 8/25, Code-OMS 12/25, Logs 15/25..."
  
Coord интерпретирует:
  ✅ Conf быстро (8 мин, ожидаемо 8-10)
  ✅ Code-OMS нормально (12 мин, ожидаемо 10-15)
  ⚠️ Logs медленнее (15 мин, ожидаемо 10-15) — но в норме
  
Действие: всё OK, не вмешиваться
```

**Как это работает:**

```
coord-pattern-interpretation.md
───────────────────────────────

1. НОРМАЛЬНЫЕ ДИАПАЗОНЫ (на основе истории)
   Conf-researcher: 8-10 мин (норма), >15 мин (медленно), <5 мин (ошибка)
   Code-researcher: 10-15 мин (норма)
   Logs-detective: 10-15 мин (норма), >20 мин (медленно)
   Black-box: 8-12 мин (норма)

2. ПАТТЕРНЫ "НУЖНА ПОМОЩЬ"
   ✅ Если исследователь идёт в норме → не трогать
   ⚠️  Если медленнее на 30% от нормы → проверить
   🚨 Если не движется 5+ минут → intervene

3. ПАТТЕРНЫ "БЛОКЕР НЕРАЗРЕШИМ"
   ✅ Если [BLOCKER] разрешится в течение 5 мин → подождать
   ⚠️  Если [BLOCKER] ждёт >10 мин → напомнить человеку
   🚨 Если [BLOCKER] ждёт >20 мин → escalate
```

## 🔍 Анализ ваших действий (Координатор)

### Повторяющиеся действия координатора

На основе вашего стиля работы видны циклические действия:

1. **Запуск исследования**
   ```
   Вы: /task-research-and-analyze "TICKET"
   → Система: 5 исследователей запущены
   → Вы (через 25 мин): /task-status
   ```
   
   **Циклично:** каждая новая задача = одинаковые команды
   
   **Паттерн для автоматизации:** `coord-task-launcher.md`

2. **Мониторинг прогресса**
   ```
   Вы (каждые 5-10 мин): /task-status
   Вы смотрите: есть ли [BLOCKER]? Есть ли проблемы?
   Вы решаете: вмешиваться или подождать?
   ```
   
   **Циклично:** повторяется через каждые 5-10 мин
   
   **Паттерн для автоматизации:** `coord-monitoring-pattern.md`

3. **Разрешение вопросов**
   ```
   Вы видите [BLOCKER]: "Контракт с OMS не совпадает"
   Вы: спрашиваете человека
   Вы: дождались ответа
   Вы: /blocker-resolve "id" --answer "..."
   ```
   
   **Циклично:** всегда одинаковый процесс
   
   **Паттерн для автоматизации:** `coord-blocker-resolution.md`

4. **Сбор метрик (в конце)**
   ```
   Вы: /task-metrics
   Вы видите: время, токены, замечания
   Вы: анализируете что прошло хорошо/плохо
   Вы: предлагаете улучшения
   ```
   
   **Циклично:** одинаковый анализ каждый раз
   
   **Паттерн для автоматизации:** `coord-metrics-interpretation.md`

### Вывод: 4 паттерна для новых скилов

```
coord-task-launcher.md
  └─ Как запустить задачу (параметры, флаги, опции)

coord-monitoring-pattern.md
  └─ Как мониторить задачу (интервалы, красные флаги)

coord-blocker-resolution.md
  └─ Как разрешать вопросы (сценарии, время ожидания)

coord-metrics-interpretation.md
  └─ Как интерпретировать метрики (хорошо/плохо, рекомендации)
```
