# Code Review Comments Format

Обязательный формат для комментариев кода при ревью (используется `review_post.py` и агентами).

---

## Два формата комментариев

### 1. **Inline Comments** (в коде на конкретной строке)

**Используется когда:** проблема локализована на конкретных 1–5 строках кода.

**Обязательная структура:**

```
[ТИП] Заголовок, 1 строка

**Проблема:** что здесь неправильно / опасно / не соответствует контракту
**Почему:** объяснение или ссылка на контракт/задачу/стандарт
**Решение:** конкретное действие или пример кода
```

**Типы комментариев (и их значение):**

| Тип | Блокирует | Описание | Соответствие |
|-----|-----------|---------|--------------|
| `[MUST]` | ✅ Да | Нарушение AC, контракта, безопасности, архитектуры | [блокер] Олейникова |
| `[SHOULD]` | ❌ Нет | Рекомендация (оптимизация, читаемость, паттерн) | [важно] Олейникова |
| `[NIT]` | ❌ Нет | Опциональное улучшение (стиль, имя переменной) | [замечание]/[мелочь] |
| `[SECURITY]` | ✅ Да | Уязвимость (всегда [MUST] даже если написано [SECURITY]) | [блокер] |
| `[PERF]` | ❌ Нет (или ✅ если AC) | Проблема производительности | [замечание] |
| `[TEST]` | Зависит от AC | Отсутствие или неправильность тестов | [замечание]/[важно] |
| `[ANALYST_QUESTION]` | ❌ Нет | Бизнес-развилка не описана в ТЗ, поведение не определено | [вопрос аналитику] |

**Пример inline-комментария:**

```
[MUST] SQL injection на линии 42

**Проблема:** прямая конкатенация $id в SQL-строку: SELECT * FROM orders WHERE id=$id

**Почему:** пользователь может передать '; DROP TABLE--' и удалить данные

**Решение:** использовать параметризованный запрос
→ $stmt = $pdo->prepare("SELECT * FROM orders WHERE id=?");
→ $stmt->execute([$id]);
```

---

### 2. **Separate Notes** (общие замечания, не привязанные к строкам)

**Используется когда:**
- Проблема затрагивает несколько строк/функций/файлов
- Архитектурное замечание
- Полнота изменений
- Отсутствие чего-либо (тестов, документации, миграций)

**Обязательная структура:**

```
## [ТИП] Заголовок (1 строка)

**Затрагивает:** файлы / функции / компоненты

**Проблема:** 
- пункт 1
- пункт 2

**Почему:**
- ссылка на контракт / AC / стандарт
- объяснение риска или упущения

**Решение:**
1. действие 1
2. действие 2
```

**Пример separate-note:**

```
## [MUST] Отсутствуют интеграционные тесты чекаута

**Затрагивает:** platform/integration/www/, platform/site/

**Проблема:**
- Добавлено 3 новых API endpoint для экспресс-доставки
- Нет e2e тестов, проверяющих полный flow сайта → Integration → OMS
- Запрос от OMS на статус может вернуть 500 при неинициализированном поле

**Почему:**
- AC (OPSOMN002-250) требует "проверить интеграцию сайта с экспресс-доставкой"
- Ручные тесты не масштабируются и не ловят регрессию

**Решение:**
1. Добавить Cypress e2e тест: `apps/site-{locale}-e2e/src/express-delivery.cy.ts`
2. Мокировать Integration responses (или использовать стенд)
3. Проверить: cart → checkout → success → API call to OMS
4. Ожидаемое покрытие: >80% новых строк
```

## Валидация формата

### Обязательные элементы каждого комментария

- ✅ **Тип в квадратных скобках:** `[MUST]`, `[SHOULD]`, `[NIT]`, `[SECURITY]`, `[PERF]`, `[TEST]`
- ✅ **Заголовок:** одна строка (макс 100 символов)
- ✅ **Проблема:** что именно неправильно (не "код плохой", а конкретно)
- ✅ **Почему:** объяснение или ссылка на контракт/задачу/памятку
- ✅ **Решение:** конкретное действие (примеры кода для inline, пункты для note)

### Что НЕ должно быть в комментарии

❌ Процесс / история ("на код-ревью заметили", "перепроверь в след. раз")  
❌ Благодарности и эмодзи  
❌ Закомментированный код  
❌ Очень длинные тексты (>3 параграфа → перенести в docs/)  
❌ "Готча" ("это же очевидно", "любой знает")  
❌ Ссылки без контекста (ссылка должна быть в "Почему")  

### Чек перед отправкой комментария

```bash
# Валидация (можно запустить вручную или в CI)
review_validate.sh review_comment.md

# Проверяет:
# 1. Есть ли [ТИП]?
# 2. Есть ли **Проблема:**?
# 3. Есть ли **Почему:** или ссылка на внешний источник?
# 4. Есть ли **Решение:**?
# 5. Нет ли "TODO", "FIXME", "later", "потом"?
# 6. Нет ли благодарностей / эмодзи?
```

## Интеграция с review_post.py

### Как review_post.py использует формат

```python
# Pseudocode
comment = ReviewComment.parse(markdown)

# Валидация
assert comment.type in ['MUST', 'SHOULD', 'NIT', 'SECURITY', 'PERF', 'TEST']
assert comment.title is not None and len(comment.title) <= 100
assert '**Проблема:**' in comment.body
assert '**Почему:**' in comment.body or has_external_link(comment.body)
assert '**Решение:**' in comment.body

# Отправка в GitLab
if comment.type == 'MUST':
    mr.request_changes()  # автоматический запрос изменений

mr.add_comment(
    body=comment.body,
    position=comment.line or None,  # inline или общий
    category=comment.type  # для фильтрации в UI
)
```

### Обработка ошибок

Если комментарий не соответствует формату:

```
❌ Rejected: Missing required section **Решение:**
   File: apps/catalog/pim/src/Query.php
   Line: 42
   Provided: [MUST] SQL injection found
   Expected: [MUST] SQL injection found
            **Проблема:** ...
            **Почему:** ...
            **Решение:** ...
```

## Когда использовать какой формат

| Ситуация | Формат | Пример |
|----------|--------|--------|
| Одна ошибка на одной строке | Inline | `[MUST] Missing null check on line 15` |
| Ошибка, но в функции много строк | Inline | `[MUST] Invalid index bounds` на строке старта цикла |
| N+1 queries (видно из контекста) | Inline на одной строке + Separate note | Inline на цикле, note про всю функцию |
| Отсутствующий тест для нового feature | Separate note | Целый note про тесты |
| Архитектура / контракт нарушен | Separate note | Note про интеграцию между 3+ сервисами |
| Typo в переменной | Inline (NIT) | Если не помешает пониманию, можно и не писать |

## Примеры (полные)

### ✅ Хороший inline-comment

```
[MUST] Потеря скидки при повторном вызове checkoutCommit

**Проблема:** 
На строке 156 функция applyDiscount вызывается без проверки, уже ли она была применена. При retries (сетевая ошибка) скидка применяется дважды.

**Почему:** 
Контракт OPSOMN002-11315: "Откат бонусов один раз на заказ: повторный вызов вернёт их дважды". Это приводит к потере денег пользователя.

**Решение:**
Добавить флаг в заказ:
→ if (order.discount_applied) return OK_ALREADY_APPLIED;
→ order.discount_applied = true;
→ apply_bonus(...);
```

### ✅ Хороший separate-note

```
## [SHOULD] Оптимизировать запросы в listProducts

**Затрагивает:** platform/integration/www/app/Services/ProductService.php

**Проблема:**
Функция листит товары в цикле, каждый раз запрашивая цены и скидки:
```
for item in items:
    item.price = catalog.getPrice(item.id)
    item.discount = offers.getDiscount(item.id)
```
При 100 товарах = 200 запросов (N+1).

**Почему:**
Запросы к catalog и offers медленные (~50ms каждый). Это 10 секунд на один запрос listProducts.

**Решение:**
1. Использовать batch-запрос: catalog.getPrices([id1, id2, ...])
2. Кешировать в Redis на 5 минут
3. Ожидаемый выигрыш: 200 запросов → 2 запроса, время: 10s → 200ms
```

### ❌ Плохой inline-comment (не соответствует формату)

```
[MUST] Плохо

Здесь опасно. Нужно проверить пользователя перед запросом.
```

**Почему плохо:**
- Нет **Почему:**
- Нет **Решения**
- Неясно, ЧТО конкретно плохо

### ❌ Плохой separate-note (не соответствует формату)

```
## Нужны тесты

Добавьте тесты для checkout.
```

**Почему плохо:**
- Нет типа `[TEST]`
- Нет раздела **Проблема:**
- Нет раздела **Почему:**
- Нет раздела **Решение:**

## Чек в code-review скиллах

Каждый код-ревью-скилл (ensi-gitlab-mr-review, site-gitlab-mr-review и т.д.) **ОБЯЗАН**:

1. **Перед отправкой комментария** проверить формат по этому файлу
2. **Отклонить** комментарий, если:
   - Нет типа `[ТИП]`
   - Нет одного из обязательных разделов (**Проблема**, **Почему**, **Решение**)
   - Текст содержит "TODO", "потом", "позже"
3. **Переформатировать** и отправить
4. **Логировать** каждое отправленное замечание с указанием файла, строки, типа

### Пример интеграции в skill

```yaml
# .claude/skills/ensi-gitlab-mr-review/SKILL.md
...
## Формат комментариев (обязательно!)

Каждый комментарий ДОЛЖЕН следовать `.claude/rules/code-review-comments-format.md`:
- [MUST] / [SHOULD] / [NIT] / [SECURITY] / [PERF] / [TEST]
- **Проблема:** что неправильно
- **Почему:** объяснение или ссылка
- **Решение:** что делать

Если комментарий не соответствует — переформатировать перед отправкой.
```
