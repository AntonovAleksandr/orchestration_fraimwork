## 🚀 Как это работает?

### Типовая задача (100 мин)

```
t=0      Координатор: /task-research-and-analyze "TICKET"
         ↓
t=0-25   Phase 1: Research (5 исследователей параллельно)
         ├─ Conf-researcher: Confluence + Jira (8 мин)
         ├─ Code-researcher (ENSI): код (10 мин)
         ├─ Code-researcher (OMS): код (12 мин)
         ├─ Code-researcher (Integration): код (10 мин)
         ├─ Logs-detective: стенд (15 мин)
         └─ Black-box-researcher: API (12 мин)
         
t=25-30  Phase 2: Analysis
         └─ Аналитик синтезирует постановку
         └─ Если [BLOCKER] → спрашивает человека
         
t=30-75  Phase 3: Development
         └─ Developer пишет код (45 мин)
         
t=75-95  Phase 4-5: Review (циклический!)
         ├─ Reviewer-1: AC, архитектура (20 мин)
         ├─ Reviewer-2: security, perf, design (20 мин параллельно)
         ├─ Developer фиксит замечания (10 мин)
         └─ Ревьюеры перепроверяют (если нужно ещё цикл)
         
t=95-100 Phase 6-7: Merge + Metrics
         └─ Merge в main/release
         └─ Собрать метрики и отчёт
```

**Итого: 100 минут вместо 180+ (параллелизм даёт 2× ускорение)**

## 🎯 Ключевые принципы

### 1. Разделение ролей

Вместо одного координатора на 150K токенов → 6 специализированных ролей:
- Каждая роль узко заточена
- Контекст каждого агента <20K токенов
- Специализм → лучше результаты

### 2. Параллелизм

- **5 исследователей одновременно** (вместо последовательно)
- **2 ревьювера одновременно** (вместо последовательно)
- Developer фиксит **параллельно с ревью** ([NB] вопросы)
- **Ускорение 2× за счёт параллели**

### 3. Циклический ревью (КЛЮЧЕВО!)

```
❌ Неправильно: один проход ревью → всё OK → merge
✅ Правильно: ревью может быть 2-3 итерации
            Iteration 1: замечания
            Developer фиксит
            Iteration 2: перепроверка
            Если OK → Merge
```

### 4. Явная коммуникация

- `[BLOCKER]` вопросы = критичные (блокируют)
- `[NB]` вопросы = некритичные (параллельно решаются)
- `[MUST]` замечания = обязательны
- `[SHOULD]` замечания = рекомендация
- `[NIT]` замечания = опционально

### 5. Автоматические метрики

```
/task-metrics  → время, токены, качество, рекомендации
```

### Для координатора (новая задача)

```bash
# 1. Запустить
/task-research-and-analyze "TICKET_ID"

# 2. Мониторить
/task-status           # каждые 5-10 мин

# 3. Разрешить вопросы
/blocker-resolve "id" --answer "ответ"

# 4. Собрать метрики
/task-metrics
```

### Для разработчика

```bash
# 1. Получить постановку из аналитика
# 2. Загрузить develop-[platform].md скилл
# 3. Писать код согласно постановке
# 4. Запушить MR
# 5. Фиксить замечания ревьюеров в цикле
```

### Для ревьювера

```bash
# 1. Получить MR готовый к ревью
# 2. Загрузить review-business-* или review-security-*
# 3. Написать замечания
# 4. Перепроверить (если Developer фиксил)
# 5. Дать Approved когда всё OK
```

## 💭 Философия системы

**"Узкая специализация + параллелизм = скорость и качество"**

- Каждый агент **знает одно направление хорошо**
- Агенты **работают одновременно**, не ждут друг друга
- Коммуникация **явная** (теги, [BLOCKER], [NB])
- Процесс **управляемый** (координатор видит всё)
- Результаты **измеримые** (метрики собираются)
