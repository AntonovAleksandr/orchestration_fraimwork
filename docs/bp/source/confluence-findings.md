> Сводный артефакт по результатам поиска в Confluence Gloria Jeans (`gloria-jeans.atlassian.net`).
> Метод: серия CQL-запросов через `mcp__gj-buddy__confluence_search_pages` + точечный
> `confluence_get_page` для ключевых страниц. Цель — собрать в одном месте всё, что
> компания формально описала о бизнес-процессах e-commerce, и обозначить пробелы.

**Дата сбора:** 2026-05-16
**Скоп:** Confluence (без Jira/Git/Логов)
**Спейсы Confluence, попавшие в выборку:**
- **OMNIES** — OMNI E-commerce (главный, ~80% всех релевантных страниц)

#### BP-2 «Создание заказа» — выжимка (из 60696279)

- **Назначение:** создать и передать в OMS заказ из корзины, учитывая товары, цены, скидки, адрес, способ оплаты и получателя.
- **Вход:**
  1. Корзина с товарами (размер, цвет, кол-во)
  2. Применённые акции
  3. Контакты получателя
  4. Способ + адрес доставки
  5. Способ оплаты (для онлайн — факт оплаты)
  6. Клик «Оформить»
- **Выход:**
  1. Клиент получил уведомление об успехе
  2. Заказ передан в OMS
  3. Витринные остатки уменьшены
- **DoD:** Заказ зарегистрирован в OMS, создан резерв позиций, OMS отправила ответ.
- **Сценарий:** Front → калькуляция → окна доставки → выбор окна → выбор оплаты → «Оформить заказ».
- **Роль исполнителей:** автоматический процесс.

### Покрытие

- **Очень глубокое покрытие**, включая много версий (v2, v3, v4) интеграций — следствие активного редизайна чекаута.
- Есть схема обработки checkout (`165388030`).
- Есть ADR на работу корзины и чекаута (`68790667`).
- Есть актуальные DRAFT-страницы новой логистики и беку чекаута.

#### BP-3 «Подтверждение заказа» — выжимка (из 60696284)

- **Назначение:** отсеять подозрительные заказы (фрод), взять реальные в работу.
- **Вход:** новый заказ в системе, очередь менеджеров; <某сумма> — автоподтверждение.
- **Выход:** уведомление клиента + обновление остатков в мастере и на сайте.
- **DoD:** заказу проставлен статус «Подтверждён», инфа разошлась в смежные системы, резерв сохраняется.
- **Исключения:** клиент при подтверждении менеджером может отказаться → «Отменён» + возврат резерва на свободные остатки.
- **Бизнес-правило:** заказы до X рублей подтверждаются автоматически; остальные — менеджером по очереди.
- **Роли:** менеджер обработки заказов + автоматика.

#### BP-4 «Комплектация заказа» — выжимка (из 60696309)

- **Назначение:** собрать и упаковать подтверждённый заказ для передачи в службу доставки.
- **Вход:** подтверждённый заказ в системе комплектовщика.
- **Выход:** посылка собрана, маркирована, в зоне передачи; статус заказа обновлён.
- **Сценарий:** комплектовщик берёт заказ из очереди → собирает позиции → пакует → клеит этикетки и сопроводительные документы → передаёт в зону → отмечает в системе.
- **Исключения:** не найдены позиции на складе.
- **Роль:** комплектовщик.

## 14. Дополнительно: BP-1 «Формирование каталога» — выжимка (из 60692611)

Корневая страница каталога как БП, с уровнем детализации L1+:

- **Назначение:** сформировать каталог товаров с офферами, которым назначены цены по бизнес-юнитам, чтобы клиент мог выбрать и заказать.
- **Триггеры (входы):**
  1. Уведомление об изменении номенклатуры товаров
  2. Регулярная проверка/обновление цен
  3. Уведомление об изменении бизнес-юнитов
  4. Время загрузки остатков
  5. Уведомление об изменении остатков
- **Результат (выход):**
  1. Загружена номенклатура (модели/цвета/размеры)
  2. Вычислено разрешение на продажу
  3. Вычислены актуальные цены
  4. Сформированы офферы (цена ↔ бизнес-юнит)
  5. Вычислены актуальные остатки (за вычетом резервов)
  6. Вычислены маскированные остатки для витрины («много/мало/1 шт»)
- **DoR:** номенклатура с обязательными атрибутами (id, название, активность, картинка, вес, НДС); SKU с (id, штрихкод, размер, цвет, габариты); цены с (SKU, дата начала продаж, цена, BU, флаг запрета); остатки с (SKU, кол-во, BU, лимит).
- **НФТ:** ≤100K товаров, ≤1M SKU, ≤10K бизнес-юнитов; скорость обновлений до 10K/сек по товарам и ценам.
- **Подпроцессы:** BP-1.1 Загрузка номенклатуры, BP-1.2 Доступность SKU по BU, BP-1.3 Цены SKU по BU, BP-1.4 Остатки.

## Gaps — что плохо/не покрыто в Confluence

### 1. Pre-purchase (поиск/просмотр товара) — частично
- **Описано:** статичные страницы каталога (`60690170`, `13`, `15`), но нет **карточки БП "Поиск и выбор товара"** — то, что в коде сделано через `catalog-cache` + Elastic + recommendation engines (DynamicYield, MindBox).
- **Реальная глубина в коде > чем в Confluence** для поиска/листинга/фильтрации/рекомендаций.

### 2. Аутентификация/сессии — фрагментировано
- AS-IS (hybris) и TO-BE (ENSI customer-auth + admin-auth) разнесены.
- Нет единого описания "флоу логина" с указанием customer-auth + adapter-token-flow + Mob app vs Web.

### 3. Корзина — endpoint-level есть, **BP-level нет полного**
- BP-2.1 "Отбор товаров и формирование корзины" есть только как карточка, но **детальной логики merge/lock/recalc нет в виде БП** — только в endpoint-описаниях.

### 4. Сервисный слой между Site/Mob и OMS — серая зона
- Integration Service (Lumen-приложение в `platform/integration/`) **почти не описан** в Confluence.
- Поиск по "integration" даёт только OPSOMN-задачи, нет архитектурного описания самого сервиса.
- API Gateway Ensi описан только через INT-страницы (контракты), но не как сервис целиком.

### 5. Сайт/Mobile фронты — частично
- `Функциональная нарезка Front (Desktop + Adaptive)` (60692563) — индекс есть.
- `Функциональная нарезка Front (MobApp)` (63455034) — индекс есть.
- TS.1..TS.10 — новейшая серия, MobApp-фокус.
- **Не описано:** SSR-стратегия NestJS, Nx module boundaries — это знание есть в коде, но не в Confluence.

### 6. Camunda BPMN — слабо
- Один pet-project в личном спейсе (`82016519`).
- В Confluence есть **PNG-аттач "Статусная схема разных типов заказов. Положительный сценарий"** (`130128632`) — единственная общая визуализация.
- BPMN-файлы лежат в коде (`platform/starfish24/awg/bpmn-process/`), но **маппинга "имя BPMN-процесса → Confluence-описание" нет**.

### 7. AI/ML — только зачатки
- В GJAIKB / GJAI спейсах есть AI-инициативы, но они на стадии видения (см. `165402838`, `165403393`, `165402727`).

### 8. Сквозные сценарии (E2E) — единственная точка `DPD — E2E (FRONT → OMS/OTS → WMS → DPD)` (`165402584`)
- Других E2E описаний нет. Большинство страниц — про "часть процесса".

### 9. Клиентский сервис / Контакт-центр для e-commerce
- Регламенты есть (REGDOC), но **специфики "клиент позвонил по заказу N — что делает оператор"** нет.
- Эта зона размазана между OMS-6.11 (Отмены), OMS-6.12 (Уведомления) и регламентами контакт-центра.

### 10. Многие критичные страницы — **гигантские** (60-70K символов)
- OMS-3 Оформление заказа (`60695639`), OMS-4 Модель заказа (`60695933`), OMS-5 Статусная схема (`60693138`),
  Функциональная нарезка Catalog (`60690170`), Сводная (`165404708`).
- **Риск:** актуальность отдельных секций неравномерна; редактирование одного куска ломает другой.

## Рекомендации к следующим шагам

1. **Использовать BP-1..BP-5 серию как скелет** для нашей карты — она уже разрезана по доменам ровно так же, как нужно нам.
2. **Не дублировать содержимое — линковать** на ID-страниц Confluence. Эти ID стабильны.
3. **Заполнить gaps** (см. список выше) — это место, где наша карта добавит ценность.
4. **Извлечь схемы** (`130128632` положительный сценарий) и линкануть.
5. **Для OMS-3/OMS-4/OMS-5** (страницы 60-70K) — при необходимости делать выборочные выгрузки секций через `confluence_get_page` с offset/limit при работе с конкретным процессом.
6. **Координация с кодом:** для каждого BP сверять «что в Confluence» vs «что реально в `platform/`» — выявлять рассинхронизации (особенно для активно дорабатываемых: новая логистика, новый чекаут, переход с редиректа ЮKassa).
