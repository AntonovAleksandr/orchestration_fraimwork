# ADR: диапазон и аллокатор `gj_order_id` для заказов WB FBS

> **Дата:** 2026-07-31 · **Тип:** ADR · **Статус:** proposed — на согласование 1С, OTS, DWH
> **Скоуп:** внутренний 10-значный номер заказа для сборочных заданий Wildberries FBS в контуре Connector → OTS → WMS → 1С → DWH.
> **Доказательная база:** `docs/research/marketplaces/` Stage 14 (история и ограничения номера), Stage 15–17 (роль номера в контуре), реестр `MP-ID-001..010`; проверка кода 2026-07-31 (`MP-ID-007`).
> **Связанные документы:** задание на правки OTS — `docs/research/marketplaces/OTS-CHANGES-WB-FBS.md`.

---

## 1. Контекст и проблема

Для WB FBS принято решение «одно сборочное задание WB = одна единица товара =
один внутренний заказ GJ» (Stage 15; это решение GJ, WB требует только одну
единицу в задании). Каждому заданию нужен внутренний номер, потому что номер —
сквозной натуральный ключ исполнения: он становится номером заказа OTS и WMS,
`idd` и частью `documentFoundation` в 1С, кодом заказа в DWH (`MP-ID-005`).

Контур fast-track не включает OMS и ENSI (Connector → OTS → WMS/1С), поэтому
существующий аллокатор ENSI (`2` + 9-значная последовательность) в цепочке
отсутствует, и номер должен выдавать сам Connector.

Жёсткие ограничения, подтверждённые контрактами и кодом:

- **ровно 10 цифр**: 1С-контракт `idd` — строка длины 10,
  `documentFoundation` — 17 = префикс источника + номер (`MP-ID-006`); OTS
  собирает `idd` как `GetPrefix() + order_id.PadLeft(10)` — 10-значный номер
  ложится без усечения (`OneSService.cs:55`);
- **без ведущего нуля**: печатные штрихкоды теряют ведущие нули
  (`MWHNSK-3152`);
- **сквозная уникальность**: повторное значение — бизнес-ошибка downstream
  (`MP-ID-004`);
- существующие пространства номеров: `1…` — Hybris, `2…` — Starfish/ENSI
  (текущий максимум последовательности `2 010 743 249`), `211…` —
  сертификаты (внутри пространства «2»), `9…` — стабы/legacy.
  Централизованного реестра пространств не существует (`MP-ID-008`).

## 2. Решение

1. **Диапазон:** `3100000000–3199999999` — блок «31», 100 млн значений.
   Семантика: первая цифра `3` — заказы маркетплейсов, вторая — площадка
   (`1` = Wildberries). Блоки `32…`–`39…` зарезервированы под будущие
   площадки.
2. **Аллокатор:** единственный владелец — `wbconnector`; последовательность в
   его Postgres с CHECK-границами блока. Координация с ENSI/OMS не требуется:
   пространства не пересекаются.
3. **Реестр пространств:** создаётся страница-реестр (Confluence) с
   перечнем `1 / 2 / 211 / 9 / 31(–39)` и владельцами; любые новые диапазоны —
   только через реестр. Это закрывает `MP-ID-008`.
4. **Маршрутизация не по первой цифре:** вся downstream-логика для заказов WB
   (уведомления, возвраты, префикс 1С-документа) ведётся по
   `source=WB_FBS`, а не по первой цифре номера — правки уже описаны в
   задании OTS. Первая цифра остаётся человекочитаемой меткой, а не
   контрактом.
5. **Идемпотентность:** сопоставление `wb_order_id ↔ gj_order_id` уникально и
   неизменяемо (UNIQUE в схеме Connector); `rid`/`srid` WB хранятся рядом; в
   OTS передаётся стабильный `guid`, детерминированно производный от заказа —
   он становится `ReserveEventId` (см. задание OTS, правка 6).
6. **Префикс 1С-документа** (`documentFoundation`) — отдельное значение по
   аналогии `0000352`/`0000354`, задаётся правкой `GetPrefix()` в OTS;
   конкретный код согласуется с 1С и фиксируется в реестре рядом с
   диапазоном.

## 3. Почему «31» безопасен — доказательства

Главное возражение против номеров выше `2 147 483 647` — скрытые
Int32-преобразования в legacy. Проверено по коду 2026-07-31 (`MP-ID-007`,
реестр содержит точные якоря file:line):

| Маршрут | Поле номера | Тип | Int32-риск |
|---|---|---|---|
| Connector → OTS (`POST /v2`) | `order.order_id` | `long` / SQL bigint | нет |
| OTS → 1С ЛЦ (напрямую, http-сервис 1С8) | `idd_order`, `order_id` | string | нет |
| OTS → WMS (`wmsinserter`) | `OrderNr`, `OrderRefNr` | string | нет |
| 1С → OTS (события) | `order_id` | `long` | нет |
| OMS → IS → ApiGW → 1С Ecom (не наш контур, для полноты) | `idd`, `documentFoundation` | string | нет |

Инцидент `OPSOMN-13708`, из-за которого возник страх Int32, разобран до кода:
Int32-парсер живёт в ApiGW на **другом поле** — `fiscal_document_number`
(номер кассового чека, `ReceiptInfoDTO.FiscalDocumentNumber: int?`) — и не
касается номера заказа. Дополнительно: исторический тест `MWHNSK-3152`
провёл `3000000001` через 1С7/WMS успешно (дефект был в ведущих нулях
штрихкода, к «31» неприменим). В самой 1С числа — decimal произвольной
точности, переполнение невозможно; её ограничение — длина строки 10, которую
«31» соблюдает.

Остаточный риск — непросмотренные пути (редкие отчёты, возвраты) — закрывается
граничной SIT-фиксацией (§6), но блокером решения не является: все основные
маршруты доказаны статически.

## 4. Отклонённые альтернативы

**`2120000000–2147483647`** (под потолком Int32, внутри пространства «2»).
Плюс был один — защита от гипотетических Int32-парсеров, и он исчез после
проверки кода. Минусы остались: заказ WB визуально неотличим от обычного eCom
(операционная путаница, сложнее аналитика и поддержка); блок живёт внутри
чужого пространства (последовательность ENSI и сертификаты `211…`) и требует
вечной координации; ёмкость 27,5 млн против 100 млн.

**Переиспользовать аллокатор ENSI** — втягивает ENSI в контур, которого в
fast-track нет; создаёт ложную зависимость пилота от релизов ENSI.

**Нечисловой/буквенный префикс** — нарушает 10-значный числовой контракт 1С и
штрихкоды форм.

## 5. Последствия

- Ёмкость блока: 100 млн номеров. Плановый объём — ~20 тыс. заказов в день
  (у WB заказ = одна единица = одно сборочное задание, подтверждено бизнесом
  2026-07-31), то есть расход ~20 тыс. номеров в день → блока хватает на
  **~13,7 года**.
- Исчерпание блока — операционное событие, а не архитектурное: маршрутизация
  ведётся по `source=WB_FBS`, ни один контракт не зависит от «31», поэтому
  через реестр пространств WB выдаётся следующий свободный блок, а в
  аллокаторе Connector меняются только CHECK-границы. Всё пространство «3…» —
  1 млрд значений (~45 лет при 60 тыс. единиц в день на все площадки).
- В витринах DWH и отчётности появится новая первая цифра — владельцев витрин
  нужно уведомить (проверка «первая цифра в маршрутизации отчётов» входит в
  SIT).
- Появляется прецедент и правило: новые площадки получают блоки `32…`–`39…`
  через реестр, а не ситуативно.

## 6. Условия фиксации (accepted) и действия

1. **SIT-фиксация границы:** заказ `3100000001` проходит
   OTS → WMS → 1С → паллетная отгрузка → `wms_shipment` неискажённым, штрихкод
   номера на формах сканируется, выгрузка DWH принимает номер. Уже включено в
   приёмку задания OTS (§5 там же).
2. **Реестр пространств создан** и содержит `31` с владельцем.
3. **Согласования:** 1С — префикс `GetPrefix()` и приём `idd` с первой
   цифрой `3`; OTS — задание `OTS-CHANGES-WB-FBS.md`; DWH — новая первая
   цифра в витринах.

После выполнения трёх пунктов статус меняется на accepted; до этого Connector
может использовать блок в тестовых контурах.
