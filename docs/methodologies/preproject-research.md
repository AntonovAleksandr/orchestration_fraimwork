# Методология: предпроектное исследование инициативы (доказательное, многосессионное)

**Статус:** канон (переиспользуемая методология). Источник истины — этот файл; проекты ссылаются, не копируют.
**Применять:** когда инициативу нужно **разобрать до запуска** — понять связи систем, зависимости, объём доработок,
риски — чтобы затем дать [индикативную оценку](initiative-indicative-estimation.md) и передать команде полуготовые задачи.

## Назначение и место в цикле

Это **вход** всего предпроектного цикла CTO:

```
Предпроектное исследование (этот документ)
   → Индикативная оценка инициативы (initiative-indicative-estimation.md)
   → Передача команде (видение, риски, открытые вопросы, нарезка задач)
```

Цель — собрать **доказательную базу**: что РЕАЛЬНО есть в коде/системах (as-is), что требуется (to-be), где **разрывы**,
какие **гипотезы** и **риски**, что нужно **решить с бизнесом**. Результат должен **пережить несколько сессий** и быть
понятен аналитику/разработчику/тестировщику/PM как стартовая точка (не замена их работы — см. §1.1 методики оценки).

> Это **agent-facing скилл** `.claude/skills/gj-evidence-ledger-research/SKILL.md` (как агенту вести такое исследование)
> + **этот процессный канон** (зачем, какие артефакты, как читать результат). Не дублировать — скилл про «как делает AI»,
> методология про «что на выходе и как этим пользоваться».

## Когда применять (и когда НЕ надо)

**Применять staged evidence-ledger исследование, когда:**
- инициатива затрагивает **3+ системы/домена**;
- требования в Confluence/Jira могут **расходиться с реальным поведением кода**;
- нужны факты из **БД/логов**;
- работа **не закроется за одну сессию**;
- выход — **as-is / to-be / gap**, а не немедленный код.

**НЕ надо (overkill):** для мелкого инцидента/вопроса — обычный `docs/research/<YYYY-MM-DD>-<topic>.md` (один файл, 1–2 экрана),
см. `docs/research/README.md`.

## Артефакты проекта

Исследование живёт **отдельной директорией** `docs/research/<initiative>/` с точкой входа `README.md`:

| Файл | Что внутри |
|---|---|
| `README.md` | точка входа: цель, **дизамбигуация** (что не путать), скоуп, карта проекта, краткие источники |
| `00-PLAN.md` | метод, таблица **стадий**, плейбук источников, протокол сессии, **progress tracker**, **resume pointer** |
| `00-requirements.md` | канонические требования инициативы (из брифа/Confluence), фаза MVP/далее, вопросы на согласование |
| `00-source-inventory.md` | реальные источники: код-локации (после sync), Confluence page_id, Jira keys, БД/лог-таргеты |
| `EVIDENCE-LEDGER.md` | сквозной реестр: **одна строка = один разрыв/находка/решение** (verdict + evidence) |
| `TEMPLATE-stage.md` | форма стадии (as-is / to-be / gap / evidence / вопросы / acceptance / resume) |
| `stages/stage-NN-<domain>.md` | один домен = одна стадия |
| `ONE-PAGER.md` | выжимка для руководства (см. методику оценки §5) |

Образцы: `docs/research/r20-order-splits/`, `docs/research/yandex-express/`, `docs/research/site-kiosk-mode/`.

## Метод (одинаковый для каждой стадии)

1. **Стартовать от требований и инвентаря источников**, а не от догадок по коду.
2. **Синхронизировать** только нужные `platform/*` репозитории (делает оркестратор), затем локальные Read/Grep.
3. Собрать **as-is** (живую правду) из кода, доков, Jira/Confluence, **БД (SELECT+LIMIT)**, логов.
4. Сопоставить с **to-be** (требованиями).
5. Построить **gap-матрицу** с confidence и **якорями доказательств**.
6. После ревью стадии — **приземлить строки в EVIDENCE-LEDGER** (делает оркестратор, не субагент напрямую).
7. Завершать стадию: **открытые вопросы + acceptance-gates + resume pointer**.

**Вердикты gap:** 🟢 есть/паритет · 🟡 частично/doc-only · 🟠 заглушка/обходной путь · 🔴 нет · `TBD` не проверено.

## Правила доказательств (evidence)

- **Код:** путь и `file:line` якорь; «0 совпадений grep ≠ отсутствие» — скоупить к подкаталогу и подтверждать Read.
- **Jira:** issue key + статус.
- **Confluence:** page_id + пометка свежести/confidence (может быть устаревшим).
- **БД:** только SELECT + LIMIT, без записей; цель запроса, источник (stage для формы данных, prod для объёмов).
- **Логи:** таргет, окно времени, trace_id/order_id, суммаризированная ошибка.
- **Секреты/ПДн:** редактировать или опускать.

## Гипотезы, вопросы, acceptance — мост к оценке и передаче

- **Гипотезы** фиксировать явно (как `H1` в yandex-пакете): формулировка, confidence, **владелец проверки**, влияние на скоуп/срок. Подсвеченные CTO риски — это гипотезы, аналитик их проверяет и может найти новые.
- **Открытые вопросы** = рабочий список «бизнес-уточнения» (полоса Ось B в оценке) и блок «Что нужно от руководства» в one-pager.
- **Acceptance-gates** = заготовка приёмки/критериев готовности для тестировщика и PM.

## Гардрейлы

- Не считать «0 grep» доказательством отсутствия (вложенные репо/ignored пути прячут результаты).
- Не смешивать **as-is факты** и **to-be дизайн** в одном абзаце.
- Не дублировать BP-доки (`docs/bp/*`) — ссылаться, фиксировать только дельту/разрывы.
- Ledger приземляет **оркестратор после ревью**, не субагент напрямую.
- Не завершать сессию без **resume pointer**, если исследование не закончено.

## Роли и инструменты

- **Оркестратор (CTO+AI)** ведёт план, синхронизирует репозитории, приземляет ledger, держит resume pointer.
- **Доменные субагенты** (`*-researcher`, `*-navigator`, `logs-detective`, `gitlab-investigator`) собирают as-is по своей зоне; один субагент пишет только свой `stages/*.md`.
- **Buddy MCP** — Jira/Confluence/логи/код: изучить документацию, вытащить факты, потом оформить Confluence и нарезать задачи.

## Связь с другими методологиями

- **Выход → вход оценки:** gap-матрица + объём доработок + риски питают [индикативную оценку](initiative-indicative-estimation.md) (включая системный анализ как «черновик», который аналитик дорабатывает).
- **Выход → передача команде:** открытые вопросы, гипотезы, acceptance-gates, нарезка — стартовая точка для аналитика/разработчика/тестировщика/PM.
- **One-pager** для руководства собирается из README + gap + оценки.
