# Режим киоска сайта e-com — one-pager для руководства

**Дата:** 2026-06-28 · **Владелец:** Александр (CTO eCommerce) · **Статус:** индикативная оценка (предпроектный анализ)

---

## Что это

Большой экран в магазине показывает сайт e-com в **режиме киоска** — покупатель сам ищет товар, смотрит ассортимент магазина и оформляет заказ прямо в зале. Пилот — на **2–3 магазинах**, на уже имеющемся железе (Ubuntu).

## Что делаем в MVP (пилот)

- Старт сразу в **каталоге** (без главной), интерфейс — текущий «планшетный», без переверстки.
- Кнопка **«товары только этого магазина»** (механизм фильтра уже есть).
- **Авто-разлогин**: после оформления заказа и при бездействии (попап с обратным отсчётом) — чтобы экран был готов для следующего покупателя.
- Запуск браузера в **режиме киоска** на устройстве в магазине.

> Принцип 1-й фазы — **минимум модификаций, максимум переиспользования** существующего фронта.

## Сроки (индикативно)

**MVP по потокам** (методика: 3 инженерных потока + Ось B «бизнес/организационное»):

| Поток | Оценка | Комментарий |
|---|---|---|
| Системный анализ (аналитик) | ~неск. дней | предпроект сократил онбординг (недели→дни); остаются валидация, доуточнение требований, Confluence-доки, согласование дизайна, нарезка задач в Jira |
| Разработка | ~1–2 нед | переиспользуем инстанс-шаблон, фильтр магазина, точку завершения заказа; с нуля — авто-разлогин по бездействию |
| Тестирование (инженерное) | ~0.5 нед | сценарии заложены на предпроекте |
| Бизнес-уточнение + согласования + инфра + установка (Ось B) | **доминирует** | решения 1-й недели, домен/DevOps, UAT, установка на устройства |
| **MVP итого** | **~3–5 недель** | при быстрых решениях — ближе к 3 |

**Фазы:**

| Этап | Срок | Комментарий |
|---|---|---|
| **MVP — пилот на 2–3 магазинах** | **~3–5 недель** | разбивка по потокам выше |
| Phase 2 — **гостевой чекаут** (заказ без логина) | ~4–8 недель | срок диктуют **юр./фискальные согласования** (Ось B), а не код |
| Phase 2 (опц.) — Android-устройство + приложение | ~3–6 недель | только если браузер-киоск на Ubuntu не подойдёт |

**Почему разработка быстрая:** ведём её с AI, и ключевое в текущем сайте **уже готово** — формат отдельного инстанса (как «режим оператора» колл-центра), фильтр по магазину, точка завершения заказа. С нуля пишем по сути только авто-разлогин по бездействию.

**Главный тезис:** срок определяет **не программирование** (оно ~1–2 недели), а **скорость согласований и организационные процессы**. Чтобы попасть в нижнюю границу — ускорять решения, а не разработку.

## Что нужно от руководства (чтобы попасть в ~3 недели)

Принять в 1-ю неделю ключевые решения:
1. Формат запуска: отдельный инстанс киоска со своим доменом **или** режим-флаг на текущем сайте (для скорости).
2. Таймаут бездействия до авто-разлогина (30 или 60 сек).
3. Способ «привязки» киоска к магазину (домен / ссылка / настройка устройства).
4. Стартовая категория каталога для киоска (весь ассортимент или товары магазина).
5. Как покупатель авторизуется на общем экране (телефон + СМС).
6. Выделение домена/инфраструктуры (DevOps) и доступ к пилотным устройствам.

## Риски / допущения

- Оценка **индикативная**: по итогам детального анализа сроки могут меняться в обе стороны.
- «Общий девайс» → нужна гарантированная очистка персональных данных между покупателями (ИБ-ревью).
- Гостевой чекаут и фискальные нюансы — намеренно вынесены в Phase 2, чтобы **не блокировать пилот**.
