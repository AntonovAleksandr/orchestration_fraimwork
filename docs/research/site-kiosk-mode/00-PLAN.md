# Режим киоска (site-kiosk) — мастер-план исследования

**Цель:** по брифу владельца ([`00-requirements.md`](00-requirements.md)) определить **направление доработок**, **порядок**
и **сроки** (по [`00-estimation-methodology.md`](00-estimation-methodology.md)). Это scoping нового функционала: сверяем
**as-is живой фронт** (`platform/site/gj-ng-front` + эталон ASM + customer-auth) с **целевым режимом киоска**, фиксируем
**решения/разрывы**, оцениваем по двум осям (effort vs календарь) и собираем поэтапный roadmap.

**Почему многосессионно:** 6 доменов + синтез; каждый требует чтения кода (`platform/*`), сверки с ASM-эталоном,
решений по согласованию. За одну сессию контекст переполнится. Поэтому **1 домен = 1 стадия = 1 файл** в `stages/`,
плюс накопительный `EVIDENCE-LEDGER.md`.

---

## 1. Метод (одинаковый для каждой стадии)

Каждая стадия даёт `stages/stage-NN-<domain>.md` по `TEMPLATE-stage.md`:

1. **As-is (живая правда).** Что уже есть в коде (фронт/ASM/auth/каталог), с якорями `путь/файл:line`. Подтверждать `Read`.
2. **Целевое (для киоска).** Что должно быть под соответствующие `KR-NN` из `00-requirements.md`.
3. **Решение + разрывы.** Конкретный подход (минимум модификаций, KR-12), что переиспользуем, что новое; матрица: 🟢 готово/переиспользуем · 🟡 частично/доработать · 🟠 обходной путь · 🔴 нет/новое.
4. **Оценка (две оси).** Таблица Ось A (AI-дни) / Ось B (календарь) / срок / что ускорит — по методике.
5. **Открытые вопросы + acceptance-gates** (→ агрегируются в Stage 07).
6. **Resume pointer.** Что не доделано, с чего продолжить.

Каждая значимая находка/решение дублируется одной строкой в `EVIDENCE-LEDGER.md`.

### Правила работы с источниками
- **Код:** перед поиском по `platform/*` — `./scripts/sync-platform-repos.sh <platform>`. На старте site не зафастфорвардился (feature-ветка `OPSOMN001-386`, дерево чистое, код от 2026-06-23) — это ок для архитектурных фактов; отмечать как caveat, не делать принудительных git-операций.
- **⚠️ «0 совпадений» НЕ доказывает отсутствие.** Скоупить `rg`/Grep к конкретному подкаталогу (напр. `platform/site/gj-ng-front/libs`, `.../apps`) и подтверждать `Read`.
- **Эталон ASM:** режим аватара/колл-центра — образец «как заведён отдельный инстанс/режим». Изучать первым (Stage 01).
- **Бэкенд auth/гость:** customer-auth / customers / checkout — `ensi-researcher`/`integration-researcher` для Phase 2.
- **Не дублировать** чекаут-доки — ссылаться на `docs/research/2026-05-20-checkout-order-creation.md` и скилл `gj-checkout-order-flow`.

## 3. Код / источники-плейбук (конкретные таргеты)

**Код (локально, после sync `site`; бэкенд — `ensi`/`integration`):**
- Фронт инстансы/флейворы: `platform/site/gj-ng-front/apps/*`, `configs/`, `project.json`/`nx.json`, `environment*`.
- Эталон ASM: искать `asm`/`avatar`/`operator`/«аватар» в `apps/` и `libs/` (Stage 01 уточняет точные пути).
- Каталог/листинг + фильтр магазина: `platform/site/gj-ng-front/libs/modules/catalog`, `libs/data-access`, `libs/core/store`.
- Auth/сессия: `libs/core` (auth/interceptors/guards), `libs/data-access` (customer-auth client); бэкенд `platform/ensi/apps/customers/customer-auth`, `platform/ensi/apps/customers-api-web`.
- Чекаут (для KR-5/KR-8): `libs/modules/checkout` + `platform/integration/integration/www` + OMS `/order/create`.

**Confluence/Jira:** на старте — нет утверждённого требования (бриф владельца). По мере согласования заводить страницу/эпик и фиксировать ID в `00-source-inventory.md`. CQL/JQL по «киоск»/«kiosk» — проверить, нет ли уже наработок.

**Логи/БД:** на этапе scoping в основном не нужны; для гостевого чекаута (Stage 06) — как в чекаут-проекте (`integration-awg-new-logs-prod`, OMS таргеты).

## 4. Протокол сессии (как продолжать)

1. Прочитать `EVIDENCE-LEDGER.md` и §2 (Progress tracker — где остановились).
2. Открыть незакрытую стадию / начать следующую по порядку.
3. Синхронизировать нужные `platform/*` (делает **оркестратор**, не субагент).
4. Работать по `TEMPLATE-stage.md`; писать в `stages/stage-NN-*.md` + строки в ledger.
5. В конце — обновить **Progress tracker** и **Resume pointer**.

### Делегирование субагентам
- `site-researcher` — as-is фронт (Stage 01–04). `devops-architect` — kiosk-режим/железо (Stage 05).
  `ensi-researcher` + `integration-researcher` — гостевой чекаут (Stage 06). `architect` — синтез/roadmap (Stage 07).
- Синк платформ — оркестратор. Один субагент пишет только свой `stages/*.md`; ledger приземляет оркестратор после ревью.
