### 3.1 MVP — по под-фичам (индикативно)

| Под-фича | Ось A (effort, AI-дни) | Ось B (главный блокер, дни) | Срок | Готовность as-is |
|---|---|---|---|---|
| Инстанс `site-kiosk` (Вариант A: флаг+Docker-таргет) | M / 2–3 | решение инстанс/флаг + домен/API-хост (DevOps), 2–5 | 3–6 дн | 🟢 шаблон ASM |
| Старт в каталоге root | XS–S / 0.5–1 | выбор категории-старт (бизнес), 1–2 | 1–2 дн | 🟡 нужен root-маршрут |
| Layout планшет→киоск (скрыть лишнее) | XS–S / 0.5–1 | ~0 (вёрстка есть) | 0.5–1 дн | 🟢 |
| Фильтр «товары магазина» + привязка | S–M / 1–3 | способ привязки (домен/URL), 1–3 | 2–4 дн | 🟢 фильтр / 🟡 привязка |
| Авто-разлогин после заказа | S / 0.5–1 | ~0 | 0.5–1 дн | 🟢 крючок thank-you |
| Idle-таймер + попап + reset | M / 1–3 | согласование N сек, 1–2 | 2–3 дн | 🔴 с нуля |
| Очистка состояния общего девайса | S–M / 1–2 | ИБ-ревью, 1–3 | 2–3 дн | 🟡 |
| Железо: Ubuntu chromium kiosk | S–M / 1–2 | доступ/координация магазинов | 2–4 дн | 🟡 железо есть |

**Инженерный effort MVP суммарно:** ~7–16 AI-дней, но фичи **параллелятся** → чистая разработка ≈ **1.5–2.5 недели**.

### 3.2 Критический путь MVP (НЕ сумма фич)

```
Согласование требований + ключевые решения (≈1 нед)
   → Разработка ядра: инстанс + фронт-правки + idle-логаут (параллельно, ≈1–2 нед)
      ↘ Провижининг устройств Ubuntu kiosk (параллельно, ≈1 нед, после готовности домена)
   → Интеграционное тестирование / UAT на пилоте (≈0.5–1 нед)
   → Прод-релиз + раскатка на 2–3 магазина (≈0.5 нед)
```

| Фаза | Инженерный effort | Главный календарный блокер | Индикативный срок |
|---|---|---|---|
| **MVP (пилот 2–3 магазина)** | ~1.5–2.5 нед (AI) | согласования + домен/API + UAT + провижининг | **~3–5 недель** календарных |
| **Phase 2: гостевой чекаут** | ~1.5–3 нед (AI, XL кросс-система) | юр/фиск/ПДн/канал продаж + кросс-системный UAT | **~4–8 недель** |
| **Phase 2 (опц.): Android-app** | ~2–4 нед (AI) | (отдельно) | **~3–6 недель** |

**Главный тезис:** срок MVP определяют **не кодинг** (он ~1–2 недели), а **согласования, провижининг устройств,
UAT и релизное окно**. Ускорять → ускорять решения, а не разработку.

### 3.3 Что двигает срок (риски/допущения для руководства)
- **Ближе к 3 нед:** железо готово, домен/API заводится быстро, ключевые решения (инстанс/флаг, N сек, привязка, root-категория, способ логина) приняты в 1-ю неделю.
- **Ближе к 5+ нед:** задержки согласований, выделение домена/инфры через DevOps, ИБ-ревью общего девайса, координация пилотных магазинов.
- **Зависимость-фундамент:** решение Stage 01 (инстанс vs флаг) определяет параллелизм; принять рано.
