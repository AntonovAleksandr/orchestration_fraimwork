# Деньги: копейки vs рубли по системам чекаута — карта + политика для нового checkout

**Дата:** 2026-05-30
**Статус:** факты из Jira + кода. Проблема ИЗВЕСТНА, отслеживается, **не до конца закрыта** (есть открытые тикеты).
**Зачем:** разработчик ИС давно подсвечивал рассинхрон представления денег (целые копейки `59900` vs рубли `599.00`) между системами. Это даёт «лишние нули» и `InvalidateTotalCost` 400. Зафиксировать карту + политику, чтобы новый checkout НЕ наступил.
**Связано:** дизайн `2026-05-29-checkout-service-design.md` (§5 payload, §6 two-phase truth/checksum), `2026-05-29-order-create-contract.md`.

---

## TL;DR — правило

**Канон GJ (OPSOMN-12987, Confluence pageId 165380364):** в контрактах **ENSI ↔ ИС ↔ OMS** деньги передаются **в РУБЛЯХ с двумя знаками копеек, округление вверх** (`599.00`, `1699.00`). Это целевой стандарт.

**Реальность:** **ENSI offers/catalog хранит цену в целых КОПЕЙКАХ** (`int 59900` = 599 ₽) — это подтверждено и нашим `clients/offers` (`Offer.Price *int` копейки), и багами ниже. Конверсия копейки→рубли (÷100) местами **теряется или смешивается** → одни поля в копейках, другие в рублях в одном payload.

**Для нового checkout:** хранить деньги как **`int64` в МИНОРНЫХ единицах (копейки)** + типизированный `Money` — НИКОГДА float. Конвертацию делать **явно на границе каждого клиента**, зная единицу источника. Checksum/two-phase-truth сравнивать в копейках (целые, без float-дрейфа). На OMS-границе конвертировать копейки→рубли-decimal по канону (2 знака, округление вверх).

## Доказательства (Jira)

### Канон — OPSOMN-12987 (Выполнено): «приведение к единообразию расчёта стоимости на чекауте»
> «В контрактах ENSI–ИС передавать цену **в рублях c двумя знаками в копейках с округлением в большую сторону**.» Документация: Confluence `pageId=165380364` + реестр изменений контрактов. Связанные этапы рефакторинга: **OPSOMN-14588 (ENSI)**, **OPSOMN-14589 (ИС)** «Рефакторинг передачи кол-ва товара/цен/скидок по флоу» (Тестирование завершено).

### Баг копеек↔рубли — OPSOMN-11196 (Блокирующий, Завершено): «price передаёт лишние нули»
Запросы `/v2/delivery/courier`, `/v2/delivery/points`, `/v3/delivery/points` слали:
```json
"totalItemPrice": 599,          // РУБЛИ (верно)
"products": [{ "id": "GRA000042F0001", "quantity": 1, "price": 59900 }]  // КОПЕЙКИ (баг!)
```
599 ₽ = 59900 коп. `price` в копейках там, где ждали рубли → «лишние нули» → заказ не оформлялся. (Тот же SKU, что в наших OMS-фикстурах.)

### Симптом в create — OPSOMN-14721 (Новый): «Ожидаемая сумма … отличается»
`POST /integration/v4/order/create`:
```json
"items": [
  { "productId": "GSL002772F0003", "price": 169900, "quantity": 1, "discount": 0 },  // КОПЕЙКИ (1699 ₽)
  { "productId": "GSL003009F0003", "price": 159900, "quantity": 1, "discount": 0 }   // КОПЕЙКИ (1599 ₽)
],
"totalCost": 2178   // РУБЛИ
```
→ OMS ждёт сумму без доставки 3298 (=1699+1599 ₽), получил `totalCost` 2178 ₽ → **`InvalidateTotalCost` 400** (errorCode 1022). Два дефекта сразу: **(а) смешанные единицы** (`items.price` в копейках, `totalCost` в рублях) + **(б)** ИС не сходил в discount-сервис (поле `discount` пусто → 3298 без скидки vs 2178 со скидкой).

> **Корень (б) подтверждён по коду (2026-05-30, integration-researcher):** `Integration .../V2/Discount/DiscountService.php::calculateOrderDiscounts` зовёт сервер скидок (`DiscountClient::getDiscounts`) **только `if (count($order['marketing']['promoApplied']) > 0)`**; перед этим всем item принудительно `discountPrice = price, discount = 0` (`:177-179`). Если `promoApplied` пуст — quote НЕ выполняется, `discountPrice` остаётся = `price`. Затем `V1/Order/OrderService.php::calculateTotals:3212` суммирует `discountPrice` и кидает `InvalidateTotalCost` если `originalTotalCost (от клиента, СО скидкой) != totalDiscountPrice (без скидки)`. Фикса 14721 в ветке `production` нет — баг открыт. **Двойной расчёт скидки:** ENSI `baskets` уже посчитал скидку корзины через СВОЙ клиент (`DISCOUNT_API_URL`), но Integration на commit это игнорирует и делает свой quote через `SALE_SERVICE_CLIENT_BASE_URL` — и роняет заказ, если на вход не пришёл `promoApplied`. См. археологию §5 «два клиента к одному серверу скидок».

## Карта представления денег по системам (путь checkout)

| Система / контракт | Единица | Примечание |
|---|---|---|
| **ENSI offers / catalog-cache** | **копейки (int)** | `Offer.Price/OldPrice *int` — подтверждено `clients/offers` + OPSOMN-11196 |
| **ENSI ↔ ИС контракты (delivery/order)** | **РУБЛИ.копейки (decimal, 2 знака, округл. вверх)** — ЦЕЛЕВОЙ канон (12987) | по факту местами едут копейки (11196/14721) — баг не везде закрыт |
| **OMS `/order/create`, `/logistics/*`** | **рубли** (ждёт по канону) | суммирует items, сверяет с totalCost → `InvalidateTotalCost` при рассинхроне |
| **discount server (WWWDKMVC `/api/Query`)** | **РУБЛИ** (decimal-строки `"1299.00"`, ПОДТВЕРЖДЕНО) | `Price/Summ/Nominal/Val(type=2)` = рубли verbatim-строки; `clients/discount` хранит как `string`, не float |
| **site / mobile (отображение)** | копейки→делят на 100 при показе | фронт-формат (вне нашего контура), но влияет на то, что приходит на commit |

> Округление: канон — **вверх (ceil)** до 2 знаков. Float здесь = источник копеечных расхождений → НЕ использовать float для денег.

### Квирки форматов в реальных ответах ИС (`basket/current`, 2026-05-30)

В одном payload `GET /api/v3/basket/current?packageIsSelected=true` деньги едут **разными типами**:
- `price: 3098` — number (₽);
- `courierSum: "1500"` — **строка** (₽);
- `pickupSum: ""` — **пустая строка** (не `0`, не `null` — «нет значения» закодировано пустой строкой);
- `bonusSum: 0`, `bonusBalance: null` — number / null;
- `priceSum` в позициях: number (выбранный размер, qty=1) | `0` (qty=0) | `null` (не-current размеры);
- `oldPrice`/`oldPriceSum`/`discountRate`: преимущественно `null`.

То есть кроме копейки↔рубли есть **второй класс**: number vs строка vs пустая-строка vs null для одного смыслового «деньги». Парсер нового checkout на границе ИС обязан принимать все эти формы и нормализовать в `Money int64` копейки (`""`→0/absent, строку→parse, number→×100). **На выход — единый тип** (json.Number с 2 знаками по канону), никогда не плодить этот зоопарк.

## Политика для нового checkout (правка дизайна)

1. **Внутреннее представление денег = `int64` копейки + тип `Money`.** Никакого `float64` для сумм/цен/скидок/итогов. (Правит §2/§5/§6 спеки, где было `float64`/`number,double`.)
2. **Единица известна на каждой границе клиента** (adapter нормализует вход→`Money` копейки):
   - `clients/offers` → копейки int → `Money` 1:1.
   - `clients/starfish-oms` (logistics/order) → **рубли-decimal**: на ВХОДЕ парсить рубли→копейки (×100, аккуратно с дробью), на ВЫХОДЕ (order/create payload) конвертировать копейки→рубли-decimal **по канону (2 знака, округл. вверх)**.
   - `clients/discount` → **РУБЛИ** decimal-строки (`string`, не float; ПОДТВЕРЖДЕНО) → адаптер парсит → копейки.
2a. **Тип денежного поля В КЛИЕНТАХ — НЕ `float64`** (правило флота): JSON-провод (OMS/ENSI шлют число) → **`json.Number`** (oapi-codegen `x-go-type: json.Number` + import `encoding/json`; число на проводе, lossless-декод, без float-арифметики). XML-провод (discount) → **`string`** (verbatim). `type: string` в OpenAPI для JSON-числа НЕЛЬЗЯ — декод числа в Go-string падает. **Координаты (lat/lng) — НЕ деньги, остаются `float64`.** Адаптер checkout парсит json.Number/string → `int64` копейки (на выход: int64 копейки → json.Number с ровно 2 знаками по канону). _Текущий `starfish-oms` v0.1.0 — все деньги `float64` → подлежит правке (см. ревью)._
3. **Checksum / two-phase-truth — в копейках (целые).** Сверка `totals_checksum` и пересчёта — сравнение `int64`, без float-эпсилон. Это убивает класс `InvalidateTotalCost`-by-rounding.
4. **Один payload — одна единица.** В OMS `/order/create` ВСЕ денежные поля (`items[].price`, `discount`, `totalCost`, `deliveryCost`) — в одной единице (рубли-decimal по канону). Никаких «items в копейках + totalCost в рублях» (корень 14721).
5. **Скидку всегда пере-выводить** перед сверкой (re-quote discount), иначе «сумма без скидки vs со скидкой» (второй дефект 14721).
