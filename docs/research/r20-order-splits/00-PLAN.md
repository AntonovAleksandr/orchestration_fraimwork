# R-20 «Сплиты заказов» — мастер-план исследования

**Цель:** для доработки фичи «Сплит заказов» (Confluence `108057394`, Jira `OPSOMN-343`) —
скрупулёзно по доменам сверить **as-is живой контур** (OMS / OTS / ИС / чекаут / скидки / 1С / DWH / фронт /
admin / уведомления) с **требованиями R-20** (`00-requirements-r20.md`), зафиксировать **разрывы**, затем
спроектировать **to-be** и поэтапный план внедрения.

**Почему многосессионно:** доменов 13 + синтез; каждый требует чтения кода (`platform/*`) + BP-доков + БД-проб +
Confluence/Jira/логов. За одну сессию контекст переполнится. Поэтому **1 домен = 1 стадия = 1 файл-находок**
в `stages/`, плюс общий накопительный `EVIDENCE-LEDGER.md`.

---

## 1. Метод (одинаковый для каждой стадии)

Каждая стадия даёт `stages/stage-NN-<domain>.md` по `TEMPLATE-stage.md`:

1. **As-is (живая правда).** Как РЕАЛЬНО работает: код `platform/*` + `docs/bp/*` + `docs/research/*` +
   Confluence + Jira + **факты из БД** (`data_pg_query`, только SELECT+LIMIT) + логи.
2. **R-20 to-be (требование).** Какие `FR-NN` из `00-requirements-r20.md` относятся к домену; что должно быть.
3. **Gap-матрица.** Построчно: 🟢 есть/паритет · 🟡 частично/doc-only · 🟠 заглушка/обходной путь · 🔴 нет +
   **упущенные нюансы** (то, что выглядит готовым, но тихо ломает БП).
4. **Evidence.** file:line, результат `data_pg_query`, Confluence page_id, Jira key, log trace_id.
5. **Открытые вопросы + acceptance-gates** (→ агрегируются в Stage 14).
6. **Resume pointer.** Что не доделано, с чего продолжить.

Каждая находка дублируется одной строкой в `EVIDENCE-LEDGER.md`.

### Правила работы с источниками (усвоено в surf-mini-rewrite)
- **Код:** перед поиском по `platform/*` — `./scripts/sync-platform-repos.sh <platform>`.
- **⚠️ «0 совпадений» НЕ доказывает отсутствие.** Grep/Glob молча не ищут по `platform/`; `rg` от родительской
  папки с вложенными git-репо даёт ложноотрицания. **Скоупить `rg` к конкретному подкаталогу** (напр.
  `.../integration/www`, `.../gloriaots/src`, `.../starfish24/core/Order`) и подтверждать `Read`.
- **БД:** только SELECT + LIMIT; `*-stage` для формы данных, `*-prod` для объёмов/реальных значений. Не писать.
- **Логи:** для рантайма/трассировки; цитировать trace_id.
- **Confluence/Jira:** цитировать page_id / issue key; Confluence может быть устаревшим (отмечать confidence).
- **Дизамбигуация:** «Сплит заказов» ≠ «Яндекс.Сплит» (оплата) ≠ «Многоместные отправления» — см. README.
- **Не дублировать** BP-доки — ссылаться на `docs/bp/*`; в research только дельта.

## 4. Протокол сессии (как продолжать)

1. Прочитать `EVIDENCE-LEDGER.md` (что найдено) и §2 (где остановились — Progress tracker ниже).
2. Открыть незакрытую стадию / начать следующую по порядку.
3. Синхронизировать нужные `platform/*` (делает **оркестратор**, не субагент).
4. Работать по `TEMPLATE-stage.md`; писать в `stages/stage-NN-*.md` + строки в ledger.
5. В конце — обновить **Progress tracker** и **Resume pointer** в файле стадии.

### Делегирование субагентам (правила)
- Использовать доменных агентов: `oms-researcher`/`oms-navigator`, `integration-researcher`,
  `ensi-researcher`, `site-researcher`, `mobile-researcher`, `gloriaots-researcher`, `logs-detective`,
  `gitlab-investigator`. Тяжёлые стадии дробить на под-стадии (как 9→9a/9b в surf).
- Синк платформ — оркестратор. Экономия контекста: Grep/Glob для поиска, Read нужных диапазонов,
  лимит MCP (~5 pg / ~2-3 confluence / ~1-3 logs), вывод ~150-220 строк.
- DB-first для крупных вопросов (объёмы, существующие таблицы split/отправлений).
- Один субагент пишет только свой `stages/*.md`; ledger приземляет оркестратор после ревью.
