# Передача работы: WB FBS, состояние на 2026-08-20

Продолжение `HANDOFF-2026-08-19.md`. Повторное ревью hardening'а (по e89c7e5)
дало GO для sandbox и NO-GO для пилота с живыми складскими операциями — список
P1 ниже закрыт в этой сессии. Изменения поверх e89c7e5, не закоммичены.

## Закрытые P1 ревью 2026-08-20

**Идемпотентность создания поставок (добивка Р5).**
- Имя поставки теперь несёт внутренний `supply_id` (`GJ LC-1 → 206844 … #123`,
  и у преемника при Ship тоже): коллизия имён невозможна, adopt-by-name
  больше не может усвоить чужой WB ID. Имя строится внутри mkCmds — supply_id
  известен только после INSERT planned-строки.
- Создание преемника в `Ship.moveOn` тоже идёт через adopt-or-create
  (`adoptSupplyByName`, лимит списка поднят до 1000 — потолок страницы WB).
- `POST /supplies` больше не ретраится внутри клиента по таймауту/5xx/сети:
  `doOnce` — исход таких попыток неизвестен, повтор плодил дубль внутри одного
  вызова. Ретраится только 429 (rate-limit = гарантированно неисполненный
  запрос) — без этого песочница кладёт create_supply на первом же 429.

**Один владелец deliver.**
- `deliverSafetyNetDelay` 2 мин → 10 мин: ретраи клиента (5 × до 60 с
  таймаута попытки) больше не пересекаются с outbox-страховкой.
- Outbox-хендлер `deliver` для draining-поставки сначала сверяется с WB
  (`GetSupply`: done/closedAt) — уже отгруженная поставка пропускает PATCH и
  доезжает до closed+QR (`finishDeliver`).
- Синхронный `Ship.deliver` при ошибке PATCH сверяется с фактом
  (`deliveredInWB`): WB отгрузил, ответ потерян → успех, а не ошибка складу.

**Монотонные терминальные статусы.** SQL-гарды в `SetGJStatus`,
`AdvanceAfterReserve` (поздний reserve не ставит и export), `SetKIZBound`:
нетерминальная цель не перетирает shortage/canceled/sold; терминальная цель
перетирает всё, кроме sold. Хендлеры reserve/export/complete/bind_kiz —
no-op на терминальных заказах.

**Сериализация pack × Ship.** `packContext` держит `FOR UPDATE` на заказе и
строке поставки (отдельным SELECT: Postgres запрещает FOR UPDATE на
nullable-стороне LEFT JOIN). Ship ждёт коммита скана и наоборот. После
уточнения складского процесса от 2026-08-20 нормальный cut-over не создаёт
pull: отсканированный хвост физически уже складывается в следующую группу,
поэтому `MoveSupplyOrders`/`MoveSupplyOrder` переносят в преемника и заказ, и
его `pack_scan` с перенумерацией `seq`.

**Outbox: полное восстановление + fencing.** Бэкфилл `claimed_at = updated_at`
для legacy `sent` (миграция 20260820090000), reclaim смотрит
`COALESCE(claimed_at, updated_at)`. MarkDone/Reschedule/MarkFailed пишут
исход только текущему владельцу claim'а (`state='sent' AND claim_owner=…`,
applied=false → Warn, тик не валим).

**Kafka: самовосстановление после failed offset.** `stalledSet`: failed-
сообщение периодически прогоняется с backoff (5 с → 5 мин), успех снимает
блок commitGate и коммитит; чтение под таймером повтора, чтобы stalled не ждал
новых сообщений. Lag и массовый replay после одной ошибки уходят.

**Производительность/БД (второй слой ревью).**
- Индекс опроса — частичный `orders_status_checked_idx
  (status_checked_at NULLS FIRST, wb_order_id)` ровно под предикат; запрос —
  литералами (частичный индекс не матчится с параметром). Терминальная история
  в индекс не попадает. Тест синхронизирует предикат с core.WBTerminalStatuses
  и pg_get_indexdef.
- RetentionSweep — батчи по 5000 (ctid), индексы под каждый DELETE
  (миграция 20260820110000), чистка активных строк supply_orders принятых
  поставок (иначе orders не удалялись никогда). mark_withdrawals осознанно
  вечны (фискально), заказы с ними остаются — зафиксировано как исключение.
- `AddSupplyOrders` — одна транзакция (insert состава + link), плюс
  `RepointOrderSupply` дожимает ссылку в fallback recordComposition.
- Пул: `WB_DB_MAX_CONNS` (default 10), комментарий про × реплики × процессы.

**Эксплуатация.**
- Старт без DSN запрещён (`Validate`), скелетный режим — только с явным
  `WB_ALLOW_DBLESS=true`.
- Станционные эндпоинты за `WB_STATION_TOKEN` (bearer, constant-time); пустой
  токен = Warn при старте (для локали). /testui и test API и так за флагом
  `WB_TEST_HARNESS_ENABLED` (default off). Полноценная защита — ingress
  allowlist до станций: это к DevOps.

## Третий раунд ревью (тот же день, по diff поверх e89c7e5)

**P0 — Kafka: потеря второго failed-сообщения.** stalledSet/commitGate вели
одно failed-сообщение на партицию: N+1, упавший вслед за N, не сохранялся, а
после восстановления N коммит N+2 сносил необработанный N+1. Теперь
commitGate — множество failed offsets по партициям: offset O коммитится,
только если каждый failed строго позже O (непрерывно обработанный диапазон);
stalledSet хранит каждое failed-сообщение (дедуп по offset) и гоняет все по
backoff. Регрессионный тест — ровно сценарий N, N+1, N+2.

**Инварианты состава.**
- `RepointOrderSupply` дожимает ссылку, только если активная строка состава
  принадлежит ЭТОЙ поставке; чужая строка → permanent (projection conflict),
  а не молчаливое переставление заказа.
- `packContext` перечитывает `supplies.state` под блокировкой строки поставки
  (FOR UPDATE на nullable-стороне LEFT JOIN запрещён — отдельный SELECT … FOR
  UPDATE с чтением state): Ship, уведший поставку в draining, пока скан ждал
  блокировку, теперь отбивает скан supply_closed. Тест с реальным
  межтранзакционным ожиданием.
- `MoveSupplyOrders` переносит только реально закрытые строки (closeQ …
  RETURNING → insert/repoint/pack_scan по факту): отменённый между чтением и
  переносом заказ не воскресает в преемнике.
- `reserve` и `AdvanceAfterReserve` — строго из `imported`: поздний дубль при
  picked/kiz_bound/accepted не звонит в OTS и не откатывает статус.

**Стабильное имя поставки.** Из имени убрано время: `GJ LC-1 → 206844 #123`
(преемник: `GJ LC-1 #123`). Имя с минутой ломало adopt-or-create — повтор в
другую минуту искал другое имя и создавал дубль. Имя формирования записано в
outbox-payload в той же транзакции, что и planned-строка, — повтор всегда
ищет то же имя.

**Эксплуатация (жёстко, в Validate).**
- `WB_ALLOW_DBLESS` — только с `APP_ENV=local`.
- `WB_STATION_TOKEN` обязателен везде, кроме `APP_ENV=local`.
- `WB_TEST_HARNESS_ENABLED` требует sandbox-URL в `WB_API_BASE_URL`.
- `WB_PRINTER_ALLOWLIST` (через запятую) — серверный справочник адресов
  принтеров для pack-scan; пустой = без ограничений (локаль).

**Зафиксировано, но сознательно не чинится в этом раунде:** orders с
mark_withdrawals не удаляются никогда (фискальный журнал — политика хранения
за маркировкой); новые индексы создаются обычным CREATE INDEX — накатывать,
пока база маленькая, на проде при большом объёме понадобится окно/CONCURRENTLY.

## Четвёртый раунд и уточнение реального cut-over (тот же день)

**Коррекция ошибочного решения `packed_leftovers`.** Промежуточный вариант
блокировал поставку и требовал искать отсканированный остаток в коробах. После
уточнения процесса это удалено как операционно недопустимое. Конвейер не
останавливается: в момент закрытия A оператор физически переключает укладку на
новую группу, а финальный список 1С определяет состав A. Всё, что отсутствует
в списке, штатно становится хвостом B — независимо от наличия скана.

Реализованный порядок:

1. общий per-supply lock сериализует `Ship` с уже начавшимся `add_orders` и с
   повторным параллельным `Ship`;
2. `OPEN → SEALED` фиксирует cut-over сразу по сигналу 1С; формирование больше
   не добавляет задания в A, но `pack-scan` в `SEALED` продолжает работать;
3. после seal перечитывается состав и вычисляется незадекларированный хвост;
4. хвост сначала переносится в поставку B на стороне WB;
5. одной DB-транзакцией переносятся `supply_orders`, `orders.supply_id` и
   существующие `pack_scans`; `seq` дописывается после хвоста B под общим с
   обычным сканом advisory-lock;
6. контрольный `orders/meta` выполняется уже после переключения хвоста, поэтому
   его длительность не оставляет новые сканы логически в A;
7. только после переноса и проверки A переходит `SEALED → DRAINING → CLOSED`,
   выполняются `deliver` и получение QR.

Нормальный cut-over не создаёт deviation/pull и не требует повторного скана.
Pull остаётся отдельным исключительным процессом для фактической отмены уже
упакованного задания.

**P0 — точные sandbox-гварды.** `WB_TEST_HARNESS_ENABLED` требует точные
sandbox-хосты всех трёх API (marketplace/content/prices), парсинг URL, не
substring. Есть тесты config — их не было вообще.

**P0 — printer allowlist обязателен вне local.** `WB_PRINTER_ALLOWLIST`
пустой вне `APP_ENV=local` — ошибка старта: иначе владелец bearer-токена
заставляет сервис дозваниваться до произвольного внутреннего TCP-адреса.

**P1.**
- `RepointOrderSupply`: штатный идемпотентный повтор (строка состава в той же
  поставке, ссылка корректна) — applied=true через RETURNING-форму, а не
  permanent. Permanent — только чужая активная строка.
- Имя поставки — единая каноническая `core.SupplyName(склад, офис, id)` для
  формирования и преемника Ship: два создателя больше не плодят два POST и
  WB-orphan. SuccessorSupply переиспользует planned-строку ключа; Ship —
  синхронный создатель с adopt-or-create по стабильному имени; смерть между
  шагами лечится повторным нажатием (имя то же).
- Kafka: пока stalledSet не пуст, fetch остановлен — failed-сообщения
  лечатся по backoff, память ограничена, порядок коммитов простой (commit
  только непрерывного диапазона через commitGate-множество).
- Validate разведён по профилям: `Validate()` — база для wbstatus/wbgoods,
  `ValidateService()` — HTTP-приложение (станция/принтеры/харнесс). wbstatus
  больше не требует WB_STATION_TOKEN.
- Тик воркера ограничен `Loop.Timeout` (default 10 мин, wb_stocks — час):
  исчерпание пула больше не вешает цикл навсегда — ошибка и backoff.

**Подтверждено ревью как закрытое (3-й раунд):** Kafka N+1, fresh-state lock
pack×Ship, reserve из imported, RETURNING-перенос, outbox backfill+fencing,
транзакционный AddSupplyOrders, индекс опроса, батчевый retention, dbless
только local.

Проверки первоначального раунда: полный сьют зелёный (вкл. config/Validate и
add_orders repeat), `go test -race ./...` — PASS, `make e2e-sandbox` — PASS

## Осознанные остатки (к следующему слою)

- Pull-completed остаётся отдельной задачей только для исключений вроде отмены
  уже упакованного заказа; к штатному cut-over поставки этот flow больше не
  относится.
- Синхронный Ship на поставке 20 000 заданий делает до 200 вызовов
  `orders/meta` и дополнительные batch-вызовы переноса. Timeout сервиса и
  `.env.stage` подняты с 30 секунд до 10 минут, но до пилота надо отдельно
  подтвердить не меньший timeout ingress и клиента 1С. Долгосрочная альтернатива
  — durable async job (`202 + polling`).
- Load-тест на 1,8+ млн строк и бенч опроса/retention — перед промышленным
  потоком, как и планировалось.
