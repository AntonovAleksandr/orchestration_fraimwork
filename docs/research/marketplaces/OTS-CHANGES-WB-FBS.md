## 1. Роль OTS в потоке WB FBS

WB Connector — **ещё один клиент того же API OTS**, которым сегодня пользуется
Integration Service. Поток внутри OTS переиспользуется без изменений:

```text
Connector → POST /v2 (ProcessStarfishRequest), action_type=ORDER_TO_CHECK
  → ON_VALIDATION: резерв (BalanceRepository.ReserveAsync)
  → WAIT_EXPORT_TO_WAREHOUSE → event bus
  → экспорт: WMS (ECOMAUF-телеграммы) + регистр 1С ЛЦ
    (OneS8ApiClient → http-сервис 1С8 напрямую, минуя ApiGW)
  → статусы склада: OrderEvents ← ECOMAUFSTAT/ECOMAUPSTAT
  → публикация статусов: Kafka `…ecom.fct.order-status…` → Integration
  → паллетная отгрузка → 1С → wms_shipment → DELIVERING (Stage 17)
```

Что подтверждено кодом:

- Вход: `GloriaOTS.Web/Controllers/OrderController.cs:133` — `POST /v2`,
  операции `ORDER_TO_CHECK / ORDER_TO_PICKING / ORDER_TO_PICKUP /
  ORDER_TO_EDIT` (`OrderController.cs:80-86`). `source` берётся из тела и лишь
  дефолтится в `Starfish` (`OrderController.cs:177`, `??=`) — контракт готов
  принять явный source.
- В теле уже есть `guid` (`OrderController.cs:148`), он становится
  `ReserveEventId` резерва (`Handlers/ORDER_TO_CHECK/OnValidation.cs:133`).
- Транспорт маршрутизируется switch'ем по enum `ShipmentService`
  (`Services/ShipmentServiceFacade.cs:63+`, отмена `:158+`); текущие значения —
  `Constants/ShipmentService.cs:3-13`.
- Статусы публикуются в **Kafka** (`StarfishSenderSettings`: brokers/topic;
  `OrderStatusNotifiers/Starfish/Sender*`), консюмит Integration и толкает в
  OMS (`MP-WB-FBS-078`: топик `…ecom.fct.order-status…`).
- Регистрация в 1С: `WmsSync/OneS/OneSService.cs:50-86` — поля строковые,
  `idd = GetPrefix() + order_id.PadLeft(10)`; 10-значный номер помещается без
  усечения.

Чего Connector от OTS **не** требует: работы с WB API, поставок, стикеров,
`sgtin`, полного КИЗ (снимается на станции, `MP-WB-FBS-054`), новых статусов
WMS. **Кода WMS задание не касается вообще** — см. §3, правка 3: новая ТК для
WMS/1С — строка в мастер-данных, а не разработка.

## 2. Почему «совсем без правок» не получается

### 2.1. `source`: все существующие значения ломаются

Enum: `Hybris, Starfish, RSG, Unknown, SPL`
(`ApplicationCore/Constants/OrderSource.cs:3-9`). `WB_FBS` нет.

| Вариант | Что произойдёт | Код |
|---|---|---|
| `source=Starfish` | статусы фантомных для OMS заказов уедут в OMS-контур; в 1С заказ ляжет с префиксом `0000352` как обычный Starfish → штатная сверка OMS↔1С (`ApiGW /api/Starfish/1CEcommOrdersList`) будет всплывать фантомами на каждом прогоне; DWH/финансы/возвраты посчитают канал обычным eCom | `StarfishOrderStatusNotifier.cs:36`; `OTSRequestParams.cs:52-61` |
| `source=Unknown` | уведомлений нет, но `GetPrefix()` вернёт `0000337` — заказ WB попадёт в 1С **как заказ Hybris** | `OTSRequestParams.cs:52-61` |
| новый `WB_FBS` без публикации статусов | события вечно крутятся в выборке `!Notificated`: skip-лист покрывает только `SPL/Unknown/ORDER_FROM_SPL/Hybris`, notifier для чужого source возвращает `null` | `OrderLaterNotificationService.cs` (skip-блок); `StarfishOrderStatusNotifier.cs:71` |

Вывод: нужен честный `WB_FBS` + публикация его статусов (правки 1, 2, 4).

### 2.2. Транспорт: без своей ТК заказ падает

У заказа WB нет внешней ТК. Неизвестное значение транспорта падает в
switch-выражении фасада (`ShipmentServiceFacade.cs:63` — нет ветки → исключение).
Ранее предлагалось переиспользовать `OWN=5`, но там своя мина: `GetClientId`
для `OWN` + курьерского типа кидает `NotImplementedException`
(`OneSService.cs:98`).

**Новая ТК решает обе проблемы сразу**: для `transport_id ≠ 5` метод
`GetClientId` не бросает исключение — клиент определяется по складу
(`OneSService.cs:101-108`), а ветки фасада для новой ТК пишутся без внешних
вызовов (по образцу `OWN`: `BuildForUnknownShipmentService`,
`ShipmentServiceFacade.cs:76`).

### 2.3. Отмена

С новой ТК отмена идёт стандартным планом (`OrderHandlersManager.cs:153-155`:
не-`OWN` → `CreateCancelingContextStandard`), внешняя ТК не вызывается, если
ветка отмены в фасаде (`:158+`) для новой ТК — no-op. Вопрос семантики
C&C-плана из версии 2026-07-31 снят.

### 2.4. Резерв: повтор команды создаёт второй резерв

`ReserveEventId` приходит из `guid` запроса (`OnValidation.cs:133`), но не
проверяется: в схеме `Reserves_*` уникальность только по identity `Id`
(`Database/SqlDeploy/tables/Reserves_ONES_MOSCOW.sql`), вставка безусловная.
Connector ретраит команды через outbox; повтор `ORDER_TO_CHECK` после таймаута
= второй резерв (`MP-WB-FBS-010`).

## 3.1. Правки Integration (зона e-commerce, вне этого задания)

Выполняет владелец коннектора; перечислены здесь, чтобы у команды OTS была
полная картина канала статусов. **Это P0: без фильтра пилот нельзя включать —
см. фактическое поведение ниже.**

Как консюмер ведёт себя сегодня (проверено по коду 2026-08-03,
`Exchange/Services/V1/Common/TransferService.php:1981+`,
`Processors/V1/Order/TransferOrderStatusProcessor.php`,
`Daemons/V1/Order/OrderStatusDaemonCommand.php`): демон **не смотрит на
`source` вообще**. Он валидирует наличие `order_id`/`order_status` и сразу
дёргает `OmsClient::getClientOrderFull(order_id)`. Для заказа WB, которого в
OMS нет, ответ придёт не-5xx (`< 500` → без RETRY), затем разбор `$order['items']`
упадёт, `Throwable` поймается в `ERROR` (`:2302-2312`) и сообщение уйдёт в
`REJECT`. То есть топик не встанет и вечного цикла не будет, но на каждое
статусное событие WB получим бесполезный запрос в OMS плюс ERROR-трейс: при
20 тыс. заказов в день и несколько статусов на заказ это десятки тысяч
отбракованных сообщений в сутки в общем eCom-потоке.

Отсюда правки:

1. **Фильтр по `source` — первым делом, до вызова OMS.** Ветка ставится сразу
   после валидации `order_id`/`order_status` и **до**
   `OmsClient::getClientOrderFull` (`TransferService.php:~1997`, вызов OMS на
   `:1999`). `source = 5` (`WB_FBS`) → `POST /api/v1/ots/order-status` в
   Connector (реализован; тело — конверт `OTSOrderResultV2` как есть, без
   преобразований), `OK` при 2xx и `RETRY` при недоступности; `1` (`Starfish`) → в OMS, как
   сегодня. Сравнение числовое: в payload ordinal, не строка. Значение вынести
   константой в `Service/Consts/Enums` — отдельного enum для `source` в
   Integration сейчас нет, магическому числу в коде не место.
2. **Явный guard по неизвестному `source`: не звать OMS, залогировать и
   отбраковать.** Сегодня любое новое значение `source` в OTS — не только наше —
   автоматически превращается в поток запросов в OMS и ERROR-трейсов на стороне
   Integration. Две строки над основной веткой закрывают класс проблемы целиком,
   а не только случай WB.
3. Резервный ключ маршрутизации, если по какой-то причине `source` в сообщении
   отсутствует, — диапазон номера `31XXXXXXXX` (ADR). Как основной не
   используем: поле в payload есть.

**Порядок выката — фильтр уезжает в прод раньше правок OTS.** Пока OTS не
публикует `WB_FBS`, новая ветка не срабатывает ни разу, поэтому релиз Integration
безопасен в любой момент и его можно делать заранее. Обратный порядок даёт ровно
тот шум, ради устранения которого правка и делается: десятки тысяч бесполезных
запросов в OMS и ERROR/REJECT в общем eCom-потоке за то время, пока Integration
догоняет релизом. Последовательность: фильтр Integration → правки OTS (1–4) →
включение пилота.

Контракт приёмника со стороны Connector: идемпотентность по `guid` (первичный
ключ), поэтому переотправка одного и того же сообщения безопасна. Ответы: `200` —
сообщение принято, включая повтор и случай «номер заказа не наш» (последний
сохраняется в аудит, но ретраить его бессмысленно); `400` — нет `guid`,
`order_id` или `order_status`; `500` — только сбой записи, то есть тот случай,
когда переотправка действительно поможет.

Полезное из живого сообщения для реализации приёмника: конверт
`EventName: "OTSOrderResultV2"`, `guid` используется как trace id
(`TransferOrderStatusProcessor::changeTraceId`), `business_unit_id` — ИДД
склада 1С, статусы приходят и на заказ (`order.order_status`), и на позицию
(`goods[].order_status_good`), марка в `goods[].good_id_mark` — **13-символьный
serial** (`5AA0086309574`), не полный КМ: подтверждает `MP-WB-FBS-024` и
решение снимать полный код на станции.

## 4. Контракт вызова со стороны Connector

`POST /v2` (`ProcessStarfishRequest`), тело `OTSOrderParams`:

| Поле | Значение | Примечание |
|---|---|---|
| `action_type` | `ORDER_TO_CHECK` (создание + резерв), далее штатные | `OrderController.cs:80-86` |
| `source` | `WB_FBS` | правка 1; контракт уже принимает явный source (`??=`) |
| `order.order_id` | `gj_order_id`, блок `31XXXXXXXX` | ADR 2026-07-31; типы по маршруту проверены (`MP-ID-007`) |
| `business_unit_id` | ИДД ЛЦ, **17 знаков** (`00005550015437530`) | обязателен: читается через `GetProperty`, при отсутствии — исключение. v2 сворачивает его в свой `id_warehouse` (`5501`) через `WarehouseTypeHelper.FromNewToOldWarehouse`; формат подтверждён логами прода 2026-08-03 |
| `order.goods[]` | по артикулу | v2 транслирует артикул ↔ ШК |
| `delivery.transport_id` | id новой ТК «Wildberries» | правка 3; значение сообщает команда OTS |
| `delivery.type` | курьерский | с новой ТК `GetClientId` определяет клиента по складу |
| `guid` | **стабильный** event id заказа | становится `ReserveEventId`; основа идемпотентности (правка 5) |

**Вызовов от Connector ровно два, и это протокол, а не наше решение**
(трассировка по коду + логи прода 2026-08-03, заказы `2010808273`/`2010843731`):

1. `ORDER_TO_CHECK` + `order.order_status = ON_VALIDATION` — проверка остатка и
   резерв. Первый вызов обязан быть именно этим: в `HandleRequest` при
   отсутствии предыдущего события и другом статусе летит `ArgumentNullException`.
2. `ORDER_TO_CHECK` + `order.order_status = WAIT_EXPORT_TO_WAREHOUSE` — запуск
   передачи. В проде эти два вызова идут с интервалом ~8 секунд.

Дальше OTS ведёт заказ **сам**: `SendToNextHandler` публикует следующий статус в
свою RabbitMQ (`Publish nextStatus ORDER_REGISTER_TRANSPORT for order …`),
`OrderEventHandler` подхватывает и кладёт обратно в тот же `HandleRequest`,
и так до `ORDER_REGISTER_WAREHOUSE` → `TgwCreateOrderEvent` в WMS. Цепочка
запускается **после** отправки HTTP-ответа (`Response.OnCompleted`).

Два следствия для контракта. Статус, по которому идёт маршрутизация, — это
`order.order_status`; заголовочный `order_status` живой вызывающий оставляет
пустым, и Connector делает так же. Идемпотентность обеспечивает `guid`: первая же
проверка в `HandleRequest` ищет событие с таким `Id` и при находке возвращает
сохранённый результат без повторного выполнения — поэтому наш `guid` выводится
детерминированно из пары «заказ + шаг».

Статусы обратно: Kafka-топик статусов → Integration → HTTP Connector (§3.1).

## 5. Порядок и приёмка

0. **Фильтр по `source` в Integration (§3.1) — раньше всего остального.**
   Выкатывается силами e-commerce, до правок OTS: на текущем трафике ветка не
   срабатывает, зато к моменту первых `WB_FBS`-событий канал уже готов.
1. Правки 1–3 (+3') — один MR + настройка мастер-данных; без них не работает
   ни один заказ.
2. Правка 4 — вторым MR; на этот момент маршрутизация в Integration уже в проде.
3. Правка 5 — до production-пилота; 6–7 — гигиена, вне критического пути.

Приёмочные проверки (SIT, тестовый контур OTS/WMS/1С + Integration):

- заказ `source=WB_FBS` с новой ТК: регистрируется в 1С с правильным префиксом
  (не `0000337`/`0000352`), уходит в WMS; фасад не падает на неизвестной ТК;
- граничный номер `3100000001` доезжает до 1С/WMS неискажённым (фиксация ADR);
- повтор `ORDER_TO_CHECK` с тем же `guid` не создаёт второй резерв;
- статусы `PICKING/ORDER_PICKUP/SUSPENDED` доезжают до Connector через
  Kafka → Integration; события в OTS помечаются `Notificated`, backlog не
  растёт; **в OMS не уходит ни одного запроса по WB-заказу** (проверять не
  только отсутствие callback'ов в OMS, но и отсутствие вызовов
  `getClientOrderFull` по номерам `31…` в трейсах Integration — именно они
  дают ERROR/REJECT без фильтра);
- ordinal'ы существующих `source` не изменились: сообщения `Starfish`
  по-прежнему приходят с `"source": 1` и обрабатываются как раньше;
- сообщение с заведомо неизвестным `source` (синтетическое, на тестовом контуре)
  не даёт ни одного вызова OMS и пишет один внятный лог вместо `Throwable`;
- отмена до и после отбора: резерв снят, внешняя ТК не вызвана, стандартный
  план отмены проходит;
- сверка OMS↔1С (`1CEcommOrdersList`) не показывает WB-заказы как фантомы
  Starfish (следствие честного префикса).

## 6. Открытые вопросы к команде OTS

1. Какой числовой id получит ТК «Wildberries» в `ShipmentService` и в
   справочниках 1С/WMS? Кто и в какие сроки заводит carrier row на каждом ЛЦ?
   **Блокирует пилот:** адаптер Connector уже читает id из конфигурации
   (`OTS_TRANSPORT_ID`) и при нулевом значении отказывается отправлять заказ,
   чтобы не зарегистрировать его в ТК номер 0.
1'. Сопоставление склада продавца WB (`warehouseId` сборочного задания) с ИДД
   логистического центра GJ. Нужен перечень пар на пилотные ЛЦ: Connector
   принимает его как `OTS_WAREHOUSE_MAP` и паркует заказ с несопоставленного
   склада, а не отправляет на склад по умолчанию.
2. ~~Несёт ли сообщение Kafka-топика статусов поле `source`?~~ **Закрыто
   2026-08-03:** несёт, как числовой ordinal (`"source": 1` = `Starfish`).
   Вместо этого просьба: добавить `WB_FBS` строго в конец enum с явным
