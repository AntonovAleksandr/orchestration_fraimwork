## 2. Что добавлено за сессию

**Цикл остатков (`wb_stocks`).** Один Loop: инкремент по курсору
`sync_state/ots_stocks` + полная сверка раз в `WB_STOCKS_FULL_INTERVAL_SECONDS`
(сутки) — обязательна, т.к. инкремент OTS не видит создание резерва. Полная
сверка зануляет сопоставленные баркоды, отсутствующие в ответе OTS (иначе ВБ
держит протухший остаток бесконечно). Батчи ≤1000, валидация amount до отправки
(4XX у ВБ = ×10 тарификации), контрольное чтение `GetStocks` после каждого
батча, расхождение → отклонение. Ручной прогон: `POST /api/v1/test/stocks/sync`
на стенде. Проверено живьём на стейдже+песочнице: 467 927 строк универсума
прочитано, отправка и контрольное чтение прошли (429 песочницы ловится ретраем).

**Реестр отклонений.** Таблица `deviations` (миграция `20260814153612`), upsert
по открытой записи `(kind, ref)`. Виды: `unmapped_barcode`, `stock_mismatch`,
`stock_sync_error`, `kafka_status_rejected`. UI/чтения наружу нет — только запись.

**Партиционирование журналов.** `wh_events`, `order_events`, `outbox` —
RANGE-партиции по месяцам (миграция `20260814173700`), DEFAULT-партиция как
страховка. Maintenance-цикл (раз в сутки): дроп партиций старше
`WB_RETENTION_DAYS` (90) + катящийся горизонт +3 месяца вперёд. Ловушки,
закрытые в коде: identity на партициях недоступен до PG 17 (у нас 15.4) —
явные sequence; `DETACH CONCURRENTLY` несовместим с DEFAULT-партицией до PG 17 —
обычный DETACH; дедуп по `(key, timestamp)`-констрейнту не работает (у повтора
другой timestamp) — вставки через `WHERE NOT EXISTS` + `pg_advisory_xact_lock`.
Прикидка роста: events-журналы ~100–160 ГБ/год при 20 тыс. заказов/сутки, outbox
~30–50 ГБ/год, остальное мелочь. `mark_withdrawals` НЕ дропать — фискально
значимо, политика хранения — вопрос маркировке.

**Консьюмер статусов Kafka (`cmd/wbstatus`).** Отдельный процесс, kafka-go
v0.4.46 (первая Kafka-зависимость в проекте). Топик
`{env}.all.ecom.fct.order-status-wb.0`, group `wbconnector-status`. Парсер
конверта `OTSOrderResultV2` общий с HTTP-эндпоинтом (он сохранён для ручного
проигрывания). Poison/исчерпанные ретраи → `kafka_status_rejected`, offset
коммитится. Закрыт долг монотонности `gj_status`: шкала `StatusMoveAllowed`,
downgrade пропускается, терминальные перетирают. E2E smoke на локальной Kafka
пройден; подключение к стейдж-кластеру подтверждено (сообщений пока нет —
заказов FBS_WB на стейдже нет).

**COMPLETED в OTS по `sold`.** `ApplyStatuses` при `sold` ставит outbox
`ots:complete` в той же транзакции, что и вывод марки. Адаптер:
`ORDER_TO_PICKING` + `COMPLETED`, стабильный guid, повтор (454) = успех. После
успеха заказ в новом терминальном `GJStatusSold` — из него не выходит ничего.
Гонки no-op'ятся (canceled/sold/без резерва). Резерв в OTS теперь снимается.

## 3. Решённые за сессию открытые вопросы

- **Метка `from` в WebGJISMP = `FBS_WB`** — подтверждено, уже в конфиге
  (`ISMP_FROM=FBS_WB`).
- **Kafka dev/stage без кредов:** bootstrap `10.190.3.31:9092`, PLAINTEXT, без
  SASL. Prod — отдельный вопрос к DevOps (учётка + ACL).
- **Архитектура фоновой работы:** непрерывные stateful-потоки — in-process
  циклы с writer-lease (advisory lock PG, active/passive, масштабирование =
  failover, т.к. лимит ВБ общий); разовые/редкие задачи — отдельные cmd
  (`wbgoods`, позже под k8s cron); Kafka-консьюмер — отдельный cmd без lease
  (координация consumer group, реплики ≤ партиций).
- **Модель статусов: один заказ — две оси.** `wb_status` (поллер WB) и
  `gj_status` (складская ось из Kafka) живут колонками в `orders`; истории —
  append-only журналы `order_events` и `wh_events`. Маппинга «наш статус →
  статус OTS» нет: пока заказ едет, OTS сам в `DELIVERING`; наша поверхность —
  два терминальных действия от оси WB (`sold` → COMPLETED, `cancel` →
  CANCELLING). Эхо `COMPLETED` из топика в lifecycle не мапим осознанно.

## 4. Ловушка конфигурации, пойманная на живом прогоне

`OTS_BASE_URL` с суффиксом `/v2` молча меняет контракт остатков: запросы
попадают на `BalanceV2Controller` (артикулы `sku_article`, timestamp строкой)
вместо v1 (барокоды). В `.env.stage` суффикс убран; при деплое проверить
`OTS_SERVICE_CLIENT_BASE_URL` в k8s. Записано в `TASK-ots-balance-client.md`
§4.5.
