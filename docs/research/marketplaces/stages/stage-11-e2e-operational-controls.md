# Stage 11 — сквозные operational/financial-контроли Ozon и WB

**Дата среза:** 2026-07-23  
**Статус:** complete-for-current-pass  
**Покрытие:** Jira + Confluence, без проверки production-баз, расписаний jobs,
логов, файловых каталогов и фактических документов закрытого периода  
**Уровни уверенности:** `confirmed` — прямо описано источником;
`high-confidence` — подтверждается несколькими связанными источниками;
`proxy` — описана реализация/задача, но production-выполнение не проверено;
`unknown` — подтверждения нет.

## 1. Главный вывод

Контур нельзя описать одной интеграцией `маркетплейс → 1С`. В доступных
источниках видны три разные цепочки контроля:

1. **Операционная:** заказ/отмена/продажа/возврат превращаются в цепочку
   `РК+ / РК- → РРН / ПН` в 1С.
2. **Поставочная:** перемещение и ПА сопоставляются с фактической приёмкой,
   затем создаются СП/ОИ, формируется УПД и контролируется его состояние в ЭДО.
3. **Финансовая:** отчёт площадки отдельно загружается или выбирается
   пользователем и сверяется с документами 1С в обе стороны.

На 2026-07-23 наиболее существенные открытые риски:

- **Ozon:** основной finance API заменён; новая загрузка `sales/accruals`
  находится на переносе в production, а два режима ручной сверки ещё
  адаптируются к изменённой с 2026-07-01 формуле суммы. Нельзя подтвердить, что
  новый финансовый контур уже целиком работает в production.
- **WB:** старый endpoint недельного отчёта отключён 2026-07-15; новая job на
  2026-07-22 ожидала внутреннего тестирования. При этом существуют отдельные
  незакрытые дефекты сверки: падение 1С на большом объёме и неверная привязка
  РРН к старой структуре РК.
- **Поставки Ozon:** новый процесс загрузки фактической приёмки и марок из
  XML УПД-2 согласован, но разработка приостановлена. Ozon supply API в найденном
  проектном документе прямо отклонён как источник фактического количества.
- **Формальное закрытие периода:** найденные документы описывают способы
  выявить расхождения, но не определяют единый обязательный gate вида
  «период закрыт», владельца его подписания и допустимые остаточные расхождения.

## 2. Термины и границы интерпретации

| Сокращение | Значение в найденных источниках |
|---|---|
| РК+ | `Резерв Клиента`, заказ/резерв |
| РК- | `Резерв Клиента` с видом операции «Возврат», в рассматриваемых процессах используется для отмены/невыкупа |
| РРН | расходная розничная накладная, реализация |
| ПН | приходная накладная, возврат |
| ПА | приёмный акт |
| СП | списание недостачи |
| ОИ | оприходование излишков |
| УПД | универсальный передаточный документ |
| ЭДО | электронный документооборот; в документах фигурируют СБИС и исторически Контур.Диадок |

Семантика документов подтверждается описаниями алгоритмов, но полная
бухгалтерская проводочная модель и юридическая роль каждого документа этим
проходом не проверялись.

## 4. Цепочка №1 — заказ, продажа, отмена и возврат

### 4.1 Ozon: подтверждаемая схема

```text
Ozon Orders/Departures
    → WebApi
    → внешняя обработка 1С ОбменOzon
    → РК+ (заказ)
    → РК- (cancelled / невыкуп)

Ozon Finance Accruals
    → WebApi api/Ozone/Accruals
    → ОбменOzon
    → РРН (продажа) / ПН (возврат)
    → ручная СверкаРеализацииOzon с отчётами Ozon
```

**Подтверждено:**

- `OPSMPC-1082`, closed 2026-07-21: в пакете Orders создаётся РК+, а при
  `status=cancelled` — отсутствующий РК-; уже существующий РК- повторно не
  создаётся.
- `OPSMPC-1060`, внутреннее тестирование завершено 2026-06-15: для ручной
  загрузки отмен сначала проверяется отсутствие sales-транзакций, затем статус
  `cancelled` в Departures, затем отсутствие РК- по `odid + ШК`. Только после
  трёх проверок создаётся РК-.
- `OPSMPC-1102`, closed 2026-07-17: WebApi оборачивает новый Ozon
  `finance/accrual/by-day`, фильтрует начисления уровня отправления и добавляет
  товарные/комиссионные атрибуты.
- `OPSMPC-1103`, «Перенос на прод», updated 2026-07-21: знак `sale_price`
  используется для выбора ПН или РРН; наличие документа проверяется по
  `gnumber + ШК`; при отсутствии основания автоматически восстанавливается
  цепочка `РК+ → РРН`, но восстановление `РРН → ПН` в тексте задачи ещё не
  было включено.
- `OPSMPC-1077`, closed 2026-06-05: Orders загружается страницами до
  `hasdata=0`, с передачей cursor следующему запросу.
- `OPSMPC-896`, closed 2025-11-10: пустой Departures больше не должен
  блокировать весь обмен; строка пропускается и логируется.

**Контроль полноты и идемпотентности:**

| Контроль | Тип | Статус доказательства |
|---|---|---|
| Переход по всем страницам Orders до `hasdata=0` | автоматический | `confirmed`, `OPSMPC-1077` закрыта |
| Переход по `last_id` в Accruals | автоматический | `proxy`: `OPSMPC-1103` только на переносе в prod |
| Проверка существования документов по бизнес-ключам | автоматический | `confirmed` как требование реализованных задач; production-данные не проверены |
| Пропуск пустого ответа без остановки всей пачки | автоматический + лог | `confirmed`, `OPSMPC-896` закрыта |
| Поиск и догрузка недостающего основания | автоматический для `РК+ → РРН` | `proxy`, новая версия ещё переносилась в prod |
| Восстановление основания `РРН → ПН` | отсутствующий/отложенный | прямо отмечено как не реализованное в `OPSMPC-1103` |
| Сверка Ozon → 1С и 1С → Ozon | ручной запуск обработки | `confirmed`, page `149765469` |

`page_id=149765469` описывает четыре ручных режима:

1. «Заказы со склада Ozon» — ежедневный источник по заказам;
2. «Отчёт по начислениям» — ежедневный источник для недельной сверки продаж,
   возвратов, отмен и невыкупов;
3. «Позаказный отчёт» — ежемесячная сверка продаж и возвратов, API или XLS;
4. «Продажи в СНГ» — ежемесячная сверка заказов/продаж СНГ.

Обработка формирует минимум три контрольных набора: «Нет в 1С», «Нет в Ozon»
и «Расхождения», то есть полнота проверяется **в обе стороны**, а не только
наличием данных площадки в 1С.

### 4.2 Ozon: незакрытая миграция суммы

С 2026-07-01 бизнес изменил сумму товара: вместо очищенного от комиссии
«Итого к начислению» используется `реализовано на сумму + выплаты по
партнёрской/лояльностной механике`.

- `OPSMPC-1111`, «Разработка», updated 2026-07-20: меняет сумму в позаказной
  сверке РРН/ПН.
- `OPSMPC-1116`, «В работе», updated 2026-07-21: добавляет сверку с вариантом
  отчёта по начислениям **в разрезе отправлений**; старый товарный вариант
  отчёта содержит прежнюю метрику и для продаж после 2026-07-01 признан
  неподходящим.
- `page_id=149765469` обновлена 2026-07-08 и ещё не содержит новый режим из
  `OPSMPC-1116`.

**Операционный вывод:** документы могли уже формироваться по новой логике
(`OPSMPC-1103` на переносе в prod), когда обе ручные сверки ещё не были
доведены до неё. До проверки production-версий и одного закрытого периода это
следует считать активным риском контрольного разрыва, а не подтверждённой
потерей денег.

### 4.3 WB: подтверждаемая схема

Полная первичная цепочка `заказ WB → РК+` в свежем источнике этого прохода не
восстановлена. Подтверждён следующий downstream-контур:

```text
WB финансовый API
    → jobs import_weekly_WB / import_weekly_WB_manual_with_dates
    → SSIS
    → hybris_import.dbo.wb_weekly
    → ручная обработка СверкаРеализаций1СВБ
    ↔ документы РРН / ПН в 1С7 WB
    → КорректировкаWB для создания/исправления документов по расхождениям
```

`page_id=55008219`, updated 2026-03-20:

- источник учётных документов — 1С7 WB;
- источник отчёта — `wb_weekly`;
- запуск сверки — **вручную**;
- строки WB сопоставляются с 1С по `srid/odid`, товару и периоду;
- проверяются количество, цена, сумма, клиент и другие реквизиты;
- сверка идёт в обе стороны и формирует «Нет в 1С», «Нет в WB»,
  «Расхождения»;
- «сторно возврата» меняет знак количества и суммы; строки одного дня
  агрегируются по `srid + товар`, чтобы не создавать дубли.

`page_id=165411281`, updated 2026-07-17:

- выгрузка начинается с `rrdId=0`;
- в следующем запросе передаётся последний `rrdId`;
- запросы повторяются до HTTP `204`;
- ряд числовых полей нового ответа приходит как string и должен быть
  преобразован перед записью в `wb_weekly`.

## 5. Цепочка №2 — поставка, приёмка, СП/ОИ, УПД и ЭДО

### 5.1 WB: наиболее подтверждённый контур

```text
1С Перемещение + ТТН + номер поставки
    → ПА
    ↔ акт/результат приёмки WB
    → проверка количества и КМ через WebGJISMP
    → СП и/или ОИ
    → УПД по акту приёмки
    → СБИС / ЦРПТ
    → статус ЭДО в отчёте СверкаПоставок
```

Источники различаются по возрасту:

- `page_id=68807090`, updated 2024-11-05, показывает исторический ручной
  процесс: файл передачи и УПД2 формируются сотрудником Ecom через
  `ВыгрузкаMarketplace`, затем УПД загружается в СБИС.
- `OPSMPC-796`, closed 2025-11-10, подтверждает восстановление в `ОбменWB`
  загрузки обычной приёмки и виртуальных поставок.
- `OPSMPC-820`, closed 2025-12-29, подтверждает создание СП/ОИ, поддержку
  виртуальных поставок и защиту при повторной обработке уже проведённых
  документов.
- `page_id=60694191`, updated 2026-02-11, даёт детальные защитные проверки.
- `OPSMPC-1007`, closed 2026-05-13, добавляет контроль статуса ЭДО в отчёт
  сверки поставок.

**Автоматические и ручные gates в `УПДМаркетплейс`:**

| Gate | Поведение | Тип |
|---|---|---|
| Поставка найдена по номеру в перемещениях за 180 дней | иначе stop + log | автоматический hard gate |
| Найдено конечное перемещение на склад WB | иначе stop + log | автоматический hard gate |
| Найден подчинённый ПА | иначе stop + log | автоматический hard gate |
| `ТоварПосчитан=1` | повторная обработка блокируется | автоматический idempotency gate |
| `СтатусВыгрузки` непустой и не `0` | изменение блокируется, поскольку данные уже отправлены в СБИС | автоматический hard gate |
| КМ существует и соответствует ожидаемому магазину/юрлицу | формируется отчёт о расхождениях | автоматическая проверка |
| Количество акта совпадает с перемещениями | расхождение попадает в отчёт | автоматическая проверка |
| Есть расхождения КМ/количества | пользователь отвечает «Сформировать УПД?» | **ручной soft gate** — источник допускает продолжение |
| Все/часть СП и ОИ уже проведены | пользователь выбирает продолжить или остановить | **ручной повторный gate**, `OPSMPC-820` |
| Несколько ПА имеют разные статусы ЭДО | отчёт выводит каждый ПА отдельной строкой | автоматический контроль наблюдаемости |

Статусы ЭДО, описанные `OPSMPC-1007`: `0/пусто` — не выгружалось; `1/2` —
ошибка GJ; `3` — выгружено, ожидается подтверждение; `4` — ошибка ЭДО; `5` —
успешно.

**Важное ограничение:** даже статус `5` подтверждает успешную выгрузку
документа по определению задачи, но найденные источники не доказывают, что это
одновременно означает юридическое принятие контрагентом, отсутствие
расхождений приёмки и готовность финансового периода к закрытию.

### 5.2 WB API поставок и источник факта

`page_id=165382074`, updated 2025-11-07, описывает две загрузки:

- старая статистическая — до 100 000 строк, с продолжением от
  `lastChangeDate`, лимит один запрос в минуту;
- «финальная расширенная» — список поставок, детали и товары. Она содержит
  `acceptedQuantity`, `readyForSaleQuantity`, обезличку, склад, статус,
  признак необходимости КИЗ и пагинацию.

Документ называет это загрузкой **в ХД**, а `OPSMPC-796` говорит о загрузке
приёмки в `ОбменWB`. Прямая трасса `WB supply API → ХД → ОбменWB → конкретный
ПА/СП/ОИ` не найдена. Поэтому назначать ХД или API единственным source of truth
приёмки нельзя.

### 5.3 Ozon: текущий разрыв

`page_id=165382074` описывает Ozon `supply-order/list/get`, но прямо отмечает:
API **не используется**, потому что показывает плановое/заказанное, а не
фактически принятое количество.

Проектируемая замена:

```text
XML УПД-2 Ozon
    + номер поставки
    → УПДМаркетплейс
    → поиск перемещения и ПА
    → проверка марок
    → СП/ОИ
    → блокировка повторной обработки
```

Однако:

- `OPSMPC-951` — схема согласована 2026-02-02;
- `OPSMPC-948` — разработка приостановлена 2026-05-21;
- `OPSMPC-946` — бизнес-запрос также приостановлен 2026-05-21;
- `OPSMPC-1056` — актуализация требований отложена 2026-05-21.

Следовательно, подробный раздел Ozon в `page_id=60694191` — это
**to-be/proxy**, а не доказательство работающего production-процесса.
Исторический `page_id=68807090` говорит о ручной загрузке расхождений приёмки
как СП/ОИ и ручных виртуальных поставках, но он обновлён в 2024 году. Точный
as-is Ozon на 2026-07-23 остаётся `unknown`.

## 7. Source of truth: что можно и нельзя утверждать

| Объект | Подтверждённый источник | Можно ли назвать master/source of truth |
|---|---|---|
| Статус заказа/отправления Ozon | Ozon API, получаемый через WebApi | источник внешнего события — да; мастер внутреннего документа — не определено |
| РК/РРН/ПН | документы 1С7 Ecomm/WB | фактический внутренний учётный слой — high-confidence; формально утверждённый master не найден |
| Финансовые начисления Ozon | отчёт/finance API Ozon | внешний источник начисления — да; окончательная бухгалтерская сумма требует сверки |
| Недельный отчёт WB | `wb_weekly`, заполненная из WB API | staging/контрольный источник; master бухгалтерии не подтверждён |
| Фактическая приёмка WB | акт/API WB + ПА/СП/ОИ 1С | распределённый контроль; единый master не установлен |
| Фактическая приёмка Ozon | XML УПД-2 в to-be; исторически ручной результат | текущий source of truth неизвестен |
| Марка | WebGJISMP + ЭДО/ЦРПТ | WebGJISMP используется для validation; окончательная юридическая mastership не исследована |
| Статус отправки УПД | `ПА.СтатусВыгрузки` | источник операционного статуса в отчёте; не доказан как полный юридический статус |

## 8. Противоречия и неоднозначности

1. **Ozon supply API подробно описан, но тот же документ говорит, что он не
   используется для факта.** Это не production-интеграция, а исследованный
   контракт.
2. **Ozon SD содержит готовую подробную логику приёмки, но Jira приостанавливает
   её разработку.** SD следует считать to-be.
3. **Исторический документ говорит о ручной загрузке Ozon, но свежая задача
   согласовала автоматизацию.** Ни один источник не подтверждает, какой именно
   вариант работает сейчас.
4. **WB API назван финальной загрузкой в ХД, а отдельная обработка 1С загружает
   приёмку.** Их связность не доказана.
5. **У Ozon новая сумма уже является бизнес-правилом с 2026-07-01, но
   сверочные режимы на 2026-07-21 ещё разрабатываются.**
6. **WB полнота отчёта обеспечивается пагинацией, но полнота контроля
   подрывается падением 1С на большом объёме и открытым дефектом коррекции.**
7. `page_id=16844531` говорит об актуальном `SalesAndReturnsApi`, а
   `OPSMPC-1080/1081` — о переводе агента в `SBRService` с ELK и email-alerts,
   завершённом 2026-07-16. Не подтверждено, все ли маркетплейсные цепочки
   проходят через этот сервис.

## 10. Acceptance gates для следующей проверки

Это **предлагаемые критерии доказательства текущего процесса**, а не найденный
утверждённый регламент.

### 10.1 Заказ/продажа/возврат

1. На одном Ozon posting показать связку:
   `API payload ID → РК+ → РРН → ПН/РК- → строки сверки`.
2. Подтвердить, что production использует новый Accrual endpoint и проходит
   все страницы без пропусков; сверить число уникальных `operation_id`.
3. Для продаж после 2026-07-01 получить нулевое расхождение новой суммы в
   позаказном и отправленческом отчётах.
4. На WB доказать полноту `rrdId=0 … HTTP 204`, сравнить количество строк API и
   `wb_weekly`.
5. Запустить WB-сверку на полном закрываемом объёме без усечения и отдельно
   подтвердить отсутствие ложной привязки из `OPSMPC-979/1009`.

### 10.2 Поставка

1. Для одной закрытой поставки WB собрать:
   `номер поставки → перемещения → ПА → акт WB → СП/ОИ → УПД → ЭДО status=5`.
2. Сопоставить declared, accepted, ready-for-sale, depersonalized и итоговое
   количество в 1С.
3. Подтвердить, является ли `status=5` финальным подтверждением получателя или
   только успешной технической отправкой.
4. Для Ozon показать фактический 2026 as-is: откуда берётся принятая
   количественная/марочная информация и кто вручную создаёт СП/ОИ.
5. Доказать идемпотентность повторного запуска на уже проведённых СП/ОИ и
   отправленном УПД.

### 10.3 Финансовый close

1. Определить business owner, дату cutoff, tolerance и обязательные отчёты.
2. Зафиксировать контрольные суммы: количество заказов, продажи, возвраты,
   отмены, товарная сумма, комиссия, логистика, штрафы, партнёрские выплаты.
3. Получить подписанный артефакт «период закрыт» либо подтвердить, что сейчас
   такого статуса нет.
4. Повторно прогнать тот же период и получить тот же результат
   (reproducibility/idempotency).
5. Доказать обработку опоздавших транзакций и корректировку уже закрытого
   периода.
