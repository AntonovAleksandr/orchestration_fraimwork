# Stage 09 — активный портфель площадок и role-based ownership

**Дата среза:** 2026-07-23  
**Статус:** complete-for-current-pass  
**Уровень покрытия:** substantial для Jira/Confluence; без runtime и данных ЛК

## 0. Scope

Эта стадия отвечает на два вопроса:

1. Как по доступным следам разделить Ozon, Wildberries, Яндекс Маркет, Lamoda,
   Мегамаркет и Kaspi на:
   - `active/live-like`;
   - `restart`;
   - `paused`;
   - `historical`;
   - `unknown`.
2. Какие **роли** участвуют в управлении направлением и отдельными процессами,
   не объявляя исполнителя одной Jira-задачи владельцем всего процесса.

В scope входят:

- Jira-задачи OPSMPC и связанные задачи 2025–2026 годов из других проектов;
- Confluence-страницы по онбордингу, контенту и ролям;
- свежесть, статусы и типы задач;
- разрыв между операционным, бизнес- и техническим владением.

Не входят:

- личные кабинеты маркетплейсов;
- договоры и перечень действующих юридических лиц;
- объёмы заказов, GMV и последние финансовые закрытия;
- production-расписания, логи и результаты последних обменов;
- назначение конкретных сотрудников владельцами процессов.

Имена, контакты, реквизиты и секреты из источников в документ не переносятся.

### 0.1. Операционные определения

| Статус | Используемое в этой стадии определение |
|---|---|
| `active/live-like` | Есть свежий предметный след эксплуатации: продажи, заказы, возвраты, финансы, поставки, production migration или исправление эксплуатационной проблемы. Это ещё не доказательство текущего коммерческого объёма |
| `restart` | Есть свежие задачи подготовки/пилота/UAT, но нет подтверждения устойчивого production-процесса |
| `paused` | Свежий источник прямо содержит статус отмены, приостановки или откладывания для инициативы |
| `historical` | Процесс или интеграция подтверждены только источниками, недостаточно свежими для вывода о состоянии на дату среза |
| `unknown` | Источники противоречивы или не дают необходимого сигнала для классификации |

У площадки могут одновременно быть разные статусы для разных потоков. Например,
операционные заказы могут быть `active/live-like`, а автоматизация карточек —
`paused`.

## 1. Метод и ограничения доказательств

### 1.1. Jira-поиск

Основной поиск выполнен 2026-07-23:

- `project = OPSMPC AND updated >= "2025-01-01" AND text ~ "<площадка>"`;
- `project = OPSMPC AND updated >= "2026-01-01" AND summary ~ "<площадка>"`;
- для Lamoda, Мегамаркета и Kaspi дополнительно выполнен поиск по всем проектам;
- после широкого поиска прочитаны метаданные наиболее свежих задач.

Полученные размеры выборок нельзя считать числом бизнес-инициатив:

- Ozon — `70` задач с Ozon в summary, обновлённых в 2026 году;
- WB — `44` задачи с WB в summary, обновлённых в 2026 году;
- Яндекс — `1` задача с Яндекс в summary, обновлённая в 2026 году;
- широкие текстовые запросы возвращают также общие coordination/incident-задачи
  и задачи, где площадка упомянута только внутри описания.

Количество задач используется только как сигнал интенсивности технической
работы. Оно не доказывает продажи.

### 1.2. Правила интерпретации

- Jira `Закрыт`/`Завершено` не равно production deployment.
- Jira `Перенос на прод` — сильный live-like сигнал, но не доказательство
  успешного переноса.
- `BugProd` — сильный эксплуатационный сигнал только для системы/потока,
  явно названных в задаче.
- Обновление старой задачи не доказывает возобновление проекта.
- Confluence AS-IS/TO-BE и draft не считаются runtime-доказательством.
- `assignee`, `reporter` и имя в заголовке coordination-задачи относятся к
  конкретной работе; формальная accountability из этого не выводится.

### 5.2. Что нельзя выводить из Jira assignee

Нельзя считать, что:

- автор CRequest владеет площадкой;
- системный аналитик accountable за финансовый результат;
- разработчик владеет 1С-обработкой в эксплуатации;
- тестировщик принимает бизнес-процесс;
- координатор общей Jira-задачи является единственным владельцем направления;
- исполнитель DataBird mapping владеет исходными данными PIM/PLM/1С.

Jira показывает **участие в работе**, но не разделяет:

- business accountability;
- process ownership;
- system ownership;
- execution;
- approval;
- production support.

## 6. Противоречия и слабые места источников

1. **Jira activity против business activity.** Ozon/WB имеют сильный live-like
   след, но продажи, кабинеты и финансовое закрытие напрямую не проверены.
2. **Яндекс:** в 2025 году виден рабочий exchange contour, а в 2026 году —
   только изучение документации. Это недостаточно и для `active`, и для
   `paused`.
3. **Lamoda:** свежие задачи указывают на restart из магазинов, а основные
   регламенты описывают историческую централизованную модель.
4. **Мегамаркет:** новая интеграция отменена, но legacy finance tickets
   обновлялись позднее. Это может быть закрытие старых обязательств, а не
   текущие продажи.
5. **Kaspi:** общие coordination-задачи OPSMPC обновлены в 2026 году и
   попадают в поиск, но последние площадочные задачи относятся к 2025 году.
6. **Ownership:** онбординг подтверждает роли, но не current RACI. Старые
   регламенты содержат персональный состав, который нельзя считать актуальным.
7. **DataBird:** задачи фиксируют проектные статусы, но не показывают
   production tenant, расписания, последние imports/exports и support SLA.
8. **Workflow residue:** старые Lamoda card tasks остаются `В Работе` после
   обновления 2026 года; без changelog нельзя понять, возобновлены ли они.

## 9. Acceptance gates

### 9.1. Gate для статуса `active/live-like`

Площадка может быть переведена из evidence-based `live-like` в
**подтверждённо активную коммерчески**, если собраны все четыре доказательства:

1. бизнес подтверждает активный кабинет и договор;
2. есть заказ/продажа не старше согласованного окна, например 30 дней;
3. есть успешный обмен или ручной operational record по ключевому процессу;
4. есть последнее финансовое закрытие или сверка.

### 9.2. Gate для `restart → active`

Для Lamoda и будущих перезапусков:

1. утверждена модель исполнения и склады;
2. назначены accountable/operational/system owners;
3. пройден end-to-end UAT:
   card → price/stock → order → label → shipment → sale/return → finance;
4. подтверждён production pilot;
5. определены monitoring, support и rollback.

### 9.3. Gate для `paused/historical → closed`

1. бизнес подтверждает прекращение продаж;
2. отключены jobs/API credentials в контролируемом порядке;
3. закрыты финансовые и возвратные обязательства;
4. документация помечена архивной;
5. указаны owner и срок хранения данных.

### 9.4. Gate для ownership

RACI считается подтверждённой, когда для каждой площадки и процесса указаны:

- accountable business role;
- operational owner;
- data/content owner;
- system owner;
- engineering executor;
- QA/UAT approver;
- incident owner;
- источник назначения и review date.
