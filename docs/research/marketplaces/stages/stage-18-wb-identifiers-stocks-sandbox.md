# Stage 18 — WB FBS: идентификаторы товара, остатки и тестовый контур

**Дата среза:** 2026-07-25  
**Статус:** complete-for-current-pass  
**Покрытие:** актуальная документация WB API (остатки, склады продавца, Контент,
песочница), спецификации 1С-справочника идентификаторов МП в Confluence,
сторонний mirror журнала изменений WB OpenAPI; без собственного smoke-прогона в
песочнице и без выборки справочника по пилотным SKU  
**Назначение:** закрыть вопрос «откуда GJ знает идентификаторы товара WB, чтобы
отправлять остатки» и определить, какую часть FBS-контура можно отладить в
тестовом контуре WB до выхода на production  
**Уровни уверенности:** `confirmed`, `high`, `proxy`, `hypothesis`, `unknown` в
значениях из `00-PLAN.md`

## 0. Короткий вывод

Три независимых факта, которые вместе дают один блокирующий пробел и один
дешёвый способ его закрыть:

1. **WB принимает остатки только по `chrtId`** — размерному идентификатору
   карточки. Загрузка по баркоду (`sku`) отключена с 13:00 МСК 20.05.2026 и
   отвечает `400 SKUUploadDisabled`.
2. **В 1С-справочнике идентификаторов МП `chrtID` нет.** Хранятся `nmID`
   (артикул WB) и `imtID` (общая карточка), а сопоставление с номенклатурой
   делается по штрихкоду. То есть по текущим данным 1С остаток на WB отправить
   нельзя.
3. **`chrtID` приходит в ответе того же метода, который уже вызывается.**
   `MPToReferenSync` ежедневно забирает карточки через
   `POST /content/v2/get/cards/list`, и `chrtID` лежит в `sizes[]` рядом с
   `techSize` и `skus`. Новый источник данных не нужен — нужно решение, кто
   хранит поле.

Четвёртый факт объясняет, почему пробел не заметили раньше: **существующий
контур остатков WB работает только в направлении «WB → BI»**. Остатки читаются
для отчётности по `nmId` и баркоду, а исходящей загрузки остатков в WB в
документированном контуре нет вообще. Для FBS это новый путь, а не доработка
существующего обмена.

Отсюда развилка, которую надо закрыть решением, а не кодом:

```text
вариант A: расширить 1С-справочник (+ chrtID) и доработать MPToReferenSync
           → единый мастер идентификаторов, но релиз 1С и WebApi

вариант B: wbconnector сам держит карту «баркод → chrtID» из Контента WB
           → быстрее для пилота, но второй владелец идентификатора
```

Отдельный вывод по тестированию: **тестовый контур WB закрывает всю цепочку
«карточка → `chrtID` → склад → остаток → сборочное задание → поставка»**,
включая синхронное создание карточек и эмуляцию `wbStatus`. Он не закрывает
ровно то, что в Stage 16 и Stage 17 уже помечено как самый дорогой риск:
реальный стикер, production-шлюз по маркировке и поведение под настоящими
лимитами. Плюс на production есть отдельный шлюз доступа, которого в песочнице
не видно.

## 1. Какой идентификатор требует WB для остатков

### 1.1. Остатки — только по `chrtId`

Текущий контракт склада продавца:

- `POST /api/v3/warehouses` — создать склад продавца;
- `GET /api/v3/warehouses` — список складов;
- `PUT /api/v3/warehouses/{warehouseId}`, `DELETE /api/v3/warehouses/{warehouseId}`;
- `PUT /api/v3/stocks/{warehouseId}` — обновить остатки;
- `POST /api/v3/stocks/{warehouseId}` — **получить** остатки (чтение выполняется
  методом `POST` с телом, это не создание);
- `DELETE /api/v3/stocks/{warehouseId}` — удалить остатки;
- `GET /api/v3/offices` — офисы WB (ПВЗ/СЦ) для пропусков и отгрузки.

Тело обновления описано как массив идентификаторов размеров и количеств;
чтение и удаление работают по `chrtIds` с ограничением 1000 позиций в запросе.
Отключение `sku` — не рекомендация, а жёсткий отказ: `400 SKUUploadDisabled`
(в части ответов тот же пример подключён как `IncorrectSkuParameter`).

Важный нюанс разграничения сущностей: **на баркоде остались стикеры и
сборочные задания**. Переход на `chrtId` затронул только остатки, поэтому в
Connector будут одновременно жить оба идентификатора, и путать их нельзя.

Evidence: актуальная документация WB API, раздел управления остатками;
официальный журнал изменений WB API (дата отключения `sku` и код ошибки);
сторонний mirror OpenAPI-спецификации, где `SKUUploadDisabled` добавлен в
ответы `400`. Confidence: `confirmed` по требованию `chrtId`, `high` по точной
дате отключения.

### 1.2. «Тихая» неудача обновления

В документации зафиксировано поведение, которое ломает наивную реализацию:
если передать неверные **имена** параметров, WB возвращает успешный ответ без
содержимого, но остаток не меняется. Ошибки не будет — будет ложное
подтверждение.

Практическое следствие для Connector: **после каждой записи остатков нужно
контрольное чтение** тем же путём (`POST /api/v3/stocks/{warehouseId}`) и
сравнение с отправленным значением. Без этого можно долго считать, что остатки
уходят.

Confidence: `confirmed` (прямое примечание в документации метода).

### 1.3. Лимиты и особые коды

| Параметр | Значение | Contour |
|---|---|---|
| Частота | 300 запросов/мин на аккаунт продавца | production |
| Минимальный интервал | 200 мс | production |
| Всплеск | 20 | production |
| Позиций в запросе | до 1000 | оба |
| Любой ответ `4XX` | учитывается как 10 запросов | production |
| `406 WarehouseStocksUpdateBlock` | склад на техработах | production |
| Частота | 1 запрос/с | sandbox |

Указанные 300 запросов/мин относятся к **Персональному и Сервисному** токенам.
Для Базового токена лимиты радикально ниже (по методам сборочных заданий —
10 запросов в час, интервал 6 минут, всплеск 1), а Тестовый токен также
намеренно ограничен. Интеграцию нужно строить на Персональном или Сервисном
токене, иначе поллер и публикация остатков не уложатся в лимит.

Правило учёта ошибок с 17.06 распространено на **все** методы домена
`marketplace-api.wildberries.ru` и на любой код `4XX`, а не только на `409`.
Это делает валидацию на нашей стороне не гигиеной, а прямой экономией лимита:
один неверный запрос стоит десяти корректных.

`406` — не ошибка интеграции, а штатное состояние склада WB; обработчик должен
уходить в отложенный повтор, а не помечать позиции как проблемные.

Confidence: `confirmed` по документации и официальному журналу изменений;
фактическое поведение под лимитом на нашем кабинете — `unknown`.

## 2. Что GJ уже знает об идентификаторах WB

### 2.1. Справочник в 1С существует

Подтверждён справочник идентификаторов маркетплейсов, подчинённый
`Номенклатуре`. Состав полей по спецификации:

| Поле WB | Реквизит 1С | Пример |
|---|---|---|
| `nmID` (артикул WB) | `идентификаторМП` | `233726436` |
| `imtID` (общая карточка) | `обКарточка` | `210297552` |
| `techSize` | `размерМП` | `S` |
| — | `МП` | фиксированный IDD фирмы Вайлдберриз |
| **`chrtID`** | **отсутствует** | — |

Ключ сопоставления с номенклатурой GJ — **штрихкод** (`sizes[].skus`), а не
артикул и не `nmID`.

Evidence: Confluence `149775329`, v13 (спецификация `МаппингМП`);
Confluence `165381358`, v4 (`ИдентификаторыМП`, WebApi-доступ). Confidence:
`confirmed` для состава полей и ключа сопоставления.

### 2.2. Наполнение — `MPToReferenSync`, ежедневно 01:00

Сервис `MPToReferenSync` забирает карточки методом
`POST /content/v2/get/cards/list` и раскладывает их в справочник. Это же
означает, что **`chrtID` уже физически проходит через наш код** — он лежит в
том же элементе `sizes[]`, из которого берутся `techSize` и `skus`, — но не
сохраняется.

Confidence: `confirmed` для расписания и метода; `high` для утверждения, что
`chrtID` присутствует в ответе (из документации Контента WB).

### 2.3. Чтение справочника наружу

Доступ через WebApi:

- `GET api/Ref/IdMp?from&to` — выборка по интервалу;
- `GET api/Ref/IdMp/{id}`;
- `POST api/Ref/IdMp` — по списку;
- `POST api/Ref/IdMpByParent`, `GET api/Ref/IdMpByParent/{id}` — по владельцу
  (номенклатуре).

Доступность справочника для 1С закрыта задачей `OPSMPC-868`.

Evidence: Confluence `165381358`, v4. Confidence: `confirmed`.

### 2.4. У справочника уже есть второй потребитель

Сервис замеров склада WB дописывает габариты в тот же справочник и
сопоставляет данные WB **по `nmId`**: если `ИдентификаторМП` с нужным `nmid` в
1С не найден, публикуется сообщение в ELK. То есть справочник уже является
разделяемым ресурсом, и расширение его состава полей — не изолированное
изменение.

Evidence: Confluence `165400467`; Jira `OPSMPC-1022`, `OPSMPC-1042`.
Confidence: `confirmed`.

### 2.5. DataBird использует другой ключ

Для цен ключ каталога DataBird — **EAN13/штрихкод**, а обновление цены идёт по
артикулу WB. Это отдельная линия идентификации, и её нельзя считать источником
`chrtID`.

Evidence: Confluence `149765159`. Confidence: `high`.

### 2.6. Текущий контур остатков WB — это чтение, а не загрузка

Существующая спецификация остатков описывает **входящее** направление: остатки
забираются из WB в BI (`NSH-BI\A2014`, БД `WB_Stocks`).

| Метод | Статус в спецификации | Ключи ответа |
|---|---|---|
| `GET statistics-api…/api/v1/supplier/stocks` | «не используется» | `warehouseName`, `nmId`, `barcode`, `isSupply` |
| `GET seller-analytics-api…/api/v1/warehouse_remains?groupByBarcode=true` | используется (таблица `WB_Stocks`, вьюха `v_WB_Stocks`) | `barcode`, `warehouses[].warehouseName` |

Особенности используемого метода: отчёт асинхронный — создание задания,
опрос статуса (`new/processing/done/purged/canceled`), затем загрузка; готовый
отчёт живёт 2 часа; лимит — 1 запрос в минуту на аккаунт продавца. Для первого
метода отдельно зафиксировано правило суммирования `quantity`,
`inWayToClient`, `inWayFromClient`, `quantityFull` в разрезе
`warehouseName + nmId + barcode` без учёта `isSupply`.

Два важных следствия:

1. **`chrtId` не встречается ни в одном используемом контракте остатков.** Вся
   существующая идентификация остатков живёт на уровне `nmId` и баркода, что
   согласуется с составом справочника из §2.1.
2. **Направления «GJ → WB остатки» в документированном контуре нет.** Для FBS
   это новый исходящий путь, а не расширение существующего обмена. Поэтому
   `PUT /api/v3/stocks/{warehouseId}` нельзя оценивать как «доработку
   существующей загрузки» — владельца, частоту, источник количества и защиту
   eCom-остатка нужно определять с нуля (см. `MP-WB-FBS-011` про отсутствие
   channel dimension в OMS threshold и потребность в отдельном logical WB
   allocation bucket).

Evidence: Confluence `130128672`, v32, updated 2026-07-07, автор Габдулин
Павел. Confidence: `confirmed` для состава методов и направления обмена;
`high` для утверждения об отсутствии исходящего пути (отсутствие в
спецификации не является абсолютным доказательством).

## 3. Разрыв и способы его закрыть

### 3.1. Формулировка разрыва

```text
GJ знает:    штрихкод → nmID, imtID, techSize
GJ читает:   остатки из WB по nmId + barcode (в BI)
WB требует:  chrtId для загрузки остатков
GJ не знает: chrtID
GJ не имеет: исходящего пути «остатки → WB»
```

Разрыв в данных — ровно одно поле, и он не требует нового интеграционного
канала. Разрыв в процессе шире: исходящую загрузку остатков нужно создавать, и
у неё пока нет ни владельца, ни источника количества, ни политики защиты
eCom-остатка.

### 3.2. Вариант A — расширить 1С-справочник

Добавить `chrtID` в справочник и в `MPToReferenSync`.

Плюсы: один мастер идентификаторов МП; переиспользуют другие потребители;
Connector остаётся без собственного справочного слоя.

Минусы: релиз 1С и WebApi, согласование с владельцем справочника и вторым
потребителем (сервис замеров); темп пилота зависит от чужого релизного цикла.

### 3.3. Вариант B — локальная карта в `wbconnector`

Connector сам вызывает `POST /content/v2/get/cards/list` и держит таблицу
`barcode → chrtID` (плюс `nmID`, `techSize`) с датой обновления.

Плюсы: не блокирует пилот; естественная зона ответственности Connector —
общение с WB API; проверяемо в песочнице целиком.

Минусы: второй владелец идентификатора и риск расхождения с 1С; нужен
собственный контроль свежести и расхождений.

### 3.4. Механика получения `chrtID` — метод спроектирован под периодический обмен

Оба варианта опираются на один метод, поэтому его механику надо зафиксировать
отдельно. В ответе `POST /content/v2/get/cards/list` связка лежит внутри одной
карточки:

```json
{"cards": [{
  "nmID": 12345678, "imtID": 123654789, "vendorCode": "...",
  "needKiz": false, "kizMarked": true,
  "sizes": [{"chrtID": 316399238, "techSize": "0", "skus": ["987456321654"]}],
  "createdAt": "...", "updatedAt": "..."
}],
 "cursor": {"updatedAt": "...", "nmID": 12345678, "total": 1}}
```

**Пагинация — курсорная.** Первый запрос:

```json
{"settings": {"sort": {"ascending": true},
              "cursor": {"limit": 100},
              "filter": {"withPhoto": -1}}}
```

Далее `updatedAt` и `nmID` из `cursor` ответа переносятся в `cursor` следующего
запроса. Признак окончания — `total` в ответе меньше запрошенного `limit`.
Максимум 100 карточек за запрос.

**Инкрементальный режим встроен в тот же курсор.** Если сохранить
`cursor: {updatedAt, nmID}` последнего ответа предыдущей выгрузки и передать его
в первый запрос следующей (с сортировкой по возрастанию), метод вернёт только
созданные и изменённые с того момента карточки. То есть периодический обмен —
не обходной путь, а штатный режим работы метода.

**Лимиты категории «Контент»:** 100 запросов/мин на аккаунт продавца, интервал
600 мс, всплеск 5. Исключения — методы создания и редактирования карточек
(редактирование: 10 запросов/мин, интервал 6 с). При 100 карточках на запрос
полная выгрузка каталога упирается не в лимит, а в объём.

**Категория токена.** С 03.08 методы `POST /content/v2/get/cards/list` и
`/get/cards/trash` недоступны по токену категории «Продвижение» — нужна
категория **«Контент»**. Для FBS это означает минимум две категории доступа:
«Контент» для идентификаторов и «Маркетплейс» для складов, остатков, сборочных
заданий и поставок.

**Ловушки, которые надо учесть в реализации:**

1. `skus` — **массив**, у одного размера может быть несколько баркодов.
   Сопоставление строится «наш баркод → найти размер», и совпадение по любому
   элементу массива является валидным.
2. После создания или редактирования карточки синхронизация занимает **до 30
   минут, и в это время остатки и цены установить нельзя**. Новый размер не
   получит остаток немедленно; это отложенный повтор, а не ошибка.
3. Семантика `withPhoto` менялась дважды и с 16.06 такова: `-1` — любые
   карточки, `0` или отсутствие параметра — тоже любые, `1` — только с фото,
   `2` — только без фото. Интеграции, написанные до этой даты под старую схему
   (где `0` означал «только без фото»), теперь получают другой объём выборки —
   это стоит проверить в `MPToReferenSync`.
4. В том же ответе приходят `needKiz` (требуется ли код маркировки для товара) и
   `kizMarked` (подтвердили ли мы, что код нанесён). Если товар требует
   маркировки, а `kizMarked=false`, карточка не проходит модерацию и
   блокируется. Для маркированного ассортимента GJ это отдельный шлюз, который
   надо контролировать до публикации остатков, и данные для него приходят
   бесплатно — тем же методом.

Confidence: `confirmed` по документации метода и официальному журналу изменений
WB API.

### 3.5. Рекомендация для P0

Вариант B на пилоте, вариант A как целевой — с оговоркой, что локальная карта
Connector с самого начала пишется как **кеш с явным источником истины**, а не
как альтернативный справочник: хранить дату получения, `nmID` и `techSize`
рядом, и уметь сравнить себя с `api/Ref/IdMp`. Тогда переход на вариант A —
замена источника наполнения, а не переписывание.

Confidence: `hypothesis` (проектное решение, не факт).

## 4. Тестовый контур WB

### 4.1. Это зеркало на каждый домен, а не один хост

| Домен | Sandbox-хост | Что покрывает |
|---|---|---|
| Marketplace | `marketplace-api-sandbox.wildberries.ru` | `/api/v3/orders*`, `/api/v3/supplies*`, `/api/v3/passes*`, `/api/v3/warehouses*`, `/api/v3/stocks/{warehouseId}`, `/api/v3/offices`, DBS, Click&Collect |
| Контент | `content-api-sandbox.wildberries.ru` | `/content/v2/*`, `/content/v3/media/*` |
| Цены и скидки | `discounts-prices-api-sandbox.wildberries.ru` | `/api/v2/*` |
| Поставки FBW | `supplies-api-sandbox.wildberries.ru` | `/api/v1/acceptance/options`, `/api/v1/warehouses` |
| Отчёты | `statistics-api-sandbox.wildberries.ru` | остатки, заказы, продажи |
| Отзывы/вопросы | `feedbacks-api-sandbox.wildberries.ru` | `/api/v1/*` |

Доступ — по токену с признаком «Тестовый контур»; рабочий токен в песочнице не
работает. Данные генерируются случайно и не принадлежат реальным продавцам.
Набор методов в песочнице меньше, чем на production.

Evidence: блоки `servers` в актуальной OpenAPI-спецификации WB (sandbox-хосты
добавлены по разделам); страница песочницы WB; статья об ограничениях
тестового контура. Confidence: `high`.

### 4.2. Что реально проверяется

- **Идентификаторы.** В песочнице Контента есть отдельные методы управления
  тестовыми карточками, а `POST /content/v2/cards/upload` создаёт карточку
  **синхронно**, без асинхронного ожидания. Значит, цепочку «создать карточку →
  прочитать `chrtID` через `POST /content/v2/get/cards/list`» можно прогнать за
  один шаг.
- **Склад и остатки.** `POST /api/v3/warehouses` и
  `PUT /api/v3/stocks/{warehouseId}` имеют sandbox-серверы, значит склад
  создаётся и наполняется в тестовом контуре.
- **Заказы и жизненный цикл.** Для FBS есть sandbox-методы эмуляции действий
  пользователя, то есть переходы `wbStatus` вызываются вручную — этим
  проверяется машина состояний Connector, идемпотентность и компенсации.
- **Поставки и пропуска.** `/api/v3/supplies*` и `/api/v3/passes*` доступны,
  включая последовательность `new → confirm` при добавлении заданий
  (см. `MP-WB-FBS-019`).
- **Обработка ошибок.** Коды ответов и валидация тел проверяются штатно.

### 4.3. Что песочница не покрывает

| Область | Поведение sandbox | Следствие |
|---|---|---|
| Стикеры сборочных заданий | всегда пустой `200` | реальный стикер, ZPL, печать и companion scan-print не проверяются |
| Стикеры трансграничных поставок | всегда `200` | то же |
| Metadata / КИЗ (`sgtin`) | заполнение необязательно | production-шлюз по маркировке не срабатывает; требование полного КМ с GS-разделителями и криптохвостом невидимо |
| `POST /api/v3/orders/status/history` | всегда `200` | история статусов не тестируется содержательно |
| Лимиты | 1 запрос/с | throughput и поведение поллера под prod-лимитами не измеряются |
| Локализация | `locale` не используется, только русский | не проверяется мультиязычность |
| Отчёты | диапазон дат ограничен последними месяцами | сверка по историческому периоду не воспроизводится |
| Статистика продвижения | последние 30 дней, только для кампаний в статусе `9`, тип `8`, 9 раз в сутки | к FBS не относится, но объясняет расхождения при общих прогонах |

Ключевой вывод: **песочница валидирует контракт и логику, но не валидирует
физику и маркировку.** Именно поэтому technical spike из Stage 16 и
marked-order walkthrough из Stage 17 остаются обязательными и не заменяются
sandbox-прогоном.

### 4.4. Sandbox smoke-сценарий для `wbconnector`

Минимальный прогон, который закрывает вопрос идентификаторов целиком:

```text
1. токен «Тестовый контур»
2. content-api-sandbox: создать карточку (синхронно)
3. content-api-sandbox: POST /content/v2/get/cards/list
   → зафиксировать nmID, imtID, sizes[].chrtID, sizes[].skus, techSize
4. marketplace-api-sandbox: POST /api/v3/warehouses → warehouseId
5. marketplace-api-sandbox: PUT /api/v3/stocks/{warehouseId} по chrtID
6. marketplace-api-sandbox: POST /api/v3/stocks/{warehouseId}
   → контрольное чтение, сравнить с отправленным
7. негативный тест: то же тело по sku → ожидать 400 SKUUploadDisabled
8. негативный тест: неверные имена параметров → ожидать «успех» без изменения,
   поймать это контрольным чтением
9. sandbox-эмуляция: создать сборочное задание, прогнать wbStatus
10. supplies: создать поставку, добавить задание (new → confirm), закрыть
```

Шаги 7 и 8 важнее остальных: они фиксируют в тестах именно те два поведения,
которые ломают наивную реализацию.

## 5. Отдельный шлюз production-доступа

По сторонней публикации, на рабочем домене WB может отдавать
`403 Access denied` на **весь** marketplace-контур при валидном токене, пока в
кабинете не заданы пункты выдачи для возвратов; указанный порог — минимум 5.
Логика в том, что без адресов возврата FBS-заказ нельзя замкнуть. В песочнице
те же запросы проходят нормально. Там же указано, что склад продавца для
доступа к API не требуется — он нужен только под реальные заказы.

Это `proxy`: источник не официальный. Но проверить дёшево, а цена пропуска
высокая — «в песочнице всё зелёное» здесь ничего не гарантирует. Проверку надо
поставить **до** технического спайка, а не после.

## 6. Что из этого следует для `wbconnector`

1. **Два базовых адреса, а не один.** Сейчас в конфигурации один
   `WB_API_BASE_URL` со значением песочницы Marketplace. Контент — отдельный
   домен, поэтому нужен второй адрес и переключение контуров одним признаком.
2. **Локальная карта идентификаторов** `barcode → chrtID` (+ `nmID`,
   `techSize`, дата обновления) как кеш с явным источником истины. Наполнение —
   инкрементальный курсор Контента плюс разрешение по требованию при промахе:
   между периодическими выгрузками может появиться новый размер, а остаток по
   нему надо публиковать без ожидания следующего цикла.
3. **Обязательное контрольное чтение** после записи остатков; расхождение —
   бизнес-инцидент, а не сетевая ошибка.
4. **Отдельная обработка `406`** как отложенного повтора и учёт любого `4XX`
   как десятикратного расхода лимита — валидация до отправки экономит лимит.
   Токен обязан быть Персональным или Сервисным, иначе лимитов не хватит.
5. **Не смешивать идентификаторы:** остатки — `chrtId`, стикеры и сборочные
   задания — баркод.
6. **Категории доступа:** «Контент» для идентификаторов и «Маркетплейс» для
   складов, остатков, заданий и поставок. Токен категории «Продвижение» для
   карточек перестал работать с 03.08.
7. **Отдельное состояние «размер ещё синхронизируется»** — до 30 минут после
   создания или изменения карточки остаток установить нельзя.
8. **Контроль `needKiz`/`kizMarked`** перед публикацией остатка по
   маркированному товару: несоответствие блокирует карточку на модерации.
9. **Токен тестового контура и рабочий токен — разные секреты**, и оба не
   должны попадать в документацию и логи (см. §7 про утечку).

## 8. Уверенность и неизвестное

### Confirmed

- остатки WB принимаются только по `chrtId`, загрузка по `sku` отключена и
  отвечает `400 SKUUploadDisabled`;
- неверные имена параметров дают ложно-успешный ответ без изменения остатка;
- 1С-справочник идентификаторов МП хранит `nmID`, `imtID`, `techSize`, `МП` и
  не хранит `chrtID`;
- сопоставление с номенклатурой в справочнике идёт по штрихкоду;
- `MPToReferenSync` наполняет справочник ежедневно в 01:00 методом
  `POST /content/v2/get/cards/list`;
- справочник читается наружу через `api/Ref/IdMp*`, доступность закрыта
  `OPSMPC-868`;
- у справочника есть второй потребитель — сервис замеров, сопоставление по

  `cursor: {updatedAt, nmID}`; лимит категории — 100 запросов/мин, интервал

## 12. Resume pointer

Следующий шаг — не расширять анализ, а выполнить два дешёвых проверочных
действия и одно решение.

1. **Sandbox smoke** по §4.4 на токене тестового контура: карточка → `chrtID` →
   склад → остаток → контрольное чтение, плюс два негативных теста. Это
   переводит `MP-WB-FBS-045` из `high` в `confirmed` и даёт основу контрактных
   тестов Connector.
2. **Проверка кабинета production**: заданы ли пункты выдачи для возвратов и
   отвечает ли marketplace-домен `200`; одновременно — отзыв токена со страницы
   `88508013`.
3. **Решение по владельцу `chrtID`**: вариант A или B из §3. До решения
   локальная карта Connector пишется как кеш, а не как справочник.

Выборка `api/Ref/IdMp` по пилотным SKU остаётся обязательной перед
production-пилотом: она показывает не наличие поля, а фактическую полноту
справочника по товарам, которые действительно пойдут в WB FBS.

Отдельно к следующему проходу: исходящая публикация остатков в WB — это новый
обмен, а не доработка существующего. До пилота нужны владелец, источник
количества, частота и политика защиты eCom-остатка. Этот вопрос смыкается с
`MP-WB-FBS-011` и должен решаться вместе с ним, а не внутри Connector.
