# Stage 07 — поставки и fulfillment

**Дата среза:** 2026-07-23  
**Статус:** complete-for-current-pass  
**Уровень покрытия:** Jira/Confluence; физические SOP не проверены

## 1. Главный вывод

Поставки — отдельный от DataBird контур. По найденным источникам он строится
вокруг 1С, площадочных API/личных кабинетов, обработок `Обмен*` и
`УПДМаркетплейс`, складских документов, GJMarkUpdate и ЭДО/ЦРПТ.

В нём смешаны автоматические и ручные этапы. Старый документ 2024 года подробно
фиксирует ручные операции, а задачи 2025–2026 показывают их последовательную
автоматизацию. Поэтому текущий уровень ручного труда нельзя восстановить только
из одного регламента.

## 2. Общая схема

Для FBO-подобных поставок источники показывают такую общую последовательность:

1. создаётся/подготавливается перемещение или поставка в 1С;
2. формируется набор товаров/коробов и документы для площадки;
3. маркированный товар проходит движения между юрлицами через УПД;
4. площадка выполняет приёмку;
5. результат приёмки загружается обратно;
6. расхождения оформляются списанием и/или оприходованием;
7. выполняются УПД/корректировки и сверка статусов ЭДО.

Конкретные шаги и документы различаются по площадкам.

## 3. WB

### Подтверждено

- `page_id=165382074`, updated 2025-11-07, описывает две реализации получения
  поставок WB: раннюю статистическую и расширенную через supplies API.
- Расширенная схема получает список поставок, детали, статусы, склады и товары,
  включая `nmID`, barcode, заявленное/принятое количество и признак маркировки.
- `OPSMPC-796` закрыта: восстановлена загрузка результатов приёмки и
  виртуальных поставок в обработке `ОбменWB`.
- `OPSMPC-820` закрыта: добавлялись закрывающие документы по приёмке,
  виртуальные поставки и обработка уже проведённых документов.
- `OPSMPC-1005` подтверждает отчёт сверки поставок WB со статусом выгрузки в ЭДО.

### Исторический процесс маркировки

`page_id=68807090`, updated 2024-11-05, описывает:

`1С перемещение → GJMarkUpdate MOVE_STORES → СБИС/ЦРПТ → файл передачи →`
`приёмка WB → УПД2 через ВыгрузкаMarketplace → СБИС/ЦРПТ`.

Этот порядок полезен как основа, но мог измениться последующими задачами.

## 4. Ozon

### Подтверждено

- `page_id=165382074` описывает supply-order API Ozon: заявки, статусы,
  таймслоты, склады, состав и теги маркировки.
- Документ прямо отмечает ограничение: товарный состав API содержит плановое,
  а не фактически принятое количество.
- `OPSMPC-951` согласовала новую схему загрузки расхождений приёмки и марок из
  XML УПД-2.
- `OPSMPC-948` — разработка режима загрузки приёмки и марок — приостановлена
  на 2026-05-21. В описании требуется поддержка и Ozon, и WB.

### Исторический процесс маркировки

`page_id=68807090` описывает:

`1С перемещение → GJMarkUpdate MOVE_STORES/УПД1 → СБИС/ЦРПТ →`
`MOVE_AGENS/УПД2 → СБИС/ЦРПТ → Ozon выводит марки при продаже`.

Статус actual production именно этой версии не проверен.

## 5. Lamoda, Яндекс, SMM, Kaspi

`page_id=68807090` содержит отдельные исторические схемы:

- Lamoda: Excel-отчёт из `ВыгрузкаMarketplace`, документ `ОтгрузкаМП`,
  затем два движения маркировки.
- Яндекс: файл передачи и марки из 1С, загрузка в ЛК, получение УПД2 из ЛК и
  ручная загрузка в СБИС.
- СберМегаМаркет: спецификация/заказ, приёмка площадкой и УПД2.
- Kaspi: отдельные задачи по поставкам, коробам и складам встречаются в OPSMPC.

**Статус:** historical/proxy; актуальный процесс по этим площадкам не подтверждён.

## 6. FBO/FBS/DBS

- Старая матрица `81986146` перечисляет поддерживаемые площадками модели
  FBO/FBS/DBS.
- Найденные документы поставок в основном описывают поставку товара на склад
  площадки, то есть FBO-подобный контур.
- Историческое исследование `OPS-10382` рассматривало FBS/DBS для WB, но
  отдельного доказательства production-запуска в текущем проходе нет.

**Вывод:** модель работы нельзя назначить площадке только по API-возможностям.
