## 0. Короткий вывод

1. **Блокирующий вопрос Stage 19 закрыт: перенос задания между поставками
   существует.** `PATCH /api/marketplace/v3/supplies/{supplyId}/orders` по
   описанию метода перемещает задания между активными поставками (и из закрытой
   при повторной отгрузке). Отдельного метода «исключить из поставки» нет, и
   вернуть задание в статус `new` нельзя — но для стратегии недосбора это
   принципиально: недособранное задание можно перебросить в следующую волну
   вместо отмены. Длительность волны перестаёт быть заложником отмены.
2. **Состав поставки частично читается.** Удалённый
   `GET /api/v3/supplies/{supplyId}/orders` заменён на
   `GET /api/marketplace/v3/supplies/{supplyId}/order-ids` (только ID).
   Проекция `supply_orders` остаётся основным источником, но сверка состава
   теперь возможна — Stage 19 §1.6 уточняется.
3. **Песочница имеет методы эмуляции жизненного цикла** (`/api/v3/test/fbs/*`):
   создание тестовых заданий, отмена покупателем, `ready_for_pickup`, `sold`,
   отказ, брак, закрытие поставки с развилкой `sorted`/повторная отгрузка. Этого
   достаточно для прогона машины состояний Connector без реального заказа.
4. Контракт метаданных уточнён: `POST /api/marketplace/v3/orders/meta`
   возвращает `metaDetails[].decision` — расширенный набор статусов проверки,
   делящийся на допускающие и блокирующие `deliver`. Предполётная проверка из
   Stage 19 §4 подтверждается и получает точный контракт.

## 2. Контракт методов FBS (хост `marketplace-api.wildberries.ru`)

Общий лимит для заданий/поставок/пропусков: **300 зап/мин, интервал 200 мс,
всплеск 20**, на аккаунт продавца. С 2026 года **любой ответ 4XX учитывается
как 10 запросов** (ранее — только 409). Авторизация: заголовок `Authorization`,
токен категории «Маркетплейс».

### 2.1. Сборочные задания

| Метод | Контракт и ключевые поля | Лимит |
|---|---|---|
| `GET /api/v3/orders/new` | Все текущие `new`. Поля: `id`, `orderUid`, `article`, `nmId`, `chrtId`, `skus[]`, `warehouseId`, `officeId`, `offices[]`, `rid`, `createdAt`, `cargoType` (1 МГТ/2 СГТ/3 КГТ+), `crossBorderType` (0/1), `requiredMeta[]`, `optionalMeta[]` (с 24.11.2025), `comment`, `isZeroOrder` (отмена без штрафа), цены ×100, `address`, `ddate`, `deliveryType:"fbs"`, `options.isB2B` | общий |
| `GET /api/v3/orders` | query `limit` (1..1000, обязателен), `next`, `dateFrom/dateTo` (Unix, макс. период 30 дней, по дате создания). **С 21.07.2026 — только задания не старше 3 месяцев**; старше — архивный метод. Возвращает `supplyId`, но не `requiredMeta` | общий |
| `POST /api/v3/orders/status` | тело `orders[]` 1..1000 ID. Ответ: `supplierStatus` (new/confirm/complete/cancel/cancel_carrier), `wbStatus` (waiting/sorted/sold/canceled*/ready_for_pickup/postponed_delivery/accepted_by_carrier/sent_to_carrier/…), **`isCancellable` (bool, с 07.05.2026)** | общий |
| `POST /api/v3/orders/status/history` | **только трансграничные** задания, до 100 ID. В песочнице всегда пустой 200 | общий |
| `POST /api/v3/orders/stickers` | query `type=svg\|zplv\|zplh\|png`, `width=58\|40`, `height=40\|30` (580×400 или 400×300 px). Тело до 100 заданий, статусы `confirm`/`complete`. Ответ `stickers[]{orderId, partA, partB, barcode, file(base64)}` | общий |
| `PATCH /api/v3/orders/{orderId}/cancel` | Отмена только до передачи задания WB (проверять `isCancellable`). Отменённое задание автоматически удаляется из поставки | **100 зап/мин, 600 мс, всплеск 20** |

### 2.2. Идентификаторы маркировки (быв. «Метаданные FBS», переименовано 29.05.2026)

| Метод | Контракт | Лимит |
|---|---|---|
| `POST /api/marketplace/v3/orders/meta` | тело до 100 ID. Ответ `orders[]{id, metaDetails[]{key, value, decision}}` — `decision` = статус проверки (схема `meta` удалена 05.06.2026) | 300/мин (получение+удаление) |
| `PUT /api/v3/orders/{orderId}/meta/sgtin` | массив 1..100 кодов, 16–135 символов, GS-разделитель `\u001D`. Только в статусе `confirm` и только если ключ требуется (иначе 409 `MetaKeyNotRequired`) | **1000 зап/мин, 60 мс, всплеск 20** |
| `PUT .../meta/uin|imei|gtin|expiration` | аналогично; expiration мин. 30 суток, удалить нельзя | 1000/мин |
| `PUT /api/marketplace/v3/orders/{orderId}/meta/customs-declaration` | номер ДТ (быв. ГТД), можно в `confirm` и `complete`; один ДТ на задание | — |
| `DELETE /api/v3/orders/{orderId}/meta?key=` | key enum `imei\|uin\|gtin\|sgtin\|customsDeclaration` | 300/мин |

Статусы проверки `decision` (спека `MetaDetails`):

- **допускают deliver:** `filled`, `optional`, `deadlineExceeded`, `imeiMaySell`,
  `imeiSoldB2B`, `uinMaySell`, `sgtinIntroduced`, `sgtinSoldB2B`;
- **блокируют deliver:** `required`, `pending`, `imeiInvalidFormat`,
  `imeiAlreadySold`, `uinInvalidFormat`, `uinBadStatus`, `uinBadProcess`,
  `uinBadStatusAndBadProcess`, `uinNotFound`, `sgtinInvalidFormat`, `sgtinNoGS`,
  `sgtinHasInvalidSymbols`, `sgtinHasNonLatinSymbols`, `sgtinInvalidPattern`,
  `sgtinNotFound`, `sgtinEmitted`, `sgtinApplied`, `sgtinWrittenOff`,
  `sgtinRetired`, `sgtinWithdrawn`, `sgtinDisaggregation`, `sgtinDisaggregated`,
  `sgtinAppliedNotPaid`.

Практическое следствие: шлюз перед `deliver` сравнивает не с тремя статусами, а
со списком блокирующих — он должен быть таблицей в коде, а не константой.

### 2.4. Пропуска, склады, остатки

- Пропуска: `GET /api/v3/passes/offices`, `GET /api/v3/passes`,
  **`POST /api/v3/passes` — 1 запрос / 10 минут**, действует 48 ч, тело
  `{firstName, lastName, carModel, carNumber(6–9), officeId}`;
  `PUT/DELETE /api/v3/passes/{passId}`.
- Склады продавца: `GET/POST /api/v3/warehouses`,
  `PUT/DELETE /api/v3/warehouses/{warehouseId}` (`{name 1..200, officeId}`;
  привязку WB-склада можно менять 1 раз/сутки).
- Остатки: `PUT` (обновить), `POST` (получить), `DELETE /api/v3/stocks/{warehouseId}` —
  **только `chrtId`**, 1..1000 позиций, amount ≤ 100000. `sku` отключён:
  400 `SKUUploadDisabled` (в спеке с 08.05.2026; отключение постепенное «от 10
  минут в час»). `PUT` отвечает 406 `WarehouseStocksUpdateBlock` при техработах
  склада. `DELETE` — отдельный лимит **10 зап/мин, 6 с, всплеск 2**.
- `GET /api/v3/offices` — склады WB.

### 2.5. Прочее

- **`GET /api/marketplace/v3/fbs/orders/archive`** (новый, 29.04.2026): задания
  старше 3 месяцев, query `year`, `month`, `next`, `limit` (100..1000). Ошибки в
  формате `application/problem+json`. **В песочнице отсутствует.**
- Возвратов покупателя в FBS-спеке нет — это раздел «Общение с покупателями»
  (`GET /api/v1/claims`, другой хост).

путей FBS (как у DBS/DBW весной 2026) пока нет, но направление очевидно —
клиент должен держать пути в одном месте.

## 4. Песочница

### 4.1. Доступ

Тестовый токен выпускается там же, где обычные: кабинет seller.wildberries.ru →
Профиль → Настройки → Доступ к API → токен с признаком «Тестовый контур».
Срок жизни 180 дней, доступ ко всем категориям песочницы, чтение+запись,
работает **только** на sandbox-хостах; рабочий токен в песочнице не работает.
Данные случайные. Обычные токены тоже 180 дней с перевыпуском за 7–14 дней.

### 4.2. Хосты

| Хост | Покрытие |
|---|---|
| `marketplace-api-sandbox.wildberries.ru` | FBS (задания, meta, поставки, пропуска), склады продавца, остатки, DBS, Самовывоз |
| `content-api-sandbox.wildberries.ru` | карточки, категории, медиа |
| `discounts-prices-api-sandbox.wildberries.ru` | цены и скидки (нужны ненулевые цены для тестовых заказов) |
| `statistics-api-sandbox.wildberries.ru` | отчёты (до 4 мес. назад) |
| `supplies-api-sandbox`, `advert-api-sandbox`, `feedbacks-api-sandbox` | FBW, продвижение, отзывы — вне FBS-контура |

Лимит песочницы: **1 запрос/с на метод** (контент — суммарно). ID в песочнице
по паттернам `WB-GI-SAND-*`, `WB-TRBX-SAND-*`. Архивного метода нет.

### 4.3. Методы эмуляции FBS (`/api/v3/test/fbs/*`)

| Метод | Эффект |
|---|---|
| `POST /api/v3/test/fbs/orders/make` | создать тестовые задания, тело `orders[]{sku, amount}` 1..10 позиций; одна корзина = один `orderUid`; нужны остатки на FBS-складе и ненулевая цена |
| `PATCH /api/v3/test/fbs/orders/{orderId}/decline` | покупатель отменил |
| `PATCH /api/v3/test/fbs/orders/{orderId}/deliver` | прибыл в ПВЗ (`ready_for_pickup`) |
| `PATCH /api/v3/test/fbs/orders/{orderId}/receive` | получен (`sold`, тело `{code}` любой) |
| `PATCH /api/v3/test/fbs/orders/{orderId}/reject` | отказ при получении (`canceled_by_client`) |

Это закрывает прогон машины состояний Connector, идемпотентность и компенсации
без единого реального заказа.

### 4.4. Подтверждённые заглушки

Стикеры трансграничных заданий и `status/history` — всегда пустой 200; meta
необязательна; в контенте нет `locale`, карточка создаётся синхронно. Вывод из
Stage 18 §4.3 остаётся в силе: песочница валидирует контракт и логику, но не
физику стикера и не production-шлюз маркировки.

## 5. Схема тестирования wbconnector

Четыре уровня, по возрастанию стоимости и достоверности:

**Уровень 1 — unit и интеграционные с Postgres (уже заложены).** Механика
циклов, backoff, outbox, upsert-проекция. Без сети: WB-клиент за интерфейсом,
подменяется фейком. Дополнить: классификацию ошибок outbox (4XX permanent,
406 отложенный повтор, 429/5XX retry).

**Уровень 2 — контрактные тесты по записанным ответам.** Фикстуры из реальных
ответов песочницы (JSON), прогон парсеров и машины состояний. Именно здесь
фиксируются ловушки Stage 18: `SKUUploadDisabled`, ложно-успешное обновление
остатков, `409SupplyDeliverError` с детализацией, `MetaKeyNotRequired`.

**Уровень 3 — sandbox smoke (готов к выполнению).** Объединённый сценарий из
Stage 18 §4.4 и Stage 19 §9, теперь с методами эмуляции:

```text
 0. токен «Тестовый контур» (180 дней, все категории)
 1. content-sandbox: создать карточку (синхронно) → get/cards/list → chrtID
 2. discounts-prices-sandbox: установить цену (нужна для test-заказов)
 3. marketplace-sandbox: POST /api/v3/warehouses → PUT stocks по chrtID
    → POST stocks контрольное чтение; негатив: sku → 400 SKUUploadDisabled;
    негатив: неверные имена параметров → «успех» без изменения (ловим чтением)
 4. POST /api/v3/test/fbs/orders/make → GET /orders/new → наш ingest
 5. создать поставку → добавить задание (new → confirm)
 6. PUT meta/sgtin → POST orders/meta → зафиксировать decision
 7. deliver без КИЗ → 409 MetaValidationFail с детализацией
 8. ПЕРЕНОС: добавить задание из поставки A в поставку B → закрыть вопрос
    переноса фактом (подтвердить описание спеки запросом)
 9. deliver пустой поставки → 409 SupplyHasZeroOrders
10. deliver после исправления → QR (barcode?type=zplv)
11. test/fbs/supplies/{id}/close → проверить развилку sorted/reshipment
12. эмуляции покупателя: decline/receive/reject/defect → наша машина статусов
13. GET supplies/{id}/order-ids → сверка нашей проекции supply_orders
14. две поставки на один ключ группировки → проверить, ограничивает ли WB
```

Шаг 8 остаётся самым ценным: описание спеки — это `confirmed` по документации,
но поведение (снимается ли с исходной поставки атомарно, что со статусом,
что при разных `officeId`) надо увидеть глазами.

**Уровень 4 — production checks до пилота (из Stage 18 §5, без изменений).**
Пункты выдачи для возвратов в кабинете (шлюз 403, `proxy`), отзыв токена со
страницы `88508013`, состояние проверки маркировки для нашего кабинета, один
контролируемый реальный заказ для стикера/печати/полного КИЗ.

Ограничения уровня 3, которые надо помнить при оценке «всё зелёное»: лимит
1 зап/с не показывает поведение поллера под prod-лимитами; стикеры и
`status/history` — заглушки; шлюз маркировки не срабатывает.

## 5.1. Результаты smoke-прогона (2026-07-27, токен тестового контура GJ)

## 6. Следствия для архитектуры wbconnector

1. **Перенос заданий есть** → стратегия недосбора меняется: вместо «успеть
   закрепить КИЗ или отменить» добавляется «перебросить в поставку следующей
   волны». Волну можно удлинять после smoke-подтверждения. В модели данных
   `supply_orders` это переход `removed_at` + `removal_reason='moved'` и новая
   строка для целевой поставки.
2. **Состав поставки сверяем** через `order-ids` → `wb_reconcile` получает
   четвёртую функцию: сверка проекции `supply_orders` с WB. Проекция остаётся
   источником истины по истории (`removed_at` WB не отдаёт).
3. **Шлюз маркировки — таблица блокирующих `decision`**, а не три константы.
   Проверка дважды (на `SEALED` и перед `deliver`) подтверждается.
4. **Отмену стробировать по `isCancellable`** из `orders/status` — экономит
   лимит (4XX × 10).
5. **`isZeroOrder`** из `orders/new` — отмена без штрафа; учитывать в политике
   недосбора.
6. **Пути методов — в одном месте клиента**: миграция `/api/v3` →
   `/api/marketplace/v3` идёт по разделам, FBS — следующий кандидат.
7. **Окно reconcile ограничено 3 месяцами**; для более старого — архивный
   метод (только prod). Для пилота некритично, но в дизайн цикла вписать.
8. Типы токенов: интеграция — только Персональный или Сервисный (категории
   «Маркетплейс» + «Контент» + «Цены и скидки» для тестов), 180 дней,
   календарь перевыпуска — эксплуатационная задача.
9. **Собственный запрет на добавление заданий в закрытую поставку** (smoke §5.1:
   WB не отклоняет добавление даже в отгруженную и закрытую поставку). Переходы
   машины состояний должны проверяться на нашей стороне, а не доверяться шлюзу WB.
10. **Цепочка идентификаторов без WebApi** (утверждено 2026-07-27). Мастер
    `баркод ↔ vendor_code` — ENSI PIM (`sku_products`, ночные импорты из 1С;
    ApiV1 `sku_products:search`, инкремент по `id`-водяному знаку, append-only;
    связки неизменны, мутаций нет). `баркод → chrtID` — WB Content (§5.2:
    баркод строгий ключ, мультибаркод — 0,005%, алерт). WebApi НЕ является
    зависимостью wbconnector ни в одном варианте: целевая схема A — это
    доработка 1С (+`chrtID`), затем PIM забирает атрибут из 1С через WebApi в
    рамках своего импорта, а сервисы читают всё из PIM. Для wbconnector
    переход B→A — это то же чтение PIM с одним новым полем, а не новая
    интеграция. Разовая проверка полноты `api/Ref/IdMp` по пилотным SKU —
    ручное действие перед пилотом, не код.

## 7. Уверенность и неизвестное

### Confirmed

- перенос заданий между активными поставками описан в контракте
  `PATCH .../supplies/{id}/orders`; отдельного метода исключения нет;
- состав поставки читается через `GET .../supplies/{id}/order-ids`;
- `deliver` пустой поставки — 409 `SupplyHasZeroOrders`;
- полный набор `decision` с делением на допускающие/блокирующие;
- `isCancellable`, `isZeroOrder`, `isPickupPointShipmentAllowed`,
  `recommendedWhId`, `scanDt` «поставки или первого заказа»;
- `SKUUploadDisabled` в спеке; `GET /api/v3/orders` ограничен 3 месяцами;
- архивный метод `GET /api/marketplace/v3/fbs/orders/archive` (prod only);
- лимиты: 300/мин общий, 100/мин отмена, 1000/мин закрепление meta,
  10/мин DELETE остатков, 1/10 мин пропуск; 4XX × 10 для всех методов;
- песочница: методы эмуляции `/api/v3/test/fbs/*`, 1 зап/с, тестовый токен
  180 дней на все категории.

### Unknown / требует smoke

- фактическое поведение переноса (атомарность, статус, разные `officeId`);
- лимиты на число незакрытых поставок и заданий в поставке;
- пересчёт `recommendedWhId` при добавлении заданий;
- состояние проверки маркировки для нашего кабинета;
- точные числовые лимиты Базового токена для FBS-методов (в спеке единые
  300/мин; типизированные лимиты заведены в других разделах).
