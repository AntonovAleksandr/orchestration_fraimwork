# ТЗ: чтение остатков из OTS в `wbconnector`

**Кому:** разработчику `wbconnector` (Go).
**Дата:** 2026-08-14. Контракты сверены по коду OTS на этом срезе.
**Репозиторий:** `platform-new/wbconnector`.

## 1. Зачем

Нужны две вещи, и обе опираются на одно и то же — чтение свободного остатка из
OTS:

1. **Проверка баркода на входе тестового стенда.** Сейчас стенд создаёт тестовое
   сборочное задание по любому баркоду, потому что проверка остатка — заглушка,
   пропускающая всё. Тестировщик проходит пять шагов, получает задание в
   песочнице ВБ и падает на резерве в OTS, не понимая причины. Проверка должна
   отказывать сразу и словами.
2. **Цикл отправки остатков в ВБ** (следующая задача, не в этом объёме). Он
   читает тот же метод OTS, поэтому клиент нужно писать сразу пригодным для
   обоих: точечная проверка одного баркода и постраничная выгрузка.

## 3. Контракт OTS

### 3.1. Метод

`POST /Balance` на `OTS_BASE_URL`. Один эндпоинт на три режима, режим задаётся
полем `action_type`.

**Почему v1, а не v2 или v3.** В OTS три метода остатков, и все говорят разными
идентификаторами: v1 — баркодами, `v2/balance` — артикулами (в контроллере прямо
сказано, что ключ переводится в штрихкод и обратно), `GET api/v3/Balance/GetStock/{sender_idd}`
— `good_idd` из 1С. Наша карта построена на баркодах, потому что `chrt_id` для ВБ
достаётся только из баркода карточки. v2 заставил бы конвертировать артикул в
баркод ради того, что OTS и так делает внутри, v3 говорит третьим
идентификатором, которого у нас нет вообще.

### 3.2. Запрос

```json
{
  "guid": "<uuid v4>",
  "timestamp": "<unix millis, строкой>",
  "action_type": "Stock_Changed_Request",
  "order_status": "",
  "id_warehouse": "9148",
  "items": ["4680622633310"],
  "limit": 1000,
  "offset": 0
}
```

| Поле | Обяз. | Смысл |
|---|---|---|
| `guid` | да | Идентификатор сообщения. |
| `timestamp` | да | Unix millis **строкой**. Для `Stock_Changed_Request` это ещё и отметка «что изменилось начиная с этого момента» — см. ловушку 4.1. |
| `action_type` | да | `Stock_Changed_Request` / `Stock_Full_Request` / `Stock_Online_Request`. Иное значение — `400`. |
| `order_status` | нет | Методом не используется, но поле есть в общем заголовке. |
| `id_warehouse` | да | `9148`. Принимается и ИДД `00005550031258229` — `WarehouseTypeHelper.FromId` знает оба варианта после правок OPSLOG-3461. Рекомендую передавать ИДД: он уже лежит в `OTS_WAREHOUSE_MAP`, а числовой код нигде в конфигурации коннектора не хранится. |
| `items` | для Online | Массив баркодов **строками**, но OTS парсит их как `long` — непарсящееся значение уронит запрос. |
| `limit`, `offset` | нет | Пагинация работает только когда **заданы оба**: в репозитории `if (limit != null && offset != null)`. Передавать по одному бессмысленно. |

### 3.3. Ответ

```json
{
  "action_type": "Stock_Changed_Request",
  "guid": "…",
  "timestamp": 1755172800000,
  "items": [
    {"barcode": "4680622633310", "id_warehouse": "9148", "available_quantity": 5}
  ],
  "count": 1234
}
```

- `items[].barcode` — баркод строкой, ключ соединения с нашей картой;
- `items[].available_quantity` — **свободный** остаток: остаток минус сумма
  резервов по складу;
- `items[].id_warehouse` — всегда числовой код склада, независимо от того, что
  передали в запросе;
- `count` — общее число строк под запрос, по нему и листать.

### 3.4. Режимы

| `action_type` | Что делает | Где нужен |
|---|---|---|
| `Stock_Online_Request` | Точечно по списку баркодов из `items`. Пагинация игнорируется. Пустой `items` даёт пустой ответ, а не ошибку. | Проверка баркода в стенде |
| `Stock_Changed_Request` | Что изменилось начиная с `timestamp`. Постранично. | Цикл остатков, инкремент |
| `Stock_Full_Request` | Всё, постранично. | Цикл остатков, редкая полная сверка |

## 4. Ловушки, проверенные по коду

### 4.1. `timestamp` служит двум целям одновременно

Для `Stock_Changed_Request` OTS берёт **тот же** `timestamp` из заголовка
сообщения и использует его как границу выборки:

```csharp
var timestamp = DateTimeOffset.FromUnixTimeMilliseconds(long.Parse(@params.timestamp)).ToUniversalTime();
... GetFreeStockAsync(warehouse: wh, from: timestamp, ...)
```

То есть нельзя поставить туда «сейчас» как метку отправки — уедет пустой ответ.
В инкрементальном режиме там должна быть **сохранённая отметка прошлого прохода**.

### 4.2. Полная выгрузка — это весь товарный универсум, а не склад

Базовый запрос идёт `from GoodBalances` с левым присоединением остатка склада.
Значит `Stock_Full_Request` вернёт **все** товары справочника, а не только те,
что лежат на 9148; у отсутствующих количество будет нулевым. Это не ошибка, но
объём другой на порядки, и полную сверку нельзя гонять часто.

### 4.3. Заблокированный товар отдаёт ноль

В запросе есть `case when balance.IsBlocked = 1 then 0 else …`. Ноль по
заблокированному товару — правильный ответ, отличить его от «нет на складе»
по этому методу нельзя.

### 4.4. Инкремент пропускает создание резерва

Отметка `BalanceActionTimestamp` двигается при движении от 1С и при снятии
резерва, но **не** при его создании: процедура `Do_Reserve_*` только вставляет
строку. Значит инкрементальная выборка не увидит уменьшение свободного остатка
от покупки. Это расхождение Р10 в `OPSLOG-3461-ots-implementation.md`; лечится
не здесь, а периодической полной сверкой. В рамках этой задачи достаточно знать,
что инкремента одного недостаточно.

## 5. Задача 1: чтение остатков в клиенте OTS

Файл: `internal/adapters/ots/balance.go` (новый).

Методы (имена ориентировочные, важна форма):

```go
// StockOf returns free stock for the given barcodes. Отсутствующие в ответе
// баркоды в карту не попадают — вызывающая сторона обязана это заметить, а не
// получить молчаливый ноль.
func (c *Client) StockOf(ctx context.Context, warehouse string, barcodes []string) (map[string]int, error)

// StockChangedSince returns one page of stock changed at or after `since`.
func (c *Client) StockChangedSince(ctx context.Context, warehouse string, since time.Time, limit, offset int) (StockPage, error)

// StockAll returns one page of the full stock.
func (c *Client) StockAll(ctx context.Context, warehouse string, limit, offset int) (StockPage, error)
```

```go
type StockPage struct {
	Items []StockItem // barcode + available_quantity
	Total int         // count из ответа, для пагинации
}
```

Требования:

1. **Отсутствующий баркод — не ноль.** `StockOf` не должен подставлять нули за
   OTS. Ноль и «OTS про такой товар не знает» это разные факты, и для стенда
   именно второй означает «баркод выбран неправильно».
2. **`guid` на каждый запрос свой**, `timestamp` — по правилу из 4.1: для
   `StockChangedSince` это переданный `since`, для остальных — текущее время.
3. **Ошибки OTS классифицировать** тем же способом, что уже сделано в
   `internal/adapters/ots/errors.go`: транзиентное отличается от постоянного,
   иначе цикл остатков будет насмерть ретраить `400`.
4. **Пагинация** передаётся только парой `limit`+`offset`; передача одного
   значения бессмысленна (см. 3.2).

## 6. Задача 2: подключить к стенду

Файл: `internal/testharness/ports.go`, интерфейс уже есть:

```go
type StockChecker interface {
	Check(ctx context.Context, barcode string) error
}
```

Сейчас в него подставлена `StubStockChecker`, пропускающая всё. Нужна реализация
поверх `StockOf` с режимом `Stock_Online_Request`, и подстановка её в контейнере
там, где стенд собирается.

Поведение `Check`:

| Ситуация | Результат |
|---|---|
| OTS не знает баркод | Ошибка с текстом, называющим баркод: товара нет в справочнике OTS |
| Известен, свободный остаток `0` | Ошибка: остатка на складе нет, задание создавать нечем |
| Свободный остаток `> 0` | `nil` |
| OTS недоступен | Ошибка, отличимая от двух первых: это не «баркод плохой», а «проверить не смогли» |

Последняя строка важна: тестировщик должен понимать, менять ему баркод или
звать разработчика.

Заглушку **не удалять** — она нужна для тестов и для запуска стенда без OTS.
Выбор реализации делается там, где собираются зависимости, по наличию
`OTS_BASE_URL`.

## 7. Приёмка

Автотесты:

1. `StockOf` на подставном HTTP-сервере: форма запроса (`action_type`, `items`,
   `id_warehouse`), разбор ответа, отсутствующий баркод не превращается в ноль.
2. `StockChangedSince`: в `timestamp` уходит именно переданный `since`, а не
   текущее время — это защита от ловушки 4.1.
3. Пагинация: `limit`+`offset` уходят только парой; `Total` берётся из `count`.
4. `Check` стенда: четыре случая из таблицы §6, ошибки отличимы друг от друга.
5. Классификация ошибок: `400` не помечается транзиентной.

Живая проверка на стейдже (OTS уже задеплоен, склад 9148 существует):

6. `Stock_Online_Request` по любому баркоду отвечает `200` с пустым `items` —
   склад пока не наполнен, и это нормальный случай, который код обязан
   переживать молча.
7. Страница стенда по любому баркоду отказывает с внятным текстом, а не создаёт
   задание.
