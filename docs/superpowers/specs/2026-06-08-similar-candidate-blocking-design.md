# Similar: candidate blocking (пре-фильтр кандидатов) — дизайн

**Дата:** 2026-06-08
**Статус:** утверждён к реализации
**Сервис:** `recomendationengine` (движок «Похожие», `internal/discovery/similar/`)

## Контекст и проблема

`FindSimilar` грузит пул кандидатов = **вся секция** (~2864 для women, `defaultPoolLimit=1_000_000`) и
прогоняет дорогой `RankSimilarCandidates` по **всем** кандидатам (с токенизацией заголовков на каждой
паре), чтобы вернуть топ-≤40. Cold-латентность ~1.6 с; полный предрасчёт базы = Σ(n² по секциям)
≈ 19.3M пар. ~99% дорогой работы выбрасывается.

## Решение

**Candidate blocking** — дешёвый in-memory пре-фильтр перед ранжированием: скорим не всю секцию, а
только кандидатов, делящих с базовым товаром хоть один сильный признак.

**Эмпирически проверено на живой базе (8.3k товаров, 12 товаров × топ-20):**
- recall: `leaf OR color` 86% → `+parent` 94% → `+article_prefix` **97%**;
- размер блока (4 ключа): median 282 vs секция 2388 (**~8×** меньше дорогих скорингов);
- `product_type` пуст во всём фиде → как ключ НЕ используется.

## Решения (зафиксированы)

1. **Флаг `cfg.Blocking.Enabled`, дефолт ON.** ~3% выдачи меняется (на валидные похожие из той же
   leaf/parent). Выключается через стратегию (admin-tunable, как остальные веса Михаила).
2. **4 блок-ключа:** `LeafCategory` OR `NormalizedColor` OR `rowParentCategory` OR `articlePrefix`
   (переиспользуем существующие хелперы — блок совпадает с тем, как скорер понимает категорию/префикс).
3. **Widen-fallback:** если `|блок| < cfg.Blocking.MinCandidates` (дефолт 60) → полный пул (текущее
   поведение) для этого товара. Защищает товары с пустым/крошечным блоком, гарантирует наполнение карусели.
4. **Ветка** `task-similar-blocking` (отдельно от sqlite/сплита), не мержим — предложение для Михаила.

## Архитектура

- **Точка вставки:** `FindSimilar` ([service.go](../../../platform-new/recomendationengine/internal/discovery/similar/service.go)),
  между `preparedPool(...)` (пул секции, кэш 30 мин — НЕ меняется) и `s.rankedCandidates(...)`.
- **Новая функция** `blockCandidates(base ProductRow, pool []ProductRow, cfg StrategyConfig) []ProductRow`
  в пакете `similar`: фильтрует пул по блок-предикату; если результат меньше `MinCandidates` — возвращает
  исходный пул (fallback).
- **Блок-предикат** `inBlock(base, cand)` переиспользует `articlePrefix`, `rowParentCategory`,
  `categoryParts`, поля `LeafCategory`/`NormalizedColor`.
- **Конфиг:** новое поле `Blocking struct { Enabled bool; MinCandidates int }` в `StrategyConfig`
  (config.go), с дефолтами в `DefaultConfig()` (`Enabled:true, MinCandidates:60`).
- **Кэш:** ранжируется блок → `rankCache` хранит ранжированный блок (меньше; попутно снимает риск ~4 ГБ).
  `cfgKey = strategyCacheKey(cfg)` (json от cfg) → при смене флага ключ авто-меняется, стейл не отдаётся.

## Что НЕ меняется

Формула скоринга, веса, пороги, attribute-rules, контракт публичного/admin API, SQL, миграции,
`preparedPool`/`poolCache`. Меняется только **сколько кандидатов уходит в ранжирование**.

## Верификация (на живом локальном стенде)

1. `GOWORK=off go build/vet/test` — зелёные.
2. **Идентичность выдачи ON vs OFF:** для выборки ≥30 товаров сравнить топ-20 при
   `Blocking.Enabled=true` vs `false` → доля совпавших позиций/множеств (ждём ~97% set-overlap).
3. **Латентность:** cold p50/p95 `/similar` до/после (ждём ~1.6 с → ~200 мс).
4. Прогон через nginx/стенд — смоук, что endpoint жив.

## Риск

- **~3% выдачи меняется** при включённом флаге (дефолт ON). Изменённые позиции — валидные похожие
  (та же leaf/parent), не мусор. Отключается флагом. Точная идентичность не гарантируется (блокинг —
  приближение by design); widen-fallback страхует только пустые/крошечные блоки, не полноту хвоста.
