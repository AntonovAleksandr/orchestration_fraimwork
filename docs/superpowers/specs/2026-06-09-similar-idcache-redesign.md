# Similar: id-кэш вместо rankCache/poolCache — редизайн кэширования

**Дата:** 2026-06-09
**Сервис:** `recomendationengine` (`internal/discovery/similar/`), ветка `task-similar-blocking`

## Проблема (как пришли сюда)

Публичный путь `/similar` потребляется через BFF/IntGateway по контракту `RecommendationSource → []ProductID`:
артикул → массив id похожих, обогащение — на BFF из catalog-cache. То есть движку нужно отдавать
**только id**. А кэшировалось «не то»: `rankCache` хранил полный ранжированный список ВСЕХ кандидатов
секции (Σ(n²)) через указатели в `poolCache` → ~460МБ-3ГБ, прогрев OOM'ил >8ГБ.

## Целевая модель (зафиксирована с пользователем)

- `/similar` отдаёт **только массив id** (без name/image/price, без score).
- Кэшируем ровно то, что отдаём: **топ-K id на артикул**.
- Хранение id (строк), а не указателей, **развязывает кэш с пулом** → постоянный пул не нужен.
- Пул — **транзиентный вход для расчёта** (грузится из БД на время ранжирования, освобождается).

## Контракт API

`GET /products/:id/similar`, `GET/POST /products/similar`:
```json
{ "items": ["GFU000078-1", "GAC026361-1", "GJC007135-1"] }
```
Батч (`articles[]`) — сгруппировано по запрошенным артикулам (каждый → `items: []id`).
Параметры `limit`, `exclude_product_ids`, `section` сохраняются (применяются к id-списку).

## Архитектура кэшей

| Слой | Было | Стало |
|---|---|---|
| `rankCache` (полные ранж-списки, указатели) | ~Σ(n²), ~460МБ+ | **удалить** → заменить `idCache` |
| `idCache` (новый) | — | `(article, section, cfgKey) → []string` топ-K id, TTL 30мин. ~10МБ на 8к |
| `poolCache` (постоянный, данные секций) | держался ради указателей rankCache | **удалить как постоянный**; пул грузится транзиентно при расчёте |
| `Cache` (5-мин result, мёртвый) | не используется | **удалить** |

## Потоки данных

**Отдача (hit, горячий путь):**
```
key=(groupKey, section, cfgKey) → idCache.Get → filter(exclude) → [:limit] → []id
```
БД/пул не трогаются.

**Расчёт (miss или прогрев):**
```
загрузить пул секции из Postgres (транзиентно)
→ RankSimilarCandidates(base, pool, cfg)   // score'ы транзиентно
→ PickSimilarFromRanked(ranked, {base}, K, cfg)  // каскад порогов, топ-K, K=100
→ извлечь item.ID → []string (топ-K)
→ idCache.Set(key, ids)
→ пул и пары освобождаются (GC) — хвост не копится, нет OOM
```
K=100 — запас над макс. limit=40 (под `exclude` и каскад).

## Прогрев

`WarmRanked(ctx, sections)`: грузит пул каждой секции **локально** (в переменную, не в постоянный кэш),
прогоняет все карточки секции → кладёт `[]id` в `idCache`, локальные пулы освобождаются. Триггеры те же
(старт + после фид-`Invalidate`). Память прогрева ограничена (пул одной секции + накопление id-кэша ~10МБ)
→ GOMEMLIMIT и low-concurrency больше не критичны (можно вернуть нормальную конкуренцию).
single-flight (`warmMu.TryLock`) — оставляем.

## Что НЕ меняется

- Алгоритм скоринга, веса, пороги, `RankSimilarCandidates`, `PickSimilarFromRanked` (каскад) — переиспользуем.
- Блокинг (default OFF, флаг) — остаётся.
- **Админ-превью** (`FindSimilarExplain`) — live, со score-breakdown; грузит пул транзиентно (~8мс на превью).

## Верификация (на стенде)

1. `GOWORK=off go build/vet/test` зелёные.
2. Прогрев завершается, память **единицы-десятки МБ** (idCache ~10МБ + транзиентный пул), `restarts=0`.
3. Латентность hit ~мс.
4. **Идентичность:** топ-N id из нового пути == топ-N id текущего (полного) ранжирования на выборке.
5. Ответ `/similar` = `{"items":["id",…]}`, без enrichment/score.

## Риски

- K=100 обрезка: теоретически может сместить хвост при экзотическом каскаде — проверяю идентичность на стенде, при расхождении ↑K.
- Смена контракта `/similar` (теперь только id). Для нового BFF/IntGateway-пути — целевое; если есть прямые
  потребители enrichment (сайт/моб напрямую) — согласовать (но IntGateway-контракт = []id, обогащение на BFF).
- Рефактор затрагивает hot-path движка Михаила — ветка `task-similar-blocking`, не мержить без ревью.
