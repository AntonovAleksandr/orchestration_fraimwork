## 1. Цель

На commit не отказывать клиенту из‑за дрейфа ключа пересчёта OMS, если **выбор клиента всё ещё существует**.

Клиент видит один 400 и часто оверлей «Технические работы». До IS заказ не доходит (BFF) или IS режет повторным поиском (1002).

## 2. Продуктовые правила (зафиксированы)

| Способ | Что нельзя менять | Что можно обновить молча |
|---|---|---|
| Курьер | календарный день + склад отгрузки + окно (слот) | актуальный `id` интервала (хеш) |
| ПВЗ | id пункта | дата, склад отгрузки |
| Магазин | id магазина + тип (`pickupinstore` / `reserveinstore`) | дата, склад отгрузки |

`calculateDaysLimit: 1` на экране чекаута **не меняем**. На commit тоже оставляем `1`, чтобы окно BFF совпадало с IS.

Чужой ПВЗ / чужой магазин / другой курьерский день — не подставляем. Если выбранного нет в свежем расчёте — 400.

## 3. Почему ломается

Commit всегда пересчитывает доступность. Матч сейчас слишком жёсткий.

- **Курьер (BFF):** `id`, затем `Collection::where('date', Carbon)` — объекты не равны календарному дню. В IS уходит **клиентский** `deliveryCourierId`, даже если дата нашлась. IS V4 ищет **только точный id** при `calculateDaysLimit: 1`.
- **ПВЗ (BFF):** сначала фильтр по складу, потом id пункта. Склад уехал — пункт в другом пакете не виден. IS: id + склад + **дата == promissedDeliveryDate**.
- **Магазин (BFF):** для `pickupinstore` пакеты с другим складом отбрасываются. Есть unit-тест, который **требует** null, если склада нет — его надо перевернуть. IS: id + дата + склад.

## 4. Контракт матча (один на BFF и IS)

### 4.1 Курьер

Интервалы — плоский список `{id, date, dispatchWarehouse, ...}`.

1. `id === deliveryCourierId` (или `shipping.deliveryOptionId` в IS).
2. Иначе `date` как `Y-m-d` **и** `dispatchWarehouse` совпадают с запросом — **и такой кандидат ровно один**.
3. Кандидатов несколько → не найдено (400), в лог `path = ambiguous` с числом кандидатов и их окнами.
4. Иначе не найдено.

Пункт 3 обязателен: на commit клиент присылает только `deliveryCourierId`, `date`, `dispatchWarehouseId` — окна в запросе нет, восстановить его нечем. По выборке 500 commit-ответов OMS из прода (2026-08-26) 1054 из 1070 групп «день + склад» содержат один интервал, а 16 — по 5–6 двухчасовых слотов Яндекс-экспресса (`yataxi_two_hours_delivery`, одинаковая цена 499, разные `from`/`to`). Взять первого означало бы молча сдвинуть окно экспресса на часы.

В create уходит **id найденного** интервала. Склад и дата — из найденного интервала (день тот же).

### 4.2 ПВЗ

Пакеты `{inventory.dispatchWarehouse, pickupPoints.list[]}`.

1. Пункт с тем же `id` в пакете с запрошенным складом.
2. Иначе тот же `id` в любом пакете (берём первый).
3. Иначе не найдено.

Дата и склад — из найденного пакета/пункта. В IS уходит этот склад, не клиентский устаревший.

### 4.3 Магазин

Пакеты `{inventory.dispatchWarehouse, pickupStores.list[]}`.

1. Магазин с тем же `id` и `deliveryTypeId`, предпочтительно пакет с запрошенным складом (`pickupinstore`). Для `reserveinstore` склад пакета = id магазина — как сейчас.
2. Иначе тот же `id` + тип в другом пакете.
3. Иначе не найдено.

Дата и склад — из найденного пакета.

## 5. Сообщения 400 (BFF)

`CommitOrderAction` сейчас кидает одну фразу на все типы. Развести:

| Тип | Текст |
|---|---|
| Курьер | `Выбранный интервал доставки больше недоступен.` |
| ПВЗ | `Выбранный пункт выдачи больше недоступен.` |
| Магазин | `Выбранный магазин больше недоступен.` |

Мобилка может по-прежнему мапить любой 400 в «Технические работы» — это **вне этого MR**, отдельный follow-up.

## 6. Логи

BFF: `Log::info` / `warning` с ключом `checkout.delivery.rematch` — `type`, `path` (`id` / `date_warehouse` / `warehouse_fallback` / `miss`), запрошенные и найденные id/склад/дата.

IS: существующий `trace(..., ErrorCodeEnum::DELIVERY)` — добавить `match_path`.

## 7. Выкатка

Контракт `v4/order/create` не меняется: те же поля, другое содержимое `deliveryOptionId` / `dispatchWarehouseId` / `promissedDeliveryDate`.

Порядок свободный. Сначала BFF снимает ~289 400 до IS. Сначала IS снимает 1002 у тех, кого BFF уже пропустил. Откат любого слоя безопасен.

Не трогаем: OMS logistics, экран интервалов, pickup/store quote API, мобильный оверлей.

## 8. Не в скоупе

- Расширение контракта commit полями `from`/`to` курьерского окна — только это закроет оставшиеся ~1,5% (Яндекс-экспресс), где сейчас честный 400.
- Пиннинг `dispatchDate` / сессия чекаута (TO-BE).
- Мобильный маппинг 400 → «Технические работы».
- `fillSelectedCourierDeliveryInterval` (не V4) — только если на проде ещё есть create V3; иначе follow-up.
- Автоподмена другого ПВЗ/магазина/дня курьера.

## 9. Приёмка

- Курьер: id сменился, день+склад те же → commit 200, в IS актуальный id.
- ПВЗ/магазин: тот же пункт, другая дата и/или склад → commit 200, в заказе новая дата/склад.
- Пункта/магазина/слота нет в ответе → 400 с текстом по типу, без вызова create (BFF) или IS 400 (если дошли).
- Экран чекаута по-прежнему окно 1 день.
