# Similar: blocking default OFF + проактивный прогрев rankCache — дизайн

**Дата:** 2026-06-09
**Сервис:** `recomendationengine` (`internal/discovery/similar/`), ветка `task-similar-blocking`

## Контекст

Эмпирика на стенде показала: блокинг даёт ~7× по латентности, но меняет ~12% выдачи
(категориальная когерентность) — это product-решение. Поэтому **блокинг переводим в default OFF**
(opt-in через strategy-документ). Отдельно решаем cold-латентность через **проактивный прогрев**:
сейчас `rankCache` заполняется лениво при первом запросе (cold ~319мс при OFF); хотим, чтобы кэш был
**всегда прогрет**, а не по запросу.

## Решения (зафиксированы)

1. **Blocking default OFF**: `DefaultConfig()` и `Document.ToSimilarConfig()` → `Blocking.Enabled=false`.
   (Off-switch через strategy-документ уже работает; включается `blocking.enabled=true` при `enabled=true`.)
2. **Греем полный `rankCache`** (а не bounded top-N результат) — выбор пользователя: проще, ноль
   изменения поведения. Цена — память: на 8к ≈ ~3ГБ, на проде десятки ГБ. **Не масштабируется на прод**
   как есть; bounded-вариант (top-N result-Cache, ~64МБ) отложен.

## Архитектура

- **`WarmRanked(ctx, sections []string) error`** в `service.go`:
  - грузит пул `"all"` (все опубликованные карточки) + пер-секционные пулы (через `preparedPool`, кэш `poolCache`);
  - для каждой карточки `base` вычисляет `effSection = base.RootSection` если валидна, иначе `"all"`
    — **зеркалит логику `FindSimilar`**, чтобы ключ `rankCache` (`productGroupKey|section|cfgKey`)
    совпадал с тем, что строит боевой запрос `/products/:id/similar`;
  - воркер-пул на `runtime.NumCPU()` вызывает `s.rankedCandidates(base, pool, effSection, cfgKey, cfg)`
    — он считает ранжирование и кладёт в `rankCache`.
- **Триггеры:**
  - старт: в `cmd/similar/main.go` после `WarmPools` — отдельная горутина, таймаут ~30 мин
    (прогрев не блокирует старт);
  - после фида: в `container.go` change-hook — после `similarSvc.Invalidate()` запускаем
    `go similarSvc.WarmRanked(...)` в фоне (фид раз в час → прогрев раз в час).
- **Что НЕ меняется:** формула скоринга, контракт API, SQL, `FindSimilar`/`rankedCandidates` логика
  (прогрев лишь заранее наполняет тот же кэш теми же ключами).

## Верификация (на живом стенде)

1. `GOWORK=off go build/vet/test` — зелёные.
2. Прогрев отрабатывает (лог `ranked warmed N cards`), память пода не падает (OOM) на 8к.
3. **Латентность:** после прогрева дернуть случайные карточки, которые НЕ трогали вручную →
   warm (~мс), не cold (~319мс).
4. **Идентичность выдачи:** топ-20 после прогрева == live-расчёт без прогрева (прогрев = тот же
   расчёт заранее, ключи совпадают).

## Риски / ограничения

- **Память:** полный rankCache на всю базу ≈ ~3ГБ (8к) / десятки ГБ (прод). Для прод-масштаба
  нужен bounded-вариант (top-N result-Cache) — отложено осознанно.
- **CPU после фида:** прогрев всех ~8к при OFF ≈ ~5 мин на 8 ядрах, раз в час. Фоновый, не блокирует.
- Прогрев греет под **активную** стратегию/конфиг; при смене стратегии (`Invalidate`) перегревается.
