# OPSOMN002-373: сохранение клиентской цены Яндекс Express

## Задача

Исправить оформление Яндекс Express в двух сервисах:

- `platform/integration/integration` — ИС.
- `platform/ensi/apps/customers-api-web` — BFF.

При повторном расчёте найти тот же слот, даже если его OMS ID изменился из-за цены. В заказ, оплату и чек должна попасть ровно та клиентская цена доставки, которая была показана для выбранной опции на чекауте. Повышение и снижение цены перевозчика не меняют подтверждённую клиентскую цену.

Пример: показали 550 ₽; повторный ответ содержит 560 ₽ или 540 ₽; `shipping.deliveryCost` остаётся 550 ₽.

Команда OMS подтвердила: OMS не перезаписывает `shipping.deliveryCost`; стоимость Яндекса может обновлять только `actualDeliveryCost`. Изменения OMS не требуются. Это подтверждение команды, а не результат нашего сквозного теста.

## Границы

Новая логика применяется только при одновременном выполнении:

```text
deliveryTypeId = expressdelivery
carrierId      = yandex
tariffId       = yataxi_two_hours_delivery
```

Остальные доставки сохраняют прежнее поведение. Классифицировать опцию по исходным данным OMS; не по фронтовому `deliveryType=delivery` и не только по префиксу токена.

Не менять фронт, мобильное приложение, OMS и публичный набор полей API. Не добавлять Redis, таблицы, сохранение интервалов, новый сервис или endpoint. Повторные запросы интервалов оставить. Не менять товарные скидки, бонусы, сертификаты и идемпотентность создания заказа.

## Контракт подписанного ID

ИС заменяет `id` целевой опции на строку `eq1.<base64url(payload)>.<base64url(HMAC-SHA256)>`. Фронт возвращает её в существующем поле выбранного интервала. В OMS при создании заказа передаётся обычный актуальный ID, не токен.

Подписанные данные:

- версия формата и исходный OMS ID;
- показанная клиентская цена, целое число копеек;
- склад, город, перевозчик, тариф, тип доставки, дата, начало и конец слота;
- отпечаток нормализованного контекста: состав корзины, количества, цены/сумма, участвующие в расчёте доставки, и адрес назначения;
- окончание действия, вычисленное из даты и конца выбранного слота с учётом его часового пояса.

**Стабильность:** одинаковые входные данные дают одинаковый токен. Не включать случайный nonce или текущее время каждой выдачи: мобильный клиент сравнивает ID при обновлении списка. Отдельный TTL «15 минут с момента выдачи» в эту правку не входит. Актуальность проверяется повторным ответом OMS и окончанием выбранного слота. Новое предложение с другой показанной ценой вправе иметь другой ID.

**Нормализация:** определить один формат для выдачи, BFF commit и ИС create. Отсортировать позиции корзины; одинаково обработать дубли SKU, числовые типы и даты. Нормализовать разные названия полей адреса к одному формату. Не включать `filterSettings`, AB-параметры и порядок JSON-ключей. Приоритет идентификации адреса — FIAS; fallback по тексту должен сохранять различия домов. Отсутствие обязательного контекста не считать совпадением. Не добавлять привязку к customer/cart ID, которых нет в этих запросах.

**Проверка:** версия, размер и структура токена, HMAC через constant-time comparison, типы и диапазоны полей, срок, целевая комбинация доставки и соответствие текущему контексту. Повреждённый, просроченный или неподходящий токен отклонять существующим механизмом ошибок checkout до создания заказа. Не переходить на обычный поиск и свежую цену после ошибки проверки.

Секрет — отдельная настройка `EXPRESS_DELIVERY_QUOTE_KEY`, одинаковая в ИС и BFF данного окружения. Не использовать разные `APP_KEY`, не хранить секрет в коде, не логировать токен целиком. Для ротации на первом этапе допустим перевыпуск предложения через обновление чекаута; старую подпись не принимать без проверки.

## Изменения ИС

### Выдача

Файл `www/app/Service/UserApi/Services/V2/Delivery/DeliveryService.php`:

1. `getCourierDeliveryIntervalsV1()` — подписывать ID целевых опций перед возвратом результата, после вычисления отображаемой цены и фильтрации.
2. `getDeliverySummary()` — подписывать ID целевых опций в `inventories[].options[]`, учитывая склад из inventory. Вычислять `selectedInterval` после замены ID, чтобы он совпадал с ID опции.
3. Проверить существующее определение `isSelected`/`deliveryIntervalFilter`: подписанный ID не должен сбрасывать выбор того же слота. Для сопоставления использовать проверенные данные слота, если текущий код сравнивает сырые ID.

Не подписывать ответы в общем OMS connector: он используется при повторных внутренних расчётах. Не изменять выдаваемую цену при упаковке ID.

### Создание заказа

Файл `www/app/Service/UserApi/Services/V4/Order/OrderService.php`, метод `fillSelectedCourierDeliveryIntervalV4()`:

1. Прочитать и проверить исходный токен из `shipping.deliveryOptionId` до его замены свежим ID.
2. Проверить контекст против текущих серверных данных корзины/адреса.
3. В повторном ответе OMS найти ровно один интервал по полному ключу: тип доставки, склад, город/контекст города, перевозчик, тариф, дата, `from`, `to`. Цена и ID в этот ключ не входят.
4. Нет совпадения или несколько совпадений — существующая ошибка выбора интервала. Не выбирать ближайший, первый или единственный интервал другого времени/склада.
5. Заполнить поля:

| Поле | Источник |
|---|---|
| `deliveryCost` | Проверенная клиентская цена из исходного токена |
| `actualDeliveryCost` | Одноимённое поле актуального интервала OMS |
| `deliveryOptionId`, `deliveryIntervalId` | Актуальный исходный ID OMS |
| Сроки, склад, перевозчик, тариф и остальные логистические поля | Найденный актуальный интервал |

Не путать `actualDeliveryCost` со свежим `deliveryCost`: клиентский прайсинг может отличаться от себестоимости. Суммы на существующей границе ИС/OMS остаются в рублях; в токене — копейки. Преобразование явное, без дополнительного округления показанной цены.

Существующий расчёт `totalCost`/`payableCost` использует `shipping.deliveryCost`. Проверить, что последующие участки до OMS create и формирования платежа его не заменяют.

## Изменения BFF

Файл `app/Domain/Orders/Actions/CourierCommonDeliveryDataAction.php`:

1. Для подписанного ID проверить подпись, срок и контекст текущего checkout.
2. После повторного запроса найти ровно тот же слот по полному ключу. Учесть, что свежие опции ИС уже могут содержать подписанные ID: их нельзя воспринимать как сырой OMS ID.
3. В `CommonDeliveryData.deliveryCost` оставить цену из исходного токена.
4. В `CommonDeliveryData.intervalId` оставить исходный токен, полученный от клиента. `ShippingOptions::fromRequestAndCommonDeliveryData()` должен передать его в ИС через существующий `deliveryOptionId`.
5. Ни на одном промежуточном шаге не заменять исходный токен токеном свежей котировки. Для остальных типов доставки сохранить прежнюю ветку.

Добавить небольшие классы подписи/проверки и нормализации в существующие структуры двух сервисов. Не создавать ради этого отдельный репозиторий или инфраструктуру. Межсервисную совместимость закрепить общими тестовыми примерами payload/token/context.

## Старые ID и выкладка

Для целевого Яндекс Express неподписанный ID не содержит доказуемой исходной цены. Не применять к нему fallback с новой ценой: вернуть существующую ошибку с указанием обновить варианты доставки. Старые открытые чекауты могут потребовать обновления. Для остальных доставок неподписанные ID остаются штатными.

Подготовить конфигурацию ключа и приём токена в обоих сервисах до включения выдачи подписанных ID. Использовать существующий механизм флагов; при его отсутствии добавить один флаг выдачи в ИС, по умолчанию выключенный. Проверка токена на приёме не должна зависеть от этого флага. Не включать выдачу, пока BFF и ИС create не готовы её принимать. Не выполнять деплой в рамках реализации.

## Проверки и критерии приёмки

Автотесты с подменой ответов OMS, без реальных заказов и платежей:

1. Было 550 ₽, стало 560 ₽, ID изменился, слот прежний → успешно, `deliveryCost=550`, сумма заказа учитывает 550, актуальный OMS ID передан дальше.
2. Было 550 ₽, стало 540 ₽ → клиентская цена также 550.
3. `actualDeliveryCost` отличается от обоих клиентских тарифов → сохраняется именно актуальная себестоимость.
4. Два разных слота одного дня и склада → выбирается исходный по `from/to`; исходный исчез или совпадение неоднозначно → ошибка, без создания заказа.
5. Подмена цены/подписи, повреждённый токен, неподдерживаемая версия, истечение срока, изменение корзины или адреса → ошибка, без fallback и OMS create.
6. Изменение порядка товаров/JSON-ключей и эквивалентное представление адреса не ломают проверку; смена дома или количества товара ломает.
7. ИС выдаёт токен → BFF проверяет и сохраняет его → ИС create проверяет тот же токен. Свежий ответ с другой ценой не подменяет исходный токен.
8. Повторная одинаковая выдача даёт одинаковый ID; `selectedInterval` и `isSelected` согласованы с options. Проверить фактические пути сайта и мобильного приложения, включая ограничения длины ID.
9. Обычная доставка, ПВЗ, самовывоз и другие express-тарифы проходят существующие тесты без нового поведения.
10. Старый неподписанный ID целевого Express не приводит к заказу с незаметно изменённой ценой.

На stage после согласованной выкладки: воспроизвести изменение цены между выдачей и commit; проверить цену в созданном заказе, сумме платежа и строке доставки чека. Не инициировать списание реальных денег ради проверки. Если stage-проверка недоступна, явно оставить её невыполненной в отчёте.
