# Ревью intgateway: импорт позиций категорий — нужны исправления

Дата: 2026-09-16. Репозиторий: `$WORKSPACE/platform-new/intgateway`.
База: `aa8053e`, ветка `codex/category-position-imports`; проверены tracked и untracked изменения.
Нормативный документ: [ТЗ B, редакция 3](../superpowers/plans/2026-09-15-intgateway-category-import-spec.md).
Одобренный опубликованный pimclient: `v0.2.0`, коммит `932c0e1`.

## Инструкция исполнителю

Исправить замечания ниже в текущей реализации. Сначала воспроизвести соответствующие дефекты тестами. Не менять PIM, AutoMerch, pimclient или общую HTTP-библиотеку; если потребуется изменение зависимости, сообщить об этом отдельно. Сохранить чужие изменения go.mod/go.sum. Не добавлять БД, Redis, дедупликацию, retry, блокировки, очередь или status endpoint. Порог остаётся **больше двух**, то есть при 0/1/2 можно продолжать, при 3+ — 409. Никаких live imports, публикации или deploy. Завершить diff и отчётом для повторного ревью.

## 1. P1 — повторный разбор всего листа для каждой строки

**Место:** `internal/domains/catalogimports/validator.go:224`, вызов из цикла на строке 145.

`validateExtraColumns` вызывает `GetCols(sheet)` для каждой строки данных. Это повторный разбор всего листа, приводящий к квадратичной стоимости. На синтетических корректных книгах получены: 50 строк — 54 мс; 100 — 189 мс; 200 — 743 мс; 400 — 3,04 с. Это локальные замеры, а не production benchmark, но рост и причина подтверждены. Заявленный лимит 100000 строк практически недостижим с текущим алгоритмом.

**Исправление:** единый ограниченный проход по листу через Excelize, без GetCols/GetRows всего листа внутри цикла данных; контроль контекста, индексов и ресурсов. Не писать собственный XLSX parser. Проверить работу на заметно большем синтетическом файле и отсутствие квадратичного роста; не закреплять нестабильный миллисекундный порог в unit test.

## 2. P2 — непредусмотренное изменение JSON других endpoints

**Места:** `internal/domains/basket/apiv1/openapi.gen.go:14`, `internal/domains/recommendations/apiv1/openapi.gen.go:87`.

Перегенерация с oapi-codegen v2.8.0 вместо указанной в Makefile v2.4.1 добавила `omitempty` к существующим nullable полям. Например, `oldPrice: null`, `promoCode: null`, `message: null` теперь могут полностью отсутствовать. Это реальное изменение сериализации корзины/рекомендаций, а не только комментарий о версии генератора, и оно не входит в задачу импорта.

**Исправление:** обеспечить воспроизводимую генерацию с сохранением прежней сериализации существующих endpoints. Generated-файлы руками не править. Проверить JSON с nil-полями и стабильность повторной генерации.

## 3. P2 — дата и запрещённый числовой формат проходят в B/C

**Место:** `internal/domains/catalogimports/validator.go:301`.

Для numeric cells, raw-значение которых состоит из цифр, код возвращает успех до `ensureAllowedNumberFormat`. Подтверждено принятие B2 с целым serial number и NumFmt=14 (дата), а также C2 с custom format `0.00`.

**Исправление:** проверять формат каждой числовой B/C до успешного возврата. Разрешены только General/NumFmt=0 и целочисленный 0/NumFmt=1 без custom format. Добавить тесты дат и custom format именно с целым raw-значением.

## 4. P2 — числовой артикул ошибочно принимается за текст

**Место:** `internal/domains/catalogimports/validator.go:395`.

`CellTypeUnset` может обозначать обычную числовую ячейку. Условие `!digitsOnly` принимает numeric A2=1.5 и A2=-123; оба случая воспроизведены. Контракт требует настоящий текст, чтобы не передавать в PIM изменённые Excel идентификаторы.

**Исправление:** разрешить только фактические строковые типы ячеек, без эвристики по raw value. Проверить дробные, отрицательные, экспоненциальные числовые артикулы и сохранение текстового `000123`.

## 5. P2 — часть значений и формул вообще не проверяется

**Места:** `internal/domains/catalogimports/validator.go:122`, `:145`.

Проверка дополнительных колонок выполняется только для строк с четырьмя непустыми A:D. В заголовочной строке E и дальше не проверяются. Формулы без cached value могут быть признаны пустотой до проверки формулы.

Подтверждено принятие книги с корректными строками 1–2 и каждым из следующих нарушений: текст E1, текст E3, формула E3, формула A3 без cached value. Эти исходные байты затем могут попасть в PIM.

**Исправление:** проверить наличие запрещённых формул/error cells/значений до отбрасывания пустых строк; включить строку заголовков и хвост в контроль дополнительных колонок. Пустое форматирование допустимо. Добавить перечисленные regression cases, включая формулу без кеша за D.

## 6. P2 — sparse row index обходит ограничение таблицы

**Место:** `internal/domains/catalogimports/validator.go:134`.

Лимит проверяет только количество непустых строк, а `hasInteriorBlank` сравнивает только найденные строки друг с другом. При MaxDataRows=2 книга с заголовками, пустыми строками 2–3 и единственной строкой данных 4 принимается. Аналогично единственная строка за индексом 100001 обходит production limit.

**Исправление:** проверять начало данных со строки 2 и допустимый индекс до дорогостоящего обхода разреженного листа. Не учитывать хвостовое форматирование как данные. Добавить тесты leading blanks и sparse row за разрешённым индексом с уменьшенным тестовым лимитом.

## 7. P2 — теряется неизвестный результат create

**Места:** `internal/adapters/catalogimports/pim.go:120`, `:157`.

Два подтверждённых сценария:

- PIM create возвращает 307. Redirect не выполняется, однако `isHTTP4xx` возвращает true через `ErrBadRequest`, которым HTTP-библиотека классифицирует и 3xx. Получается `pim_rejected` вместо `pim_registration_unknown`.
- Отмена во время create превращается только в `ErrCanceled`, хотя запись уже могла появиться в PIM. Признак неизвестной регистрации теряется в метаданных/логах.

**Исправление:** явным отказом считать фактический HTTP 400..499. Для create 3xx и cancellation сохранить неизвестный результат, preload ID и stage. Отключившемуся клиенту не нужно пытаться отправить успешный ответ. Добавить тесты create 307/308 и отмены после начала create; ни повторов, ни обращения к redirect target.

## 8. P2 — timeout после заголовков search становится обычной недоступностью

**Место:** `internal/adapters/catalogimports/pim.go:72` и классификация ошибки на строках 98–106; тот же риск у create.

В httptest PIM отправляет 200 headers, flush, затем не отдаёт body до истечения общего бюджета 50 мс. Фактический результат — ErrPIMUnavailable/502 вместо ErrPIMTimeout/504. Причина в опубликованном gj-go-httpclient v0.1.2: DoJSON теряет ошибку чтения тела, возвращая decode error. Это существующее поведение зависимости, но новый адаптер обязан соблюдать timeout-контракт. Исправление preload в pimclient не распространяется на JSON search/create.

**Исправление в разрешённой области:** при обработке неуспешного вызова учитывать состояние дочернего ctx общего PIM-бюджета, сохраняя stage и семантику create unknown. Не подменять известный успешный ответ ошибкой только по позднему истечению ctx. Добавить тесты задержки body после headers для search и create; не менять соседний репозиторий без отдельного согласования.

## 9. P2 — отсутствует наблюдаемое число активных импортов в логах

**Места:** `internal/domains/catalogimports/handler.go:251`, `internal/adapters/catalogimports/pim.go:37`.

`stageFromError` всегда возвращает active=0, успешный путь также передаёт 0, а `logOutcome` пишет поле только при active>0. В итоге `active_imports_observed` не появляется ни при busy, ни при успехе. Это не позволяет проверить по логам, что именно увидел защитный предохранитель. Row count также теряется при отказах после успешной валидации.

**Исправление:** передавать наблюдённое число и известный row count в структурированных результатах/ошибках; различать «search не выполнен» и «наблюдалось 0». Логировать 0/1/2/3, где 3 означает не меньше трёх. Не разбирать error string и не использовать ID/filename как metrics labels. Проверить захватом структурированного лога busy и accepted сценарии.

## Что уже подтверждено

- Используется опубликованный pimclient v0.2.0 без local replace.
- Порядок search → preload → create, фильтр status=[1,2], offset=0, limit=3 и условие >2 реализованы.
- Token guard отделён от customer auth; wiring не переносит incoming auth/initial-event в PIM.
- Исходные XLSX bytes передаются без пересохранения, общий downstream ctx существует, retry/БД/очереди не добавлены.
- Проверка текущих тестов `GOWORK=off go test -race ./... -count=1` прошла.
- `GOWORK=off go vet ./...` и `git diff --check` прошли.
- Дополнительные локальные probes воспроизвели перечисленные обходы валидации и ошибки классификации. Они выполнялись через временные Go overlays без изменения исходников.

Зелёные текущие tests не означают выполнение всей матрицы ТЗ: в частности, они не покрывают найденные сценарии. В отчёте исполнителя `make lint` завершился ошибками, названными существующими в basket; в этом ревью происхождение lint failures отдельно не перепроверялось. Перед повторной сдачей зафиксировать точный результат lint и, если он красный, сравнение с базой; не расширять задачу посторонними исправлениями.
