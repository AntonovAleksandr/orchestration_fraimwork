## R2-1. P1 — пустое форматирование вызывает большой обход, отмена не ограничивает хвост

**Места:** `internal/domains/catalogimports/validator.go:146`, `:266`.

Повторный GetCols для каждой строки убран, однако глобальный maxCol теперь применяется к каждой строке. Одна пустая форматированная ячейка в XFD заставляет проверять тысячи пустых ячеек каждой строки через несколько вызовов Excelize.

Подтверждённые локальные замеры, без race:

- 100 корректных строк без дальнего форматирования: 3,18 мс.
- Те же строки плюс одна пустая форматированная XFD102: 1,44 с, файл всего около 7,5 КБ.
- Одна строка данных, пустая форматированная XFD500, тестовый MaxDataRows=2: при отмене ctx сразу после проверки заголовков функция возвращает отмену только через 4,69 с. `rejectRowsBeyondLimit` не принимает ctx и полностью обходит хвост до следующей проверки отмены.

Это реальные сценарии случайного форматирования Excel. При больших координатах маленький файл занимает CPU и память на длительное время. Отмена запроса и 60-секундный deadline не останавливают текущий цикл хвоста.

**Исправить:** исключить обход пустого прямоугольника по глобальным maxRow/maxCol. Работа должна зависеть от реально присутствующих данных/элементов книги, с ограниченным обходом и проверкой ctx во всех длительных циклах. Не решать проблему отказом от допустимого хвостового форматирования: оно разрешено ТЗ. Не заменять Excelize собственным XLSX parser.

**Проверить:** валидная книга с дальним форматированием; отмена во время обхода разреженного хвоста; разреженные запрещённые данные/формулы за D и за лимитом строк. Данные должны отклоняться, пустое форматирование — допускаться.

`TestValidator_ScalesSubQuadratically` не подтверждает отсутствие квадратичного роста: при увеличении 100 → 400 строк квадратичный коэффициент 16 проходит установленный порог 25. Не считать этот тест доказательством производительности. Использовать воспроизводимые измерения и корректные регрессионные сценарии, не хрупкие миллисекундные пороги.

## R2-2. P2 — worksheetExtents читает не обязательно действующий лист

**Места:** `internal/domains/catalogimports/validator.go:217`, `:137`.

Жёстко задан `xl/worksheets/sheet1.xml`, а Excelize проверяет лист из workbook. Физическое имя XML не обязано совпадать с sheet1.xml даже у книги с единственным листом.

Подтверждены оба сценария:

1. Excelize NewSheet("Actual"), затем DeleteSheet("Sheet1"): корректная книга с одним листом и данными в sheet2.xml получает ошибку «не удалось прочитать книгу».
2. Действующий sheet2.xml содержит корректную строку 2 и запрещённую формулу A3. В архив добавлен не связанный с workbook sheet1.xml с границей строки 2. Validator возвращает rows=1, err=nil: обход настоящего листа прерывается по maxRow чужой XML-части, и формула не проверяется.

**Исправить:** проверять именно действующий worksheet, выбранный Excelize, не ограничивать его обход сведениями из другой ZIP-part. Устранить жёсткое имя sheet1.xml. Предпочесть возможности Excelize; если без отдельной обработки XML невозможно выполнить ограничения ТЗ, сначала описать ограничение и предложить узкое решение, а не развивать независимый парсер молча.

**Проверить:** единственный лист после создания/удаления другого листа; исходный worksheet part с иным именем; неподключённый XML в ZIP не меняет результат валидации; запрещённые данные за его фиктивной границей не пропускаются.

## R2-3. P2 — active_imports_observed всё ещё теряется при downstream failure

**Места:** `internal/adapters/catalogimports/pim.go:49`, `:57`.

Busy и accepted теперь логируют количество правильно. Но при успешном search и последующей ошибке preload/create методы mapPreloadError/mapCreateError создают RegisterError с ActiveImportsKnown=false и ActiveImportsObserved=0.

Подтверждение через настоящий pimclient + httptest: search возвращает две активные записи; далее preload=500 либо create=500. В обоих случаях в ошибке Known=false, Observed=0, поэтому лог не содержит уже известного числа 2.

**Исправить:** после успешного search сохранять observed/known во всех последующих ошибках. Сохранить stage, preload ID, row count и классификацию unknown. Search failure по-прежнему не должен выглядеть как наблюдение нуля.

**Проверить:** адаптерные тесты search=0/2 → preload failure и search=0/2 → create failure; проверить metadata и итоговый структурированный лог. Только тест вручную созданного RegisterError не проверяет передачу полей реальным адаптером.
