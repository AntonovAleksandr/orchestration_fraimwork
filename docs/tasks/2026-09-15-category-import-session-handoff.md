# Передача задач: импорт позиций категорий через intgateway

> **Актуально на 2026-09-16, редакция 3.** Решение согласовано: PIM не меняем, gateway без БД. Проверка search(status=[1,2], limit=3): 0–2 записи разрешают импорт, 3 и более дают 409. Дедупликация, распределённые блокировки и строгий лимит параллелизма не входят в MVP. Исполнительные сессии можно запускать в указанном порядке.

Два самостоятельных задания для двух исполнительных сессий. Обе сессии реализуют только свои репозитории и возвращают diff с отчётом. Основная сессия проводит независимое ревью.

## Порядок

1. Сессия A: [pimclient](../superpowers/plans/2026-09-15-pimclient-category-import-spec.md).
2. Вернуть отчёт A в основную сессию; провести ревью и исправления.
3. По отдельному поручению владельца опубликовать одобренную версию pimclient. Само ТЗ не разрешает push/tag/release.
4. Сессия B: [intgateway](../superpowers/plans/2026-09-15-intgateway-category-import-spec.md), передав ей фактическую одобренную опубликованную версию зависимости.
5. Вернуть отчёт B в основную сессию; провести ревью и исправления.
6. Настройка стенда и один контрольный импорт — после ревью и отдельного поручения владельца.

Не запускать B раньше готовности версии клиента: иначе её зависимость от A не воспроизводима.

## Чек-лист основной сессии для ревью

### A: pimclient

- Проверять actual diff относительно заявленного base, не только отчёт исполнителя.
- Совпадение Go signatures и wire paths/DTO с ТЗ.
- Multipart Content-Type на gj-go-httpclient >=v0.1.2; filename/bytes/decorator проверены через HTTP server.
- Положительный ID обязателен, bad 2xx не успех; HTTP/transport errors имеют правильную классификацию. Search отличает data=[] от missing/null, не выполняет встроенный paging.
- Response body закрывается и upload response ограничен; нет retry и изменения SKU-контракта.
- Целевые tests и regression, генерация воспроизводима; нет непредусмотренных replace/посторонних изменений.

### B: intgateway

- Одобренная опубликованная версия клиента зафиксирована, HTTP-код клиента не скопирован.
- Token guard fail-closed, отдельно от customer auth; секрет не уходит в PIM/логи.
- Полная локальная проверка предшествует всем upstream calls; исходные bytes неизменны.
- Excel validator не принимает строковые «истинные» значения, которые PIM прочитает как false; ограничены zip/rows/body.
- Три вызова идут search→preload→create. Search без type/user_id, status=[1,2], limit=3. При 2 записях разрешено, при 3 — 409 и ноль записывающих вызовов. Ошибка search запрещает запись.
- Type=1 при create фиксирован, общий deadline, нет retry/redirect; не обещана атомарная защита от гонок или дублей.
- 202 только после положительного import_id; create timeout/network/decode возвращают unknown outcome.
- CMS/audit не переделаны, пользовательский initial-event не подделан.
- Новая роль gateway описана узким ADR; без очереди/БД/status API и scope creep.
- Server/ingress timeout и body prerequisites согласованы в runbook; не заявлена непроведённая live приёмка.

## Принятые технические ограничения нового endpoint

ТЗ B фиксирует 10 MiB на файл, 11 MiB на HTTP body, 64 MiB распакованного XLSX, один worksheet и максимум 100000 строк данных. Это ограничения контракта нового endpoint, а не утверждение о пределах старой CMS. Их нужно передать команде-потребителю вместе с OpenAPI и полным Excel-контрактом.
