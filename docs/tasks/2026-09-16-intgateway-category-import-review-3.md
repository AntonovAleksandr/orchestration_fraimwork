## R3-1. P2 — ячейки с неявными координатами обходят контроль дополнительных колонок

**Место:** `internal/domains/catalogimports/worksheet_stream.go:159–162`.

При отсутствии атрибута `r` у элемента `<c>` новый обход выполняет `continue`. Excelize при этом восстанавливает координату ячейки по её положению. Поэтому два механизма по-разному определяют наличие данных.

Подтверждённые примеры: корректная строка 2 содержит A:D и пятую ячейку E2. Из XML убран только атрибут `r="E2"`:

- E2 содержит текст EXTRA: Excelize GetCellValue(E2) возвращает EXTRA, но Validator возвращает rows=1, err=nil.
- E2 содержит формулу `1+1`: Excelize GetCellFormula(E2) возвращает формулу, но Validator также принимает файл.

Исходный файл передаётся в PIM, поэтому непросмотренная ячейка не исчезает после такой проверки.

**Исправить:** согласовать определение координат в проверке структуры с фактическим представлением Excelize. Не пропускать ячейку только из-за отсутствия явного `r`; восстановление координат должно учитывать реальную последовательность и явные координаты. Не считать неизвестную/некорректную координату доказательством отсутствия данных. Сохранить проверку формул без cached value и запрет значений правее D.

**Тесты:** на уровне Validator, с оригинальными байтами XLSX и контрольным чтением E2 через Excelize: текст и формула пятой ячейки без `r` должны отклоняться. Также проверить допустимые строковые/числовые ячейки A:D с неявными координатами и смешение явных/неявных координат, чтобы исправление не ввело новые обходы или ложный отказ.

## R3-2. P2 — XML-разбор всё ещё не учитывает отмену контекста

**Места:** `internal/domains/catalogimports/worksheet_stream.go:48–56`, `:117–180`; вызов `internal/domains/catalogimports/validator.go:111`.

В отчёте говорится о проверке ctx на каждой строке XML-потока. Фактически `streamWorksheetRows` вообще не принимает ctx: сначала readZipFile полностью читает XML через io.ReadAll, затем весь XML разбирается и накапливается в slice. Только после завершения этой работы Validator проверяет ctx при обходе готового slice.

Контрольный пример: книга со 100000 физически присутствующими formatting-only строками (ZIP около 510 КБ, XML-хвост 4,18 MiB). Контекст отменён после последней проверки заголовка. Следующая проверка отмены произошла лишь после полного разбора хвоста; локальная задержка после отмены — около 82 мс. Замер показывает место задержки, а не production SLA. Число ctx.Err() — всего пять: четыре заголовка и одна проверка после полного разбора.

**Исправить:** передать ctx в добавленные функции чтения/обхода XML и проверять его непосредственно во время работы, а не только после получения полного результата. По возможности читать worksheet через reader вместо второй полной копии XML. Сохранять cancellation/deadline как context error, не превращать их в invalid_excel. Контролировать отмену и во внутреннем цикле обработки дополнительных ячеек одной большой строки. Лимиты распаковки и закрытие ресурсов сохранить.

**Тест:** детерминированная отмена во время чтения/разбора хвоста с подтверждением, что остаток не обработан. Случайный sleep и общий таймер вокруг Validate не доказывают остановку XML-разбора: отмена может попасть ещё в предварительное открытие Excelize.
