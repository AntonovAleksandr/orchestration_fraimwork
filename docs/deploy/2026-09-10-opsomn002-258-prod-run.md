# OPSOMN002-258 — прогон правки координат на проде

Разовая правка координат адресов, записанных фолбэком витрины, на настоящие точки домов
из справочника OMS. Инструкция под **прод**. Для стенда — `2026-09-10-opsomn002-258-stage-run.md`.

**Сервис:** `customers-api-web` (в кластере — deployment `customer-gui-web-master-ms`)
**Namespace:** `prod`
**База:** `ensi-gs-customers-prod`
**Команда:** `customers:normalize-address-coordinates`
**Что меняет:** `addresses.lat/lot` — через API `customers`, не напрямую в БД

## Зачем

Закрывает кейс, когда адрес уже лежит в карточке с координатами фолбэка, покупатель его
не трогает и оформляет заказ — фолбэк уезжает в OMS и в расчёт стоимости доставки.
Страховка на записи адреса такой случай не ловит, потому что записи не было.

## Объём на 10.09.2026

| | Записей |
|---|---|
| Всего адресов | 210 810 |
| Координаты Кремля `55.7558 / 37.6176` | **5201** |
| Питерская точка `59.9311 / 30.3609` | **702** |

Итого 5903. При паузе 200 мс — около 20 минут на московский прогон, 2–3 на питерский,
столько же на отчётные. Часть записей отсеется как «дом не подтверждён».

- [ ] Есть доступ `kubectl -n prod exec` в под `customer-gui-web-master-ms`.

## 1. Под

В проде **восемь реплик**. Команда выполняется в одном конкретном поде, и все шаги —
копирование списка, прогон, забор снимка — должны идти в том же самом.

```bash
POD=$(kubectl -n prod get pods -o name | grep customer-gui-web-master-ms | head -1 | cut -d/ -f2)
echo "$POD"

kubectl -n prod get pod "$POD" -o jsonpath='{.spec.containers[*].name}{"\n"}'
```

Записать имя пода. Если он перезапустится посреди прогона, файл снимка внутри пропадёт —
поэтому снимок из шага 2 обязателен и хранится вне кластера.

## 2. Снимок «до» — обязательно

Основная страховка отката. Выполняется на `ensi-gs-customers-prod` **на чтение**.

```sql
SELECT id, lat, lot, fias_house, fias_street, full_city_name, street, house, updated_at
FROM addresses
WHERE (abs(lat - 55.7558) < 0.000001 AND abs(lot - 37.6176) < 0.000001)
   OR (abs(lat - 59.9311) < 0.000001 AND abs(lot - 30.3609) < 0.000001)
ORDER BY id;
```

Сохранить как `before.csv` **вне кластера**. Зафиксировать число строк — с ним сверяется итог.

## 3. Списки идентификаторов

```sql
-- ids-moscow.txt
SELECT id FROM addresses
WHERE abs(lat - 55.7558) < 0.000001 AND abs(lot - 37.6176) < 0.000001 ORDER BY id;

-- ids-spb.txt
SELECT id FROM addresses
WHERE abs(lat - 59.9311) < 0.000001 AND abs(lot - 30.3609) < 0.000001 ORDER BY id;
```

По одному id в строке, без заголовков. Положить в под:

```bash
kubectl -n prod cp ids-moscow.txt "$POD":/tmp/ids-moscow.txt -c php
kubectl -n prod cp ids-spb.txt    "$POD":/tmp/ids-spb.txt    -c php
```

## 4. Отчёт — ничего не пишет

Сначала на подвыборке, чтобы убедиться, что цепочка живая:

```bash
kubectl -n prod exec -it "$POD" -c php -- \
  php artisan customers:normalize-address-coordinates \
    --ids-file=/tmp/ids-moscow.txt --threshold=0 --limit=50
```

| Поле | Норма |
|---|---|
| исправлено | 0 — без `--apply` всегда |
| в пределах порога | 0 — порог снят |
| дом не подтверждён | единицы из 50 |
| **ошибок** | **0** |

**Останавливаться, если** «ошибок» больше нуля или «дом не подтверждён» близко к 50:
справочник не отвечает либо авторизация. Смотреть в логах BFF
`address coordinates normalization failed`.

Затем полный отчёт по обоим городам:

```bash
kubectl -n prod exec -it "$POD" -c php -- \
  php artisan customers:normalize-address-coordinates \
    --ids-file=/tmp/ids-moscow.txt --threshold=0 | tee /tmp/report-moscow.txt

kubectl -n prod exec -it "$POD" -c php -- \
  php artisan customers:normalize-address-coordinates \
    --lat=59.9311 --lon=30.3609 \
    --ids-file=/tmp/ids-spb.txt --threshold=0 | tee /tmp/report-spb.txt
```

Занимает ~25 минут суммарно и прогревает кеш, поэтому запись пойдёт быстрее.
**Зафиксировать итоговые числа** — это и есть цифра для владельца аналитики.

## 5. Запись

```bash
kubectl -n prod exec -it "$POD" -c php -- \
  php artisan customers:normalize-address-coordinates \
    --ids-file=/tmp/ids-moscow.txt --threshold=0 \
    --backup=/tmp/backup-moscow.csv --apply

kubectl -n prod cp "$POD":/tmp/backup-moscow.csv ./backup-moscow.csv -c php
```

```bash
kubectl -n prod exec -it "$POD" -c php -- \
  php artisan customers:normalize-address-coordinates \
    --lat=59.9311 --lon=30.3609 \
    --ids-file=/tmp/ids-spb.txt --threshold=0 \
    --backup=/tmp/backup-spb.csv --apply

kubectl -n prod cp "$POD":/tmp/backup-spb.csv ./backup-spb.csv -c php
```

Без `--backup` команда не стартует. Снимок забирать **сразу после** каждого прогона.

Если прогон оборвался — запустить снова с тем же списком: исправленные записи уже не
совпадут с парой фолбэка и будут пропущены.

## Дробление нагрузки

Если владелец аналитики попросит размазать события во времени — добавить `--limit=500`
и запускать повторно, с паузами между запусками. Обработанное отсеется само.

Ещё один рычаг — `--sleep`, пауза между записями в миллисекундах, по умолчанию 200.

## Две вещи, на которых легко споткнуться

**`--lat/--lon` для Питера обязательны.** Без них отбор идёт по московской паре, и 702
питерские записи молча не попадут в обработку.

**`--threshold=0` в каждой команде.** Умолчание 0.5 км пропустит дома в радиусе
полукилометра от центра — в Москве это Никольская, Ильинка, Варварка, Моховая — и они
останутся с координатами Кремля. Порог задумывался для прогона без отбора по
координатам; здесь мы и так знаем, что точка это константа витрины.

## 6. Проверка

```sql
SELECT count(*) FILTER (WHERE abs(lat - 55.7558) < 0.000001 AND abs(lot - 37.6176) < 0.000001) AS moscow,
       count(*) FILTER (WHERE abs(lat - 59.9311) < 0.000001 AND abs(lot - 30.3609) < 0.000001) AS spb
FROM addresses;
```

Остаток должен равняться сумме «дом не подтверждён» из отчётов шага 4.

Выборочно — попала ли точка в свой город:

```sql
SELECT id, full_city_name, street, house, lat, lot
FROM addresses WHERE id IN (<десяток id из backup-moscow.csv>);
```

## Откат

По снимку `before.csv`, для каждой затронутой записи:

```sql
UPDATE addresses SET lat = <old_lat>, lot = <old_lot>, updated_at = now()
WHERE id = <id>
  AND abs(lat - <new_lat>) < 0.000001 AND abs(lot - <new_lot>) < 0.000001;
```

Условие по текущему значению обязательно: между прогоном и откатом покупатель мог
поправить адрес сам, и затирать его правку нельзя.

Откат породит столько же событий в Kafka, сколько и прогон.

## Чего прогон не закрывает

- **Координаты, отличные от двух пар выше** — по решению считаются верными.
- **Дома, у которых ФИАС нет в реестре** — строгий матчинг откажется выбирать подсказку,
  адрес останется с прежней точкой.
- **Уже созданные заказы** — правится адресная книга, координаты в OMS остаются прежними.
- **Записи мимо `SetDeliveryAddress*`** — админка, импорты: страховка их не перехватывает,
  прогон придётся повторять.
