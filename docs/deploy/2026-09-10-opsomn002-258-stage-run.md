# OPSOMN002-258 — прогон правки координат на stage

Разовая правка координат адресов, записанных фолбэком витрины, на настоящие точки домов
из справочника OMS. Инструкция под **stage**; прод — отдельный документ
`2026-08-27-opsomn002-258-coordinates-runbook.md`.

**Сервис:** `customers-api-web` (в кластере — deployment `customer-gui-web-master-ms`)
**Namespace:** `stage`
**База:** `ensi-gs-customers-stage`
**Команда:** `customers:normalize-address-coordinates`

## Зачем

Закрывает **кейс 1** из возврата задачи: адрес уже лежит в карточке с координатами
фолбэка, покупатель его не трогает, оформляет заказ — и фолбэк уезжает в OMS. Страховка
на записи адреса такой случай не ловит, потому что записи не было.

Без прогона тестировщику нечего перепроверять по кейсу 1: у клиента 4466148 адрес
Москва, ул Душинская, д 18 к 1 так и останется с координатами Кремля.

## Объём на 10.09.2026

| | Записей |
|---|---|
| Всего адресов на стенде | 5653 |
| Координаты Кремля `55.7558 / 37.6176` | 122 |
| Питерская точка `59.9311 / 30.3609` | 4 |

Прогон занимает минуты. Согласование нагрузки на Kafka для стенда не требуется — это
126 записей, в отличие от прода, где их 5903.

## 0. Предусловия

- [ ] Образ BFF на стенде содержит правку пути справочника (MR !801). На 10.09 это
      `…-ec0acbda`, проверено. Без неё команда получит 404 на каждом адресе и покажет
      «дом не подтверждён» по всем — отработает вхолостую.
- [ ] Есть доступ `kubectl -n stage exec` в под `customer-gui-web-master-ms`.
      Проверяется командой из шага 1; если `Forbidden` — к DevOps.

## 1. Под и контейнер

```bash
POD=$(kubectl -n stage get pods -o name | grep customer-gui-web-master-ms | head -1 | cut -d/ -f2)
echo "$POD"

# имена контейнеров: приложение обычно php
kubectl -n stage get pod "$POD" -o jsonpath='{.spec.containers[*].name}{"\n"}'
```

**Все шаги выполнять в одном и том же поде** — там лежат список и снимок.

## 2. Снимок «до»

Выполняется на `ensi-gs-customers-stage` **на чтение**. Это основная страховка отката:
он не зависит от того, доживёт ли файл внутри пода до конца прогона.

```sql
SELECT id, lat, lot, fias_house, fias_street, full_city_name, street, house, updated_at
FROM addresses
WHERE (abs(lat - 55.7558) < 0.000001 AND abs(lot - 37.6176) < 0.000001)
   OR (abs(lat - 59.9311) < 0.000001 AND abs(lot - 30.3609) < 0.000001)
ORDER BY id;
```

Сохранить вне кластера.

## 3. Списки идентификаторов не нужны

Команда сама находит нужные записи: листает таблицу страницами и фильтрует по координатам
**до** обращения к справочнику. Здоровые адреса пропускаются бесплатно.

Опция `--ids-file` осталась как ускоритель листания, но для прогона она не требуется — и
выгруженный список стареет, а сканирование находит и свежие записи.

На стенде всего 5653 адреса, листание занимает секунды.

Отдельно про питерскую выборку: у всех четырёх записей ФИАС дома пуст (Кронштадт,
ул Ленинградская, д 12 — три записи, и Санкт-Петербург, пл Ленина, д 1). Строгий матчинг
примет подсказку, только если справочник вернёт ровно одну непротиворечивую. Итог
«дом не подтверждён» по всем четырём для этой выборки ожидаем и сбоем не является.

## 4. Отчёт — ничего не пишет

```bash
kubectl -n stage exec -it "$POD" -c php -- \
  php artisan customers:normalize-address-coordinates \
    --threshold=0

kubectl -n stage exec -it "$POD" -c php -- \
  php artisan customers:normalize-address-coordinates \
    --lat=59.9311 --lon=30.3609 \
    --threshold=0
```

Как читать итоговую строку:

| Поле | Норма |
|---|---|
| исправлено | 0 — без `--apply` всегда |
| в пределах порога | 0 — порог снят |
| дом не подтверждён | единицы по Москве, до 4 по Питеру |
| **ошибок** | **0** |

**Останавливаться, если** «ошибок» больше нуля или «дом не подтверждён» почти по всем
московским записям: справочник не отвечает. Смотреть в логах BFF
`address coordinates normalization failed`.

## 5. Запись

```bash
kubectl -n stage exec -it "$POD" -c php -- \
  php artisan customers:normalize-address-coordinates \
    --threshold=0 \
    --backup=/tmp/backup-moscow.csv --apply

kubectl -n stage exec -it "$POD" -c php -- \
  php artisan customers:normalize-address-coordinates \
    --lat=59.9311 --lon=30.3609 \
    --threshold=0 \
    --backup=/tmp/backup-spb.csv --apply
```

Без `--backup` команда не стартует. Сразу забрать снимки наружу:

```bash
kubectl -n stage cp "$POD":/tmp/backup-moscow.csv ./backup-moscow.csv -c php
kubectl -n stage cp "$POD":/tmp/backup-spb.csv    ./backup-spb.csv    -c php
```

Если прогон оборвался — запустить снова: исправленные записи уже не совпадут с парой
фолбэка и будут пропущены.

## Две вещи, на которых легко споткнуться

**`--lat/--lon` для Питера обязательны.** Без них отбор идёт по московской паре, и
питерские записи молча не попадут в обработку.

**`--threshold=0` в каждой команде.** Умолчание 0.5 км пропустит дома в радиусе
полукилометра от центра — в Москве это Никольская, Ильинка, Варварка, Моховая — и они
останутся с координатами Кремля. Порог задумывался для прогона без отбора по
координатам; здесь мы и так знаем, что точка это константа витрины.

## 6. Проверка

```sql
SELECT count(*) FILTER (WHERE abs(lat - 55.7558) < 0.000001 AND abs(lot - 37.6176) < 0.000001) AS moscow,
       count(*) FILTER (WHERE abs(lat - 59.9311) < 0.000001 AND abs(lot - 30.3609) < 0.000001) AS spb
FROM addresses;
```

Остаток должен равняться сумме «дом не подтверждён» из отчётов шага 4.

Выборочно — попала ли точка в свой город:

```sql
SELECT id, full_city_name, street, house, lat, lot
FROM addresses WHERE id IN (<десяток id из backup-moscow.csv>);
```

## 7. Передать тестировщику

Кейс 1: клиент 4466148, Москва, ул Душинская, д 18 к 1, `houseFias`
`075d2f69-eb66-42c1-a2e0-bc4c0bb680d5`. Адрес должен получить точку дома
(ориентир ~55.7449 / 37.7054), и она же должна уехать в `POST /order/create`
в `shipping.address.coordinates`.

## Откат

По снимку из шага 2, для каждой затронутой записи:

```sql
UPDATE addresses SET lat = <old_lat>, lot = <old_lot>, updated_at = now()
WHERE id = <id>
  AND abs(lat - <new_lat>) < 0.000001 AND abs(lot - <new_lot>) < 0.000001;
```

Условие по текущему значению обязательно: между прогоном и откатом адрес мог измениться,
и затирать это нельзя.

## Чего прогон не закрывает

- **Координаты, отличные от двух пар выше** — по решению считаются верными.
- **Дома, у которых ФИАС нет в реестре** — строгий матчинг откажется выбирать подсказку.
- **Уже созданные заказы** — правится адресная книга, координаты в OMS остаются прежними.
- **Записи мимо `SetDeliveryAddress*`** — админка, импорты: страховка их не перехватывает,
  прогон придётся повторять.
