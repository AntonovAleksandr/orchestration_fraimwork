# OPSOMN002-258 — прогон правки координат адресов

Инструкция для оператора. Правит координаты адресов, записанные фолбэком витрины
(центр Москвы `55.7558/37.6176`, центр Питера `59.9311/30.3609`), на настоящие точки домов
из справочника OMS.

**Скрипт:** `customers:normalize-address-coordinates` в `customers-api-web`
**Где запускается:** под `customer-gui-web-master-ms` в namespace `prod`
**Что меняет:** `customers.addresses.lat/lot` — через API `customers`, не напрямую в БД

## Область прогона

Чиним **только две точки** — фолбэки витрины, которые записывались вместо настоящего адреса:

| Город | Пара | Прогон |
|---|---|---|
| Москва | `55.7558 / 37.6176` | по умолчанию |
| Санкт-Петербург | `59.9311 / 30.3609` | с `--lat/--lon` |

**Все остальные координаты считаем верными и не трогаем.** Это решение по объёму, а не
недосмотр: искать другие подозрительные точки в этом прогоне не нужно.

Отсюда `--threshold=0` во всех командах ниже. Порог 0.5 км по умолчанию задумывался для
прогона без отбора по координатам — чтобы не перезаписывать адреса, у которых точка и так
верная. Здесь он вреден: в крупном городе дома в радиусе 500 м от центра (в Москве это
Никольская, Ильинка, Варварка, Моховая) прошли бы как «в пределах порога» и остались бы с
координатами Кремля. Раз отбор идёт по константе витрины, любая подтверждённая домовая
точка лучше неё независимо от расстояния.

## 1. Снимок «до» и список идентификаторов

Выполняется на БД `ensi-gs-customers-prod` **на чтение**. Снимок — основная страховка
отката: он не зависит от того, доживёт ли файл внутри пода до конца прогона.

```sql
-- Снимок. Сохранить как before-moscow.csv и положить вне кластера.
SELECT id, lat, lot, fias_house, fias_street, full_city_name, street, house, updated_at
FROM addresses
WHERE abs(lat - 55.7558) < 0.000001
  AND abs(lot - 37.6176) < 0.000001
ORDER BY id;

-- Список id для команды. Сохранить как ids-moscow.txt, по одному id в строке.
SELECT id FROM addresses
WHERE abs(lat - 55.7558) < 0.000001
  AND abs(lot - 37.6176) < 0.000001
ORDER BY id;
```

Ожидаемый объём — порядка 5300 строк. Точное число зафиксировать: с ним сверяется итог.

Для питерского прогона те же запросы с `abs(lat - 59.9311) < 0.000001 AND abs(lot - 30.3609) < 0.000001`,
файлы `before-spb.csv` и `ids-spb.txt`, порядка 700 строк.

## 3. Отчёт на подвыборке

Ничего не пишет. Задача — убедиться, что цепочка работает.

```bash
kubectl -n prod exec -it "$POD" -c php -- \
  php artisan customers:normalize-address-coordinates \
    --ids-file=/tmp/ids-moscow.txt \
    --threshold=0 \
    --limit=50
```

В выводе:

```
Режим отчёта, для записи добавьте --apply
Отбор по паре фолбэка: 55.7558 / 37.6176
id=… fias_house=… расхождение 712.4 км
…
Обработано: 50, исправлено: 0, в пределах порога: 0, дом не подтверждён: 3, ошибок: 0
Другие пары фолбэка этим прогоном не затронуты — для них нужен отдельный запуск.
```

**Как читать:**

| Поле | Что значит | Норма |
|---|---|---|
| исправлено | всегда 0 без `--apply` | 0 |
| в пределах порога | точка уже верная, трогать не надо | немного |
| **дом не подтверждён** | справочник не нашёл дом | единицы из 50 |
| **ошибок** | сбой связи или авторизации | **0** |

**Останавливаться, если:**
- «ошибок» больше нуля — проблема с ИС или авторизацией, дальше не идти;
- «дом не подтверждён» близко к 50 — справочник не отвечает или адреса не сходятся;
- строк `расхождение` нет вовсе — отбор не находит цели, проверить список id.

## 4. Полный отчёт

```bash
kubectl -n prod exec -it "$POD" -c php -- \
  php artisan customers:normalize-address-coordinates \
    --ids-file=/tmp/ids-moscow.txt \
    --threshold=0 \
  | tee /tmp/report-moscow.txt
```

Занимает ~25–35 минут при паузе 200 мс. Заодно прогревает кеш, поэтому шаг 5 пойдёт
быстрее и почти без обращений к справочнику.

Зафиксировать итоговые числа — с ними сверяется результат.

## 5. Запись

```bash
kubectl -n prod exec -it "$POD" -c php -- \
  php artisan customers:normalize-address-coordinates \
    --ids-file=/tmp/ids-moscow.txt \
    --threshold=0 \
    --backup=/tmp/backup-moscow.csv \
    --apply
```

Без `--backup` команда не стартует — правка необратима.

**Сразу после — вытащить снимок наружу:**

```bash
kubectl -n prod cp "$POD":/tmp/backup-moscow.csv ./backup-moscow.csv -c php
```

Если прогон оборвался — просто запустить снова с тем же списком: исправленные записи
уже не пройдут отбор по паре фолбэка и будут пропущены.

Если нужно дробить (например, по просьбе владельца Kafka) — добавить `--limit=500` и
запускать повторно, отбор сам отсеет обработанное.

## 6. Проверка

```sql
SELECT count(*) FROM addresses
WHERE abs(lat - 55.7558) < 0.000001 AND abs(lot - 37.6176) < 0.000001;
```

Ожидаемый остаток = «дом не подтверждён» из отчёта шага 4.

Выборочно — попала ли точка в свой город:

```sql
SELECT id, full_city_name, street, house, lat, lot
FROM addresses
WHERE id IN (<десяток id из backup-moscow.csv>);
```

## 7. Питер

Те же шаги 1–6 с другими параметрами:

```bash
kubectl -n prod exec -it "$POD" -c php -- \
  php artisan customers:normalize-address-coordinates \
    --lat=59.9311 --lon=30.3609 \
    --ids-file=/tmp/ids-spb.txt \
    --threshold=0 \
    --backup=/tmp/backup-spb.csv \
    --apply
```

Без явных `--lat/--lon` питерские записи не будут затронуты: по умолчанию отбор идёт по
московской паре. Команда предупреждает об этом в конце вывода.

Учесть: у части питерских записей нет ФИАС дома, справочник может их не подтвердить.
Реальное покрытие покажет отчёт.

## Откат

По снимку `before-moscow.csv`, для каждой затронутой записи:

```sql
UPDATE addresses
SET lat = <old_lat>, lot = <old_lot>, updated_at = now()
WHERE id = <id>
  AND abs(lat - <new_lat>) < 0.000001
  AND abs(lot - <new_lot>) < 0.000001;
```

Условие по текущему значению обязательно: между прогоном и откатом покупатель мог
поправить адрес сам, и затирать его правку нельзя.

## Что прогон не закрывает

- **Адреса, где справочник дом не подтвердил** — останутся с прежней точкой. Сколько,
  покажет отчёт.
- **Уже созданные заказы в OMS** — там координаты остаются прежними, прогон правит
  только адресную книгу.
- **Источник на витрине** — константы в `CITY_SECTORS_CONFIG` живы. Новые записи
  перехватывает страховка на записи адреса, но только когда справочник подтверждает дом
  и только на путях `SetDeliveryAddress*` — адрес, записанный мимо них, прогон придётся
  повторять.
- **Координаты, отличные от двух пар выше** — по решению считаются верными, см. «Область
  прогона».
- **Дома, у которых ФИАС нет в реестре** (например Казань, ул Коновалова) — справочник
  вернёт несколько подсказок, строгий матчинг откажется выбирать, адрес останется как есть.

## Что делать при проблемах

| Симптом | Действие |
|---|---|
| «ошибок» больше нуля в отчёте | проверить, задеплоен ли ИС и доступна ли ручка `/integration/v1/address/suggestion`; в логах BFF искать `address coordinates normalization failed` |
| «дом не подтверждён» массово | проверить, отвечает ли справочник OMS; не идти в `--apply` |
| Прогон оборвался | перезапустить с тем же `--ids-file`, обработанное отсеется |
| Нужно остановить | прервать выполнение; записанное останется в снимке CSV |
| Записали не то | откат по снимку, см. выше |
