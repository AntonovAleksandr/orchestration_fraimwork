# Набор скриптов GJ

Запуск задач и формы контроля. Собран по разбору 66 журналов сессий
(6,72 млрд токенов, 14 833 хода, 1 437 задач — только родительские сессии) — каждый скрипт закрывает
конкретную статью расхода, найденную в этих журналах.

| Скрипт | Что делает | Что экономит |
|---|---|---|
| `task.sh` | заводит вводную и печатает команду запуска отдельной сессии | старт с 62 тыс. токенов вместо медианных 394 тыс. |
| `mr-brief.py` | сжимает запрос на слияние до набора различных правок | cms!7: 587 диффов → 25 правок, 4 тыс. токенов |
| `shot.sh` | снимает экран и уменьшает его | 390 КБ ≈ 97 тыс. токенов → 6 тыс. |
| `visual-check.py` | сверяет снимок с эталоном числами | вердикт 200 байт вместо картинки |
| `golden.sh` | прогоняет набор эталонных экранов | одна строка итога вместо десятка кадров |
| `stats.py` | аналитика по журналам сессий | измеряет, работают ли остальные |
| `fleet.sh` | пачка задач одной командой, вкладка на каждую | запуск N задач без N команд |
| `worktree-vendor.sh` | честный vendor в рабочем дереве | секунды вместо 17 ГБ копии |

## Запуск задачи

```bash
scripts/gj/task.sh back  OPSOMN002-123 "краткий заголовок"
scripts/gj/task.sh front OPSOMN002-124 "краткий заголовок"
scripts/gj/task.sh review https://gitlab.gloria.aaanet.ru/.../merge_requests/7
```

Каждая команда кладёт вводную в `.tasks/<ключ>/brief.md` и печатает команду
запуска. Запускать **отдельной сессией**: по журналам сессии живут неделями и
к концу идут при контексте 700–800 тыс. токенов, где каждый ход стоит вдесятеро
дороже первого.

## Контроль бэка — ревью по выжимке

```bash
scripts/gj/mr-brief.py <адрес запроса> --out review.md
```

Дифф берётся локальным git в кеш-клоне (`~/.cache/gj-mr-brief`). Через интерфейс
GitLab нельзя: при большом наборе он молча отдаёт пустые диффы — на cms!7 пустыми
пришли 566 файлов из 587, и ревью по ним было бы слепым.

Правки группируются по форме: имена и числа стираются, остаётся структура
изменения. Одинаковые правки схлопываются в одну запись с числом повторов.

## Контроль вёрстки — эталонные экраны

```bash
scripts/gj/shot.sh ios .golden/shots/pdp.png     # снять (симулятор)
scripts/gj/shot.sh adb .golden/shots/pdp.png     # снять (устройство)
scripts/gj/golden.sh check                       # сверить весь набор
scripts/gj/golden.sh accept pdp                  # принять снимок как эталон
```

Раскладка: `.golden/ref/` — эталоны (макет или принятый результат),
`.golden/shots/` — текущие снимки, `.golden/report/` — вырезки расхождений.

Сравнение идёт числами, картинка попадает к агенту только при расхождении выше
допуска — и то вырезкой по области расхождения, а не полным кадром. Допуск по
умолчанию 2%, меняется через `--tolerance=N` или `GJ_GOLDEN_TOLERANCE`.

Зависимостей нет: чистый Python 3 и `sips` из состава macOS.

## Порог допуска

2% берёт мелкие отличия рендера (сглаживание, курсор). Для экранов с живыми
данными — временем, ценами, счётчиками — порог поднимать не нужно: лучше снимать
на фиксированных данных, иначе проверка перестаёт ловить настоящие сдвиги.

## Аналитика

```bash
scripts/gj/stats.py                       # свод: расход, на ход, на задачу
scripts/gj/stats.py --phases              # структура расхода по фазам работы
scripts/gj/stats.py --sinks               # куда уходит объём
scripts/gj/stats.py --waste               # отказы, повторные чтения
scripts/gj/stats.py --skills              # скиллы, делегирования, цена ревью
scripts/gj/stats.py --compare 14          # период против предыдущего
scripts/gj/stats.py --snapshot base.json  # зафиксировать замер
scripts/gj/stats.py --baseline base.json  # сравнить с ним позже
```

Смотреть на **расход на задачу**, не на общий: общий растёт вместе с объёмом работы.

Две ловушки, обе учтены в скрипте и обе стоили неверных выводов при первом замере:
один ответ модели пишется несколькими записями с общим usage (сырой подсчёт завышает
вдвое, склейка идёт по `requestId`), а ходы подагентов не логируются вовсе — все числа
относятся только к родительским сессиям. Подробности — `.claude/skills/gj-session-analytics`.
